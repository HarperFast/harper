## OIDC trusted publishing (`security/authn/oidc/`)

`exchange_oidc_token` exchanges a runtime identity token for a 1h operation token for a trust policy's user without stored credentials (#2171; `NO_AUTH_OPERATIONS` in `server/serverHelpers/serverHandlers.ts`, `serverUtilities.ts` `verifyPerms` bypass, `permission(false, [], OPERATIONS_ENUM.EXCHANGE_OIDC_TOKEN)`).

Issuer-agnostic core; issuer rules live in `providers/` (new issuer = profile, not core/storage edits): `claims.ts` (matching and constraint shapes), `jwks.ts` (unknown-`kid` refetch rate-limit clock outside the cache entry so replacement never resets it and rotations work on first use), `identityToken.ts`/`tokenExchange.ts` (shared `rejectToken`; per-audience verification memo), and `providers/` (`assertPolicyIsSpecific`, `assertAudienceIsSpecific`, `normalizeClaims`, `describePrincipal`, optional `vetoClaims` by normalized issuer; unregistered issuers use `providers/generic.ts` pinning `sub` for Kubernetes/GCP/SPIFFE; GitHub uses `githubActionsProfile` since `sub` varies by trigger and changed after 2026-07-15).

1. Generic rejection error blocks claim-by-claim enumeration; reasons log to `oidc-trust`.
2. `githubActionsProfile.assertPolicyIsSpecific` rejects repo + workflow alone (any branch pusher could add that workflow).
3. Mint via `createOperationToken`, never `createTokens` (overwrites `hdb_user.refresh_token`, revoking standing credentials, #2018).
4. Optional policy `operations` only subtracts from the role via `tokenOperations`, intersected before all early returns (`super_user` included) and never merged into `permission.operations` (`operation_authorization.ts` gate 2 treats listed SU-only ops as grants). Gates operations API and SQL (`verifyPerms` / `verifyPermsAST`), not REST/GraphQL `checkPermission` (#2201; #2173), so roles must stay least-privilege; write SQL DML also requires `insert`/`update`/`delete` so `read_only` (including `sql`) cannot `DELETE` via `verifyPermsAST`'s `super_user` bypass.
5. Policy IDs never choose authority: enabled policies matching with different users or operations fail unspent; agreeing ones pick first by ID.

`tokenUseTable.ts` declares `hdb_oidc_token_use` every start so non-exchanging nodes evict replicated rows (`dataLayer/DESIGN.md`). Spent tokens carry replicated metadata expiry past `exp`, keyed on SHA-256 of **signed input** (`header.payload`): stores no credential, needs no `jti` (Azure `uti`), and collapses signature malleability (RS256 trailing base64url bits, ES\* `s -> n-s`). Non-atomic get-then-put suffices (holders already earn one token).

Beside `workload_identity`, exchange signs `deploy_source` (`{ via: 'oidc', policy, ... }` via `attestedSource`, `components/deploymentSource.ts`); `validateToken` sets `deploySource`, impersonation preserves it, and `deploy_component` records it as attested over request fields (#3061; no credential stored).

`harper deploy setup=true provider=github-actions` (`bin/deploySetupGithubActions.ts`) is create-only, matching Studio's `<component>-ci-deploy` user/role and `github-actions-<component>` policy: keeps matches, aborts on drift/deactivation (never repurposing roles or undoing revocations), re-lists pre-write (`add_oidc_trust` replaces; cross-node `hdb_oidc_trust` races stay unexcluded), and verifies saved claims against opaque 401s.

## Scoped tokens and synthetic-role identity (`security/tokenAuthentication.ts`, `security/impersonation.ts`)

`create_authentication_tokens` with an inline `role` **object** (`super_user` or `isOperationAuthorizationBypassed()`; string `role` stays legacy component-defined, rejected by `validateOperationToken`) mints a `sub: 'scoped-operation'` JWT with downgraded deep-validated permissions, attribution-only `username`, no `hdb_user`/`hdb_role` row, and no refresh token — **irrevocable until expiry**, so `auth.ts` evicts cached Bearer hits at exact `authExpiresAt`, not cache TTL.

`username` cannot match an `hdb_user` at mint (default `scoped:<minter>`), preventing by-name rehydration from substituting real permissions or failing closed. The three known by-name sites short-circuit on `_scopedToken` — MQTT wills (`DurableSubscriptionsSession.ts` persists role/marker/expiry and refuses replay or abnormal-disconnect publish past `authExpiresAt`), live subscriptions (`Resource.ts` `registerLiveSubscriptionForContext`), and MCP `list_changed` (`components/mcp/listChanged.ts` `refreshSessionUser`) — and **any future by-name rehydration must check `_scopedToken`** (and `isLocalPrincipal`, and carry a certificate admission, below). Passwordless `createTokens` rejects `hdb_user._scopedToken`; later colliding users stay inert unless a new site omits `_scopedToken`.

`operations` allowlists gate the operations API (including `sql` via `verifyOperationsAllowlist` in `chooseOperation`), never REST/GraphQL/MQTT table CRUD (`operations: ['read_only']` does not block REST writes; table permissions still apply). `verifyPerms` receives the handler, so gate 1 checks `permission`'s required `api_name` (`null` when ungrantable; unregistered `sql` checks as given). Shared-handler aliases grant both via canonical name, neither via alias. `get_backup` (gate 2 precedes whole-DB READ), `read_transaction_log` (no `system.hdb_secret` guard like `read_audit_log`), and `catchup` (unrestricted writes) use `null` (`unitTests/utility/operation_authorization.test.js`).

`permissionsTranslator.getRolePermissions` memoizes by `(role name, __updatedtime__, schema)`, so synthetic roles never use constant names or per-request timestamps (same-ms `Date.now()` collisions leak permissions). `syntheticRoleName()` hashes post-downgrade permissions with `__updatedtime__: 0` (`applyImpersonation` re-keys all three modes alike); leading-`_` names use the 256-entry LRU `syntheticRolePermsMap` instead of `rolePermsMap` (>256 sets translate per request; persisted `_` roles safely land there). `verifyPerms` runs the role `operations` gate before `super_user`, `structure_user`, and system-table early returns so inline `structure_user` + allowlist roles cannot reach unlisted schema ops.

## TLS hot-reload publishes matching configured pairs (`security/keys.ts`)

`loadCertificates` publishes configured leaves only after `X509Certificate.checkPrivateKey` passes. Only main watches cert/key dirs (shallow watches + 5m poll sharing one fingerprint; unreadable dirs use Node file polling while configured files are absent). Incomplete pairs return `false` and retry (warn, error at 30 s — immediately without a non-self-signed row — then hourly); restoring prior files clears the alarm. Raw watch events arm an unpostponed <=1/s trailing check for unattempted fingerprints (chokidar drops add/change after two removals in 100 ms); missed OS events rely on the poll. CA-only rows ignore leaf keys. Workers reload on `hdb_certificate` subscriptions and read key files on build (no worker watch/poll). File-backed `getPrivateKeys()` entries refresh on read/rebuild, keeping cached values while unreadable unless an explicit key differs (rename-order/per-worker/poll-disabled in `integrationTests/security/cert-key-reload.test.ts`, `unitTests/security/keys.test.js`, `unitTests/security/tlsFileWatch.test.js`).

Older-file guard blocks disk from overwriting newer replicated certs and freezes `hostnames`/`private_key_name`, while `ciphers`/`uses` follow config via `from_config: true` (`file_timestamp` survives `setCertTable` patches). Load patches config `ciphers`/`uses` (`null` if `ciphers` removed) onto marked rows with matching PEM; `setCertTable` nulls `from_config` when API writes set `ciphers`/`uses` so operator overrides survive restarts. Pre-marker rows adopt only if matching config; declined mismatches log. Shared-cert entries let the first own load reconciliation while full writes (first load/renewal) reflect whichever wrote until restart. Applied on start or file change, not `restart_service` (`ciphers and uses follow config` in `unitTests/security/keys.test.js`). Unrelated table notifications during a key-first install gap or a second rotation before worker key reads can briefly mismatch; trust-aware last-good retention below keeps serving while the next pair propagates.

**Transactional publication (#2382).** `updateTLS` builds hostname->context, CA, and default-candidate state pass-locally, then mutates live maps in place (`server.secureContexts` and `availableCAs` alias their identity). Rows failing build (`ERR_OSSL_X509_KEY_VALUES_MISMATCH` or missing worker key) keep live entries and default candidacy; on CA changes, retained pairs rebuild against current trust (keeping active sessions/ticket keys) or drop on failure unless the zero-cert guard holds old state when nothing else serves. Deleted rows drop contexts; corrupt CA rows fail the pass and drop trust until healed. Failed passes retry on the shared debounce with per-signature backoff (`1.5s` doubling to `5min`) and throttled logs; subscriptions use plain debounce. `loadAndWatch` latches its fingerprint pre-callback and rolls back on `false`/error (guarded against stale rejections) so polling heals lost `hdb_certificate` writes.

**System-context reads (harper-pro#1189).** `initialize()` can first run inside a request (harper-pro non-owner reads opening replication), so `updateTLS` re-enters under `contextStorage.exit()` (`run(undefined, ...)` across runtimes; Node 22 `async_hooks` `exit()` leaks across nested `run()`, `resources/DESIGN.md`) so `hdb_certificate` calls skip request auth, preserve one-shot `authorize`, and keep request context off timers/subscriptions. Initial failure rejects `.ready`, while live selectors keep subscriptions and backoff retries, replacing `.ready` on recovery; later `initialize()` calls replace failing attempts (clearing timers/subscription), one-shot selectors retire at once, and `.ready` keeps the rejected promise until replaced (Bun treats `undefined` as no TLS) (`createTLSSelector initialized by a request` in `unitTests/security/keys.test.js`).

## Self-signed renewal replaces the pair in one transaction (`security/keys.ts`)

`prepareSelfSignedCerts` builds CA and replication rows in memory; `publishSelfSignedCerts` writes them in one `transaction()` (`renewSelfSigned` deletes old self-signed rows there) since `setCertTable` patches by name and a repeated `node.hostname` CA name lets partial failure overwrite CA without leaf. Renewal excludes self-signed rows (`getCertAuthority(true)`, `getReplicationCert(true)`) so self-signed `replication` leaves never outscore external generic certs. Publication re-reads in-transaction and never overwrites/deletes non-self-signed rows (renewal fails; boot review warns and skips, leaf included if CA skipped; same-key commit-window races uncovered). If an external row holds `<node>`, the self-signed leaf uses `<node>-self-signed` (selected by hostname, not row name). Configured CA key paths apply only if parsed; generated keys open exclusively (`wx`, `0o600`) in `keys/` post-build, never overwrite files, and unlink on failure (self-signed review/renewal in `unitTests/security/keys.test.js`, `integrationTests/security/renew-certs-missing-privatekey.test.ts`).

## Client-certificate revocation checking keeps three tables (`security/certificateVerification/`)

`verificationTables.ts` declares all three on writable starts and verification (`dataLayer/DESIGN.md`). Row expiry is record metadata; table `expiration` is fallback only.

- Verdicts (`hdb_certificate_cache`) expire `cacheTtl` post-check via `CertificateVerificationSource` setting `context.expiresAt` (`sourceContext.expiresAt`), never a returned field; `createCacheKey` hashes a key version so expiry-less legacy rows are ignored.
- Revocations (`hdb_revoked_certificates`) expire at `crl_next_update + gracePeriod` so `performCRLCheck` honors the grace window past `crl_next_update` instead of evicting at `nextUpdate` and passing revoked certs on overdue CRLs.
- CRL revocations replace the prior set atomically in their own transaction outside `performCRLCheck`'s verdict-fill transaction. The downloader decides from the downloaded CRL directly (another worker may replace rows first); cached-CRL checks read outside the verdict-fill transaction so LMDB snapshots see newer commits.

## A component-facing export needs BOTH `index.ts` and `getHarperExports` (`security/jsLoader.ts`, `index.ts`)

`index.ts` publishes package exports; VM compartments resolve `'harper'` from the hand-maintained `getHarperExports()` literal. Missing either breaks `import { x } from 'harper'` at component load, which `#src/...` unit tests miss; verify with a `'harper'`-importing fixture (`integrationTests/security/fixtures/deferred-credential-rejection/resources.js`, harper#2703). Import from the defining module, not re-exports, to preserve module-private `Symbol` identity (`markCredentialRejection` / `isCredentialRejection`).

## Both application loaders resolve through one `resolveModule` (`security/jsLoader.ts`)

VM loader and compartment `resolveHook` share module-scope `resolveModule` for `applications.moduleLoader` parity. It resolves CommonJS-first (dual packages keep `require` targets), falling back to `PACKAGE_EXPORTS_RESOLVE` (`node` and `import` conditions, plus `bun` on Bun; `module-sync`, `node-addons`, and `--conditions` unmodeled; checked by `resolves package exports as native Node import does`) only when bare-specifier `import` fails CommonJS (`ERR_PACKAGE_PATH_NOT_EXPORTED`, or `MODULE_NOT_FOUND` on Bun); `require()` never falls back. Fallbacks track `package.json` and entry digests, not resolution edges (`RuntimeModuleTracker` re-resolves edges via `createRequire`, marking import-only packages changed every deploy).

SES loads once via `loadSES` from `ses/index.js` ESM shims (shared by lockdown and compartments), never `require('ses')`, because Bun strips function-level `'use strict'` in CommonJS and trips `SES_NO_SLOPPY` (`pure-ESM package resolution` in `unitTests/security/jsLoader/jsLoader.test.js`, `integrationTests/components/compartment-pure-esm-dependency.test.ts`).

## `require()` and `import` pass the same gates in the VM loader (`security/jsLoader.ts`)

In `vm` and `vm-current-context`, all four entry points (ESM `linker`, both `importModuleDynamically` hooks, CommonJS `cjsRequire`) apply in order: `'harper'` alias, `checkAllowedModulePath` (`allowedDirectory`, `allowedBuiltInModules`, substitutes like constrained `child_process`), `shouldUseApplicationLoader`, and `readApplicationModule` (byte tracking + TS strip); `require()` differs only in sync native `require(path)` vs `import()`. New entry points/branches owe all four. URL-keyed `cjsCache` (app CommonJS) and `nativeModules` (registered before native `require()`/`import()`, released if failed unloaded) share one instance per scope across `require()` and `import`, returning post-check hits directly. Only a wrapper compile error triggers `createModuleFromSource`'s ESM retry; evaluation throws propagate. Uncovered: app-loaded ESM stays in `moduleCache` only (bare `require()` under `dependencyLoader: native` gets Node's `require(esm)` instance; JSON imports stay default-only), compartment `importHook`, and transitive `require()` in native packages (`CommonJS require` in `unitTests/security/jsLoader/jsLoader.test.js`, `integrationTests/components/cjs-require-loader.test.ts`, `integrationTests/components/require-confinement-parity.test.ts`).

## Authentication converts every principal-resolution failure into a decision (`security/auth.ts`)

`authentication()` resolves mTLS cert CN, `Authorization`, and `hdb_session` via overridable `server.getUser`. Every failure routes through `settleAuthFailure()` / `rejectAuthenticationInPlace()`, never throws (escaped throws unwind to `server/http.ts` as plain text, harper#2703): internal faults and operations-API routes answer 401 in place; tagged credential rejections defer to the route owner.

- `server/REST.ts` and `server/mqtt.ts` discard `await chainCompletion`, so `rejectAuthenticationInPlace` sets `markAuthenticationRejectedInPlace` for `assertNoDeferredCredentialRejection` to fail WebSocket/MQTT upgrades closed.
- Route owners call `settleDeferredCredentialRejection` before reading `request.user`, so a rejected cert never falls through to Basic, session, or local bypass.

## A request's session helpers are bound module functions, never function literals assigned to a property (`security/auth.ts`)

`request.session.update` and `request.login` bind module functions `updateSession` / `loginWithSession` to a per-request `SessionState` after copying stored session fields (overwriting stored `update`, working detached). Never assign function literals directly to properties (`request.login = async function ...`) on hot paths: V8's `CheckAssigningFunctionLiteralToProperty` pretenures them in old space, pinning the young context (`request`, headers, `response`) until major GC; bind module functions or assign locals first (`unitTests/security/authSessions.test.js`). `SESSION_VERSION` shares accessor functions: fresh functions put the clone in dictionary mode. `loadedSessions` keeps the record outside the request's function context.

`updateSession` reads outside the request snapshot: RocksDB uses `COMMITTED_SESSION_READ`; LMDB renews its shared reader. It rejects non-live, changed, `VERSION_REUSED`, payload `version`, or versions beyond the clock before the ordinary put. In-flight, later or unreplicated writes can still race (#2983, `unitTests/security/sessionUpdateIfVersion.test.js`).

## User and role lookups read the records, and nothing derived from them outlives them (`security/user.ts`)

Lookups read `hdb_user` (by name) and `hdb_role` (by id) from the primary store cache without cross-thread broadcasts:

- RocksDB point reads share no snapshot, so `readUserEntries` rechecks user version after reading its role and retries on movement against torn grants. LMDB uses the thread's turn-renewed shared read txn (next-turn visibility; per-lookup resets exhaust reader slots).
- Uncached reads return fresh objects; per-role memos, `isCurrentUser`, and `auth.ts` cache hits compare entry versions (or values on `VERSION_REUSED`); external `server.getUser` principals check pre-resolution `trackUserRecords` versions.
- `onUserChange` feeds live-subscription revocation and MCP `list_changed` from per-thread `hdb_user`/`hdb_role` subscriptions with changed primary keys, or no args when unknown (reload, oversized batch, gap reconnect) so all holders recheck. `userChangeNotificationEpoch()` is non-zero only on RocksDB while both subscriptions stay open with certified progress: seeing one unchanged non-zero epoch across a period certifies every change in it was notified (`liveSubscriptionAuth` skips full sweeps on it). Unaudited tables are never subscribed (which persists auditing), leaving epoch `0` for fallback sweeps.
- `cloneUserView(user)` isolates per-request `role`/`permission` replacement from cached principals, carrying record provenance on an own symbol across spreads without WeakMap writes (`trackedProvenance` covers external users) (`unitTests/security/userRecordLookups.test.js`, `unitTests/resources/replicatedUserWrites.test.js`).

### A certificate's principal keeps one admission across its views

Live-subscription rechecks re-read a principal by name and require a role (#1414), except a principal a verified client certificate named while no `hdb_user` record has backed it: `allowRead` alone admitted it, so `allowRead` alone rechecks it (#4062).

- `certificatePrincipal(user, getUser)` runs wherever a certificate selects the principal: `security/auth.ts` (HTTPS, WSS) and `server/mqtt.ts` (MQTT over TLS). It marks the built-in lookup's view in place (new per call) and an override's result only as a copy of a plain object from any realm with no non-enumerable own property; anything else stays unmarked and needs a role.
- The mark is a symbol, so data never carries it, and its value is the admission: the principal it was set on. A re-read that replaces the principal must carry it (`cloneUserView(fresh, undefined, admission)`, MCP's `withCertificateAdmission`), or the view fails closed.
- `latchRoleRequirement` holds an admission behind which a recheck or MCP refresh found a record (an inactive refusal counts), plus the contexts it used, for the process's life; an admission that arrived with a role or a record is instead re-derived at each registration. Either way every later subscription of it, by any view, needs a role even after `drop_user`. A record created and dropped unseen latches nothing (#4382).
- #4071's fixed principals (`_scopedToken`, `isRecordlessPrincipal`) and `isLocalPrincipal` are checked first and are never re-read. Enforced by `unitTests/server/liveSubscriptionAuth.test.js`, `unitTests/security/userRecordLookups.test.js` and `integrationTests/security/certificate-principal-subscriptions.test.ts`.

### A component grant answers to its names ahead of every operations listing (`security/componentGrant.ts`)

`component_deploy` (harper#3046; avoiding `RESERVED_DATABASE_NAMES` collisions with `components`) scopes `deploy_component`, `drop_component`, `get_deployment`, `list_deployments`, and `get_components` by `names` patterns (`componentNameMatches` in `utility/componentNames.ts`, shared with deploy credentials, harper#3090).

1. `verifyPerms` runs the grant check before gate 2 (which grants listed SU-only ops globally), making its verdict final for those five ops; gate 1 still requires listing them on an `operations` allowlist.
2. Deploy/drop resolve names via `canonicalProjectName` else `projectNameFromPackage`; component-less reads filter (`get_components`, `list_deployments`) or 403 (`get_deployment`).
3. `deployComponent` enforces `isolated`, `hostSuffix`, and `branchedDatabases: required` on the origin against the effective post-deploy entry (package, payload routing, or existing entry) pre-write, under preparation lock, and against staged descriptors on activation; peers trust the origin.
4. `grant_secret component=my-app-pr-*` applies only at deploy (`resolveCredentials`, harper#3090; `harper deploy setup=true` allows patterns only for `github`/`npm`); runtime `components/componentSecrets.ts` stays exact-match. `preview`, `maxPreviews`, and `maxTtlDays` bound preview identities below.

## PR previews are enabled by the cluster (`components/previewOperations.ts`)

`enable_previews`, `disable_previews`, and `get_preview_policy` (harper#3042) are server operations (not client composition) managing system-table rows (replicated in harper-pro) via `utility/previewIdentity.ts` names/claims shared with CLI/Studio: role/user `<app>-ci-preview` (`CI_PREVIEW_OPERATIONS`, `component_deploy` for `<app>-pr-*` with `preview: required`, no table perms) plus OIDC policies `github-actions-<app>-preview` (env `preview`) and `github-actions-<app>-preview-cleanup` (env `preview-cleanup`, scoped to `drop_component` so `preview` reviewer gates never block teardown and deploy tokens cannot match cleanup).

- `maxPreviews` (`deployment.previews.maxPerApplication`) and `maxTtlDays` (default 7) sit in `component_deploy.constraints` as one replicated record enforced on the origin (super-user previews face only the configured cap). `preview: required` requires `preview` metadata naming app `A` matching `A-pr-*` as `A-pr-<n>` (blocking expiry/cap bypass, `shop-pr-pr-3` miscounting, or `shop` dropping `shop-pr-tools`), clamps `expiresAt` pre-write/pre-replication, and refuses expired activations against the build row before live-release returns. `maxPreviews` counts under the per-origin lock (two origins can each take the last slot).
- One enable/disable runs per node at a time, keeping matches, 409ing on drift or overlapping authority (`policiesOverlap`, `sameAuthority`), and rechecking before `add_oidc_trust` (cross-node concurrent writes stay unexcluded, #3127).
- Disable drops trust policies, deactivates the user (`isCurrentUser` halts in-flight activations), and runs `fence_preview_releases` (#3613) under the per-app admission lock to revoke the grant's `generation` (minted on enable, stamped on builds) and census live previews. Origin/peer activations check that fence under the lock, grants activate only matching-generation builds, unacknowledged peers count unreachable, and peer fencing uses node-identity bypass (`isOperationAuthorizationBypassed()`, avoiding `REPLICATED_FROM` lifting deploy grants). Unfenced: super-user previews, pre-generation in-flight builds (`get_preview_policy`; rerun once `inProgress` drains), and — bounded by expiry (#3805) — late timed-out peer swaps, crash roll-forward, rollback/canary restores to fenced predecessors, and racing enables. Disable drops live releases per node (`ifDeploymentId`, halting non-origin drops pre-replication), then user/role; failed drops, releases still live after an empty drop, unknown node state, or missing rows stop disable with identity revoked so reruns resume.

## The password hash function and token lifetimes are read when used, never at module load (`security/user.ts`, `security/tokenAuthentication.ts`, `utility/password.ts`)

Empty-root `harper run` loads auth/installer modules before `install()` writes config and creates `admin` before `runStartup()`, so `authentication.hashFunction` resolves per password write (`password.configuredHashFunction()`) into `hash_function`. `password.hash` defaults to configured; `password.validate` defaults to SHA-256 so sync refresh-token checks never get a Promise from an async configured hash (`!Promise` accepts superseded tokens). Token lifetimes resolve per mint (`integrationTests/security/firstboot-auth-config.test.ts`).

## Local trust is a principal, not a stored user (`security/user.ts`, `security/auth.ts`)

Transport-trusted requests (`authentication.authorizeLocal` on `isLocalPeerAddress` loopback, operations socket `bypassLocalAuth`, loopback MQTT, test `bypassAuth()`) run as `localPrincipal()`: a record-less super user named `local` working with zero stored users.

- `isLocalPrincipal` checks `_localPrincipal: true`, set only by trusted code (never copied by `userView` or external auth paths; string key for Bun/uWS JSON forwarding and MQTT wills). `add_user` rejects `local`; pre-existing stored `local` rows stay ordinary users.
- Dropped by `session.update` and never token-minted: credential-free `create_authentication_tokens` mints for `getSuperUser` (first active stored `super_user`) or 409s. By-name rehydration checks `isLocalPrincipal` first (MQTT wills rebuild from marker; live-subscription and MCP `list_changed` skip it as irrevocable).
- Each call returns fresh user/`role`/`permission` objects matching default install `super_user` (`role.id` included for redirector/early-hints templates), frozen `system` entries, and shared mutable table-name map (`unitTests/security/localPrincipal.test.js`, `integrationTests/security/local-principal-token-mint.test.ts`).

## Named component children are identified by lifetime (`security/jsLoader.ts`, `security/spawnPidFile.ts`)

`pids/<name>.pid` stores positive PID, version (`0` if omitted), and OS birth identity (#2968: Linux boot ID/PID/start ticks excluding zombies/TIDs; macOS PID + UTC/C `ps lstart` at 1 s; Windows PID + `Win32_Process.CreationDate` ticks) via write-then-rename (pre-publish crashes can leave unrecorded children). Adoption, version replacement (`process.kill(pid)`; Windows sets `ChildProcess.exitCode`, `signalCode: null`), wrapper kill, and exit polling (1 s Linux/macOS, 5 s Windows, non-overlapping async macOS/Windows probes; exit lags by poll interval + probe time; no `kill(0)` fast path so recycled PIDs never hold exited wrappers open) compare birth identity. Cross-boot Linux records retire pre-probe; probe failures and same-boot `hidepid`/`ProtectProc` or permission-denied PIDs stay unknown (never retiring records or emitting exit; may need operator verification/repair or exit). Legacy two-line records warn and retire without signaling unverified PIDs, so a surviving legacy child may coexist once on upgrade; older builds ignore line 3 (no mixed-version guarantee).

Synchronous spawn/adoption probes under a filesystem bakery lock (UUID choosing/ticket files sharing `componentPreparationLock.ts` ordering; Windows sharing retries; unique release markers on claim-unlink failure — operator repair/restart needed if both fail). Foreign owner matches cache 1 s (stale positives only delay reclamation). Acquisition, publication, and non-waiting exit cleanup (cached own identity + conservative foreign claims without new probes; busy records defer to next spawn) share one claim protocol so stale checkers or older exits never delete newer records. `Atomics.wait` lock waits (50 ms) fail after 60 s without original-predecessor cohort progress; newcomers cannot renew stalled waits, live claims are never stolen, unreadable owners fail closed, external probes cap at 30 s, and synchronous capture prevents child reaping before identity read. Terminated-worker orphan claims in a live Harper block until Harper restarts (OS identity is process-wide; main-thread worker-exit sweep deferred since constrained spawning also runs in standalone workers/main-thread scopes). Native PID handles would be needed to close the identity-check-to-signal race and OS timestamp-resolution limits. Release errors report separately from spawn results/native arg errors; probe/lock failures throw `NamedProcessError` (`ServerError` with `cause`) (`unitTests/components/spawnPidIdentity.test.js` and `unitTests/components/spawnPidFile.test.js`, Windows-gated; `integrationTests/components/named-process.test.ts`).

## Application lockdown seals the intrinsics by default (`security/intrinsicsLockdown.ts`)

`applications.lockdown` defaults to `seal-after-load` on fresh installs; upgrades keep prior modes since `install()` writes full config. Sealing blocks additions/deletions on 21 intrinsic globals/prototypes plus `Function`/`Function.prototype` while allowing overwrites (not a sandbox). Never make seal-mode prototype properties read-only (~45x slower array-hole stores, ~3x slower msgpackr decode; accessors block built-in inlining); only freeze modes need `overridableProperty`. Sealing covers replaced globals and realm originals (kept by literals/async functions); freezing covers current globals, leaving `Function.prototype` extensible. Unknown truthy modes freeze eagerly (fail closed); falsy skips lockdown (`unitTests/security/intrinsicsLockdown.test.js` in fresh workers, `integrationTests/components/intrinsics-lockdown.test.ts`, `benchmarks/lockdown/run.mts`).

## A scoped mirror is never advertised before its allowlist is read (`security/networkAccess.ts`)

`system.hdb_network_access` holds one replicated row per scope (`operations` today). A fronting proxy enforces it; Harper only publishes `allowedSources` in UDS mirror metadata (`writeUdsMetadata`, `server/http.ts`).

- The writer, not `ready`, holds a scoped mirror until this thread's first read (`security/keys.ts` fires `secureContextsListeners` pre-readiness). Absent table post-load means unrestricted.
- Subscriptions, 60 s tick, and `onUpdatedTable` trigger one serialized `table.get(scope)` ignoring payloads, so missed events converge on next read and failed writes retry on tick.
- `set_network_access` refuses lists excluding caller `runWithCallerAddress` (never body input). Only Node's operations UDS skips it; other unknown addresses need `force`. Matching unmaps `::ffff:a.b.c.d` like the proxy; proxied peers only warn.

## Resource attribute permissions

`getTablePermissions` adds unlisted keys' `implicitPrimaryKeyPermission`; operations translation drops listed undeclared properties. Explicit key denials, timestamps, and sealed membership apply; `updatedAttributes` resets the permission memo.

`allowUpdate` retains `allowTableUpdate`'s map through puts/locks until its next call. Payloads omit protected values. `restrictedReplacement` patches full puts: omitted writable keys stay own `undefined` properties (visible to JS/MessagePack, omitted by JSON), avoiding stale protected bases. Restricted source writes use implemented `patch` or materialized `put`. PATCH limits: delete/retry can create partial rows, put-only sources with cold/stale caches can lose protected values, and `__op__` values are operations. Invalid full roots are refused. Trusted direct PATCH/create thenables check resolved keys while storing original fields. Dispatch resolves bodies; helpers reject failed promises without override re-entry (`unitTests/resources/permissions.test.js`, `unitTests/server/preconditions.test.js`, `integrationTests/security/resource-attribute-permissions.test.ts`; gaps: commit-time retry, crash replay, replication apply).

## System permissions on roles

`permission.system` derives from `super_user` and the registry. Held identities share mutable maps with frozen entries. API declarations return 400; files strip and warn on changed contents, not replay. Legacy copies strip without writes that could race `alter_role`; warnings dedupe by revision/thread. Impersonation reinstalls managed maps; scoped tokens strip before hashing to avoid MCP churn. External response reuse is per-call; listeners are lazy to avoid the Resource import cycle.
