## OIDC trusted publishing (`security/authn/oidc/`)

`exchange_oidc_token` authenticates a workload with no stored credential (#2171), exchanging a runtime identity token for a 1h operation token for the user a stored trust policy names. Unauthenticated like `create_authentication_tokens` (`NO_AUTH_OPERATIONS` in `server/serverHelpers/serverHandlers.ts`, `verifyPerms` bypass in `serverUtilities.ts`, `permission(false, [], OPERATIONS_ENUM.EXCHANGE_OIDC_TOKEN)`).

The core is issuer-agnostic; issuer-specific rules live in `providers/` by normalized issuer:

- `jwks.ts` keeps the unknown-`kid` refetch rate-limit clock outside the cache entry so replacing the entry never resets the limit and real rotations work on first use.
- `identityToken.ts` shares `rejectToken` with `tokenExchange.ts`; `tokenExchange.ts` memoizes verification per audience across policies.
- Unregistered issuers use `providers/generic.ts`, requiring a pinned `sub` (Kubernetes, GCP, SPIFFE). GitHub uses `githubActionsProfile` because `sub` varies by trigger and changed format after 2026-07-15.

Invariants:

1. **Uniform rejection message.** Unauthenticated callers get one generic error against claim-by-claim enumeration; reasons log to `oidc-trust`.
2. **GitHub policies gate the ref.** `githubActionsProfile.assertPolicyIsSpecific` rejects repository + workflow alone, since any branch pusher could add that workflow.
3. **`createOperationToken`, never `createTokens`.** `createTokens` overwrites `hdb_user.refresh_token` (#2018), revoking standing credentials.
4. **Role boundary narrowed by `tokenOperations`.** Optional policy `operations` only narrows the user's role via `tokenOperations`, intersected before every early return (`super_user` included) and never merged into `permission.operations` (`operation_authorization.ts` gate 2 treats explicit SU-only ops as grants). It gates the operations API and SQL (`verifyPerms` / `verifyPermsAST`), not REST/GraphQL table `checkPermission` (#2201; #2173), so the role must be least-privilege. `sql` grants the interface; write DML also requires `insert`/`update`/`delete` in scope so `read_only` (expanding to `sql`) cannot run `DELETE` under `verifyPermsAST`'s `super_user` bypass.
5. **Policy IDs never choose authority.** Tokens matched by enabled policies granting different users or operations fail unspent; agreeing policies pick the first by ID.

`hdb_oidc_token_use` (declared every start by `tokenUseTable.ts` so non-exchanging nodes evict replicated rows; `dataLayer/DESIGN.md`) records spent tokens with replicated record-metadata expiry past `exp`, keyed on SHA-256 of the **signed input** (`header.payload`): stores no credential, works without `jti` (Azure `uti`), and collapses signature malleability (RS256 trailing base64url bits, ES\* `s → n−s`). Non-atomic get-then-put suffices since a holder already earns one token.

Alongside `workload_identity`, exchange signs `deploy_source` (`{ via: 'oidc', policy, … }` via `attestedSource`, `components/deploymentSource.ts`); `validateToken` sets `deploySource` on the principal, impersonation preserves it, and `deploy_component` records it as attested over request fields (#3061) without storing credentials.

`harper deploy setup=true provider=github-actions` (`bin/deploySetupGithubActions.ts`) is a create-only client flow matching Studio's `<component>-ci-deploy` user/role and `github-actions-<component>` policy: keeps matches, aborts on drift/deactivation (never repurposing roles or undoing revocations), re-lists before replacing `add_oidc_trust` (replicated `hdb_oidc_trust` leaves cross-node races unexcluded), and verifies saved claims since mismatches fail as opaque 401s.

## Scoped tokens and synthetic-role identity (`security/tokenAuthentication.ts`, `security/impersonation.ts`)

`create_authentication_tokens` with an inline `role` **object** (`super_user` or `isOperationAuthorizationBypassed()` only; string `role` stays legacy component-defined, rejected by `validateOperationToken`) mints a `sub: 'scoped-operation'` JWT embedding its downgraded, deep-validated permissions, attribution-only `username`, no `hdb_user`/`hdb_role` row, and no refresh token. Scoped tokens are **irrevocable until expiry**, so `auth.ts` evicts cached Bearer identities at exact `authExpiresAt` rather than the auth-cache TTL.

`username` cannot match an existing `hdb_user` at mint (default `scoped:<minter>`), preventing by-name rehydration from substituting a real user's permissions or failing closed. Every by-name site checks `_scopedToken` (and `isLocalPrincipal`, below): MQTT last-will (`DurableSubscriptionsSession.ts` persists scoped role/marker/expiry and refuses replay or abnormal-disconnect publish past `authExpiresAt`), live-subscription rechecks (`Resource.ts` `registerLiveSubscriptionForContext`), and MCP `list_changed` (`components/mcp/listChanged.ts` `refreshSessionUser`). Passwordless `createTokens` rejects `hdb_user._scopedToken` against self-minting standing tokens; later colliding users stay inert unless a new site omits `_scopedToken`.

`operations` allowlists gate the operations API (including `sql` via `verifyOperationsAllowlist` in `chooseOperation`), never REST/GraphQL/MQTT table CRUD (`operations: ['read_only']` does not block REST writes). `verifyPerms` receives the handler, so gate 1 checks `permission`'s required `api_name` (`null` when ungrantable; unregistered `sql` checks as given). Shared-handler aliases grant both via the canonical name and neither via the alias. `get_backup` (gate 2 bypasses whole-DB READ), `read_transaction_log` (no `system.hdb_secret` guard like `read_audit_log`), and `catchup` (unrestricted writes) register `null` (`unitTests/utility/operation_authorization.test.js`).

`permissionsTranslator.getRolePermissions` memoizes by `(role name, __updatedtime__, schema)`, so synthetic roles never use a constant name or per-request timestamp (same-ms `Date.now()` collisions leak permissions across principals). `syntheticRoleName()` hashes post-downgrade permissions with `__updatedtime__: 0` (`applyImpersonation` re-keys all three modes identically). Leading-`_` names use the 256-entry LRU `syntheticRolePermsMap` instead of `rolePermsMap` (>256 concurrent sets fall back to per-request translation; persisted `_` roles safely land there too). In `verifyPerms`, the role `operations` gate precedes `super_user`, `structure_user`, and system-table early returns so inline roles combining `structure_user` with an allowlist cannot reach unlisted schema ops.

## TLS hot-reload publishes matching configured pairs (`security/keys.ts`)

`loadCertificates` publishes a configured leaf only after `X509Certificate.checkPrivateKey` passes. Only main watches cert/key dirs (shallow watches + 5-min poll sharing one fingerprint; unreadable dirs use Node file polling while configured files are absent). Incomplete pairs return `false` and retry (warn, error at 30 s — immediately without a non-self-signed record — then hourly); restoring prior files clears the alarm. Raw watch events arm an unpostponed <=1/s trailing check for unattempted fingerprints (chokidar drops add/change after two removals in 100 ms); missed OS events rely on the poll. CA-only rows ignore leaf keys. Workers reload via `hdb_certificate` subscriptions and read key files on build, without worker watches/polls. File-backed `getPrivateKeys()` entries refresh on read/rebuild, keeping cached values while unreadable unless an explicit key differs (`integrationTests/security/cert-key-reload.test.ts`, `unitTests/security/keys.test.js`, `unitTests/security/tlsFileWatch.test.js`).

The older-file guard prevents disk from overwriting newer replicated certs and freezes `hostnames` and `private_key_name`, while `ciphers`/`uses` track config via `from_config: true` (`file_timestamp` survives `setCertTable` patches). At load, marked rows with matching PEM get config `ciphers`/`uses` patched (`null` when `ciphers` is removed); `setCertTable` nulls `from_config` when an API write sets `ciphers` or `uses` so operator overrides survive restarts. Pre-marker rows adopt only when matching config; declined mismatches log. Shared-cert entries let the first entry own load reconciliation while full writes (first load or renewal) reflect whichever entry wrote until restart. Changes apply on start or file change, not `restart_service` (`unitTests/security/keys.test.js`).

**Transactional publication (#2382).** `updateTLS` builds replacement hostname→context, CA, and default-candidate state pass-locally, then mutates the live maps in place (`server.secureContexts` and `availableCAs` alias their identity). Existing rows failing build (`ERR_OSSL_X509_KEY_VALUES_MISMATCH` or missing worker key) keep live entries and default candidacy; if CAs changed, retained pairs rebuild against current trust (keeping active sessions/ticket keys) or drop on failure unless the zero-cert guard holds old state when nothing else serves. Deleted rows drop contexts; corrupt CA rows fail the pass and drop trust until healed. Failed passes backoff-retry on the shared debounce with throttled logs while subscriptions use plain debounce. `loadAndWatch` latches its fingerprint pre-callback and rolls back on `false`/error (guarded against stale rejections) so polling heals lost `hdb_certificate` writes.

**System-context reads (harper-pro#1189).** `initialize()` can first run inside a request (harper-pro non-owner reads opening replication), so `updateTLS` re-enters under `contextStorage.exit()` (`run(undefined, …)` across runtimes; Node 22's `async_hooks` `exit()` leaks across nested `run()`, `resources/DESIGN.md`) so `hdb_certificate` calls neither run request auth, consume one-shot `authorize`, nor pin request context on timers/subscriptions. Initial failure rejects `.ready`, while live selectors keep subscriptions and backoff retries, replacing `.ready` on recovery; a later `initialize()` replaces a still-failing attempt (clearing timers/subscription), one-shot selectors retire at once, and `.ready` keeps the rejected promise until replaced since Bun reads `undefined` as "no TLS" (`unitTests/security/keys.test.js`).

## Self-signed renewal replaces the pair in one transaction (`security/keys.ts`)

`prepareSelfSignedCerts` builds CA and replication records in memory; `publishSelfSignedCerts` writes them in one `transaction()` (where `renewSelfSigned` also deletes old self-signed rows) because `setCertTable` patches by name and a repeated `node.hostname` CA name would let a partial failure overwrite the CA without the leaf. Renewal excludes self-signed rows (`getCertAuthority(true)`, `getReplicationCert(true)`) so self-signed `replication` leaves never outscore external generic certs. Publication re-reads inside the transaction and never overwrites/deletes non-self-signed rows (renewal fails; boot review warns and skips, leaf included if CA was skipped; commit-window races on the same key are uncovered). If an external row holds `<node>`, the self-signed leaf uses `<node>-self-signed` (selected by hostname, not row name). Configured CA key paths apply only if parsed; generated keys open exclusively (`wx`, `0o600`) in `keys/` after record build, never overwrite files, and unlink on failure (`unitTests/security/keys.test.js`, `integrationTests/security/renew-certs-missing-privatekey.test.ts`).

## Client-certificate revocation checking keeps three tables (`security/certificateVerification/`)

`verificationTables.ts` declares all three on writable starts and verification (`dataLayer/DESIGN.md`). Row expiry is record metadata; table `expiration` is only the fallback when omitted.

- Verdicts (`hdb_certificate_cache`) expire `cacheTtl` after check via `CertificateVerificationSource` setting `context.expiresAt` (`sourceContext.expiresAt`), never a returned field; `createCacheKey` hashes a key version so expiry-less legacy rows are ignored.
- Revocations (`hdb_revoked_certificates`) expire at `crl_next_update + gracePeriod` so `performCRLCheck` can honor the grace window past `crl_next_update` instead of evicting at `nextUpdate` and passing revoked certs on overdue CRLs.
- CRL revocations replace the prior set atomically in their own transaction outside `performCRLCheck`'s verdict-fill transaction. The downloader decides from the downloaded CRL directly (another worker may replace table rows first); cached-CRL checks read outside the verdict-fill transaction so LMDB snapshots see newer commits.

## A component-facing export needs BOTH `index.ts` and `getHarperExports` (`security/jsLoader.ts`, `index.ts`)

`index.ts` publishes package exports, while VM compartments resolve `'harper'` from the hand-maintained `getHarperExports()` literal. Missing either breaks `import { x } from 'harper'` at component load, which `#src/…` unit tests miss; verify with a `'harper'`-importing fixture (`integrationTests/security/fixtures/deferred-credential-rejection/resources.js`, harper#2703). Import directly from the defining module rather than re-exports so module-private `Symbol` identity holds (`markCredentialRejection` / `isCredentialRejection`).

## Both application loaders resolve through one `resolveModule` (`security/jsLoader.ts`)

Both the VM loader and compartment `resolveHook` call module-scope `resolveModule` for parity across `applications.moduleLoader` modes. It resolves CommonJS-first (dual packages keep `require` targets), falling back to `PACKAGE_EXPORTS_RESOLVE` (`node` and `import` conditions, plus `bun` on Bun; `module-sync`, `node-addons`, and `--conditions` unmodeled) only when bare-specifier `import` fails CommonJS resolution (`ERR_PACKAGE_PATH_NOT_EXPORTED`, or `MODULE_NOT_FOUND` on Bun); `require()` never falls back. Fallback resolutions track `package.json` and entry digests rather than resolution edges because `RuntimeModuleTracker` re-resolves edges via `createRequire` and would mark import-only packages changed every deploy.

SES loads once via `loadSES` from `ses/index.js` ESM shims (shared by lockdown and compartments), never `require('ses')`, because Bun strips function-level `'use strict'` in CommonJS and trips `SES_NO_SLOPPY` (`unitTests/security/jsLoader/jsLoader.test.js`, `integrationTests/components/compartment-pure-esm-dependency.test.ts`).

## `require()` and `import` pass the same gates in the VM loader (`security/jsLoader.ts`)

In `vm` and `vm-current-context`, all four entry points (ESM `linker`, both `importModuleDynamically` hooks, CommonJS `cjsRequire`) apply in order: `'harper'` alias, `checkAllowedModulePath` (`allowedDirectory`, `allowedBuiltInModules`, and substitutes like constrained `child_process`), `shouldUseApplicationLoader`, and `readApplicationModule` (byte tracking + TypeScript strip); `require()` differs only in synchronous native `require(path)` vs `import()`. New entry points or branches owe all four. URL-keyed `cjsCache` (app CommonJS) and `nativeModules` (registered before native `require()`/`import()`, released if failed unloaded) are shared across `require()` and `import` for one instance per scope, returning post-check hits directly. Only a wrapper compile error triggers `createModuleFromSource`'s ESM retry; evaluation throws propagate. Uncovered: app-loaded ESM stays in `moduleCache` only (bare `require()` under `dependencyLoader: native` gets Node's `require(esm)` instance; JSON imports stay default-only), compartment `importHook`, and transitive `require()` in native packages (`unitTests/security/jsLoader/jsLoader.test.js`, `integrationTests/components/cjs-require-loader.test.ts`, `integrationTests/components/require-confinement-parity.test.ts`).

## Authentication converts every principal-resolution failure into a decision (`security/auth.ts`)

`authentication()` resolves mTLS certificate CN, `Authorization`, and `hdb_session` via overridable `server.getUser`. Every failure must go through `settleAuthFailure()` / `rejectAuthenticationInPlace()`, never throw (escaped throws unwind to `server/http.ts` as plain text, harper#2703): internal faults and operations-API routes answer 401 in place; tagged credential rejections defer to the route owner.

- **Upgrades need recorded in-place rejections.** `server/REST.ts` and `server/mqtt.ts` discard `await chainCompletion`'s return value, so `rejectAuthenticationInPlace` sets `markAuthenticationRejectedInPlace` for `assertNoDeferredCredentialRejection` to fail WebSocket/MQTT upgrades closed.
- **Deferred rejections stop fallthrough.** Route owners call `settleDeferredCredentialRejection` before reading `request.user`, so a rejected certificate never falls through to Basic, session, or local bypass.

## A request's session helpers are bound module functions, never function literals assigned to a property (`security/auth.ts`)

`request.session.update` and `request.login` bind module functions `updateSession` / `loginWithSession` to a per-request `SessionState` after copying stored session fields (overwriting any stored `update` and working detached). Never assign function literals directly to properties (`request.login = async function …`) on hot paths: V8's `CheckAssigningFunctionLiteralToProperty` pretenures them in old space, pinning the young context (`request`, headers, `response`) until major GC. Assign literals to locals first or bind module functions (`unitTests/security/authSessions.test.js`).

## User and role lookups read the records, and nothing derived from them outlives them (`security/user.ts`)

Lookups read `hdb_user` (by name) and `hdb_role` (by id) from the primary store cache without cross-thread broadcasts:

- **Consistent state.** RocksDB point reads share no snapshot, so `readUserEntries` rechecks the user version after reading its role and retries on movement against torn grants. LMDB uses the thread's turn-renewed shared read txn (next-turn visibility; per-lookup resets exhaust reader slots).
- **Version-validated caches.** Uncached reads return fresh objects; per-role memos, `isCurrentUser`, and `auth.ts` cache hits compare entry versions (or values on `VERSION_REUSED`), and external `server.getUser` principals check pre-resolution `trackUserRecords` versions.
- **Holder notifications.** `onUserChange` feeds live-subscription revocation and MCP `list_changed` from per-thread `hdb_user`/`hdb_role` subscriptions with changed primary keys, or no args when unknown (reload, oversized batch, gap reconnect) so all holders recheck. `userChangeNotificationEpoch()` is non-zero only on RocksDB while both subscriptions stay open with certified progress; unaudited tables are never subscribed (which persists auditing), leaving epoch `0` for fallback sweeps.
- **Request views.** `cloneUserView(user)` isolates per-request `role`/`permission` replacement from cached principals, carrying record provenance on an own symbol across spreads without WeakMap writes (`trackedProvenance` covers external users). Enforced by `unitTests/security/userRecordLookups.test.js` and `unitTests/resources/replicatedUserWrites.test.js`.

### A component grant answers to its names ahead of every operations listing (`security/componentGrant.ts`)

`component_deploy` (harper#3046; avoiding `RESERVED_DATABASE_NAMES` database-name collisions with `components`) scopes `deploy_component`, `drop_component`, `get_deployment`, `list_deployments`, and `get_components` by `names` patterns (`componentNameMatches` in `utility/componentNames.ts`, shared with deploy credentials, harper#3090).

1. **Ahead of gate 2.** `verifyPerms` runs the grant check before gate 2 (which grants listed SU-only ops globally), and its verdict is final for those five ops; gate 1 still requires listing them when an `operations` allowlist exists.
2. **Handler-aligned names.** Deploy/drop resolve names via `canonicalProjectName` else `projectNameFromPackage`; component-less reads filter (`get_components`, `list_deployments`) or 403 (`get_deployment`).
3. **Origin-only constraints.** `deployComponent` enforces `isolated`, `hostSuffix`, and `branchedDatabases: required` on the origin against the effective post-deploy entry (package declaration, payload routing, or existing entry) pre-write, under the preparation lock, and against staged descriptors on activation; peers trust the origin.
4. **Deploy-only secret patterns.** `grant_secret component=my-app-pr-*` applies only at deploy (`resolveCredentials`, harper#3090; `harper deploy setup=true` allows patterns only for `github`/`npm`); runtime `components/componentSecrets.ts` stays exact-match. `preview`, `maxPreviews`, and `maxTtlDays` bound preview identities below.

## PR previews are enabled by the cluster (`components/previewOperations.ts`)

`enable_previews`, `disable_previews`, and `get_preview_policy` (harper#3042) are replicated system-table ops sharing `utility/previewIdentity.ts` names/claims with CLI and Studio: role/user `<app>-ci-preview` (`CI_PREVIEW_OPERATIONS`, `component_deploy` for `<app>-pr-*` with `preview: required`, no table perms) plus OIDC policies `github-actions-<app>-preview` (env `preview`) and `github-actions-<app>-preview-cleanup` (env `preview-cleanup`, scoped to `drop_component` so `preview` reviewer gates do not block teardown and deploy tokens cannot match cleanup).

- **Grant-hosted bounds.** `maxPreviews` (`deployment.previews.maxPerApplication`) and `maxTtlDays` (default 7) sit in `component_deploy.constraints` as one replicated record enforced on the origin (super-user previews face only the configured cap). `preview: required` mandates `preview` metadata naming app `A` matching `A-pr-*` as `A-pr-<n>` (preventing expiry/cap bypass, `shop-pr-pr-3` miscounting, or `shop` dropping `shop-pr-tools`), clamps `expiresAt` pre-write/pre-replication, and refuses expired activations against the build row before live-release returns. `maxPreviews` counts under the per-origin lock (two origins can each claim the last slot).
- **Serialized create-only enable.** One enable/disable runs per node at a time, keeping matches, 409ing on drift or overlapping authority (`policiesOverlap`, `sameAuthority`), and rechecking before `add_oidc_trust` (cross-node concurrent writes stay unexcluded, #3127).
- **Revoke-then-drop disable.** Drops trust policies and deactivates the user (`isCurrentUser` halts in-flight activations), then runs `fence_preview_releases` (#3613) under the per-app admission lock to revoke the grant's `generation` (minted on enable, stamped on builds) and census live previews. Origin and peer activations check that fence under the lock, grants activate only matching-generation builds, unacknowledged peers count unreachable, and peer fencing uses node-identity bypass (`isOperationAuthorizationBypassed()`, avoiding `REPLICATED_FROM` lifting deploy grants). Unfenced: super-user previews, pre-generation in-flight builds (`get_preview_policy`; rerun once `inProgress` drains), and — bounded by expiry (#3805) — late timed-out peer swaps, crash roll-forward, rollback/canary restores to fenced predecessors, and racing enables. Disable then drops live releases per node (`ifDeploymentId`, halting non-origin drops pre-replication) and drops user/role; failed/empty drops, unknown node state, or missing rows stop with identity revoked so reruns resume.

## The password hash function and token lifetimes are read when used, never at module load (`security/user.ts`, `security/tokenAuthentication.ts`, `utility/password.ts`)

Empty-root `harper run` loads auth/installer modules before `install()` writes config and creates `admin` before `runStartup()`, so `authentication.hashFunction` resolves per password write (`password.configuredHashFunction()`) and persists on `hash_function` for validation. `password.hash` defaults to configured; `password.validate` always defaults to SHA-256 so synchronous SHA-256 refresh-token checks never receive a Promise from an async configured hash (`!Promise` would accept superseded tokens). Token lifetimes resolve per mint (`integrationTests/security/firstboot-auth-config.test.ts`).

## Local trust is a principal, not a stored user (`security/user.ts`, `security/auth.ts`)

Transport-trusted requests (`authentication.authorizeLocal` on `isLocalPeerAddress` loopback, operations socket `bypassLocalAuth`, loopback MQTT, test `bypassAuth()`) run as `localPrincipal()`: a record-less super user named `local` working with zero stored users.

- **Marker-identified.** `isLocalPrincipal` checks `_localPrincipal: true`, set only by trusted code (never copied by `userView` or external auth paths; string key for Bun/uWS JSON forwarding and MQTT wills). `add_user` rejects `local`; pre-existing stored `local` rows stay ordinary users.
- **Non-portable.** Dropped by `session.update` and never token-minted: credential-free `create_authentication_tokens` mints for `getSuperUser` (first active stored `super_user`) or 409s. By-name rehydration checks `isLocalPrincipal` first (MQTT wills rebuild from marker; live-subscription and MCP `list_changed` skip it as irrevocable).
- **Per-call view.** Fresh user/`role`/`permission` objects matching default install `super_user` (including `role.id` for redirector/early-hints templates), frozen `system` entries, and a shared mutable table-name map (`unitTests/security/localPrincipal.test.js`, `integrationTests/security/local-principal-token-mint.test.ts`).

## Named component children are identified by lifetime (`security/jsLoader.ts`, `security/spawnPidFile.ts`)

`pids/<name>.pid` stores positive PID, version (`0` if omitted), and OS birth identity ([#2968](https://github.com/HarperFast/harper/issues/2968): Linux boot ID/PID/start ticks excluding zombies/TIDs; macOS PID + UTC/C `ps lstart` at 1 s; Windows PID + `Win32_Process.CreationDate` ticks) via write-then-rename (pre-publish crashes can leave unrecorded children). Adoption, version replacement (`process.kill(pid)`; Windows sets `ChildProcess.exitCode` with `signalCode: null`), wrapper kill, and exit polling (1 s Linux/macOS, 5 s Windows, non-overlapping async macOS/Windows probes; no `kill(0)` fast path so recycled PIDs never hold exited wrappers open) compare birth identity. Cross-boot Linux records retire pre-probe; probe failures, `hidepid`/`ProtectProc`, and permission denials stay unknown and never retire records or emit exit. Legacy two-line records warn and retire without signaling unverified PIDs (older builds ignore line 3).

Synchronous spawn/adoption probes under a filesystem bakery lock (UUID choosing/ticket files sharing `componentPreparationLock.ts` ordering; Windows sharing retries; unique release markers if claim unlink fails). Foreign owner matches cache for 1 s (stale positives only delay reclamation). Acquisition, publication, and non-waiting exit cleanup (cached own identity + conservative foreign claims without new probes; busy records defer to next spawn) share one claim protocol so stale checkers or older exits never delete newer records. `Atomics.wait` lock waits fail after 60 s without original-predecessor cohort progress; newcomers cannot renew stalled waits, live claims are never stolen, unreadable owners fail closed, external probes cap at 30 s, and synchronous capture prevents child reaping before identity read. Terminated-worker orphan claims inside a live Harper process require Harper restart (OS identity is process-wide). Release errors report separately from spawn results/native arg errors; probe/lock failures throw `NamedProcessError` (`ServerError` with `cause`) (`unitTests/components/spawnPidIdentity.test.js`, `unitTests/components/spawnPidFile.test.js`, `integrationTests/components/named-process.test.ts`).

## Application lockdown seals the intrinsics by default (`security/intrinsicsLockdown.ts`)

`applications.lockdown` defaults to `seal-after-load` on fresh installs; the installer writes the whole config, so upgrades keep their prior mode. Sealing blocks additions/deletions on 21 intrinsic globals and prototypes plus `Function`/`Function.prototype`, while allowing overwrites; it is not a sandbox. Never make seal-mode prototype properties read-only: array-hole stores become ~45× slower and msgpackr decode ~3× slower; accessors prevent built-in inlining. Only freeze modes need `overridableProperty`. Sealing covers replaced globals and realm originals, which literals/async functions retain; freezing covers current globals, leaving `Function.prototype` extensible. Unknown truthy modes freeze eagerly (fail closed); falsy modes skip lockdown. Tests: `unitTests/security/intrinsicsLockdown.test.js` (fresh workers), `integrationTests/components/intrinsics-lockdown.test.ts`; measurements: `benchmarks/lockdown/run.mts`.

## A scoped mirror is never advertised before its allowlist is read (`security/networkAccess.ts`)

`system.hdb_network_access` holds one replicated row per scope (`operations` today). A fronting proxy enforces it; Harper only publishes `allowedSources` in UDS mirror metadata (`writeUdsMetadata`, `server/http.ts`).

- **No unrestricted advertisement.** The writer, not `ready`, holds a scoped mirror until this thread's first read, because `security/keys.ts` fires `secureContextsListeners` before readiness. An absent table after databases load means unrestricted.
- **One reconciler per scope.** Subscription events, the 60 s tick, and `onUpdatedTable` trigger one serialized `table.get(scope)` ignoring payloads, so missed events converge on the next read and failed writes retry on tick.
- **Lockout check.** `set_network_access` refuses lists excluding the caller's `runWithCallerAddress` (never body input). Only Node's operations domain socket skips it; other unknown addresses require `force`. Matching unmaps `::ffff:a.b.c.d` like the proxy; proxied peers only warn.

## Resource attribute permissions

`getTablePermissions` adds the unlisted key’s `implicitPrimaryKeyPermission`; operations translation drops listed undeclared properties. Explicit key denials, timestamps and sealed membership apply. `updatedAttributes` resets the permission memo.

`allowUpdate` retains `allowTableUpdate`’s map through puts/locks until its next call. Payloads omit protected values. `restrictedReplacement` patches full puts: omitted writable keys remain own `undefined` properties (JavaScript/MessagePack see them; JSON omits them). This avoids stale protected bases. Restricted source writes use implemented `patch` or materialized `put`. PATCH limits remain: delete/retry can create partial rows, put-only sources with cold/stale caches can lose protected values, and `__op__` values are operations. Invalid full roots are refused. Trusted direct PATCH/create thenables can check resolved keys but store original fields. Dispatch resolves bodies; helpers reject failed promises without override re-entry. Tests: `unitTests/resources/permissions.test.js`, `unitTests/server/preconditions.test.js`, `integrationTests/security/resource-attribute-permissions.test.ts`. Gaps: commit-time retry, crash replay and replication apply.

## System permissions on roles

`permission.system` derives from `super_user` and the registry. Held identities share mutable maps with frozen entries. API declarations return 400; files strip and warn on changed contents, not replay. Legacy copies strip without writes that could race `alter_role`; warnings dedupe by revision/thread. Impersonation reinstalls managed maps; scoped tokens strip before hashing to avoid MCP churn. External response reuse is per-call; listeners are lazy to avoid the Resource import cycle.
