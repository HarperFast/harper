## OIDC trusted publishing (`security/authn/oidc/`)

`exchange_oidc_token` exchanges a workload token for a 1h operation token without a stored credential (#2171), wired via `NO_AUTH_OPERATIONS` (`serverHandlers.ts`), `verifyPerms` (`serverUtilities.ts`), and `permission(false, [], OPERATIONS_ENUM.EXCHANGE_OIDC_TOKEN)`.

`claims.ts` validates/matches claims; `jwks.ts` caches keys with the unknown-`kid` refetch clock _outside_ the entry (fetch replacement never resets the limit; rotations work on first use); `identityToken.ts` checks signature, issuer, audience, `exp`, and lifetime (`rejectToken`); `tokenExchange.ts` runs selection, replay, minting, and audit (memoizing signatures per audience). `providers/` (`assertPolicyIsSpecific`, `assertAudienceIsSpecific`, `normalizeClaims`, `describePrincipal`, `vetoClaims`) keys by normalized issuer: unregistered issuers use `generic.ts` (pins `sub`: K8s, GCP, SPIFFE); GitHub needs a profile (`sub` varies by trigger and changed after 2026-07-15).

1. **Uniform rejection:** unauthenticated endpoint; specific errors leak policy claims; reasons log to `oidc-trust`.
2. **GitHub policies gate the ref:** `githubActionsProfile.assertPolicyIsSpecific` rejects pinning only repo + workflow (any branch pusher could add it); profile-scoped.
3. **`createOperationToken`, not `createTokens`:** `createTokens` overwrites `hdb_user.refresh_token` (#2018).
4. **Role is the boundary; per-policy `operations` only narrows it:** subtracts as `tokenOperations` (never in `permission.operations`, where gate 2 in `operation_authorization.ts` treats SU-only listings as grants) and intersects before early returns (`super_user` included). Enforces on operations API/SQL (`verifyPerms`/`verifyPermsAST`), **not** app REST/GraphQL (`checkPermission` ignores it; #2201), so roles must be least-privilege (#2173 left open whether to keep a 2nd mechanism beside roles). Naming `sql` still requires `insert`/`update`/`delete` for DML writes so `read_only` cannot admit DELETE on `super_user` early returns.
5. **Policy ids never choose authority:** refuses, unspent, a token 2 enabled policies grant different users/operations; agreeing policies pick first by id.

`hdb_oidc_token_use` (`tokenUseTable.ts` at start so passive nodes expire replicated rows; `dataLayer/DESIGN.md`) keys spent tokens by SHA-256 of `header.payload` past expiry (no stored credentials, `jti`/`uti`, or RS256/ES\* malleability; non-atomic get-then-put replay is no escalation). Beside `workload_identity`, tokens sign `deploy_source` (`attestedSource`, `components/deploymentSource.ts`); `validateToken` lifts `deploySource` (kept across impersonation) and `deploy_component` prefers it over request values (#3061). `harper deploy setup=true provider=github-actions` (`bin/deploySetupGithubActions.ts`) creates `<component>-ci-deploy` and `github-actions-<component>` (create-only: keeps matches, aborts on differing/deactivated records; re-lists before `add_oidc_trust`—which replaces, so a policy another SU writes in the last RTT is overwritten, and a server-side create-only check would not close this across `hdb_oidc_trust` replication—and verifies claims, else a mismatch surfaces only as an opaque 401).

## Scoped tokens and synthetic-role identity (`security/tokenAuthentication.ts`, `security/impersonation.ts`)

`create_authentication_tokens` with an inline `role` **object** mints an irrevocable-until-expiry `sub: 'scoped-operation'` JWT embedding downgraded, deep-validated permissions without `hdb_user`/`hdb_role` rows (`username` is attribution only; requires `super_user` or `isOperationAuthorizationBypassed()`; string `role` keeps legacy component-token meaning, rejected by `validateOperationToken`). `auth.ts` evicts cached Bearer entries at `authExpiresAt`.

Attribution `username` (default `scoped:<minter>`) cannot match an existing `hdb_user` at mint so by-name rehydration never substitutes a real principal or fails closed. All 3 by-name sites short-circuit on `_scopedToken`: MQTT will replay (`DurableSubscriptionsSession.ts` persists role/marker/expiry, skips rehydration, refuses replay/publish past `authExpiresAt`), live subscriptions (`Resource.ts` `registerLiveSubscriptionForContext`), and MCP `list_changed` (`listChanged.ts` `refreshSessionUser`). Passwordless `createTokens` rejects `_scopedToken` (no self-minted standing tokens). **Future by-name sites must check `_scopedToken`** (and `isLocalPrincipal`); post-mint colliding users are inert at current sites and expiry-bounded.

`operations` allowlist gates the **operations API** (including `sql` via `verifyOperationsAllowlist` in `chooseOperation`), **not** app REST/GraphQL/MQTT (table CRUD perms only). `verifyPerms` checks registered `api_name` (never `handler.name`; `permission` requires an API name or `null`), except unregistered `sql`. Canonical names grant aliases; aliases grant neither. `get_backup` (whole-DB READ), `read_transaction_log` (no `system.hdb_secret` guard), and legacy `catchup` (unauthorized writes) register with `null` (`unitTests/utility/operation_authorization.test.js`).

`permissionsTranslator.getRolePermissions` memoizes by role name + `__updatedtime__` + schema. `syntheticRoleName()` (`applyImpersonation`) hashes post-downgrade permissions with `__updatedtime__: 0` (never a constant name or `Date.now()`, as sharing a name serves another principal's cached permissions). Leading-`_` roles use a 256-entry LRU (`syntheticRolePermsMap`, not `rolePermsMap`). In `verifyPerms`, `operations` allowlist must stay **ahead of** `super_user`, `structure_user`, and system-table early returns (inline roles can combine `structure_user` with an allowlist keeping unlisted schema ops unreachable).

## TLS hot-reload publishes matching configured pairs (`security/keys.ts`)

`loadCertificates` publishes a configured leaf only after `X509Certificate.checkPrivateKey`. Only the main thread watches cert/key dirs; shallow watches and a 5m poll share a fingerprint. Incomplete pairs return `false` and retry, warning then erroring at 30s (immediately without a non-self-signed record) and hourly after; restoring files clears the alarm. Raw watch events arm a trailing check (<=1/s, never postponed) for unattempted fingerprints (chokidar drops rapid re-adds in its 100ms throttle); OS-dropped events rely on the poll. CA-only records ignore the leaf key. Workers reload on `hdb_certificate` subscriptions and read keys when building contexts. File-populated `getPrivateKeys()` entries refresh on retrieval/rebuild, keeping cached values while unreadable; explicit values differing from the last file key win. Unreadable dirs poll files while absent (`integrationTests/security/cert-key-reload.test.ts`, `unitTests/security/keys.test.js`, `unitTests/security/tlsFileWatch.test.js`).

Loader-written records carry `from_config: true`; load patches config `ciphers`/`uses` edits onto marked records with matching PEM (`null` if `ciphers` removed) despite the older-file guard. `setCertTable` nulls `from_config` when an API write sets `ciphers`/`uses` (`file_timestamp` kept on patches), preserving API edits across restarts; pre-marker records adopt only when matching config. Shared cert files reconcile from the first config entry on load (full writes use last/first until restart). Changes apply at start or file change, not `restart_service`; `hostnames` and `private_key_name` stay frozen (`ciphers and uses follow config`). Older-file guards protect newer replicated certs.

**Transactional publication (#2382):** `updateTLS` builds replacement contexts, CAs, and default candidates pass-locally, then reconciles `server.secureContexts` and `availableCAs` in place. Failed builds (`ERR_OSSL_X509_KEY_VALUES_MISMATCH` or missing key) keep live entries and default candidacy. Retained pairs rebuild on `ca:` change (keeping sessions/ticket keys) or drop on failure unless nothing else is servable (zero-cert guard). Deleted rows drop contexts; corrupt CA rows fail the pass and drop trust. Failed passes backoff-retry (1.5s–5m, throttled logs); subscriptions debounce. `loadAndWatch` rolls back its latched fingerprint on `false`/rejection (equality-guarded) so polling heals lost writes.

**System-context reads (harper-pro#1189):** `updateTLS` re-enters under `contextStorage.exit()` (`run(undefined, …)`, avoiding Node 22 `async_hooks` `exit()` leaks; `resources/DESIGN.md`) so request-triggered `initialize()` never runs request auth, consumes one-shot `authorize`, or pins request context on timers/subscriptions. Pre-`.ready` failures reject `.ready`, while live selectors keep retrying and replace `.ready` on recovery; later `initialize()` calls replace failing attempts (one-shot selectors retire immediately; `.ready` stays rejected for Bun, `createTLSSelector initialized by a request`).

## Self-signed renewal replaces the pair in one transaction (`security/keys.ts`)

`prepareSelfSignedCerts` builds self-signed CA and replication-cert records in memory; `publishSelfSignedCerts` writes them in 1 `transaction()`, where `renewSelfSigned` also deletes old self-signed rows (`setCertTable` patches by name; CA name repeats when `node.hostname` is set). Renewal excludes self-signed rows when finding reusable certs (`getCertAuthority(true)`, `getReplicationCert(true)`) so a self-signed `replication` leaf never outscores an external generic one. Publication re-reads each row in-txn and refuses to replace/delete non-self-signed rows (renewal fails; boot review warns and skips it, plus the leaf when it is the CA). If an external row holds the node name, the self-signed leaf uses `<node>-self-signed` (selected by hostname, not row name); same-key commit-window writes are uncovered. Configured key paths name the CA key only when parsed; generated keys use `wx` (`0o600`) in `keys/` after building records, never overwrite, and unlink on failure (`integrationTests/security/renew-certs-missing-privatekey.test.ts`).

## Client-certificate revocation checking keeps three tables (`security/certificateVerification/`)

`verificationTables.ts` declares all 3 on writable starts and verification paths (`dataLayer/DESIGN.md`). Row expiry is record metadata; table `expiration` is only the fallback:

- **Verdicts (`hdb_certificate_cache`)** expire `cacheTtl` after check via `CertificateVerificationSource` `context.expiresAt` (judged by stored `sourceContext.expiresAt`, never a source-returned field). `createCacheKey` hashes a key version so verdicts cached before expiries were stored (which would read as fresh forever) are never read again.
- **Revocations (`hdb_revoked_certificates`)** live until `crl_next_update + gracePeriod`, matching `performCRLCheck`'s `crl_next_update` window (expiring at `nextUpdate` reported revoked certs on overdue CRLs as good).
- **Whole-CRL replacement:** revocations replace the prior set atomically in their own txn outside the verdict fill's `performCRLCheck` txn. Downloading checks decide from the in-memory CRL (another worker may replace rows before re-read); cached-CRL checks read the table outside the verdict fill's txn so LMDB snapshots see newer commits.

## A component-facing export needs BOTH `index.ts` and `getHarperExports` (`security/jsLoader.ts`, `index.ts`)

`export { x } from './…'` in `index.ts` publishes `x` on `harper`, but `import { x } from 'harper'` in a VM/compartment resolves `harper` to `getHarperExports()` — a hand-maintained literal, not a re-export of `index.ts`. Missing either fails at component load (`The requested module 'harper' does not provide an export named 'x'`), which `require('#src/…')` unit tests miss; only a fixture importing `'harper'` catches it (`integrationTests/security/fixtures/deferred-credential-rejection/resources.js`, harper#2703). Import from the defining module, not `index.ts`, so component values share private `Symbol` tags (`markCredentialRejection`/`isCredentialRejection`).

## Both application loaders resolve through one `resolveModule` (`security/jsLoader.ts`)

VM and compartment `resolveHook` share `resolveModule` so `applications.moduleLoader` modes match. It resolves CommonJS-first (dual packages keep their `require` target) and falls back to `package.json` `exports` only on bare imports rejected by CommonJS (`ERR_PACKAGE_PATH_NOT_EXPORTED`, or `MODULE_NOT_FOUND` on Bun); `require()` never falls back. The fallback ports Node's `PACKAGE_EXPORTS_RESOLVE` with `node`/`import` conditions (plus `bun` on Bun; `module-sync`, `node-addons`, and `--conditions` not modeled), checked against Node (`resolves package exports as native Node import does`). Fallback resolutions record `package.json` and entry digests, not a resolution edge, so `RuntimeModuleTracker` `createRequire` re-resolution does not mark import-only packages changed every deploy. SES loads from `ses/index.js` via `loadSES`, never `require('ses')` (Bun drops function-level `'use strict'` in CommonJS, triggering `SES_NO_SLOPPY`), sharing 1 instance across lockdown and compartments (`pure-ESM package resolution`, `integrationTests/components/compartment-pure-esm-dependency.test.ts`).

## `require()` and `import` pass the same gates in the VM loader (`security/jsLoader.ts`)

In `vm`/`vm-current-context`, all 4 entry points — ESM `linker`, both `importModuleDynamically` hooks, and CommonJS `cjsRequire` — apply in order: `'harper'` alias, `checkAllowedModulePath` (`allowedDirectory`, `allowedBuiltInModules`, substitutes like constrained `child_process`), `shouldUseApplicationLoader`, and for app-loaded files `readApplicationModule` (digests and TS stripping). `require()` differs only in loading synchronously (`require(path)` vs `import()`). A file keeps whichever route loaded it first: `cjsCache` (app-loaded CJS) and `nativeModules` (registered before native `require()`/`import()`, released on failure) key by URL and are shared by `require()` and `import` (both hold only path-checked modules, so hits skip re-checking). Not covered: app-evaluated ESM lives only in `moduleCache` (bare `require()` under `dependencyLoader: native` gets Node's `require(esm)` instance), JSON imports are default-only, compartment mode's `importHook` (covered below), and transitive requires in native packages. Only a CJS wrapper compile error selects the ESM retry in `createModuleFromSource`; evaluation errors propagate (`CommonJS require`, `integrationTests/components/cjs-require-loader.test.ts`).

## Compartment `importHook` checks `allowedPath` once (`security/jsLoader.ts`)

`checkAllowedModulePath` runs once at the top of the compartment `importHook`, after the synthetic `harper` return and before branch selection, so `.node`, plain-file (`.js`, `.ts`, `.json`), and native-import branches cannot load unapproved paths, and future branches inherit the check (#3485; previously only `.node` and native-import branches called it, loading out-of-tree plain files that VM `createModule` refused). Uses the prefix check only, not containment (#1929, #2970), and skips native packages' transitive loads (`compartment importHook`, `unitTests/security/jsLoader/jsLoader.test.js`, `integrationTests/components/compartment-allowed-directory.test.ts`).

## Compartment dynamic CommonJS names (`security/jsLoader.ts`)

For bare or `node_modules` native `import()` in compartment `importHook`, `dynamicCjsExports` copies enumerable `module.exports` data properties the namespace lacks (skipping accessors, throwing Proxy traps, and callable `then`) while keeping namespace keys and `default` (#3485). Reads `require.cache` (Node 22 omits `'module.exports'`); `normalizeImportedModule` (kept by VM loaders) is a Node 22 no-op and elsewhere rebuilds exports from enumerable properties, dropping non-enumerables and replacing transpiled `default` (`CommonJS dependencies imported natively`, `unitTests/security/jsLoader/jsLoader.test.js`).

## Authentication converts every principal-resolution failure into a decision (`security/auth.ts`)

`authentication()` resolves principals from mTLS CNs, `Authorization` headers, and `hdb_session` cookies via overridable `server.getUser`. Every failure becomes a **decision** via `settleAuthFailure()`, never an escaping throw (unwinding middleware to `server/http.ts` plain text, harper#2703): internal faults and operations-API routes answer in place (`rejectAuthenticationInPlace()`), while tagged credential rejections defer and stop resolution so rejected certs never fall through to Basic, session, or local bypass. `server/REST.ts` and `server/mqtt.ts` discard `chainCompletion`'s return, so `rejectAuthenticationInPlace()` sets `markAuthenticationRejectedInPlace` on the request for `assertNoDeferredCredentialRejection` to fail WS/MQTT upgrades closed (first missed on cert revocation). Route owners call `settleDeferredCredentialRejection` before reading `request.user`; any new principal-resolution path must go through `settleAuthFailure()` / `rejectAuthenticationInPlace()`.

## A request's session helpers are bound module functions, never function literals assigned to a property (`security/auth.ts`)

`request.session.update` and `request.login` are `updateSession`/`loginWithSession` bound to 1 per-request `SessionState`, installed after copying stored fields (overwriting any stored `update`), and work detached or copied. Never use `request.login = async function …`: V8 pretenures function literals assigned to properties (`CheckAssigningFunctionLiteralToProperty`, `deps/v8/src/parsing/parser.h`), allocating the closure in old space and pinning its young context until major GC (~1.8 KB/request, ~3× major GCs on warm REST GETs). Bind module functions or assign literals to locals (`unitTests/security/authSessions.test.js`).

## User and role lookups read the records, and nothing derived from them outlives them (`security/user.ts`)

Lookups read `hdb_user` by name and `hdb_role` by id via the primary store cache; LMDB shares the thread's read txn (renewed <=1/turn by lmdb-js):

- **One committed state:** RocksDB point reads share no snapshot, so `readUserEntries` re-checks the user's version after reading its role and retries if it moved, preventing role-move + grant txns from combining old role with new grant.
- **Version-keyed derived data:** uncached reads return fresh objects; per-role memo, `isCurrentUser`, `auth.ts` cache hits, and `trackUserRecords` validate entry versions (or values for `VERSION_REUSED`).
- **Holder notifications (`onUserChange`):** feeds live-subscription revocation and MCP `list_changed` from per-thread `hdb_user`/`hdb_role` subscriptions with changed keys (no arg on reload, oversized batch, or gap recovery rechecks all). `userChangeNotificationEpoch()` is non-zero only while both subscriptions are open with certified RocksDB progress (an unchanged non-zero epoch across a window proves every change in it was notified) and never calls `subscribe()` on unaudited tables (which would persist auditing), leaving epoch 0 so consumers use backstops.
- **Request user views:** `cloneUserView(user)` replaces `role`/`permission` without mutating cached principals and carries provenance via an own symbol across spreads without a `WeakMap` write (`trackedProvenance` is only for external users; `unitTests/security/userRecordLookups.test.js`, `unitTests/resources/replicatedUserWrites.test.js`).

### A component grant answers to its names ahead of every operations listing (`security/componentGrant.ts`)

A role's `component_deploy` grant (harper#3046) covers `deploy_component`, `drop_component`, `get_deployment`, `list_deployments`, and `get_components` matching `names` (`componentNameMatches`, `utility/componentNames.ts`, shared with deploy credentials, harper#3090):

1. **Checked ahead of gate 2:** `verifyPerms` checks the grant before gate 2 (which would admit any component if `operations` listed `deploy_component`), and its decision is final for those 5 ops; gate 1 still requires listing them on an allowlist.
2. **Name resolution:** deploy/drop resolve `canonicalProjectName` else `projectNameFromPackage`; reads filter (`get_components`, `list_deployments`) or 403 (`get_deployment`).
3. **Origin-enforced constraints:** `deployComponent` checks `isolated`, `hostSuffix`, and `branchedDatabases: required` against the effective release (or staged descriptor on activation) before writes under the preparation lock; peers apply what the origin admitted.
4. **Deploy-only pattern secrets:** `grant_secret component=my-app-pr-*` resolves deploy credentials (`resolveCredentials`, harper#3090), while runtime secrets (`componentSecrets.ts`) stay exact-match; `harper deploy setup=true` accepts patterns only for `github`/`npm`.
5. **Named `component_deploy`, not `components`:** role permission keys share `RESERVED_DATABASE_NAMES` with DB names.
6. **`preview`, `maxPreviews`, and `maxTtlDays`** bound preview identities below.

## PR previews are enabled by the cluster (`components/previewOperations.ts`)

`enable_previews`, `disable_previews`, and `get_preview_policy` (harper#3042) manage role/user `<app>-ci-preview` (`CI_PREVIEW_OPERATIONS`, `component_deploy` for `<app>-pr-*` with `preview: required`, no table perms), `github-actions-<app>-preview` (`preview`), and `github-actions-<app>-preview-cleanup` (`preview-cleanup`, `drop_component` only) via `utility/previewIdentity.ts` over replicated system tables:

- **Bounds:** `maxPreviews` (`deployment.previews.maxPerApplication`) and `maxTtlDays` live in `component_deploy.constraints` on the role and enforce on the origin without `hdb_preview_policy` (SU previews use only `maxPerApplication`).
- **`preview: required`:** deploys must name `A` as `A-pr-<n>` matching an `A-pr-*` pattern (preventing cap/expiry bypass, `shop-pr-pr-3` counting against `shop-pr`, or `shop` dropping `shop-pr-tools`). `maxTtlDays` (default 7) clamps `expiresAt` before storage/replication; activations past it fail against the build row before live-release return. Origin caps count live previews under the origin lock (2 origins can each take the last slot).
- **Create-only, serialized per node:** enable keeps matches and 409s on differing records or overlapping enabled policies (`policiesOverlap`, `sameAuthority`). 1 enable/disable runs per node at a time, rechecking policies before `add_oidc_trust` (cross-node concurrent writes not excluded, #3127).
- **Disable revokes, fences, then removes:** drops policies and deactivates the user (`isCurrentUser` blocks earlier-admitted deploys). `fence_preview_releases` (#3613) records the role's `generation` as revoked under the admission lock on every node and lists live previews; activations require a matching generation. Peers fence under node identity (`isOperationAuthorizationBypassed()`, avoiding `REPLICATED_FROM` lifting deploy grants). Not fenced: SU previews, pre-generation builds (`get_preview_policy` `inProgress`), and expiry-bounded (#3805) timed-out peer swaps, crash roll-forwards, rollbacks/canary restores to fenced predecessors, or losing racing enables. Disable then drops live previews (`ifDeploymentId`) and user/role, stopping with identity revoked on failed drops so reruns resume.

## The password hash function and token lifetimes are read when used, never at module load (`security/user.ts`, `security/tokenAuthentication.ts`, `utility/password.ts`)

`harper run` on an empty root evaluates these modules (and `installer.ts`) before `install()` writes config and creates the admin before `runStartup()`, so `authentication.hashFunction` resolves per write (`password.configuredHashFunction()`) and stores `hash_function` on the row for validation. `password.hash` defaults to config; `password.validate` defaults to SHA-256 as refresh-token validation needs sync SHA-256 (`!Promise` would accept superseded tokens). Token lifetimes resolve per mint (`integrationTests/security/firstboot-auth-config.test.ts`).

## Local trust is a principal, not a stored user (`security/user.ts`, `security/auth.ts`)

Transport-trusted requests — `authentication.authorizeLocal` from loopback (`isLocalPeerAddress`: `127.0.0.x`, `::ffff:127.0.0.x`, `::1`), operations UDS (`bypassLocalAuth`), loopback MQTT, and test `bypassAuth()` — run as `localPrincipal()`, a recordless SU named `local`:

- **Marker-identified (`_localPrincipal: true`), never by name:** `isLocalPrincipal` checks string property `_localPrincipal` (JSON-survivable for Bun/uWS forwarding and MQTT will rows), never copied by `userView` or token/OIDC/impersonation builders. `add_user` refuses `local`; pre-existing stored `local` rows stay ordinary users.
- **Non-portable:** `session.update` drops it; credential-free `create_authentication_tokens` mints for the first active stored `super_user` (`getSuperUser`) or 409s. By-name rehydration checks `isLocalPrincipal` first: MQTT will replay rebuilds it from the marker; live-subscription re-auth and MCP `list_changed` skip it.
- **Fresh view per call:** fresh user, `role` (default `super_user` `role.id`), and `permission` objects; shared `system` table entries are frozen while the table-name map stays mutable (`unitTests/security/localPrincipal.test.js`, `integrationTests/security/local-principal-token-mint.test.ts`).

## Named component children are identified by lifetime (`security/jsLoader.ts`, `security/spawnPidFile.ts`)

To prevent adopting/signaling recycled PIDs or zombies (#2968), `pids/<name>.pid` stores positive PID, version (`0` if omitted), and OS birth identity (Linux: boot ID/PID/start ticks, excluding zombies/TIDs; macOS: PID/`ps lstart` UTC/C, 1s; Windows: PID/`Win32_Process.CreationDate` ticks). Adoption, version replacement (`process.kill(pid)`; Windows sets `ChildProcess.exitCode`, `signalCode` null), wrapper kill, and exit observation compare recorded identity; different-boot Linux records retire before probing. Records publish via write-then-rename (pre-rename crash can leave an unrecorded child). Probe failures (`hidepid`/`ProtectProc`) are unknown, never retiring records or emitting exit. macOS/Windows wrapper probes run async without overlap; sync spawn/adoption probes run under the lock. Polls at 1s (Linux/macOS) or 5s (Windows; a signal-0 fast path was rejected as it would hold wrappers open on reused PIDs). Legacy 2-line records retire with a warning without signaling (mixed-version upgrades lack this guard, so a legacy child may coexist with its replacement once).

Sync spawning uses a filesystem bakery lock (per-UUID choosing/ticket files, shared ticket ordering with `componentPreparationLock.ts`). Matching foreign owner identities cache 1s; Windows sharing errors retry; unremovable claims publish a release marker honored before retired claims. Acquisition, publication, and exit cleanup share the claim protocol. Waits sleep 50ms (`Atomics.wait`), failing after 60s without initial-cohort progress (never stealing from live processes); external probes time out at 30s. Exit cleanup makes 1 non-waiting attempt with cached own identity and conservatively live foreign claims (no new probes); release errors report separately. Terminated-worker claims in a live process wait until restart (standalone workers/main-thread scopes lack a worker manager). Unreadable owners fail closed; closing check-to-signal races and timestamp gaps needs native PID handles. Probe/lock errors throw `NamedProcessError` (`ServerError` subtype keeping `cause`); invalid child-process args keep native error classes/codes (`unitTests/components/spawnPidIdentity.test.js`, `unitTests/components/spawnPidFile.test.js`, `integrationTests/components/named-process.test.ts`).

## Application lockdown seals the intrinsics by default (`security/intrinsicsLockdown.ts`)

`applications.lockdown` defaults to `seal-after-load` on fresh installs (installer writes full config, so upgrades keep prior mode). Sealing blocks add/delete on 21 intrinsic globals/prototypes plus `Function`/`Function.prototype` while allowing overwrites; it is not a sandbox. Never make seal-mode prototype properties read-only (array-hole stores ~45× slower, msgpackr decode ~3× slower; accessors block built-in inlining); only freeze modes need `overridableProperty`. Sealing covers replaced globals and realm originals (kept by literals/async functions); freezing covers current globals and leaves `Function.prototype` extensible. Unknown truthy modes freeze eagerly (fail closed); falsy modes skip lockdown (`unitTests/security/intrinsicsLockdown.test.js`, `integrationTests/components/intrinsics-lockdown.test.ts`, `benchmarks/lockdown/run.mts`).

## A scoped mirror is never advertised before its allowlist is read (`security/networkAccess.ts`)

`system.hdb_network_access` holds 1 replicated row per scope (`operations` today); a fronting proxy enforces it and Harper publishes it as `allowedSources` in UDS mirror metadata (`writeUdsMetadata`, `server/http.ts`):

- **No unrestricted advertisement:** the writer, not `ready`, holds a scoped mirror until this thread's first read (`keys.ts` fires `secureContextsListeners` before readiness); an absent table after DBs load is unrestricted.
- **One reconciler per scope:** subscriptions, the 60s tick, and `onUpdatedTable` trigger 1 serialized `table.get(scope)`; payloads are ignored so missed events converge on the next read, and failed writes retry on the tick.
- **Lockout check:** `set_network_access` refuses lists excluding the caller (`runWithCallerAddress`, never body). Only Node's operations UDS skips it; other unknown addresses need `force`. Matching unmaps `::ffff:a.b.c.d` first; proxy-routed peers must be listed too (Harper only warns).

## Resource attribute permissions

`getTablePermissions` adds the unlisted key’s `implicitPrimaryKeyPermission`; operations translation drops listed undeclared properties. Explicit key denials, timestamps and sealed membership apply. `updatedAttributes` resets the permission memo.

`allowUpdate` keeps `allowTableUpdate`’s map through puts/locks until the next call. Payloads omit protected values. `restrictedReplacement` patches full puts: omitted writable keys stay own `undefined` properties (JS/MsgPack see them; JSON omits them) to avoid stale protected bases. Restricted source writes use implemented `patch` or materialized `put`. PATCH limits: delete/retry can create partial rows, put-only sources with cold/stale caches can lose protected values, and `__op__` values are operations. Invalid full roots fail. Trusted direct PATCH/create thenables can check resolved keys but store original fields. Dispatch resolves bodies; helpers reject failed promises without override re-entry (`unitTests/resources/permissions.test.js`, `unitTests/server/preconditions.test.js`, `integrationTests/security/resource-attribute-permissions.test.ts`; gaps: commit retry, crash replay, replication).

## System permissions on roles

`permission.system` derives from `super_user` and the registry. Held identities share mutable maps with frozen entries. API declarations 400; files strip and warn on content change, not replay. Legacy copies strip without writes racing `alter_role`; warnings dedupe by revision/thread. Impersonation reinstalls managed maps; scoped tokens strip before hashing to avoid MCP churn. External response reuse is per-call; listeners load lazily to avoid the Resource cycle.
