# agent/ — Design notes

The built-in Harper agent component.

**Read this when:** changing the agent's toolset, the `http_fetch` tool, the filesystem tools or their scopes, what `set_agent_config` can patch, how the loop ends a run, how tool results reach the transcript, or how a run records and caps model usage.

Index of every design note: [DESIGN.md](../DESIGN.md).

## `http_fetch` egress is fixed at boot and checked on every hop (`agent/tools/httpFetchTool.ts`)

The agent reads untrusted text (table rows, logs, component source) with the same toolset that can send HTTP, so `agent.httpFetch` is the operator's bound on where that text can make `http_fetch` send. It bounds that tool only, not every egress path the agent's operations tools might open. Two things keep the bound from being widened (harper#2974):

- **Boot-time only.** `startOnMainThread` builds the tool once from the boot config and `compose()` reuses that instance. Nothing reads the policy from `liveConfig`, and `set_agent_config` rejects an `httpFetch` patch. Like every other `agent_*` key, it is in `CONFIG_PARAMS` (`agent_httpFetch`, `agent_httpFetch_allow`) for env vars, CLI flags and `set_configuration`. Those write the config file and take effect on restart, and `set_configuration` is a destructive operation outside the agent's default toolset. The name `http_fetch` is reserved in `composeToolset`: with the tool disabled, no registry or extra tool can take its place.
- **Every hop is checked before it is sent.** `fetchCheckingRedirects` follows redirects itself (`redirect: 'manual'`) and runs `checkHttpFetchTarget` on each `Location`. Letting `fetch` follow would send the request before any check could see it. The hop step mirrors fetch's own method, body and credential-header rules, which the redirect tests in `unitTests/agent/httpFetchTool.test.js` pin.

Host matching compares canonical forms. Targets and allow entries both go through `URL` host parsing, so case, IDNA and IPv4 shorthand compare equal. The metadata and link-local blocklist checks IP literals with `net.BlockList`, which also catches their IPv4-mapped IPv6 spellings. Allow entries compare as strings, so an IPv4 entry does not admit its IPv4-mapped form; that direction fails closed. The check is by host name only. A permitted name that resolves to an internal address is not caught.

## The fs tools never return key material, and `config` is the config file (`agent/tools/fsTools.ts`)

Everything an fs tool returns enters the model's context, and the session transcript is persisted and replicated, so a read is an exfiltration path even with `http_fetch` off (harper#3041). Two rules hold whatever scope or override is in force:

- **Scopes are fixed at boot and narrow by default.** `resolveScopes` makes `config` the Harper config file alone (`configFile`), canonicalized so a symlinked config file is its target: `resolveScoped` admits only that file, and `list_dir`/`grep_files` never enumerate or walk it, even if it is swapped for a directory later. `agent.configScope` replaces that target with another file or directory, so the config file stays in scope only if the new target contains it; a target that is neither leaves the scope unavailable rather than guessing. `set_agent_config` rejects `httpFetch`, `componentsScope` and `configScope`, because a patch that cannot take effect must not look applied.
- **Key material is refused in every scope.** `keyDirs` (`<rootPath>/keys`, `<rootPath>/ssh`) are resolved to real paths on every call, like scope roots, so a symlinked root, a key directory that is or later becomes a link, and a Windows short name all compare equal. They refuse reads and writes. Reads also refuse `*.pem`, `*.key` and `.jwtPass` by name, any returned text holding a PEM private-key armor line, a `read_file` page that starts inside a key, and a `tail_file` that ends inside one. Both look back 128 KiB before their window, longer than any PEM private-key block, post-quantum ones included, for a last armor line that is a BEGIN, since a page of key body alone carries no armor line. With no armor line in the look-back, a look-back of nothing but key-body characters (base64 and line breaks) that does not reach the start of the file fails closed: only a block whose BEGIN lies further back looks like that. The armor check covers an inline `tls.privateKey` in the config file (`readPEM` accepts one). `grep_files` skips such files and prunes key directories instead of failing. A key with no armor and no key file name passes, so the path rules are the guarantee and the armor check is the backstop.

The rules bound the fs tools only: an operations tool returns its own text unfiltered (`read_log` is in the default set), and the config file can still hold non-PEM secrets (model `apiKey`, storage credentials). The narrowed default limits the read surface; it does not make what remains safe to show a model.

## A turn that did not finish is rejected before anything is recorded (`agent/loop.ts`)

Callers poll `get_agent_session` and read `completed` as success, so `completed` with no `lastError` must mean a natural, non-empty final answer (harper#3039). The `maxTurns` ceiling is the one documented exception: it ends `completed` and sets `lastError`. `rejectTurn` runs right after each `generate` and ends the run `error` when the backend reports `length` or `content_filter`, when it reports `tool_calls` but no call parsed, or when a reply has neither text nor tool calls.

- **Nothing from a rejected turn is appended.** Partial text would read as the answer. Tool calls recorded without their responses would make the session's next request invalid, and a truncated call carries truncated arguments, so none is executed or queued for approval. The rejection is one status write, so there is no partial state to recover.
- **Tool calls still dispatch on `stop`.** Only the explicit cut-short reasons block dispatch. `synthesizeGenerateFromStream` (`resources/models/backendRegistry.ts`) reports `stop` for a stream-only backend that emits no finish reason, so gating dispatch on `tool_calls` would stop such a backend from calling tools at all. The cost: truncation from such a backend is invisible here, and the guarantee holds only for backends that report it. The four built-in backends implement `generate` and do.

The rule only works if backends report truncation. Anthropic's `model_context_window_exceeded` maps to `length` and `refusal` to `content_filter` in `components/anthropic` and in `components/bedrock`'s Anthropic path. `agent.maxTokens` (default 16384) is sent on every request, so truncation is rarer, but the check above is what keeps it visible.

## Tool results are capped where they are stored; a context-window rejection shrinks the newest once (`agent/loop.ts`)

Every request replays the whole transcript, so one oversized tool result fails every later request and the session cannot continue (harper#3068). Two rules keep a session continuable:

- **Nothing over `agent.maxToolResultBytes` is appended.** `invokeTool` passes every observation, tool errors included, through `serializeToolResult`, which cuts on a UTF-8 boundary. The cap applies at append time, not when a request is built, because the session row is rewritten whole on every append. The fs read tools measure each page JSON-escaped against half the cap (`ctx.maxResultBytes`), so the loop never cuts one of their pages, and `read_file` returns a byte cursor (`nextOffset`) beside its line cursor, so a line longer than a page is read in parts rather than skipped. `list_dir` pages its entries by name the same way, and a path that leaves no room for a page under the cap is an explicit error rather than a result the loop cuts. Registry, inspector and MCP tools rely on the loop cap alone.
- **A context-window rejection shrinks, then retries once.** Backends own provider wording. They set `contextWindowExceeded` on their error (`isContextWindowRejection`, `resources/models/backendHelpers.ts`), and the loop reads only `isContextWindowExceeded`. It cuts each result over 2 KiB in the newest run of tool messages that has one down to a 2 KiB head, then retries. Selecting by size makes the step idempotent and reaches a result stored before a later prompt. It is best effort: a long prompt or history ends the run `error` with a `lastError` saying so. `Models.generate` surfaces the first candidate's error, so a rejection from a fallback candidate behind an unrelated primary failure is not recovered.

The system prompt is sent only as `input.system`. The backends hoist or prepend it, so an inline copy would be sent twice.

## Spend caps are folded from the transcript and fail closed (`agent/budget.ts`, `agent/loop.ts`)

`agent.maxSessionTokens` and `agent.maxCostUsd` bound a session, not a run: `approve_agent_action` and a follow-up `agent_prompt` each start a new `runAgent`, so a per-run counter (which is what `maxTurns` is) would reset on every resume (harper#3040). Three rules keep the caps honest:

- **Usage lives on the call it describes.** Each assistant message carries the `usage` its `generate` reported and its `costUsd`, in the same write as the message. Session totals are folded from the transcript by `summarizeSessionUsage`, never stored, so they cannot drift from the calls. A rejected turn (above) never reaches the transcript, but it was billed, so `endRun` records its usage on `rejectedCalls`, which the fold counts as a call. A total stays present only while every assistant message reported it, so a backend that reports nothing, an unpriced model, or a message written before usage was recorded makes that total unmeasured, not zero.
- **Unmeasured stops the session.** `budgetViolation` treats a cap whose total is unmeasured as violated. Checked before `consumeResolvedApprovals` (so a cap lowered during a pause stops an approved action from running) and after every call.
- **A stop leaves a sendable transcript.** `endRun` appends the assistant turn, a response for every tool call and every open approval, resolved or not (`budget_exceeded`, or `denied_by_operator` for a denial), and the terminal status in one write. A crash cannot leave tool calls without responses, which the provider would reject on the next call, and no approval stays pending once the session leaves `awaiting_approval`. A cancel that landed first keeps its `aborted` status; the stop still completes the transcript. `cancel_agent_run` closes every open approval the same way (`cancelled_by_operator`) in the write that marks the session `aborted` (`cancelSession`). An approval is claimed under the lock before its action runs (`claimApproval`), and every writer that answers approvals decides which are open on the row it read under the lock, so a cancel or a stop never answers an action already running and no tool call gets two responses. The run checks the cancel before each approved action. Every status the loop writes after `running` goes through `endRun`, and `addPendingApproval` answers a gated call `cancelled_by_operator` on an `aborted` session, so nothing the loop writes replaces a cancel. `cancelSession` decides under the lock, so it leaves a session a run already finished as it is. A cancel between a turn's tool calls answers the rest of the turn in one write, and `agent_prompt` answers 409 while a cancelled run is still finishing (`isRunInFlight`), because a prompt appended then would land between that run's tool calls and their results. Every cancel also bumps a per-session count (`fenceRuns`); a request that starts a run takes an `admitRun` token before its first await, and `runAgent` starts nothing for a token a later cancel fenced out, so a cancel that arrives while `agent_prompt` or `approve_agent_action` is still writing is not undone by the run it would start. The trade is at-most-once: a crash between the claim and the result write leaves that call without a result, and the next run starts by answering it `interrupted` (outcome unknown), inserted right after its tool call (`answerInterruptedClaims`), instead of running it again; the call is matched on its most recent turn, as a provider may reuse a tool-call id. A run that fails closes its open approvals and answers its turn's remaining tool calls `run_failed` in its final write. An approval resolved while the run drains earlier ones joins that run, so the drain repeats until nothing resolved is left, and the pause is decided under the lock (`pauseWhileApprovalsOpen`). A scheduled followup that fires while a run is in flight or approvals are pending retries until neither holds, carrying its admission token so a cancel drops it.

A final answer that crosses a cap is delivered; the run ends `completed` with `lastError` naming the cap. What a cap does not bound, by construction: one call can cross it (it is a stop-after-call threshold), a failed attempt before a model fallback is not counted (failure records carry no usage), and an unpriced model is detected only after its first call. Pinned by `unitTests/agent/loop.test.js` and `integrationTests/server/agent-budget.test.ts`.
