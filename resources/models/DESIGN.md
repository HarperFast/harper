# resources/models/ — model facade, backends, decisions

Notes on invariants the models layer relies on that the code cannot state itself. User-facing behavior is documented in HarperFast/documentation.

## Decision outputs are validated at the facade

A `Decision` returned by `models.decide` names a value from the schema's allowed set, and its distribution has exactly one entry per allowed value, with finite probabilities in [0, 1] that sum to one (within 1e-3), sorted descending with ties in schema order unless the backend chose one of the tied values, which then leads. `normalizeDecision` (`decision.ts`) enforces this on every backend output, so no backend's arithmetic is trusted; a violation is a `DecisionContractError`, which `Models.decide` treats like any backend error (recorded against that backend, next candidate tried). A malformed schema or state rejects before routing and writes no analytics row, because nothing was called. Object schemas are marginal-only: `value` is assembled from each field's argmax and may be a combination no single sample produced. Enforced by `unitTests/resources/models/decision.test.js` and `decide.test.js`.

## The generative adapter reports no usage of its own

Every sample the adapter (`generativeDecision.ts`) takes is a `models.generate` call with its own `hdb_model_calls` row and token metrics. The adapter therefore returns no `usage` on its `ModelCallResult`; reporting the sum again would count each sample twice in `SUM(prompt_tokens)` and in `model-*-tokens`, the same double-billing the `toolMode: 'auto'` outer call avoids by writing no row. Samples run under one `AbortController`: the first failure aborts the rest, and the worker pool is awaited to settlement before the error is thrown, so no sample rejects unobserved and the facade never falls back to another candidate while calls are still in flight. Enforced by `unitTests/resources/models/generativeDecision.test.js`.

## Required capabilities are checked on the candidate about to be invoked

The router's candidate list is advisory: the default router filters by `requires`, but a custom router installed with `registerRouter` may return any backend. `assertCapabilities` (`Models.ts`) therefore re-checks every required capability against `capabilities()` immediately before each candidate is invoked, in every facade method, fallbacks included, and for a stream both before the iterable is returned and again on its first `next()`; a miss is a `ModelCapabilityError` recorded as `capability_unsupported`, and the next candidate is tried, except by a stream, which only ever uses its first candidate. Candidates are backend instances captured when the call was resolved, so the check sees a backend's own `capabilities()` at invocation time, not a registry entry a reload has since replaced; the built-in providers return one frozen object, so the check allocates nothing. The generative decision backend relies on it: by default it passes `requires: ['structuredOutput']` on every sample, so a generative candidate whose integration does not send the response schema as a decoding constraint (Anthropic and Bedrock today) is refused before a completion is billed, whatever router produced it, unless the entry sets `requireStructuredOutput: false`. Enforced by the custom-router cases in `unitTests/resources/models/Models.test.js`; the bootstrap cases in `generativeDecision.test.js` cover the default router's filtering of the same requirement.

## Likelihood scoring is a leaf-level hook with voting as the fallback

A generative backend may implement `scoreChoices` (#2838): one finite, unnormalized log-likelihood per choice, in order, for a whole call, or a `ChoiceScoringUnsupportedError` for a call it cannot score. A decline is weaker news than a failure, and the two are kept apart at every layer. The facade's internal `models.scoreChoices` validates the vector's shape before it records a success, so a malformed result is one failed attempt against that backend and the next candidate is tried; when every candidate fails it surfaces the first failure, and the primary's decline only when every candidate declined, so a decline never hides a broken fallback. A declined call is recorded as `scoring_unsupported` with the usage the error carries, because a completion that came back without log-probabilities was still billed: those tokens land on that attempt's failure row and in the token metric while the call-count metric stays a count of successes. They are billed once: no other error's `usage` is read, no other method's failure row carries usage (the `decide` row stays usage-free when a decline propagates under `score`), and the adapter aborts sibling calls with a fresh reason rather than the decline itself, so a call cut short is recorded as `aborted` and not as another copy of the decline. The adapter scores one leaf per call (each property of an object schema separately), normalizes by softmax, and never mixes paths: in `auto` mode a decline, or a `ModelCapabilityError`, discards any leaf already scored and votes the whole decision under the same budget, so a distribution is wholly scored or wholly voted; any other error fails the decision. `auto` asks the router synchronously before deciding, so a generative backend whose capabilities say no costs no attempt, no exception and no analytics row. The same probe reads each candidate's `maxScoredChoices`: when no scoring candidate can take the schema's largest leaf, `auto` votes without a scoring attempt, and the facade treats a call above a candidate's limit as a decline it records without invoking that backend, so sibling leaves are never scored and then discarded. A candidate that advertises scoring without implementing it still counts as able, so its contract failure is reported rather than hidden by a vote. `maxScoredChoices` is a limit, not a `Capability`: it cannot be required. The OpenAI backend labels the choices `A`..`T` on one line each (a value that cannot sit on one line as itself is JSON-quoted, so it cannot pose as a further option and values that differ only in whitespace stay distinct), asks for one token with `top_logprobs: 20`, combines spellings of a label by log-sum-exp, and places a label with no listed spelling only when the mass the list leaves over is smaller than the leading observed label's, so a wholly unlisted label can never be the chosen value; otherwise the call is declined rather than guessed. An unlisted label then stands at a floor no higher than the smallest listed alternative or the leftover, finite even when the list leaves nothing over. Every placed score is still an estimate: an observed label's own unlisted spellings can add up to the leftover to it, so two observed labels closer than that may be ordered wrongly, and a response with no label at all is declined rather than reported as uniform. A malformed alternative is a failure, not a decline. A model that refuses `logprobs`, by a 400 (by `param`, or by a message that names it and says it is unsupported) or by an answer with no log-probability field at all, has scoring switched off until reload and `capabilities()` says so for the configured model, so later decisions vote without an attempt; a completion with no content token or no alternatives, and an answer that is simply not a label, are declined for that call only, and any other HTTP failure stays an error so an outage does not silently turn into voting. Probabilities from scoring are still `calibrated: false`. Enforced by `unitTests/resources/models/generativeDecision.test.js`, `scoreChoices.test.js` and `unitTests/components/openai/index.test.js`.

## `@decide` and `@embed` share one trigger rule

Both directives derive an attribute on the originating node before the record is staged, in `_writeUpdate` and in the cache-from-source write. `writeHookApplies` and `sourceState` (`embedHook.ts`) are the only trigger logic: a replication receive, an `x-replicate-from: none` write or an audit replay never re-derives, a payload without the source leaves the derived attributes alone, a null source clears them, and a CRDT op is skipped. `@decide` writes the chosen value and, when named, its probability from one `models.decide` call, and a failure fails the write, so the two are never from different decisions and never half-written; a missing decider or an override without the promised probability fails the write too. `runWriteJobs` aborts the siblings of a failed hook and settles them before the failure is reported, so a rejected write neither waits on a hook that honors the signal nor keeps being mutated by one; the built-in hooks forward the signal to their model calls. `assertDerivedFieldOwnership` gives every derived field one writer, refuses a directive whose source is another directive's output, because the hooks run concurrently within a write, holds a decided field and its confidence to what the loader accepts, and refuses an `Object.prototype` key as any of those fields, because `sourceState` tests presence with `in`. The loader runs it, and `declareTable` runs it on the complete list (a peer's fields merged, an omitted primary key inherited) before that list replaces the live one or reaches the catalog, so a programmatic `table({ attributes })` declaration is held to the same rules and a refused declaration changes nothing. `Table.updatedAttributes` runs it too but only logs a violation, because it also runs when a descriptor an earlier build accepted is loaded from the catalog, and a table must keep loading. The hooks receive the request's signal, so a client that disconnects cancels the model calls as it did before the hooks were combined. A `decide` descriptor change persists without a reindex: a stored decision does not depend on the model, unlike an embedding, whose `version` carries the model. Enforced by `unitTests/resources/models/decideHook.test.js`, `decideDirective.test.js`, `decideWrite.test.js` and `integrationTests/server/decide-directive.test.ts`.

## Built-ins serve one kind

The provider factories (`ollama`, `openai`, `anthropic`, `bedrock`) treat every non-embedding kind as generative, so a `models.decision` entry naming one would register a backend with no `decide`. `builtinServesKind` (`bootstrap.ts`) refuses that entry at boot and reload, and `wrongKindEntrySchema` (`validation/configValidator.ts`) refuses it at validation, in both directions: `backend: generative` is the only built-in for `decision` and is refused under `embedding` and `generative`. Module backends are exempt because their factory receives `kind`.

## A recorded decision is committed before its id is returned, and its facts are separate rows

Recording is opt-in: `Models.decide` stores nothing beyond the per-call analytics row unless the call passes `persist: true`, so by default it costs what `embed` and `generate` cost and works on any node; only callers that will report outcomes pay for a durable record. The option types carry that promise: `RecordedDecideOpts` (`persist: true`) returns a `RecordedDecision` whose `id` is present, and any other options object returns a `Decision` whose `id` is optional. With `persist: true`, `Decision.id` names a row in `hdb_model_decisions` that `Models.decide` commits in a transaction of its own (`decisionStore.ts`: `transaction()` with a fresh context object, so the write never joins an ambient application transaction and survives that transaction's abort) before the decision is returned. The row is written once and never rewritten; each recorded fact (`truth` or `action`, per field for object schemas) is its own `hdb_model_outcomes` row keyed `<id>/<fact>[/<field>]`, so two facts recorded on two nodes cannot overwrite each other and a report never re-expires the prediction: facts copy the decision's `expiresAt`, and a report whose state equals the stored fact writes nothing. The id is a UUID because `getNextMonotonicTime()` is monotonic per process, not unique across nodes, and both tables replicate: they are declared with `replicate: true`, as the scheduler state table is, so a scoped `replication.databases` cannot exclude them, with `audit: true` as the feed, and neither is in `NON_REPLICATING_SYSTEM_TABLES`. With `persist: true`, a commit failure after the backend succeeded throws `DecisionPersistenceError` outside the candidate loop, so a storage fault never bills a second model call, and a read-only node rejects before routing. Both tables are provisioned with their primary key by `json/systemSchema.json` and the `5.3.0` directive, and `declareDecisionTablesAtBoot` (called from `componentLoader` after `bootstrapModels`) layers the attributes and the indexed `expiresAt` TTL on every writable node, so a peer that never decides still evicts. Enforced by `unitTests/resources/models/decisionStore.test.js` and `decideOutcome.test.js`.

## No-match is a separate score, never a value

A leaf opts in with `noMatch: true` (#2846, decided on #2843). The backend then returns a score in `[0, 1]` that the input matches none of the allowed values, beside the unchanged forced-choice `distribution`; the two are not a joint distribution, so the all-votes-no-match case still has a closest allowed value. No sentinel ever enters an enum, which is why boolean and integer leaves can opt in. An opted-in call requires the `noMatch` capability (and `calibratedNoMatch` when it requires `calibrated`), checked per candidate like every other requirement, and reports `calibrated: true` only when both scores are calibrated. A score on a leaf that did not opt in is dropped, so a schema without the flag sees exactly the pre-#2846 output. The generative adapter asks an opted-in leaf for `{ value, noMatch }` when voting and adds one distinct "none" choice when scoring, renormalizing the allowed values without it. Enforced by `unitTests/resources/models/noMatch.test.js`.

## A `@decide` decision is recorded only when the record can reach it

The built-in decider passes `persist: true` only when the directive names a `decision` attribute, so a directive nobody can report outcomes for writes no `hdb_model_decisions` row (#2852). With one, the decider records the decision and the hook stores `Decision.id` beside the value and confidence; a null source clears all three. The id is provenance an outcome report trusts, so `buildDecideBefore` rejects a write that carries it unless that same write derives or clears it, or arrives by replication or replay; `x-replicate-from: none` and a CRDT operation on the source do not qualify, since any request can send them. The association is bounded, not atomic: the decision commits in its own transaction before the record, so an aborted write, a later source write, or a delete leaves an unreferenced row that expires with the retention. On a read-only node no write can commit, so `Table` skips the model hooks and serves a source-cache fill without staging it (`noCacheStore`), for every table. Enforced by `decideHook.test.js`, `decideWrite.test.js`, `decideOutcome.test.js` and `integrationTests/server/decide-directive.test.ts`.

## A fitted calibration never crosses a score source, and never waits on storage or fails a call

`calibrated: true` from a fit (#2841) means an eligible, unexpired version, fitted under the active policy, was applied to every field of the decision. A population is `populationKey` (`calibration.ts`): tenant, logical model, the decision entry's fingerprint, the signature, the instructions hash and the schema hash. The fingerprint is `sourceFingerprint` (`decisionStore.ts`): the entry's expanded configuration without credentials or `fallback`, published per backend by `bootstrap.ts` into `backendRegistry.ts`. An operator-set `revision` covers a deployment change the configuration cannot show, such as a floating model tag. The accounting context's `app` is left out on purpose, because it is the calling route, not an application, and would split one question into a population per endpoint. The generative adapter signs a decision with `;source=<fingerprint>` only when every inner call reported the same identified source through the `SERVED_SOURCE` hook. The facade calls that hook after a successful attempt, outside its `try`, and swallows its faults. A fallback inside a vote, or a backend registered from code, leaves the decision unsigned, and an unsigned decision is never calibrated or learned from. A custom decision backend registered from code identifies its score source only through the `signature` it returns, which it must change whenever that source changes; Harper cannot see a replaced implementation behind the same name and signature. Only decisions recorded while calibration is enabled carry a `population`, so a fit never reads scores whose source was not collected.

`applyFits` (`calibrationStore.ts`) reads the in-memory cache only. A miss returns the decision raw and starts one load, at most `maxLoads` in flight, each counted until its read settles. Faults are logged through `safeErrorMessage` and return the decision raw. Calibration runs after the analytics row, outside the candidate loop, so it never bills a second call. `requires: ['calibrated']` still routes on the backend's own claim. A schema with a no-match leaf is never fit-calibrated, because its no-match score would stay raw under the flag; its population gets reports whose reason is `no-match-schema`, never an eligible version.

Versions in `hdb_model_calibrations` (`replicate: true`) are immutable. `fitId` covers the input digest, the policy and the result, so a repeated run writes nothing. The reader takes the greatest `rank` (`key | evidenceAt | fittedAt | fitId`) in one descending prefix read. `evidenceAt` is the newest decision or truth fact a version read, so the version that saw newer evidence wins whatever node wrote it and in whatever order rows arrive. A new version's `evidenceAt` is also at least one above the version it replaces, so a correction stamped by a node with a slower clock still supersedes it. A version is written whenever a population's input digest changes, even with no labels left, so a correction revokes an older eligible version. Rows expire after their decisions do. `calibrate()` can only lower a run's budgets, never raise them or change its policy, and a run invalidates only the cache entries of the keys it wrote. A population's decisions are read newest first through the indexed `populationRank` (`population | expiresAt | id`) with a limit, so a large population is never loaded in full. Discovery spends half its decision budget on the newest decisions and the rest from a saved cursor that keeps the ids on its boundary, so ties at one timestamp never stall it. A failed run fails its scheduled job. A run walks known populations least recently fitted first, then those discovered newest first, under global decision, population, byte and time budgets, and writes a population only after its report is complete. Its job is registered with `registerInternalJobs` (`resources/scheduler/engine.ts`), under a reserved prefix no component can register or unregister. Enforced by `unitTests/resources/models/calibration.test.js`, `calibrationStore.test.js`, `sourceIdentity.test.js` and `unitTests/resources/scheduler/engine.test.js`.
