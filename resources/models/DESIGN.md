# resources/models/ — model facade, backends, decisions

Notes on invariants the models layer relies on that the code cannot state itself. User-facing behavior is documented in HarperFast/documentation.

## Decision outputs are validated at the facade

A `Decision` returned by `models.decide` names a value from the schema's allowed set, and its distribution has exactly one entry per allowed value, with finite probabilities in [0, 1] that sum to one (within 1e-3), sorted descending with ties in schema order unless the backend chose one of the tied values, which then leads. `normalizeDecision` (`decision.ts`) enforces this on every backend output, so no backend's arithmetic is trusted; a violation is a `DecisionContractError`, which `Models.decide` treats like any backend error (recorded against that backend, next candidate tried). A malformed schema or state rejects before routing and writes no analytics row, because nothing was called. Object schemas are marginal-only: `value` is assembled from each field's argmax and may be a combination no single sample produced. Enforced by `unitTests/resources/models/decision.test.js` and `decide.test.js`.

## The generative adapter reports no usage of its own

Every sample the adapter (`generativeDecision.ts`) takes is a `models.generate` call with its own `hdb_model_calls` row and token metrics. The adapter therefore returns no `usage` on its `ModelCallResult`; reporting the sum again would count each sample twice in `SUM(prompt_tokens)` and in `model-*-tokens`, the same double-billing the `toolMode: 'auto'` outer call avoids by writing no row. Samples run under one `AbortController`: the first failure aborts the rest, and the worker pool is awaited to settlement before the error is thrown, so no sample rejects unobserved and the facade never falls back to another candidate while calls are still in flight. Enforced by `unitTests/resources/models/generativeDecision.test.js`.

## Required capabilities are checked on the candidate about to be invoked

The router's candidate list is advisory: the default router filters by `requires`, but a custom router installed with `registerRouter` may return any backend. `assertCapabilities` (`Models.ts`) therefore re-checks every required capability against `capabilities()` immediately before each candidate is invoked, in every facade method, fallbacks included, and for a stream on its first `next()`; a miss is a `ModelCapabilityError` recorded as `capability_unsupported` and the next candidate is tried. Candidates are backend instances captured when the call was resolved, so the check sees a backend's own `capabilities()` at invocation time, not a registry entry a reload has since replaced; the built-in providers return one frozen object, so the check allocates nothing. The generative decision backend relies on it: by default it passes `requires: ['structuredOutput']` on every sample, so a generative candidate whose integration does not send the response schema as a decoding constraint (Anthropic and Bedrock today) is refused before a completion is billed, whatever router produced it, unless the entry sets `requireStructuredOutput: false`. Enforced by the custom-router cases in `unitTests/resources/models/Models.test.js`; the bootstrap cases in `generativeDecision.test.js` cover the default router's filtering of the same requirement.

## Likelihood scoring is a leaf-level hook with voting as the fallback

A generative backend may implement `scoreChoices` (#2838): one finite, unnormalized log-likelihood per choice, in order, for a whole call, or a `ChoiceScoringUnsupportedError` for a call it cannot score. A decline is weaker news than a failure, and the two are kept apart at every layer. The facade's internal `models.scoreChoices` validates the vector's shape before it records a success, so a malformed result is one failed attempt against that backend and the next candidate is tried; when every candidate fails it surfaces the first failure, and the primary's decline only when every candidate declined, so a decline never hides a broken fallback. A declined call is recorded as `scoring_unsupported` with the usage the error carries, because a completion that came back without log-probabilities was still billed: those tokens land on that attempt's failure row and in the token metric while the call-count metric stays a count of successes. They are billed once: no other error's `usage` is read, no other method's failure row carries usage (the `decide` row stays usage-free when a decline propagates under `score`), and the adapter aborts sibling calls with a fresh reason rather than the decline itself, so a call cut short is recorded as `aborted` and not as another copy of the decline. The adapter scores one leaf per call (each property of an object schema separately), normalizes by softmax, and never mixes paths: in `auto` mode a decline, or a `ModelCapabilityError`, discards any leaf already scored and votes the whole decision under the same budget, so a distribution is wholly scored or wholly voted; any other error fails the decision. `auto` asks the router synchronously before deciding, so a generative backend whose capabilities say no costs no attempt, no exception and no analytics row. The OpenAI backend labels the choices `A`..`T` on one line each (a value that cannot sit on one line as itself is JSON-quoted, so it cannot pose as a further option and values that differ only in whitespace stay distinct), asks for one token with `top_logprobs: 20`, combines spellings of a label by log-sum-exp, and places a label with no listed spelling only when the mass the list leaves over is smaller than the leading observed label's, so a wholly unlisted label can never be the chosen value; otherwise the call is declined rather than guessed. An unlisted label then stands at a floor no higher than the smallest listed alternative or the leftover, finite even when the list leaves nothing over. Every placed score is still an estimate: an observed label's own unlisted spellings can add up to the leftover to it, so two observed labels closer than that may be ordered wrongly, and a response with no label at all is declined rather than reported as uniform. A malformed alternative is a failure, not a decline. A model that refuses `logprobs`, by a 400 (by `param`, or by a message that names it and says it is unsupported) or by an answer with no log-probability field at all, has scoring switched off until reload and `capabilities()` says so for the configured model, so later decisions vote without an attempt; a completion with no content token or no alternatives, and an answer that is simply not a label, are declined for that call only, and any other HTTP failure stays an error so an outage does not silently turn into voting. Probabilities from scoring are still `calibrated: false`. Enforced by `unitTests/resources/models/generativeDecision.test.js`, `scoreChoices.test.js` and `unitTests/components/openai/index.test.js`.

## `@decide` and `@embed` share one trigger rule

Both directives derive an attribute on the originating node before the record is staged, in `_writeUpdate` and in the cache-from-source write. `writeHookApplies` and `sourceState` (`embedHook.ts`) are the only trigger logic: a replication receive, an `x-replicate-from: none` write or an audit replay never re-derives, a payload without the source leaves the derived attributes alone, a null source clears them, and a CRDT op is skipped. `@decide` writes the chosen value and, when named, its probability from one `models.decide` call, and a failure fails the write, so the two are never from different decisions and never half-written; a missing decider or an override without the promised probability fails the write too. `runWriteJobs` aborts the siblings of a failed hook and settles them before the failure is reported, so a rejected write neither waits on a hook that honors the signal nor keeps being mutated by one; the built-in hooks forward the signal to their model calls. `assertDerivedFieldOwnership` gives every derived field one writer, refuses a directive whose source is another directive's output, because the hooks run concurrently within a write, holds a decided field and its confidence to what the loader accepts, and refuses an `Object.prototype` key as any of those fields, because `sourceState` tests presence with `in`. The loader runs it, and `declareTable` runs it on the complete list (a peer's fields merged, an omitted primary key inherited) before that list replaces the live one or reaches the catalog, so a programmatic `table({ attributes })` declaration is held to the same rules and a refused declaration changes nothing. `Table.updatedAttributes` runs it too but only logs a violation, because it also runs when a descriptor an earlier build accepted is loaded from the catalog, and a table must keep loading. The hooks receive the request's signal, so a client that disconnects cancels the model calls as it did before the hooks were combined. A `decide` descriptor change persists without a reindex: a stored decision does not depend on the model, unlike an embedding, whose `version` carries the model. Enforced by `unitTests/resources/models/decideHook.test.js`, `decideDirective.test.js`, `decideWrite.test.js` and `integrationTests/server/decide-directive.test.ts`.

## Built-ins serve one kind

The provider factories (`ollama`, `openai`, `anthropic`, `bedrock`) treat every non-embedding kind as generative, so a `models.decision` entry naming one would register a backend with no `decide`. `builtinServesKind` (`bootstrap.ts`) refuses that entry at boot and reload, and `wrongKindEntrySchema` (`validation/configValidator.ts`) refuses it at validation, in both directions: `backend: generative` is the only built-in for `decision` and is refused under `embedding` and `generative`. Module backends are exempt because their factory receives `kind`.

## A decision is committed before its id is returned, and its facts are separate rows

`Decision.id` names a row in `hdb_model_decisions` that `Models.decide` commits in a transaction of its own (`decisionStore.ts`: `transaction()` with a fresh context object, so the write never joins an ambient application transaction and survives that transaction's abort) before the decision is returned. The row is written once and never rewritten; each recorded fact (`truth` or `action`, per field for object schemas) is its own `hdb_model_outcomes` row keyed `<id>/<fact>[/<field>]`, so two facts recorded on two nodes cannot overwrite each other and a report never re-expires the prediction: facts copy the decision's `expiresAt`, and a report whose state equals the stored fact writes nothing. The id is a UUID because `getNextMonotonicTime()` is monotonic per process, not unique across nodes, and both tables replicate (`audit: true`, not in `NON_REPLICATING_SYSTEM_TABLES`). A commit failure after the backend succeeded throws `DecisionPersistenceError` outside the candidate loop, so a storage fault never bills a second model call; a read-only node rejects before routing. Both tables are provisioned with their primary key by `json/systemSchema.json` and the `5.3.0` directive, and `declareDecisionTablesAtBoot` (called from `componentLoader` after `bootstrapModels`) layers the attributes and the indexed `expiresAt` TTL on every writable node, so a peer that never decides still evicts. Enforced by `unitTests/resources/models/decisionStore.test.js` and `decideOutcome.test.js`.
