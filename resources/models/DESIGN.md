# resources/models/ — model facade, backends, decisions

Notes on invariants the models layer relies on that the code cannot state itself. User-facing behavior is documented in HarperFast/documentation.

## Decision outputs are validated at the facade

A `Decision` returned by `models.decide` names a value from the schema's allowed set, and its distribution has exactly one entry per allowed value, with finite probabilities in [0, 1] that sum to one (within 1e-3), sorted descending with ties in schema order unless the backend chose one of the tied values, which then leads. `normalizeDecision` (`decision.ts`) enforces this on every backend output, so no backend's arithmetic is trusted; a violation is a `DecisionContractError`, which `Models.decide` treats like any backend error (recorded against that backend, next candidate tried). A malformed schema or state rejects before routing and writes no analytics row, because nothing was called. Object schemas are marginal-only: `value` is assembled from each field's argmax and may be a combination no single sample produced. Enforced by `unitTests/resources/models/decision.test.js` and `decide.test.js`.

## The generative adapter reports no usage of its own

Every sample the adapter (`generativeDecision.ts`) takes is a `models.generate` call with its own `hdb_model_calls` row and token metrics. The adapter therefore returns no `usage` on its `ModelCallResult`; reporting the sum again would count each sample twice in `SUM(prompt_tokens)` and in `model-*-tokens`, the same double-billing the `toolMode: 'auto'` outer call avoids by writing no row. Samples run under one `AbortController`: the first failure aborts the rest, and the worker pool is awaited to settlement before the error is thrown, so no sample rejects unobserved and the facade never falls back to another candidate while calls are still in flight. Enforced by `unitTests/resources/models/generativeDecision.test.js`.

## Required capabilities are checked on the candidate about to be invoked

The router's candidate list is advisory: the default router filters by `requires`, but a custom router installed with `registerRouter` may return any backend. `assertCapabilities` (`Models.ts`) therefore re-checks every required capability against `capabilities()` immediately before each candidate is invoked, in every facade method, fallbacks included, and for a stream both before the iterable is returned and again on its first `next()`; a miss is a `ModelCapabilityError` recorded as `capability_unsupported`, and the next candidate is tried, except by a stream, which only ever uses its first candidate. Candidates are backend instances captured when the call was resolved, so the check sees a backend's own `capabilities()` at invocation time, not a registry entry a reload has since replaced; the built-in providers return frozen constants, so the check allocates nothing. The generative decision backend relies on it: by default it passes `requires: ['structuredOutput']` on every sample, so a generative candidate whose integration does not send the response schema as a decoding constraint (Anthropic and Bedrock today) is refused before a completion is billed, whatever router produced it, unless the entry sets `requireStructuredOutput: false`. Enforced by the custom-router cases in `unitTests/resources/models/Models.test.js`; the bootstrap cases in `generativeDecision.test.js` cover the default router's filtering of the same requirement.

## Likelihood scoring is a leaf-level hook with voting as the fallback

A generative backend may implement `scoreChoices` (#2838): one finite, unnormalized log-likelihood per choice, in order, for a whole call, or a `ChoiceScoringUnsupportedError` for a call it cannot score. A decline is weaker news than a failure, and the two are kept apart at every layer. The facade's internal `models.scoreChoices` validates the vector's shape before it records a success, so a malformed result is one failed attempt against that backend and the next candidate is tried; when every candidate fails it surfaces the first failure, and the primary's decline only when every candidate declined, so a decline never hides a broken fallback. A declined call is recorded as `scoring_unsupported` with the usage the error carries, because a completion that came back without log-probabilities was still billed: those tokens land on that attempt's failure row and in the token metric while the call-count metric stays a count of successes. They are billed once: no other error's `usage` is read, no other method's failure row carries usage (the `decide` row stays usage-free when a decline propagates under `score`), and the adapter aborts sibling calls with a fresh reason rather than the decline itself, so a call cut short is recorded as `aborted` and not as another copy of the decline. The adapter scores one leaf per call (each property of an object schema separately), normalizes by softmax, and never mixes paths: in `auto` mode a decline, or a `ModelCapabilityError`, discards any leaf already scored and votes the whole decision under the same budget, so a distribution is wholly scored or wholly voted; any other error fails the decision. `auto` asks the router synchronously before deciding, so a generative backend whose capabilities say no costs no attempt, no exception and no analytics row. The same probe reads each candidate's `maxScoredChoices`: when no scoring candidate can take the schema's largest leaf, `auto` votes without a scoring attempt, and the facade treats a call above a candidate's limit as a decline it records without invoking that backend, so sibling leaves are never scored and then discarded. A candidate that advertises scoring without implementing it still counts as able, so its contract failure is reported rather than hidden by a vote. `maxScoredChoices` is a limit, not a `Capability`: it cannot be required. The OpenAI backend labels the choices `A`..`T` on one line each (a value that cannot sit on one line as itself is JSON-quoted, so it cannot pose as a further option and values that differ only in whitespace stay distinct), asks for one token with `top_logprobs: 20`, combines spellings of a label by log-sum-exp, and places a label with no listed spelling only when the mass the list leaves over is smaller than the leading observed label's, so a wholly unlisted label can never be the chosen value; otherwise the call is declined rather than guessed. Each unlisted label then takes an equal share of that leftover, so together they never exceed it and one can still sit above a listed tail label; when the list leaves nothing over they sit a fixed margin (`UNLISTED_MARGIN`) below its smallest entry, so the vector stays finite. Every placed score is still an estimate: an observed label's own unlisted spellings can add up to the leftover to it, so two observed labels closer than that may be ordered wrongly, and a response with no label at all is declined rather than reported as uniform. A malformed alternative is a failure, not a decline. A model that refuses `logprobs`, by a 400 (by `param`, or by a message that names it and says it is unsupported) or by an answer with no log-probability field at all, has scoring switched off until reload and `capabilities()` says so for the configured model, so later decisions vote without an attempt; a completion with no content token or no alternatives, and an answer that is simply not a label, are declined for that call only, and any other HTTP failure stays an error so an outage does not silently turn into voting. Probabilities from scoring are still `calibrated: false`. Enforced by `unitTests/resources/models/generativeDecision.test.js`, `scoreChoices.test.js`, `scoringLimit.test.js` and `unitTests/components/openai/index.test.js`.

## `@decide` and `@embed` share one trigger rule

Both directives derive an attribute on the originating node before the record is staged, in `_writeUpdate` and in the cache-from-source write. `writeHookApplies` and `sourceState` (`embedHook.ts`) are the only trigger logic: a replication receive, an `x-replicate-from: none` write or an audit replay never re-derives, a payload without the source leaves the derived attributes alone, a null source clears them, and a CRDT op is skipped. `@decide` writes the chosen value and, when named, its probability from one `models.decide` call, and a failure fails the write, so the two are never from different decisions and never half-written; a missing decider or an override without the promised probability fails the write too. `runWriteJobs` aborts the siblings of a failed hook and settles them before the failure is reported, so a rejected write neither waits on a hook that honors the signal nor keeps being mutated by one; the built-in hooks forward the signal to their model calls. `assertDerivedFieldOwnership` gives every derived field one writer, refuses a directive whose source is another directive's output, because the hooks run concurrently within a write, holds a decided field and its confidence to what the loader accepts, and refuses an `Object.prototype` key as any of those fields, because `sourceState` tests presence with `in`. The loader runs it, and `declareTable` runs it on the complete list (a peer's fields merged, an omitted primary key inherited) before that list replaces the live one or reaches the catalog, so a programmatic `table({ attributes })` declaration is held to the same rules and a refused declaration changes nothing. `Table.updatedAttributes` runs it too but only logs a violation, because it also runs when a descriptor an earlier build accepted is loaded from the catalog, and a table must keep loading. The hooks receive the request's signal, so a client that disconnects cancels the model calls as it did before the hooks were combined. A `decide` descriptor change persists without a reindex: a stored decision does not depend on the model, unlike an embedding, whose `version` carries the model. Enforced by `unitTests/resources/models/decideHook.test.js`, `decideDirective.test.js`, `decideRegistry.test.js`, `decideWrite.test.js` and `integrationTests/server/decide-directive.test.ts`.

## Built-ins serve one kind

The provider factories (`ollama`, `openai`, `anthropic`, `bedrock`) treat every non-embedding kind as generative, so a `models.decision` entry naming one would register a backend with no `decide`. `builtinServesKind` (`bootstrap.ts`) refuses that entry at boot and reload, and `wrongKindEntrySchema` (`validation/configValidator.ts`) refuses it at validation, in both directions: `backend: generative` is the only built-in for `decision` and is refused under `embedding` and `generative`. Module backends are exempt because their factory receives `kind`.

## A recorded decision is committed before its id is returned, and its facts are separate rows

Recording is opt-in: `Models.decide` stores nothing beyond the per-call analytics row unless the call passes `persist: true`, so by default it costs what `embed` and `generate` cost and works on any node; only callers that will report outcomes pay for a durable record. The option types carry that promise: `RecordedDecideOpts` (`persist: true`) returns a `RecordedDecision` whose `id` is present, and any other options object returns a `Decision` whose `id` is optional. With `persist: true`, `Decision.id` names a row in `hdb_model_decisions` that `Models.decide` commits in a transaction of its own (`decisionStore.ts`: `transaction()` with a fresh context object, so the write never joins an ambient application transaction and survives that transaction's abort) before the decision is returned. The row is written once and never rewritten; each recorded fact (`truth` or `action`, per field for object schemas) is its own `hdb_model_outcomes` row keyed `<id>/<fact>[/<field>]`, so two facts recorded on two nodes cannot overwrite each other and a report never re-expires the prediction: facts copy the decision's `expiresAt`, and a report whose state equals the stored fact writes nothing. The id is a UUID because `getNextMonotonicTime()` is monotonic per process, not unique across nodes, and both tables replicate: they are declared with `replicate: true`, as the scheduler state table is, so a scoped `replication.databases` cannot exclude them, with `audit: true` as the feed, and neither is in `NON_REPLICATING_SYSTEM_TABLES`. With `persist: true`, a commit failure after the backend succeeded throws `DecisionPersistenceError` outside the candidate loop, so a storage fault never bills a second model call, and a read-only node rejects before routing. Both tables are provisioned with their primary key by `json/systemSchema.json` and the `5.3.0` directive, and `declareDecisionTablesAtBoot` (called from `componentLoader` after `bootstrapModels`) layers the attributes and the indexed `expiresAt` TTL on every writable node, so a peer that never decides still evicts. Enforced by `unitTests/resources/models/decisionStore.test.js` and `decideOutcome.test.js`.

## No-match is a separate score, never a value

A leaf opts in with `noMatch: true` (#2846, decided on #2843). The backend then returns a score in `[0, 1]` that the input matches none of the allowed values, beside the unchanged forced-choice `distribution`; the two are not a joint distribution, so the all-votes-no-match case still has a closest allowed value. No sentinel ever enters an enum, which is why boolean and integer leaves can opt in. An opted-in call requires the `noMatch` capability (and `calibratedNoMatch` when it requires `calibrated`), checked per candidate like every other requirement, and reports `calibrated: true` only when both scores are calibrated. A score on a leaf that did not opt in is dropped, so a schema without the flag sees exactly the pre-#2846 output. The generative adapter asks an opted-in leaf for `{ value, noMatch }` when voting and adds one distinct "none" choice when scoring, renormalizing the allowed values without it. Enforced by `unitTests/resources/models/noMatch.test.js`.

## A `@decide` decision is recorded only when the record can reach it

The built-in decider passes `persist: true` only when the directive names a `decision` attribute, so a directive nobody can report outcomes for writes no `hdb_model_decisions` row (#2852). With one, the decider records the decision and the hook stores `Decision.id` beside the value and confidence; a null source clears all three. The id is provenance an outcome report trusts, so `buildDecideBefore` rejects a write that carries it unless that same write derives or clears it, or arrives by replication or replay; `x-replicate-from: none` and a CRDT operation on the source do not qualify, since any request can send them. The association is bounded, not atomic: the decision commits in its own transaction before the record, so an aborted write, a later source write, or a delete leaves an unreferenced row that expires with the retention. On a read-only node no write can commit, so `Table` skips the model hooks and serves a source-cache fill without staging it (`noCacheStore`), for every table. Enforced by `decideHook.test.js`, `decideWrite.test.js`, `decideOutcome.test.js` and `integrationTests/server/decide-directive.test.ts`.

## A fitted calibration never crosses a score source, and never waits on storage or fails a call

`calibrated: true` from a fit (#2841) means an eligible, unexpired version, fitted under the active policy, was applied to every field of the decision. A population is `populationKey` (`calibration.ts`): tenant, logical model, the decision entry's fingerprint, the signature, the instructions hash and the schema hash. The fingerprint is `sourceFingerprint` (`decisionStore.ts`): the entry's logical name, because a module-backed backend may choose its scorer by name, and its expanded configuration without its named credential fields (`apiKey`, `accessKeyId`, `secretAccessKey`, `sessionToken`, `authorization`, `password`, `token`, `credentials` and the like, matched by exact name) or `fallback`, published per backend by `bootstrap.ts` into `backendRegistry.ts`. An operator-set `revision` covers a deployment change the configuration cannot show, such as a floating model tag. The accounting context's `app` is left out on purpose, because it is the calling route, not an application, and would split one question into a population per endpoint. The generative adapter signs a decision with `;source=<fingerprint>` only when every inner call reported the same identified source through the `SERVED_SOURCE` hook. The facade calls that hook after a successful attempt, outside its `try`, and swallows its faults. A fallback inside a vote, or a backend registered from code, leaves the decision unsigned, and an unsigned decision is never calibrated or learned from. A custom decision backend registered from code identifies its score source only through the `signature` it returns, which it must change whenever that source changes; Harper cannot see a replaced implementation behind the same name and signature. Only decisions recorded while calibration is enabled carry a `population`, so a fit never reads scores whose source was not collected. `getCalibrations` returns that same key on every summary, because the fields a summary otherwise shows (signature and hashes) do not include the entry fingerprint: a caller matching a decision to its report on those alone would read another population's risk after an entry setting changed.

`applyFits` (`calibrationStore.ts`) reads the in-memory cache only. A key never loaded returns the decision raw and starts one load; an entry older than the freshness window keeps serving while it refreshes, so a population is uncorrected only before its first load or after a load times out or fails, at most `maxLoads` in flight, each counted until its read settles, so a store whose reads never settle holds the slots and leaves that node's decisions uncorrected rather than piling up reads. Faults are logged through `safeErrorMessage` and return the decision raw. Reliability scores the value a decision returned, which on tied scores need not be the schema-first one, so a fit is judged on the decisions it will actually serve. A reload that leaves the calibration block unchanged keeps the cache and the scheduled job, so frequent unrelated config changes never postpone the first run. Calibration runs after the analytics row, outside the candidate loop, so it never bills a second call. `requires: ['calibrated']` still routes on the backend's own claim. A schema with a no-match leaf is never fit-calibrated, because its no-match score would stay raw under the flag; its population gets reports whose reason is `no-match-schema`, never an eligible version.

Versions in `hdb_model_calibrations` (`replicate: true`) are immutable. `fitId` covers the input digest, the policy and the result, so a repeated run writes nothing. A row is applied only when its `key`, its `rank` prefix and the key recomputed from its `population` and `field` all match the key it was read under, so a malformed replicated row cannot cross a population. The reader takes the greatest `rank` (`key | evidenceAt | fittedAt | fitId`) in one descending prefix read. `evidenceAt` is the newest decision or truth fact a version read, so the version that saw newer evidence wins whatever node wrote it and in whatever order rows arrive; two runs on different nodes that both step past the same previous version tie on `evidenceAt`, and the later `fittedAt` wins until a run that reads both writes a successor. A new version's `evidenceAt` is also at least one above the version it replaces, so a correction stamped by a node with a slower clock still supersedes it. A version is written whenever a population's input digest changes, even with no labels left, so a correction revokes an older eligible version. Rows expire after their decisions do. `calibrate()` can only lower a run's budgets, never raise them or change its policy, and a run invalidates only the cache entries of the keys it wrote. A population's decisions are read newest first through the indexed `populationRank` (`population | expiresAt | id`) with a limit, so a large population is never loaded in full. The limit is the newest decisions whose examples, at their cost across every field, fit in the configured `maxBytes` beside the population's own head: a size fixed by the configuration and the schema, so a population too large for the byte budget is still refit, on the same sample each run. A run that cannot afford that sample, because `calibrate()` lowered `maxBytes`, stops on the byte budget and writes nothing, because a smaller sample could revoke a fit its evidence still supports. Heads and a population's sample are budgeted separately, each against `maxBytes`, so other populations in a run never crowd a sample out, and a run holds at most about twice `maxBytes`. A head is renewed only by a run that read decisions for it, so a population whose decisions have all expired lapses instead of staying in the table. Discovery uses at most half of `maxDecisions`, split between the newest decisions and a saved cursor that keeps the ids on its boundary, and splits its population budget the same way. A row that hits a cap is left for the next run, a newly discovered population gets a head at once, and ties at one timestamp never stall the cursor. No discovery page asks for more rows than the scan may still take. Decisions read for fitting come out of the rest of the same budget, so one run reads at most `maxDecisions`, plus one decision per deferred population. A population is read up to one decision past what is left of the budget, and deferred to a later run when that extra decision exists, so a truncated read is never fitted and a population that exactly fits is not deferred forever; a population a run could not finish, deferred or stopped by the byte or time budget, moves to the back of the queue so it cannot hold up the ones behind it, and configuration requires `maxDecisions` of at least twice `maxExamplesPerKey` plus 2, so the first population fitted in a run always has room for a full sample, because a partial sample would write a version that revokes a fit its evidence still supports. A failed run fails its scheduled job. A run walks known populations least recently fitted first, then those discovered newest first, under global decision, population, byte and time budgets, and writes a population only after its report is complete. Its job is registered with `registerInternalJobs` (`resources/scheduler/engine.ts`), under a reserved prefix no component can register or unregister. Enforced by `unitTests/resources/models/calibration.test.js`, `calibrationStore.test.js`, `sourceIdentity.test.js` and `unitTests/resources/scheduler/engine.test.js`.

## A process-wide backend has one live instance per key at a time for what its runs are handed, and no per-thread fallback

`registerProcessBackend` (`processBackend.ts`, #3081) is for in-process models, where a copy per worker means a model, a GPU context and a warmup per worker. Every registering thread installs a proxy in its own registry and claims the key from the main thread. Main elects the owner among the eligible claimants, and only that thread runs the factory. Main is eligible only as the lone worker, because it loads no application code while it has workers, and it coordinates because it is never restarted and sees every worker exit.

**One live instance per key at a time, for what its runs are handed.** One live instance per key holds for every object handed over during a run until the run is sealed; an object registered under the key on a thread with no live run of it, such as one a factory's leftover code registers after its run is sealed, has its disposal tried at once on that thread, outside election, and can coexist with another thread's instance until that disposal completes, indefinitely if its `dispose()` hangs or keeps rejecting (a disposal that keeps rejecting is logged). No election waits for such an object: main accepts a disposal report only from the key's owner or the thread it holds as draining, so fencing one would take a report with no run behind it. Within that scope it is one live instance at a time, not one per process lifetime: a restart or a handover builds a new instance, but never while the previous one may still be live. An instance is the backend its factory registered under the key and what it returned when that is a different object, as when a module factory registers its backend and returns the engine behind it. A second registration under the key is refused (`registerBackend` throws `ModelBackendRegistrationError`), so one registration is the key's, and it fails the start whatever the factory does with the error. It counts as gone once each of those has had its `dispose()` resolve, the registered one first (one without `dispose()` is taken to hold nothing its finished calls and its thread's exit do not release, so it is gone once its running calls finish), or once its thread exits. A `dispose()` that rejects is tried three times in all, and a `dispose` property that throws when read counts as a rejected try; if every try of one rejects, the others are still tried, and the owner reports `DISPOSE_FAILED` instead of `DISPOSED`, which fails the key (`reason: 'dispose-failed'`). A worker told to `SHUTDOWN` releases its claims and drains the run it owns; what that, a disposal report and a thread's exit do to the election, and how long shutdown waits for the drain, is stated once, in [Handover and election](#handover-and-election). The owner owns every object the factory hands over from the moment it is handed over: `constructBackend`'s `hold` gives it each backend the factory registers, under any key, before `registerBackend` checks it, so one refused as invalid or as a second registration under the key too, and the owner holds what the factory returns before it awaits it or reads any of its properties. An async factory returns its own promise, which reads the `then` of what the factory returns before the owner can, so an object whose `then` throws there reaches the owner only as that rejection and is the factory's to free, or to register before returning. A failed start, for any reason, the factory's own error included, tries to dispose every object held, in the order handed over, before main hears of it. A start that succeeds keeps the instance and tries to dispose the rest (a backend registered under another key, which is never installed, or an invalid one whose refusal the factory caught) before it reports, and if every try of one rejects, the start fails as `DISPOSE_FAILED`. A returned extra stays in the instance and has its disposal tried at run end; a non-instance extra is disposed before the start report. A registration under the key outside the capture, such as one that work the factory left running makes after it settles, is never installed over the key's proxy on any thread that registered the key: `guardInstalled` (`backendRegistry.ts`) hands it to the process-wide backend, which logs a warning naming the key, and the registration does not throw, so leftover work cannot crash the worker. While that thread holds a live run of the key, the run owns the object as it owns its instance: it joins what the run holds, so the owner tries to dispose it, with the usual tries, before it reports the run ended, and reports `DISPOSE_FAILED` if every try rejects. A run is live until it is sealed: its owner tries to dispose what it holds until a pass finds nothing left, and in that same synchronous step, with no await between, leaves the live phases and reports the run ended, so an object handed over before then is tried before main hears, and one handed over after finds no live run. A ready run does not dispose it sooner, since it may share what the instance is serving with. An object the run already holds, such as its own backend or what its factory returned registered again, is left as it is, never disposed under the run that serves with it. With no live run on the thread, its disposal is tried at once, with the usual tries, outside any election, as the scope above says. Registrations under keys that are not process-wide are unchanged.

**Election.** Among the eligible claimants present when it elects, main prefers the newest worker generation, then the earliest claim; after a failed start it ranks the thread whose start failed last, so any other eligible claimant, even one of an older generation, is preferred to it. It takes a claimant's generation from the worker record `startWorker` stamped, never from the claim; a claimant states only its own eligibility. When it elects, and when it can choose nobody, is the table in [Handover and election](#handover-and-election): an owner's `RELEASE` with `live: false` elects at once, and one with `live: true` elects only once the released thread's `draining` clears, among the claimants present then. A healthy owner is never replaced by a newer claim, so a later claim does not load the model again. While its thread's view names no owner, a call to a `failed` key fails at once, and any other waits at most `ownerWaitMs` for one, with at most `maxPending` calls waiting per thread, before it fails by name.

**Trust.** Every handler takes the sender from the port the message came over, never from the message, and drops a message whose `origin` disagrees. Calls (`REQUEST`, `CANCEL` and their responses) go directly between the caller's thread and the owner's thread over the port mesh; main carries a call's arguments or results only when it is itself the caller or the owner, as in single-thread mode. Main alone elects and publishes authoritative state; each thread's `onThreadExit` handler also clears a dead owner from its local view before the next push. Keys include the application domain: main checks a claim's domain against the worker it started, and an owner serves only threads main admitted for the key, and only the methods the key's kind forwards. An owner acts only on main's election: a request names the state version and election epoch it was routed with. One routed with an older epoch is refused `moved`, whatever state version it names, so it is never held. One naming a state the owner has not seen is held until main's push arrives, but only when main's last push to the owner admitted its sender; any other is refused `unconfirmed` at once and never held. The proxy may try the route again after a short pause (doubling to 50 ms) while `ownerWaitMs` permits.

**Resend.** A response carries a result, the backend's error, or a refusal (`moved`, `unconfirmed`, `busy`, `not-owner`, `start-failed`), which only admission, a drain and a failed start send, each for a request that never reached the backend. The proxy may attempt another route only after `moved` or `unconfirmed`; the move limit (at most four newer states per call after `moved` refusals), a failed key, no eligible owner and wait expiry can end the call first. A backend's error is rebuilt on the caller as a plain error of its name and is never taken for a refusal, whatever it is named, so a call that reached the backend is never sent again.

**State.** Main holds authoritative state and pushes its changes, so the threads' views converge on it; one can trail it by the push in flight. A thread that sees its owner exit locally clears that owner and changes a non-failed view to `starting`; `backendStatus()` reads that local view, which can differ from the last pushed state until main's next push. Main sets `ready` only when it accepts the owner's valid `STARTED` report. Until that state reaches a proxy, it advertises only its kind's base method, so a call that requires more (tools, scoring, a calibrated decision) fails the facade's capability check instead of queueing at the owner. The proxy's name follows the owner's answers, so the caller's analytics row names the backend that served the call.

**Failure.** An unplanned loss (an exit or a failed start) rejects the calls waiting on that owner with `ModelBackendUnavailableError`. They are never retried, because the backend may already have billed or applied them. While the generation's `maxRestarts` lasts, each such loss is charged one restart and main runs `elect` again, which prefers a claimant other than the lost owner and may choose nobody; a loss with no restart left fails the key until the next generation (`restartNumber`, which `restartWorkers` bumps and a crash restart does not), so a crash loop stops loudly instead of reloading the model forever. A thread that is not the owner never runs its factory, so there is no per-thread fallback: a bad factory fails the key for every caller, and runs with the owner worker's full privileges, as it would per thread. The loss's error is in `backendStatus` for operators, never on a caller's error.

**Load.** The owner runs `concurrency` calls and queues `maxPending` more, beyond which it refuses `busy` (`ModelBackendBusyError`). With `maxBatchInputs`, queued `embed` requests whose options and accounting, as the owner receives them after structured clone, are equal as primitives, arrays and plain objects, compared by value and never by identity, are merged. A class instance arrives as a plain object of its own enumerable fields, its prototype dropped, so two whose fields are equal merge, and the backend gets that plain object merged or not; an object the clone keeps as its own type (a Date, a Map, a RegExp, a typed array) never matches, even one two calls share. A merged call carries at most `maxBatchInputs` inputs, and a larger request runs as consecutive calls of at most that many. A merged call is aborted only when every member has cancelled. Its usage is split so the shares add up to exactly the reported value, in any order; latency is the merged call's for every member. When a later part of a split request fails, the error carries the usage of the parts that completed, and the facade bills it on that attempt's failure row, once (`takePartialUsage`); a fallback candidate's row bills only its own call. A split call its caller has cancelled reports none, since the caller has already settled. Errors cross threads by name, message, status code and code (and a `ModelBackendUnavailableError`'s `reason`), plus a scoring decline's usage, so the facade classifies them and falls back exactly as it does for a local backend. Options and arguments cross by structured clone, and a message a thread sends itself (an owner's own calls, every call in single-thread mode) is cloned the same way before it is handled, so such a call is refused, copied and merged exactly as one from another thread. Results cross the same way: an ordinary buffer is copied, so a backend may reuse its output buffer, but structured clone shares a `SharedArrayBuffer`, so a vector over one is still the backend's memory. The caller's `signal` and the `toolMode: 'auto'` loop's `toolHandlers` and `conversation` stay on the caller; an abort reaches the owner as a cancel. `accounting` is sent as a field of the request, not as an option, and the owner hands it to its backend as `opts.accounting`. An option whose value structured clone refuses (a function at any depth, a symbol, a WeakMap) fails the call before it waits for an owner, naming the option, rather than being dropped; what the clone leaves out without refusing (a symbol-keyed option or property, a non-enumerable one, a class instance's prototype) is left out, as it is across threads. Streams are not forwarded (`stream: false`). Claims of one key are expected to carry the same options: main logs the first that differs and keeps the first claim's restart budget, and each owner serves with the options it registered.

Enforced by `unitTests/resources/models/processBackend.test.js`.

## Handover and election

This is the one statement of when main elects an owner for a process-wide key (`processBackend.ts`) and what a handover waits for; the comments in `processBackend.ts` and `types.ts` point here rather than restate it. Main's entry for a key holds `owner`, `draining` (a thread whose run may still hold objects it was handed) and `state` (`starting`, `ready` or `failed`). `owner` and `draining` are never both set. Only `elect` sets `owner`, and only while no `owner` is set, no thread is `draining` and `state` is not `failed`; with those gates open it chooses an eligible claimant (newest worker generation, then earliest claim, the owner just lost only when no other is eligible), or, with none eligible, sets `reason: 'no-owner'`, which nothing else sets. A thread runs its factory only when main's push names it owner and it has not released (`onState` → `startOwner`). A claim main ignores (from outside the sender's application, from a thread that has exited, or with malformed options) changes nothing, and a `STARTED` is valid only when its `name` is a string and its `capabilities` an object. Below, "Yes" means the handler runs `elect` with its gates open, so an owner is chosen if a claimant is eligible; "Not run" means the handler does not call `elect`.

| Event at main (handler)                                                      | `state` after                                                                          | `draining` after     | `owner` after                                        | `elect` can choose an owner                                                |
| ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | -------------------- | ---------------------------------------------------- | -------------------------------------------------------------------------- |

**What clears each gate.** `draining` clears only on a `DISPOSED` from that thread (`onDisposed` ignores one from any other) or on that thread's exit. `failed` clears only on a claim from a newer worker generation than the key's (`onClaim`, which takes the generation from the worker record `startWorker` stamped, never from the claim); no release, report or exit clears it. Clearing one gate runs `elect`, which still chooses nothing while another is closed. So after `DISPOSE_FAILED` the thread's exit alone does not restore service: an owner is elected only once that thread has exited and a newer generation has claimed, in either order, and whichever comes second runs the election. While a newer generation has claimed and the thread still lives, `state` reads `starting` and calls wait for an owner within `ownerWaitMs`; while `state` is `failed`, calls fail at once with reason `failed`. A spent restart budget clears the same way, on a newer generation's claim.

**The released owner (`releaseAll`, `beginDrain`, `finishDrain`, `failRun`).** A worker told to shut down sends `RELEASE` for every key it claimed, with `live` set when it holds a run of the key that is not yet sealed, and refuses `moved` the requests it was holding for a newer state. Its run stops taking work: queued requests are refused `moved`, and the caller's proxy may attempt to route an unstarted call again, within its limits (see the routing rows above); the factory's `signal` aborts if the factory is still running, never under a ready backend's calls; calls already running are left to run. Once none is running and the start has settled, `finishDrain` tries to dispose each object the run holds and, in the step that seals the run, reports `DISPOSED` when every needed disposal resolves (an object without `dispose()` needs none), or `DISPOSE_FAILED` if every try of any one rejects; a hanging `dispose()` yields no report. A run whose start fails reports from `failRun` after its disposal tries finish: `DISPOSE_FAILED` if every try of an object it or the start handled rejected, otherwise `DISPOSED` if it was released and `START_FAILED` if not. `releaseAll` runs only on workers, so main never releases and a handover is always a worker's.

**How long a handover waits.** The drain sets no deadline on a running call or a `dispose()`: it leaves running calls to run, though a caller's abort or `timeoutMs` still sends its own call's cancellation to the owner. `threadServer` waits for `releaseAll` (`runShutdownDrains`) only until the drain deadline (`getShutdownDrainCeilingMs`, from `replication_blobSendDrainTimeout`, 10 minutes by default); there `runShutdownDrains` stops waiting and `threadServer` continues the worker's shutdown (servers, scopes, databases) whether or not the disposal has ended, while the termination backstop in `manageThreads.js` allows time past that deadline before it terminates a worker that has not exited. The deadline bounds that wait, not the worker's exit or a disposal's end. A call still running when the owner's worker exits fails on its caller with `owner-exited` (`onThreadExit`) and is not sent again, and the exit clears `draining` (the table). A caller's own `timeoutMs` and `ownerWaitMs` bound its wait from its side. So after a live `RELEASE` the key has no owner at least until `draining` clears (on `DISPOSED`, or on the old worker's exit), and after `DISPOSE_FAILED` at least until a newer generation has also claimed; `elect` then chooses an eligible claimant if one is present.

**Why this keeps one live instance.** Every handler that clears `owner` either sets `draining` (a live run's release, a failed disposal) or runs once the run has been sealed with every disposal it tried resolved (`START_FAILED`), once the releasing thread holds no live run (`live: false`), or once the thread has exited, and `elect` chooses only while nothing is `draining`. So no owner is elected while an earlier run of the key may still hold an object handed to it before it was sealed: the guarantee [the section above](#a-process-wide-backend-has-one-live-instance-per-key-at-a-time-for-what-its-runs-are-handed-and-no-per-thread-fallback) states, with its one exception, an object registered on a thread with no live run, whose disposal is tried outside election.

Enforced by `unitTests/resources/models/processBackend.test.js` (the handover, generation, owner-exit and failed-disposal cases).
