## Full-text declarations and reader snapshots

User-facing syntax: [Full-text search](FULL_TEXT.md).

- Compile `name: FullText @fullText(...)` into `fullTextIndexes` and the internal durable `fullTextFields` name set. Programmatic declarations default that name set to every index name. Keep write/projection guards independent of query-reader readiness; the name set does not distinguish earlier declarations from new ones. Never add the declaration to `attributes` or record `properties`: it has no stored, computed, or selectable value. Source fields own permissions.
- Accept only field placement with its name supplied by the field. Reject a `name` argument, table-level declarations, and index names that collide with current stored attributes. Earlier beta declarations and indexes have no supported upgrade path.
- Hold one reader lease for the entire search, including every native result page and highlight trace. Reload only an idle reader. Publication during an active query opens a replacement for subsequent queries and retires the old reader after its lease drains. Offset paging across different native snapshots can duplicate or skip hits; deduplication cannot recover skipped hits.
- Native process budgets are captured before `startHTTPThreads()` loads application components, or on an earlier main-thread native load/managed spawn. Managed worker data and worker environment data carry the snapshot; standalone application workers created before capture must fail before configuring the addon. Validate the raw snapshot at activation; worker replacement cannot reconfigure a process-global addon. Non-runtime query policies still resolve live.
- Native fulltext owns commits and reader snapshots. Harper owns audit coverage, worker epochs, readiness, and publication notifications. A stable native snapshot does not imply a global record snapshot during concurrent writes; source versions are checked when hydrating hits.

Sources: [schema parser](graphql.ts), [declaration compiler and generation identity](fullTextSchema.ts), [table read/write guards](Table.ts), [reader leases and paging](indexes/fullTextQueryIndex.ts), [publication-between-pages regression](../unitTests/resources/fullTextQueryIndex.test.js).

**A bare nullish id is never a collection target for `get` or `delete`.** `transactional()` throws `ClientError` 400 synchronously for `Class.get()` / `Class.delete()` whose first argument is a bare `null`/`undefined` (harper#1837; the delete used to remove every record). Collection delete takes an object target. Known gap, not a contract: an object whose `id` is nullish (`{ id: undefined }`) is still a collection target and deletes every record. A function-form `defineResource` object never passes through `transactional()`, so its `delete` handler receives the `undefined` target. Caller shapes are pinned in `unitTests/resources/deleteNullResourceApi.test.js`.

## A static get by a primitive id skips instance dispatch only when nothing could observe it (`Resource.ts` `registerPrimitiveIdGet`, `Table.ts`)

`Table.get(id)` with a string or number id, inside an open joinable transaction, is served by the getter `makeTable()` registers for that exact class: no `RequestTarget`, no `TableResource`. It runs the same `loadRecord()` closure function `_loadRecord` runs (validation, read transaction, `loadLocalRecord`, residency/source resolution), so a change to loading reaches both routes. Equivalence rests on the gate in the registered getter: every extension point the instance dispatch would call is compared, per call, to the original captured before application code can replace it (`Resource.getResource` in its own module), and contexts that change the dispatch (`authorize`, `onlyIfCached`, `isCollection`, a write condition, a context that is itself a provider, no open transaction) decline, as does a table after `cleanup()`. **When the instance dispatch starts calling a new hook for a get, add it to that gate.** A subclass never matches the per-class registration (its constructor may have effects). A read that goes asynchronous hands a loaded instance back to the general dispatch, so authorization and the instance `get` still run after the load, as before. Pinned in `unitTests/resources/tableGetPrimitiveId.test.js`.

**An audit record carries two clocks; never substitute one for the other (harper#2412 stage 0b).**
`AuditRecord.version` is the originating write's record version — LWW ordering in
`precedesExistingVersion`, `@updatedTime`, ETag/`Last-Modified`. Historical audit-only entries may
carry the surviving version instead. `AuditRecord.txnLogKey` is that
entry's key in the per-origin transaction log: write identity, the record→log lookup
(`auditStore.get(logKey, tableId, id, nodeId)`), and every resume cursor. On LMDB these have always
been distinct fields; on RocksDB the read surface used to overwrite `version` with the log key, and `#2409`'s `recordVersion` alias is now absorbed back into `version`.

They match for every ordinary local write (its record version is its own commit timestamp), so confusing them stays invisible until a **source fill** (`getFromSource`, core #2065) stores the record at the source-reported version and keys its log entry at the fill's commit. A RocksDB record keeps its version in the existing word and, when the clocks diverge, its audit head in `additionalAuditRefs`; stage 2 can replace that pointer with a dedicated log-key word.

Consequences worth knowing:

- **Identity is `(nodeId, log key)`, never a version.** `isAuditEntryWrite` (`auditStore.ts`) is the single predicate; `removeAuditEntry`'s tombstone removal and `blob.ts`'s orphan sweep both gate on it, and both retain rather than delete when identity is unknown. A version compare there would let one write authorize destroying another's tombstone or blob.
- **A RocksDB applied write carries its own record version.** `TransactionWrite.recordVersion`, set from
  `options.version` by every `_write*` builder and read in `save()` only when the transaction is
  `sourceApply` or `isReplay`, is how a replication receiver stores the origin's version while the
  transaction commits under the origin's log key — so a peer's copy of an origin's log stays in the
  origin's clock. New audit entries persist that write version even when an out-of-order merge leaves
  a newer record version in the primary store. The version is stored as received, including one above the log key (an origin's explicit timestamp ahead of its clock, whose key is minted below it): a peer that lowered it to the key would disagree with the origin on which of two later writes wins. The `min(version, key)` clamp that guarded pre-v5.3 audit-only entries (an overloaded body version above the fold key, harper#2497) is gone. Mixed-cluster window, for as long as `auditRetention` keeps the entries: an upgraded receiver stores such an entry from an un-upgraded sender at its body version, and an un-upgraded receiver still clamps an upgraded sender's above-key version to the key.
  One frame can carry writes at different record versions, so this cannot be a per-transaction value. Deprecated LMDB keeps its legacy transaction-version apply behavior.
- **A record's audit reference states its kind; nothing infers the kind from value equality.** A log key, a record version and an origin's key are separate clocks that can be bit-equal (a minted key on a caller's version, a named origin's key on its own version), so a value comparison across kinds misjudges receipts and branches. `additionalAuditRefs` holds **log keys** only — folded out-of-order branch heads and, when a RocksDB record version differs from its log key, the record's own audit head — and every consumer follows them into `auditStore.get`. `receivedIdentityRefs` holds **received identities**: for a write whose identity is not its key (a caller's timestamp, a lock stamp, an unmapped origin's key), what a re-delivery carries; they address no entry and never enter an audit entry. A write's own kind is decided by provenance (`identityIsNotKey`: its reservation minted around a caller's value, or its received identity is not its appended key); such a write, when it becomes the record's head, always records that head as a log-key ref (one that leaves the record at the existing head stays a branch), even when its minted key equals its version, so a retry finds its own key there. Each consumer compares like with like: the receipt check matches log keys against the appended key and identities against the received one; `isBranchRef` excludes only the head, and the walk reads every other branch, since a key does not bound its version (a branch keyed below the audit floor may still be retained and newer than the write); the walk orders an equal version by key only for a key-kind write. The kind is bit 31 of a ref's stored node-id word (`RECEIVED_IDENTITY_REF`; node ids are small mapping indexes), so the layout is unchanged; over the encoder's budget the oldest identities go before any middle log key (a log key also leads the walk to a branch). Released builds (v5.3 and earlier) wrote log keys only, so an unflagged ref is exactly a log key; records from unreleased builds between [#3085](https://github.com/HarperFast/harper/pull/3085) and this rule read their identities as keys until the next in-order write. An older build reads a flagged ref as one in a log that does not exist (a keyed miss it already tolerates), and `readAuditEntry` drops one such a build copied into an audit entry. Replay reserves no key: its context carries the entry's log key, which the write handlers append under (so a replayed record keeps its head ref), and it rebuilds no identity. Covered by `auditRefKinds.test.js`. An `audit: false` record has no log: its `receivedIdentityRefs` holds the received identity of each commutative out-of-order merge folded in since the last in-order write, the only proof a re-delivery was already applied. Under stage 2 the stored log-key field can be renamed; until then, "fixing" a log key to the record version silently unaddresses the entry it points at.
- **An LMDB merge stores the merging write's older version ([#3388](https://github.com/HarperFast/harper/issues/3388)).** The entry version is also the token `LMDBTransaction.commit` conditions every write on (`ifVersion`), so keeping the head's version, as RocksDB does under its key-conflicting transactions, would let a write staged against the pre-merge entry commit over the merge (`noAuditOutOfOrderPatch.test.js`, "staged against the head"). The cost is ordering: the next out-of-order write to that record compares as in-order.
- **Replicated duplicates use committed identity before audit I/O ([#3361](https://github.com/HarperFast/harper/issues/3361), [#3467](https://github.com/HarperFast/harper/issues/3467)).** `Table._writeUpdate` recognizes an implicit head only when origin, version and received log key match and no explicit refs exist, on first delivery and on retry alike. Identity comes from the commit base unless another write to the key in the transaction has saved without being skipped; then it is read from the committed record, outside the transaction, because a publish or relocate saves when it is added and restamps the base, before or after this write, which would make a write that never applied look like its own head. The out-of-order ref check reads its refs from the same record, and a source-applied relocate that ties with the committed head is skipped too: re-applied, it would restamp the head, which can be its own transaction's put. The head's own log entry is not required: a base-copied record has none, and looking for it costs an end-of-log scan and, on a miss, re-appends the duplicate for every peer to re-receive. A retry whose prior attempt staged may read back that attempt's own record (RocksDB keeps the batch across a same-handle recommit): its head ref is the key minted for this handle, which no other transaction in `local` has, so the record's refs are no receipt for it, while a committed competitor's record carries another minted head and its refs still are (`readsOwnStaging` in `Table._writeUpdate`). Only a minted key tells the two apart: a re-delivery in an origin's log shares its key with a competing delivery of the same source transaction. `replicatedRetryDuplicate.test.js` covers real conflicts, including multiple writes to the same key; `relayedHeadTieDuplicate.test.js` covers a relayed duplicate of a base-copied record, a put before or after a same-key publish or relocate, a competing delivery committing while a publish is staged, a log key that differs from the version, and a re-delivered non-resident relocate; `uniqueLocalLogKeys.test.js` covers a lock holder's retried save.
- **A full-write head skips an older write before any audit read ([#3532](https://github.com/HarperFast/harper/issues/3532)).** `FULL_WRITE_HEAD` (record metadata `0x40000`, which harper-pro's copy walk masks from the audit flags it mirrors; RocksDB, audited tables, `Table.ts`) means the write at `record.version` replaced the whole record, an in-order put (`_writeUpdate` at `precedesExisting >= 0`, not rebuilt against newer patches, not copy-apply, and leaving no ref but its own head ref: a tie can inherit the previous head's ref, which would make `fullWriteHeadKey` name the wrong write) or a delete's tombstone, and nothing has changed the body since. Every other committed write clears it: a patch, any out-of-order fold (the below-floor commutative fold and the no-audit fold included), any base-copy frame, a snapshot or past the replay boundary an audited put (`copyFrame`: it carries the source row's body, not the kind of write at its version; its audit entry carries `COPIED_RECORD`, which relays forward unchanged and receivers and `replayLogs` map back to `copyFrame`, harper#3703. The walk still treats a copied put as superseding later older writes: the post-copy replay re-delivers writes its body already holds, and telling those from late ones it lacks needs the source's log position at the copy read, harper#3704), `_writeInvalidate`, `_writeRelocate` and `_writePublish` (which move `record.version` without a full write), and source fills (whose version can be the raced record's). A strictly older write (`precedesExisting < 0`; a tie keeps the audit path) against a flagged head is skipped before the refs, keyed and walk lookups, which is where the walk would stop, but only while the floor is known, the write is at or above it, and the head's log key (`fullWriteHeadKey`) is at or above it. Below the floor the commutative fold still runs, and a head whose entry the floor may have purged still takes the walk. Rows written before the bit have it clear and take the old path; replica admission is its other reader (below).
- **A numeric transaction-log selector is a lookup, never a log name (`RocksTransactionLogStore.getRange`).** `useLog` is get-or-create, so only a string log name may reach it ([harper#2778](https://github.com/HarperFast/harper/issues/2778)). A node id with no log reads where `put()` files that id's entries: an id with no node name (`isLocalOrigin`) reads `local`, and a named id whose log does not exist yet reads nothing. For an id that reads `local` this way, `getSync` returns only an entry whose `nodeId` is that id, because `local` also holds every local write; the received-key dedup lookups skip such an id, since its entries sit under minted keys and an exact-start miss scans to the end of `local` ([harper#3516](https://github.com/HarperFast/harper/issues/3516)). An id used while it had no name and later minted for one loses keyed access to its earlier entries in `local`; falling back to `local` after every named-log miss would add a second scan to every first delivery of an out-of-order write. Pinned by `auditLog.test.js` "a numeric log id with no log reads where put files it, without creating one".
- **Equal versions order by origin, and the out-of-order walk never rewrites the head comparison (`precedesExistingVersion`, `Table._writeUpdate`).** At an equal version, `precedesExistingVersion` returns 0 only for the same origin id, because callers read 0 as a re-delivery. Distinct ids are strictly ordered: by node name when both have one; a named origin ranks above one with no name; and two unnamed origins are ordered by local id. Ids are minted per database, so two nodes can order the same two unnamed origins differently. That still beats dropping one write (the old `undefined === undefined` tie) or keeping whichever arrived first (the old -1 both ways) ([harper#3516](https://github.com/HarperFast/harper/issues/3516)). `precedesExisting` compares the write with the record's head. After the walk, three steps read it: the stale-put skip, the head slot in `additionalAuditRefs`, and `recordNodeId`. The walk orders each visited entry in a local `precedesAudited`. Only the head's own entry, in a same-origin tie, may resolve a 0 head comparison. Before this, a walk that reached an older entry at the write's own version from a lower-named origin turned -1 into +1. An older put then revalidated a newer invalidation, and an older patch stamped its own origin on the newer head ([harper#3521](https://github.com/HarperFast/harper/issues/3521)). Pinned by `equalVersionOriginOrder.test.js`.
- **Crash replay uses both.** `replayLogs` replays each write at its stored `version`; stamping a
  replayed record at its log key would move its version forward and make a later legitimate write
  look stale. Its transactions follow native commits: one ends at a commit's last-entry `endTxn`
  marker, at a change of physical log, or at a change of `txnLogKey` (what
  `CorruptFrameStop.truncatedVersions` records), and one a corrupt frame or a stalled replay cut
  short is discarded, never committed. A log key alone is not a commit: a receiver commits every re-delivery of a source
  transaction under the origin's key, and grouping by key once staged millions of them into one
  replay transaction (harper#2161). Entries skipped as unrecoverable are still left out of their
  commit. Other consumers still treat a second commit at one key as a duplicate
  (`resumePastExactStart`, the derived-index runtime, subscription delivery).
- **Compatibility surfaces still report `localTime` as the transaction timestamp.** Subscription, history, and pro-to-core replication event shapes predate this internal name and stay unchanged.

**QUERY admission uses the body projection.** `Resource.transactional` resolves an asynchronous HTTP QUERY body before resource resolution, recursively clones away client-supplied `checkPermission`, and copies the body's `select` onto the operation admission target before `allowRead`. After authorization, `Resource.query` transfers only the narrowed projection to the body target. This ensures a body-only relationship select is checked before `Table.search`; permission-control fields from QUERY data must never reach a search target.

**Async false-mode read gates preserve the streaming contract.** `Table.search` returns an `ExtendedIterable` carrying the internal `SEARCH_AUTHORIZATION` promise. Static `Resource.search`, `query`, and false-mode `get` await that verdict before returning a response, including when it rides on a `{ headers, data }` envelope's `data`, so a custom `get` that delegates to the instance `search` gets the same status as a search (default-mode `get` skips the check: `transactional()` already awaited `allowRead` and cleared `checkPermission` before dispatch, so a default-mode read pays no extra promise step); on success the wrapper initializes the real search before the transaction settles so its normal read snapshot stays reserved until iteration completes. A returned gate (bare or as an envelope's `data`) then settles to the search's own value — lazy results, a `Prefer: count` page array or an explain plan — exactly what a synchronous `allowRead` returns, which is what REST's count headers and serializers read; the verdict names its gate so a transform derived from it is never unwrapped (`asyncAllowReadSearchResults.test.js`). REST sets `Content-Range` only for a bare count page; an envelope owns its headers. The marker follows supported iterable transforms and retains `selectApplied`/`getColumns`, so async or mapped delegation cannot turn a denial into a truncated successful response.

**False-mode collection write gates stay per dispatch.** Built-in array PUT, query DELETE, and publish perform one request-scoped `allowUpdate`, `allowDelete`, or `allowCreate` verdict respectively. After query DELETE authorizes, it scans with a private cloned target whose permission check is disabled; the caller target stays untouched, and concurrent reads using it still run `allowRead`. Static publish overload routing marks the fresh per-dispatch resource receiver in `staticResourceDispatch.ts`, so copied targets and delayed delegation retain the `(target, message)` signature without putting reusable state on caller objects.

**Array PUT is a collection dispatch in both modes.** `Class.put(batch, context)` arrives with no target, so `transactional` synthesizes one — and the collection it inferred from the null id has to carry over onto it, or the resource resolves as a single record with a null primary key and the batch never fans out. Default (instance) mode then dispatches per element through `getResource`, and each element call must carry its own normalized target in the second position — minted by `elementTargetFactory` so the element's id and `isCollection === false` sit on top of the request's query and route metadata, with `checkPermission` deliberately omitted so a per-element dispatch cannot re-arm the verdict the collection receiver already gave. Each element gets its own object, because its id must not be visible to a sibling whose dispatch resolves later; the request's contribution is resolved once for the batch rather than deep-cloned per element, and nested metadata is shared rather than copied — not the outer collection target and not the context: `Table`'s back-compat `put(target, record)` shift only recognizes a target that is a `RequestTarget`, so a context there is taken for the record and staged as record data (harper#2000). A default-mode `put()` override consequently sees one call per element with that element's id and `isCollection === false`; a component that needs the whole array in one call belongs in `loadAsInstance === false` mode. Static-mode classes are outside the fan-out entirely: their `put(target, data)` receives the whole array, so neither element targets nor the pre-dispatch element guard apply to them — a `null` element in a static-mode `Table` batch still fails as a 500 from `Table.put`'s own array branch, a known gap in the malformed-body rule below. `unitTests/resources/arrayPutCallerImpact.test.js` pins each caller shape.

**A malformed element fails the whole batch, and never abandons a sibling write.** The dispatch loop starts each element's write as it goes, so an element that throws _synchronously_ — `null`, or an id the store rejects — aborts the loop with earlier writes already in flight. Those are settled before the batch rejects: otherwise a sibling that rejects afterwards has no handler and surfaces as an unhandled rejection. Any element that is not an object — `null`, `undefined`, or a primitive — is rejected _before_ anything is dispatched, so a malformed body cannot race a sibling's write and nothing needs unwinding. The nullish case alone is not enough: only a `Table`'s own key validation rejects a primitive later, so a plain `Resource`, or any `put()` override that writes onto the record it is handed, would otherwise be given one. For a failure raised once dispatch is underway the batch reports the **earliest-index** one, uniformly — the same rule whether that element's `getResource` resolved synchronously or asynchronously, so the reported error does not move with cache residency — and the surrounding transaction rolls every element back — array PUT is all-or-nothing, not per-element reporting. The up-front rejection names the offending index as a `ClientError`, so a malformed body cannot land as a 500 carrying an engine-generated `TypeError`. A resource class that implements no `put` answers 405 through `missingMethod` here, matching the single-record path rather than throwing a bare `TypeError`.

**The batch cannot settle while an element is outstanding.** `settleElements` — not `Promise.all` — closes the fan-out. `Promise.all` rejects the batch on the first failing element, which lets `transactional` unwind the transaction while a slower element is still resolving its resource; that element then stages its write against no live batch and commits on its own, leaving a _partially applied_ array PUT. It is only reachable once the async branch passes the target rather than the context — before that the late write failed for its own reasons and hid the hole — so the two fixes belong together. Every element has to stage or fail its write before the transaction may unwind. When several elements fail, the batch reports the **earliest-index** failure rather than whichever rejected first in wall-clock time, so the error a client sees does not move with scheduling. Only that one failure is reported: the framework does not attach a `cause` onto it, because the thrown value belongs to application code and may be a primitive, frozen, or a shared singleton that a per-request mutation would contaminate for every later request.

## Sharding resolves fixed slots through an authoritative database map

Public schemas accept only primary-key hashing; `by` and `slotFrom` are refused with harper-pro#1178. The following expression/attribute mechanics describe the retained test-only implementation. `residencyPolicy.ts` owns normalization, FNV key hashing, per-thread expression compilation and canonical snapshot validation. `graphql.ts` installs a map before declaring a policy; `databases.ts` persists and refuses policy changes/removal. Existing-table adoption requires a custom map even on an empty non-owner and supports key policies only: existing rows have no attribute-slot metadata. `compareResidencyPlacement` reads the actual legacy function without rewriting records. After activation, old function hooks cannot bypass declarative stub handling or indexed replica reads. The public `@sharded` declaration resolves an omitted count inside map preparation, adopting the installed database count or 1024 for first creation. A losing initial-map race re-reads the winner before resolving omission; explicit mismatches name both counts. Every table shares the database count, which cannot change while a policy is active. `by` records the attribute name in the existing policy object: its default evaluator hashes a non-null string or finite number with the same ordered-binary/FNV function as keys. No generated-expression grammar or map value assignments are needed. An explicit `slotFrom` retains its exact string and compiles per thread against the record; fresh writes with noninteger, out-of-range or thrown results refuse before logging. Attribute changes and adding/removing/changing expressions remain immutable after activation. Each value occupies one logical slot; range spreading is deferred to harper-pro#1122. Declarative policy is trusted schema configuration replicated by the authenticated Pro schema route, including its expression; it is not a full-text model that must be enabled separately on each node. Policy changes/removal are refused after activation, and the receiver validates the policy and authoritative map. Applications must not grant schema-writing authority to untrusted peers.

`residencyMaps.ts` caches a complete `system.hdb_residency_slots` snapshot and expanded Uint16 map per store/database. Map installation loads the transaction helper lazily: importing it eagerly changes boot order and captures configuration defaults before the environment is initialized (covered by blob-commit-over-time and response-compression integration tests). The 5.4.0 upgrade directive provisions the same audited map table as fresh installation; lazy declaration also supports pre-release upgrades. Default version 1 depends only on slot count and sorted configured shards. A nonblocking native lock on the system map store serializes map writes with table activation across threads. Map writes retain it through commit or abort; first declarations hold it until their catalog publication. Unchanged policies and identical installed snapshots need no fence. Contention returns 503; schema loading retries that specific condition for at most five seconds. Terminal write detachment releases the fence, including expired-lease retries. Commit-time validation rejects divergent versions before LWW and protects active assignments/counts; source-applied map refusals are classified placement errors so replication holds its cursor without exhausting the permanent failure budget, while local operations retain their original client errors; an older complete snapshot with identical prefix assignments is an idempotent no-op; lost maps are never reconstructed from current configuration. Declaration markers in the local system catalog record activation attempts, including failed first activations, for status reporting; they do not decide ownership. Per-condition shared atomic flags deduplicate failure logs across threads. Map reassignment checks every distinct native catalog in a logical database, including configured aliases that combine several roots. Validating an initial map may create its empty database catalog. Live owner resolution refuses a self-membership view that disagrees with the configured numeric shard used by recovery. The check runs when filling the owner cache, which is invalidated by membership or local-shard changes. A custom-map reader with no local shard remains a non-owner; startup recovery does not depend on peer discovery or runtime topology agreement. Reassigning a node's shard is not a supported data migration.

`Table.getRecordResidency` takes precedence over historical residency IDs. Key policies add no stored slot metadata. Attribute policies carry `residencySlot`, including zero, through primary/audit encoding, invalidation, deletion, replica demotion and copying; see `storage-format.md`. Publishing an event preserves the existing row's slot and stub/replica flags. Indexed non-owners keep projections and can cache temporary replicas. Declarative sharding requires RocksDB; legacy LMDB residency still proxies reads. Unindexed key policies keep nothing and cannot admit replicas. Cached replicas never count as owners. Declarative sharding is RocksDB-only. Initialization and activation check actual existing native roots, including aliased catalogs, rather than trusting the default engine. LMDB still accepts replicated map metadata, but policy activation refuses through the database fence; system/security metadata may continue replicating. Legacy residency functions are unchanged. Declarations require effective auditing and table replication, including redeclarations. Map validation opens the durable database catalog even on a thread that scanned before the database existed. `captureResidencyOwners` pins placement for commit and rechecks membership before submission. An attribute-slot transition emits a complete put at the same version as old-owner invalidations. A replicable local transition outside the new owners requires one new-owner acknowledgment and refuses admission without a connected owner. An application LOCAL_ONLY transition to owners excluding the writer instead refuses with 400 before native submission: no body can be delivered. Its commit and placement callbacks retain that refusal if caught, so the affected database transaction still aborts. Copy/source/replication apply and replay are exempt. Native retries reuse the admission-time owners and confirmation decision on the same retained handle. Owner-load continuations capture the native read-owner guard before yielding; a detached RocksDB snapshot reports the existing retryable read error instead of materializing a late response. Temporary replicas do not waive refusal. LMDB placement/map writes use an exclusive, abortable transaction: its optimistic ifVersion callback does not undo queued writes on a later throw. Confirmation uses the durable native log position, captured under the child transaction's writer lock even when placement omits every primary row. The automatic confirmation applies only to transitioning records, while an explicit caller count still covers every write. Disconnect after commit remains an uncertain outcome. `declarativeResidency.test.js` covers RocksDB placement and the retained LMDB confirmation behavior; Pro's cluster tests exercise RocksDB main-thread/pool parity, mismatch refusal, conversion and previous-binary key rollback.

Supported `@sharded` policies hash only primary keys. Declarations with `by` or `slotFrom` are refused pending [harper-pro#1178](https://github.com/HarperFast/harper-pro/issues/1178): ordinary concurrent moves can produce a committed stale-slot frame that demotes its current owner, independently of native retries. The retained implementation is available only under the undocumented test switch `replication.experimentalAttributeSlots`; actual attribute placement additionally requires native `usesAbortMarkers` capability and enabled `storage.rocks.transactionLogAbortMarkers`. The exact per-transaction signal remains authoritative after logging. No concurrent-move protocol is implemented here.

System-map replay never opens a user catalog: those map changes passed admission before their original audit append. During the boot catalog scan, declarative database replay waits until the system map and its audit tail have recovered, validates local configuration and exact database/table slot-count equality before consuming the tail, then compares the mapped shard to this node's configured shard without peer discovery. A failed catalog scan retains pending replays and leaves the load latch unset so a retry recovers them; an initial snapshot recovered from its own audit log is restoration, never default-map initialization. A queued LMDB full replacement also supplies the basis for later patches before native staging. A transaction retains each complete attribute write separately from its local projection so a subsequent same-key PATCH merges the complete body. A key-policy PATCH of an invalidated stub remains a projection; reference equality with the stored object does not prove a complete body. Cold attribute patches load a complete owner response and compare its version and origin name to the local stub before evaluating placement; another projection is refused after one load. Application branches never replicate, so their schema declarations and checkpoint creation/open refuse sharding before accepting writes or initializing a live database map.

### Sharding startup quarantine and writer replicas

Catalog loading recovers system first, validates each newly opened declarative database before replaying any of its user roots, and moves blocked replay entries aside. Rescanning already recovered roots never makes a new permanent quarantine decision; peer agreement is an admission check, not a prerequisite for local recovery. Only classified sharding configuration failures are isolated; a system/native failure still aborts initialization. `databaseRootUnavailable` includes the blocked roots. Existing permanent commit and derived-index fences stop cached Tables without adding a lookup to healthy read admission; error construction supplies the configuration reason. Table and audit maintenance are retired and explicit flushes skip blocked roots. Main completes its startup catalog scan before starting HTTP workers and publishes the reason in system's shared native memory. Workers consume only that main-thread recovery decision, even after map repair or when first loading a database created since their initial scan, and schema loading reuses fenced classes and defers new tables in blocked databases so healthy declarations in the same schema still load. Operations admission rejects quarantined tables before per-record exception wrapping, so refusal cannot become a successful result row. A process restart is the only release.

Owner-baseline admission is separate from the database-wide live configuration fence. `databaseBaselineHoldReason` is consulted for owned misses, unqualified queries, and originating owned writes; complete read hits, nonowned data and ordinary tables do not inherit that hold. Queries fail before opening a read transaction. The source-subscription loop stamps `REPLICATION_APPLY` from its actual source, so replication may fill an incomplete owner while an external source cannot borrow that exemption. Source fills check admission before resolving their early response as well as at commit. Replay retains the permanent startup decision. Pro supplies the completeness predicate through `residencyMaps`, with a native-root shared readiness word. Activating another legacy table clears that word before persisting the conversion marker.

`initialize_shard_map` accepts an assertion-only request with `existing_owner: true` and `expected_digest`. It rejects malformed assertions, slots/ranges in the same request and digest mismatches before receipt writes. Under the map fence it captures every local native root generation and existing table identity, writes the same receipt in each catalog and flushes before replying. The receipt is operator trust, not a completeness check. Partial or disagreeing receipts, replacement generations and later converted tables cannot reuse it. The local conversion marker is written before the policy descriptor; no receipt is replicated with schema or map metadata. `verify_shard_map` remains read-only.

An eligible local non-owner write stores REPLICA and its deadline in the canonical native transaction, while its normal full audit entry remains authoritative for delivery. The deadline's catalog is opened before staging. Sweep arming runs after commit and neither aborts nor retries publish a replica. Full staged values remain available to same-key patches. The local cache is not an owner and cannot satisfy automatic confirmation. Recovery may recreate the non-owner projection; replica persistence is not a durability promise. Expiration zero and index-free tables retain their prior omission behavior; legacy LMDB residency remains independent of this RocksDB-only feature.

Replica replacement and demotion retain exact files referenced by the canonical audit chain, resolving additional audit references and stopping when all files being released are accounted for or the full snapshot is reached. Scalar patches retaining the same files need no walk. The synchronous walk is capped at 32 native reads, including additional-reference resolution. An unfinished scan resumes after commit in bounded batches through tracked maintenance, rechecks current file references, and reclaims unused cache files automatically. Deferred cleanup captures each candidate's shared reference generation before commit; raw refresh and demotion capture before their native commit too. Encoders increment the generation before checking a reclaim claim. Reclamation compares the captured generation both before and after taking the claim, and never clears it. A later canonical reference therefore defeats an older scan even when another write has already replaced that reference in the live row. Native retries discard callbacks from the abandoned attempt, and one failing post-commit callback cannot skip its siblings. The fixed 4096-entry shared table remains 32 KiB per store: collisions conservatively retain files until later cleanup, while a full generation wrap requires over four billion encodes to the same bucket during a pending cleanup. No persisted blob format changes. A fetched replica can have the same writer/version and different files: those cache files are reclaimed when unused, while the original audit files survive until audit/orphan cleanup releases them. Orphan scanning inspects the audit body of both invalidations and replicas even when the canonical identity matches. Audit retention therefore bounds an additional disk cost beyond the replica TTL. Non-owner subscription row filters still see the invalidation payload, including missing unindexed fields; no implicit full-body lookup or predicate bypass is introduced. A blob encoder increments the shared reference generation before checking the reclaim claim. An already claimed file refuses encoding, because publishing its pointer after the reclaimer's final generation check could reference deleted bytes. Hash collisions can conservatively refuse an encoder while that bucket is claimed, as they already refuse new holders; they can also retain unrelated files. Encoding reports retryable 503 `BLOB_RECLAMATION_BUSY` without claiming that the requested file itself is being deleted; callers should reload the record before retrying. Deferred audit walks stop after a yield if table maintenance has closed, leaving unverified files for orphan cleanup. The fixed table bounds shared memory rather than guaranteeing independent per-file lifetimes. The age cap retains its existing override of old holds and snapshots.

### Live sharding holds and schema registration

A topology disagreement holds every table root of the affected database. A persisted declaration marks root membership on every worker, including workers that scanned before an application reload. A narrow dependency-free root guard shares commit admission without changing module initialization order. The guard is total: unavailable shared state refuses admission rather than escaping transaction cleanup. Healthy checks use the cached immutable map presence and current configuration; Pro caches agreement by shared generation, configuration identity and membership identity. Plain databases never install this guard. The guard adds a constant-time check to admission on sharded databases, including their plain tables. Live holds use retryable `DATABASE_SHARDING_HELD` errors, heal from current inputs, and never enter the permanent `databaseResidencyBlockReason` map. Startup recovery quarantine still requires a repaired full-process restart. Replay and interrupted catalog-drop recovery bypass only live holds; they cannot bypass permanent startup quarantine. Schema registration reuses an unchanged policy without live placement admission, catches a new declaration's transient placement refusal within its database, and continues unrelated declarations. A subsequent valid reload registers a deferred table. Configuration repair does not depend on the order of declarations or replacing workers.

## Full PUT resequencing

`Table._writeUpdate` replays retained newer patches onto the PUT body and stores a replacement, or skips the PUT when the stored head is strictly newer and no replacement can be verified. On RocksDB each visited frame is scanned once through `endTxn` within the walk budget, even when its first same-key entry is a message or an older version; LMDB bounds each equal-version cohort. Collect all newer same-key mutations, then order by record version, origin-name tie-break and same-origin log/program order. When a same-transaction publish or relocate restamped the record (`identityBase`), a committed head at or above the incoming version is restored before walking, while an earlier same-key write in this transaction stops at the transaction's uncommitted log key. When the head is newer only because of a message, a verified walk with no newer patches still replaces the record at the head's version. Missing entries, unreadable IDs or clocks, unavailable patch bodies, unresolved mixed-version audit heads, a pruned predecessor below the incoming version or bounded walks keep the per-node merge fallback, which can retain omitted fields or overwrite an uncollected newer value until full-copy convergence ([#1148](https://github.com/HarperFast/harper/issues/1148)). `outOfOrderFullPut.test.js` covers both engines, omissions, additions, indexes, metadata, blobs, transaction siblings and history boundaries ([#3404](https://github.com/HarperFast/harper/issues/3404)). A newer applied `invalidate` entry is also a boundary for a full PUT, like a newer `put` or `delete`: the stub replaced the record, so the older body is skipped (no audit entry), with or without patches before or after the invalidation. The stored `INVALIDATED` flag is not the test, because a patch over a stub keeps it: a PUT newer than the invalidation (`invalidate` 50, `patch` 200, then `put` 100) still replaces the stub with the complete record. An older patch is unaffected and folds into the stub's carried-forward indexed fields. A walk that cannot reach the invalidation (depth cap, missing entries) keeps the per-node merge fallback above when it collected patches, so a PUT newer than the unseen invalidation is kept; when it collected none, an `INVALIDATED` head still skips the PUT (#3469). A stub made by `relocate` has no `invalidate` entry and is not covered. Pinned by `outOfOrderInvalidatedHead.test.js` on both engines.

## Database generation and resumable positions

Every copy path gives the copy a generation of its own before anything can read it (harper#2451), so no live subscription or persisted position carries over from the source. **Invariant: no readable copy carries its source's generation; a position resumes only if it names the current generation, its cursor is finite, and no prune within the generation reached above it** (`isResumablePosition`). RocksDB only: an LMDB database carries neither a generation nor a resume floor, so no position resumes against it, and a caller applies the check to RocksDB databases alone.

- **Two records beside the floor:** the generation (a 16-byte random id and a float64 epoch, 0 for genesis) and the resume floor (highest prune cutoff in the generation). `raiseAuditFloor` raises both in one verified transaction; the resume floor is not absorbed by an unknown floor.
- **Stamped into the copy before publication:** restore (before `completeRestore`), branch and migration (before their renames), via a private open plus an engine flush — a root-store write is not power-loss durable and directory fsync is best-effort. `harper copydb` and `compactOnStart` copy LMDB databases, so they stamp nothing.
- **An ordinary open never repairs:** it adopts the record, mints genesis as a compare-and-set on absence, or leaves the handle without one (every resume refused). The resume floor is read as never below a finite audit floor, since an older binary's prunes raise only the audit floor.
- **No scalar mode.** A position without an id is never resumable; bind an id only to a position established within the generation. Cursors must be progress-based: a snapshot's newest in-scope key can sit below a floor that retention advances on a quiet database, and would be refused forever.
- **Live subscriptions:** the per-path registry outlives the store, but a subscription from before a reopen can never deliver again (its commit listener and table stores belong to the closed handle). Every open first records its audit store as the only handle a registration on the path may use, then detaches the registry and ends each subscription: `DatabaseGenerationChangedError` for another or an unknown generation on RocksDB, and otherwise (the same generation, or any LMDB reopen) the retryable `DatabaseClosingError`. A registration through an earlier or closed handle, even from inside that close, is refused with the same pair of errors.
- **Resuming through `subscribe`:** a request carrying `databaseGeneration` (with a finite `startTime`, where 0 is a position) is checked before it registers — 409 for another generation or any LMDB table, 410 `ResumeHistoryUnavailableError` below the floor — and again during the replay. A collection replay reads forward, so each check (at every replay yield, before each wait for a slow consumer to drain, and at the end) compares the floor with the position reached at the _previous_ check: a prune raises the floor before it deletes below it, so a pass means nothing unread was removed, while a prune of already-replayed history does not end the replay. The replay also refuses when its log range records a failed or corrupt log read (the store ends that log quietly), when it meets an entry or record id that failed to decode (the decoder returns a sentinel with no table), or when it crosses a `reload` marker for the table, whose back-filled rows have no history to replay; a record walk treats an undecodable version as missing. A record's history walk is its own evidence, checked before anything is sent: a walk that reaches the cursor with every version present verifies whatever the floor says (so a quiet or long-offline record does not reset), a missing version or the 10,000-version cap refuses, and a record with no entry, or a walk that ends at a first version before the cursor, falls back to the floor, since a pruned tombstone takes its history with it and a recreation then starts a new chain. The pre-check for a record is therefore the generation only. `resumeVerified` resolves true only after the final check; nothing delivered before that is safe to checkpoint.
- **Certified progress (`reportProgress`):** the broadcaster keeps a dispatched-through watermark per database (the raw mark; `progress()` and `registeredThrough` read the certified mark below it, see the origin-floor section), advanced only when a new key begins or a pass exhausts the log (never at a yield inside a transaction), tracked only while a progress consumer exists, and stopped for good by a failed read or an undecodable entry. A `reportProgress` subscription's `progress()` follows its checked replay, holds at the registration watermark while a snapshot or buffered live events are pending, and follows the watermark once live; its snapshot keeps every buffered event (harper#2933), and a `reload` marker or a live event it fails to build ends it. MQTT durable sessions persist the older of `progress()` and the position before every unacknowledged message's transaction (`server/DESIGN.md`).
- **Not covered:** copies no generation-aware code made, a pre-generation binary pruning while the audit floor is unknown, keys reissued below a cursor after a clock rollback across a restart, a transaction that commits after a position was recorded with a key below it (keys are assigned at creation; harper#2928; `progress()` holds below a _local_ write, harper#3112, but a position from another source and a named remote origin's write, which takes no reservation, stay uncovered), rows a replication base copy back-fills without history, for a record resume or for any resume while the copy runs, since the `reload` marker follows the back-fill (harper-pro#944 decides whether a base copy starts a new generation), cross-node identity (an id is per database per node), and subscription teardown and the handle check on a legacy LMDB `auditPath` root, which is reopened on every metadata read.

## Origin-closed timestamp floor

A RocksDB transaction's log key is minted when its native handle is created, or installed by `setTimestamp`, and the batch is appended only at commit — so a transaction can commit below a key that was already observed as progress (harper#2928), and nothing bounded that lag (`maxTransactionOpenTime` never aborts a submitted commit; a lock stamp is as old as its lease; an explicit timestamp is any value). `originClosedFloor.ts` certifies a floor `F` for this node's `local` log: **no transaction can append to `local` with a key below `F`** (harper-pro#922, item 1). Replication's per-origin resume and the single-node resume cursor consume it in later slices.

- **Invariant:** every key that reaches `local` was reserved on its thread before its first staged write (`DatabaseTransaction.save`, and `reserveLocalKey` explicitly on the two derived-index eviction handles); the reservation keeps the thread's published bound at or below the key until the handle commits or is abandoned; a certifier publishes `F ≤ min(a clock sample taken first, every thread's bound)`. `RocksTransactionLogStore.put` throws on an unreserved `local` append, because a logged violation could repair nothing.
- **Shared state:** one `getUserSharedBuffer('origin-closed-floor')` per root store, read with `Atomics` as `BigInt64` bit patterns of float64s (positive doubles order as their bits, and +1 on the bits is `nextafter`). Per thread one bound word. _Before_ minting or adopting a key a thread marks its word pending: the negated lower bound `min(its last settled bound, proposed)`, which holds because admission compares the key against `proposed` only after that store. The certifier, and a progress subscription with no watermark sampling its start at registration (`localStartBound`), raise `proposed` (their clock sample) before reading the bounds — so either the reader saw the pending word or the thread saw this round's sample. A certifier that still sees a pending word after 8 scans does not advance (it retries after a yield); `localStartBound` cannot yield — registration is synchronous, and a worker terminated mid-reservation keeps its pending word until this thread processes `origin-floor-retire` — so it uses the carried magnitude, or the floor published before its sample when that is higher (one read after the scan could pass a key the scan saw commit meanwhile), and never falls back to a clock (harper#3599). A carried bound is as old as its pending reservation, so the start can be early, never late. `proposed` is seeded with a clock sample when the first registry is created, so a carried bound is never `0`; a `0` word is the initial value of a slot being claimed, whose claimer has reserved nothing yet and constrains nothing (a reused slot's stale word in that window only errs low). All floor words are compare-and-swap maxima and persistence is read-compare-write, so two certifiers (a replacement maintenance worker starts before its predecessor retires) can only repeat a round, never regress one. A bounds scan visits only the slots below the slot limit (header word 5, one past the highest slot ever claimed): a claimer raises it right after it owns the slot, before `reserve` reads `proposed`, and a sampler raises `proposed` before it loads the limit, so a claim the scan misses admits only keys above the sampler's value. The limit never falls; a freed slot below it is scanned and skipped by its cleared owner word. **Certified local watermark (harper#3112):** a progress subscription's `progress()` and a joining subscription's `registeredThrough` are `certifiedThrough` (`transactionBroadcast.ts`), not the raw dispatched watermark: a RocksDB transaction takes its `local` key at its first staged write and commits later, so the raw mark can pass a key still in flight, which then commits, is delivered below a saved position and is skipped on resume. Each cross-thread notify pass captures `localStartBound` _before_ it drains (kept across `NOTIFY_BATCH_SIZE` yields) and, after draining to the end with no read failure, certifies `min(raw watermark, that ceiling)`, never lower than before. Every key at or below the ceiling belonged to a reservation released before the capture, so it was in the log and the drain read it; a key reserved after the capture is above its sample. The capture must precede the drain: a reservation is released a microtask after its commit settles and its entry is read only by the next pass, so a scan after a drain, or on a read, takes a released key for a dispatched one. A hold ends with the commit's own pass or, since an explicit transaction releases its reservation after its commit settles and that pass can capture first, with the one follow-up pass a held, dispatching pass schedules (an empty pass re-arms it only while a reservation holds it: a clock-sample ceiling below the mark means another origin's key ahead of this clock, which only time certifies); after an abort, with the next capture tick's pass (`startOriginTracking`, `ORIGIN_FLOOR_TICK_MS`). Reads never scan. The same-thread registry (`crossThreads: false`) delivers only this thread's commits, so its ceiling is this thread's own lowest outstanding reservation (`threadStartBound`, no shared scan), and it runs no capture tick, whose pass would drain the cross-thread registry's log range: its follow-up pass and the timer that re-captures after an abort read an empty log. **Scalar replay progress:** a generation-checked collection replay walks committed keys but does not prove that no lower local key is still reserved. Its private live floor is bounded by the pre-replay registration sample, failing closed if that sample is unavailable. Its observed last key (only when the replay advanced) also becomes an uncertified broadcaster candidate: a coalesced notify pass captures its reservation ceiling before draining and only then certifies it. This lets an acknowledged replay catch up after a hold ends without needing an unrelated commit, including when the registry opened at the log tail after the replayed key committed. Other subscribers share this certificate safely: commits before their registration are outside their live-delivery contract, and the registry drains later commits. A same-thread registry sees only its own reservations and commits while replay reads all threads, so a same-thread scalar replay supplies neither a private floor nor a shared candidate; it uses its live certificate alone. `subscribeProgress.test.js` covers quiet catch-up, another table sharing the certificate, same-thread exclusion and failed reads; `durableSessionResume.test.js` covers saving/reconnecting while the lower write is held.
- **Every key in `local` is unique, because every key is minted.** `reserve` admits only the handle's own native mint, and only when it is at or above `proposed` and beats the ratchet; otherwise the handle takes a fresh key (`freshKey`: the native clock's next value, unique and above every sample so far, else the ratchet's next ulp). A caller's value — a context timestamp, `options.timestamp`, a lock stamp — is never a key: `txnTime` stays the record version and the handle takes a minted key, so such an entry carries both clocks exactly as an applied write does (the record points at its audit head through `additionalAuditRefs`; `_write*` take the log key from the handle). Before this rule an explicit value above the ratchet was admitted as the key without moving the ratchet, so two local transactions with one explicit timestamp shared a key, and a later mint could land on an admitted value; `RocksTransactionLogStore.getSync` stops at the first transaction at a key, so the second was unreachable, and the out-of-order walk and keyed dedup misjudged it (an older write won; a re-delivered additive op applied twice; the `transaction.test.js` resequencing flake — the investigation is [harper#3181](https://github.com/HarperFast/harper/pull/3181), which this rule supersedes). Logs written before this rule may still hold two transactions at one key until `auditRetention` (default 3 days) ages them out; there is no migration, and the keyed lookup keeps returning the first. An unmapped origin (an id with no node name) is filed in `local` too, under a minted key, so its writes carry no origin key in the log: an equal version there — a local write's own, or the same unmapped origin's — is a re-delivery (an origin gives distinct writes distinct versions); unmapped origins are exceptional and do not follow the dual-clock identity. A read handle's minted key holds nothing: it is re-admitted at the first write. A write for a named remote origin (`isLocalOrigin` is `put`'s own resolver; an unnamed non-relayed id resolves to `local`) takes no reservation — the origin's floor governs its log. Crash replay never appends.
- **Durability and restart:** the floor is persisted (`origin-closed-floor`, WAL-durable through `commitAuditMetadata`), then synced to disk (`syncWal`, when the engine offers it — `originFloorsDurable`; the tick skips while a sync is in flight) _before_ it is published; advertised `F` is always the persisted value, at most every `ORIGIN_FLOOR_TICK_MS` (5 s) per database on the maintenance worker. Readers consume only the published value, so after a power loss the restarted origin still seeds its ratchet above every floor anyone saw (harper-pro#922 item 4). At open the record seeds the ratchet, which a native key must beat (one load in the ordinary case). Only once a key has been issued from the ratchet (the clock was behind it) do native keys also raise it by compare-and-swap, so a stale ratchet step never repeats a native key another thread admitted meanwhile; strict mode is never lifted within the process, because any hand-back to load-only admission races a fallback still in flight. A key that cannot beat the ratchet is minted fresh — the native clock's next value when that beats it, else the ratchet's next ulp. A caller's value never touches the ratchet (one far in the future would pin every later key) and is never a key. Behind a recovered floor (a restart after a backward clock step) keys therefore come one ulp at a time above it until the clock passes. The largest key in the log is deliberately _not_ a seed either. A record-lock admission floor within `storage.maxLockClockSkew` is claimed by raising the ratchet just below it and minting a distinct record version above it; the local log key is reserved separately when the write is staged. A key issued from the ratchet is not ordered by the clock, so before it is used a ceiling one second above it is persisted (`local-issuance-ceiling`, `coverLocalIssuance`, flushed before use; restart seeds above that whole reserve), and the first opener seeds issuance above that ceiling (`seedLocalIssuance`); later workers share the immutable initial ceiling in the ratchet buffer and do not consume unused headroom: a restart before the clock passes a claim, or the keys issued after it or after a recovered floor, cannot issue them again. The admission path rejects floors beyond the configured skew cap before claiming a key or persisting its ceiling, and refusal is fenced on the specific record-lock handle. **Release and liveness:** a reservation ends on the terminal settle of its handle (the success branch after the coordinated-retry check, the terminal-failure branch, `commitTrackedRocksTransaction`'s settle for raw handles) and on every abort path (`abortNativeTransaction`, `doneReadTxn`, the lease-lapsed and no-writes aborts, `abortChainAfterRetries`, the eviction paths). A retry keeps the key and the reservation — the batch it already wrote carries that key; a replay handle past an open iterator takes it over, with its admitted key, and the retained handle holds nothing further. A worker's bounds are retired only from the main thread's `worker.on('exit')`, which fires after rocksdb-js's env cleanup closed the worker's handles with their commits drained (the worker's own exit event fires before that, while a queued commit can still append); main retires them in the stores it has open and broadcasts `origin-floor-retire` so every thread does the same in the stores it has open, since main need not hold them all. A stalled writer holds the floor by design; the lag is visible through `getOriginClosedFloor` (floor, lag, holders).
- **Not covered:** power loss on an engine without `syncWal` (harper-pro then certifies at level 1 only, and no checkpoint is issued); a transaction-log entry below `F` appended but not on disk at power loss is lost at the origin while a receiver may hold it — Harper's commit contract, unchanged; a re-delivery of a local explicit-timestamp write that carries only the version (an own-origin or caching-source replay; replication frames carry the log key and take the keyed dedup) is matched through the received-identity ref the record keeps and the equal-version rule, not by log key: an in-order write rebuilds that ref list, so such a re-delivery that then arrives buried past the reconciliation walk's cap applies a commutative operation twice — bounded only by harper#1148's convergence; an older binary writing below a saved floor; LMDB (no floor, `getOriginClosedFloor` is undefined). Regression coverage: `unitTests/resources/uniqueLocalLogKeys.test.js` (distinct keys for one explicit timestamp, a mint that would have landed on an admitted value, the consumer outcomes); `unitTests/resources/originClosedFloor.test.js` (stalled and killed worker commits, read promotion, explicit timestamps below and above the floor, equal-version local writes, remote-origin routing, the choke point, a concurrent writer against a racing certifier, issuance behind a persisted floor simulated in-process, without a restart or a cleared registry); lock stamps use a claimed record version above the admission floor and reserve a distinct local log key separately; `recordLock.test.js` pins their version semantics but no stamp below the floor.

## Historical record reconstruction (`getRecordAtTime`)

- **A field a newer patch wrote keeps its reversed value only when the reversal is exact.** A plain set has no inverse; an `add` that established its field from absent or `null` reverses to `0`, and float or unsafe-integer arithmetic can leave a rounding residue. So only an `add`-only field reversed in safe-integer arithmetic to a nonzero result keeps it (a coerced numeric string or boolean comes back as its number), which spares a counter a walk to its base. Every other written field takes its value from the forward rebuild at the timestamp, and a field that rebuild lacks did not exist then. Over incomplete history (a pruned link, a corrupt entry, an entry with no body, an `invalidate`, whose stub lacks the fields it did not index or project, or an out-of-order write merged on an `additionalAuditRefs` branch the single-link walks do not follow) a field the rebuild cannot settle keeps its reversed value. A newer patch with no body, or a newer `invalidate` (whose stub replaced the record), cannot be reversed; it is crossed like a put.
- **Only a patch can be reversed.** The backward walk from the live record undoes patches; a put or delete newer than the requested timestamp replaced the whole record, so nothing recorded about it recovers what came before. After crossing one the walk stops reversing, keeps following links to the entry at or before the timestamp, and rebuilds forward from there (`reconstructForward`). Carrying a newer put's image back across it returns a future state, or throws when a later patch fills unknown fields into the frozen decoded put (harper#1413).
- **An unlinked put ends the walk early, and that is not an empty past.** A put written with no predecessor link (a re-insert after eviction) cuts the chain although older entries are retained. The walk then falls to the timestamp-keyed rebuild, as it does for any broken chain. Rebuilding from a crossed put's own predecessor link would report an empty past for every state older than such a re-insert.

## Path routing & parameterised routes

`Resources.ts` is the registry that maps URL paths to `Resource` classes; `jsResource.ts` registers a component's exports. The user-facing rules — the default export-name path, `static path`, export-name-as-path, the root-relative leading `/`, `:name`/`*name` parameters and precedence — are documented in [Resources → Path Parameters](https://github.com/HarperFast/documentation/blob/main/reference/resources/overview.md#path-parameters).

Mechanics:

- **Registration** (`Resources.set`): parameterised paths are compiled into `paramRoutes` (kept _out_ of the base `Map`) so the exact/prefix matching fast path is untouched. Routes are ordered most-specific-first: compared segment by segment from the left, a literal beats a `:param`, which beats a `*` wildcard (`SEGMENT_SPECIFICITY`); on a tie the longer pattern wins.
- **Matching** (`Resources.getMatch`): exact and prefix matches are tried first and win ("static wins"); only when no static resource matches — and only if `paramRoutes` is non-empty — does `matchParamRoute` run. Matched segment values are decoded and stored on `entry.params`.
- **Binding to the target:** request handlers (`server/REST.ts`, `server/DurableSubscriptionsSession.ts`) `Object.assign(target, entry.params)` after building the `RequestTarget`, so `:id` lands on `target.id`, `*rest` on `target.rest`, etc.
- Named params match exactly one segment; a wildcard captures the remainder (zero or more segments) and must be the final segment.
- **Discovery surfaces:** because parameterised routes live outside the base Map, the enumerators read `resources.paramRoutes` explicitly — `openApi.ts` emits them as templated paths (`:id` → `{id}`) with path parameters, and `components/mcp/resources.ts` lists them via `resources/templates/list` as `{param}` URI templates. The converter is not shared: `openApi.ts` uses `routePatternToTemplate` (`Resources.ts`), and `components/mcp/resources.ts` mirrors it in `paramPatternToUriTemplate` from the pattern string to stay free of a `Resources` import, so a change to the template syntax touches both.

Tests: `../unitTests/resources/paramRoutes.test.js` (unit) and `../integrationTests/apiTests/param-routes.test.mjs` (end-to-end); enumeration coverage in `../unitTests/resources/openApi.test.js` and `../unitTests/components/mcp/resources.test.js`.

## Persisted relationship catalog

GraphQL `@relationship` attributes are live objects in component workers, but the operations API runs in a separate thread that does not load component schemas. `processGraphQLSchema` therefore records each relationship's target `database.table`, and `table()` persists a normalized, data-only relationship list on the table's primary catalog descriptor. The primary descriptor is deliberate: older Harper versions ignore the unknown field instead of loading a per-attribute row without the runtime table definition and silently returning `null`.

`getDatabases()` waits until the complete table catalog is loaded, then hydrates catalog-owned relationship attributes with a stable target-class snapshot and calls `updatedAttributes()` to rebuild resolvers. The list is authoritative only when the GraphQL authoring path explicitly supplies `schemaRelationshipsDefined`; admin and replication callers that omit it cannot erase component-owned metadata. An empty list removes catalog-owned relationships. Live schema relationships and same-name runtime attributes always win, and `@enumerable` is not persisted, so operations queries traverse relationships only when explicitly selected. The primary-descriptor update shares the `update-attributes` serialization boundary with `dropTable()`, re-reads the row after locking, and refuses to replace a drop tombstone. Missing or malformed targets are skipped rather than installed without authorization metadata.

Only the GraphQL authoring path persists relationships. `defineTable()` resolves its relation targets through a lazy thunk so forward references and cycles work, and the target class is not resolvable at registration time — so code-first relationships remain worker-only, and the operations API still rejects them as unknown attributes. Operations-API object entries in `get_attributes` (`{ name, select }`) are held to the same catalog invariant as string entries: top-level names must be declared in `table.attributes` (which the string form already enforced), and relationship targets recursively enforce their own `tableClass.attributes` on `select`, while nested keys under a declared non-relationship (plain JSON) attribute stay unchecked because arbitrary JSON sub-keys have no catalog entry (role permission enforcement across operations-API relationship selectors is tracked in [harper#3316](https://github.com/HarperFast/harper/issues/3316)). Tests: `../unitTests/resources/schemaMigrationFragility.test.js` (catalog round-trip and failure behavior), `../unitTests/validation/searchValidator.test.js` and `../unitTests/resources/restSelectProjectionFixes.test.js` (object `get_attributes` validation and `search_by_hash` projection), and `../integrationTests/apiTests/graphql.test.mjs` (operations API in both directions).

## Typed, discoverable resources (code-first schema + request contract)

**The principle** (full RFC and type-level proofs: **HarperFast/harper#1503**). Harper strips TypeScript at runtime (`--conditions=typestrip`), which erases types and rules out metadata-emitting decorators. So **runtime metadata must be values, and TypeScript types are _derived_ from those values — never the reverse.** Everything here is erasable syntax; the values survive stripping, the types are inferred, nothing can drift. One shared IR — `JsonSchemaFragment` (`jsonSchemaTypes.ts`), produced by `attributeToFragment` — feeds validation, OpenAPI, and MCP, so those surfaces cannot silently disagree.

**Code-first tables (`defineTable.ts`).** `defineTable(name, shape, opts)` authors a table in TypeScript and eagerly registers it through the same `table()` factory GraphQL drives — the returned value _is_ the live table class (`Track.get/put/...` work, `new Track()`/`instanceof` hold). Fields come from the `types` vocabulary (getter flags: `string.indexed`, `id.primaryKey`, `date.createdTime`); per-verb shapes are inferred projections discoverable as members (`(typeof Track)['$insert' | '$upsert' | '$patch' | '$query' | '$record']`). Relationships use lazy thunks (`types.relation(() => Album, { from })`) so forward references/cycles resolve at query time; `relationOf`/`hasManyOf` are the escape hatch for a mutual pair whose eager const-inference would otherwise collapse to `any`.

**Per-method request contract (`defineResource.ts`).** Two front-ends, same runtime metadata: `defineResource(contract, impl)` (function form: an object of verb handlers) and `Resource.withSchema(contract)` (class form: `extends` it and implement the declared verbs; pins `static loadAsInstance = false` so instance verbs receive the converged `(target, data)` arg order the types assume, whereas the default dispatch order is `(data, target)` — see `Resource.post/put/patch`).

A contract is `{ path, record?, get/post/put/patch/delete: { query?, body?, response? } }`. Handler types are **derived** from it: path params from a template-literal parse of `path`, query/body/response from the schema's inferred type. It is a **subset, not a fork** — a handler gets the SAME `RequestTarget`, structurally narrowed (`target.id: string`, `target.get('expand')` typed by the query schema), and the resource still registers/serves like a plain one. The narrowed types are justified by **runtime enforcement**: each declared verb validates/coerces `query`/`body` before dispatch and throws a structured 400 (`ValidationError`, per-field `{ path, code, message }[]`) — the same bargain `Table.validate` makes for tables.

**Vocabulary.** The built-in `t` (`t.string/number/integer/boolean/date/enum/array/object`) and `schemaOf<T>(source?)` both reduce to `JsonSchemaFragment`. A `defineTable` projection slots straight into a contract body/response — `schemaOf<(typeof Track)['$insert']>({ table: Track, projection: 'insert' })` derives the compile-time type from the projection and the runtime fragment from the table's attributes (via `projectTableFragment` → `attributeToFragment`). **Nullability:** non-nullable by default (a bare `t.string` rejects `null`); `.optional` allows absence, `.nullable` allows an explicit `null`; table-derived bodies mirror `Table.validate` at every nesting depth: null rejected only where `nullable === false`, and a nested `nullable === false` property required in every projection (`Table.validate` checks nested properties in full even for a patch); an `undefined` array element (CBOR/MessagePack only) is not checked. Date columns take `t.date`'s ISO-string-or-`Date` policy (no epoch numbers, unlike `Table.validate`). **Body presence:** a validated body must be present unless its schema is `.optional`; `compileVerb` owns that decision and publishes it as `inputSchemas[verb].bodyRequired`, which OpenAPI emits as `requestBody.required`. Passthrough (`schemaOf<T>()`) bodies are exempt — checking presence would resolve the body, collecting a multipart form the handler gets raw — and so are untyped fragments, which validate nothing. Over HTTP only an unframed request (no Content-Length/Transfer-Encoding) arrives as `undefined`; a zero-length framed body (what fetch sends for a bodyless POST/PUT/PATCH) is deserialized per Content-Type — `application/json` gives `null` under the default bigint parser, no Content-Type gives a `{ contentType, data }` wrapper — so it is not an omitted body.

**Downstream surfaces.** `openApi.ts` emits a contract's query params, request body, and response for parameterised routes; `components/mcp/tools/application.ts` drives the tool input/output schema off the contract (converting OpenAPI 3.0 `nullable: true` to a `"null"` type-union member at every depth, since MCP schemas are JSON Schema 2020-12, which ignores `nullable`; query params just drop it, as a URL cannot carry null) and binds arbitrary path params + query (`applyContractInputs`), which lifts the generated-verb binding restriction for contract resources. `ValidationError` (`../utility/errors/hdbError.ts`) extends `ClientError` (400) so existing HTTP handling is unchanged; the structured issues ride on `.detail`/`.errors`. Tests: `../unitTests/resources/defineResource.test.js`, `../unitTests/resources/defineTable-registration.test.js`, `../unitTests/resources/openApi-contract.test.js`, `../unitTests/components/mcp/tools/application-contract.test.js`.

## Conventions

- Nested relationship `conditions`, `sort`, `offset`, and `limit` share `Table._prepareRelationshipSelection` across search and single-record GET. Predicates keep parent inclusion and inherited relationship candidates; only unsorted eligible pagination bounds reads (sorting or unmatched predicates can scan every candidate). Nested predicates qualify only the immediate selected children; descendant narrowing requires its own subselect, while outer-join candidate restrictions remain inherited. Predicate compilation must not mutate projection maps. Candidates and sort keys retain top-level cache-local semantics; predicates are rechecked after source refresh before offset/limit counts a returned child. Cancellation must terminate the raw source before an upstream mapper reads again. Lazy resolver mode is per-call so ordinary property access stays synchronous. Unsorted FK pagination preserves missing slots; sorting drops them. `unitTests/resources/nestedRelationshipConstraints.test.js` pins authorization, iterator cleanup, missing-value behavior, and bounded entry reads.

- Single-record nested selections use `Resource.transformForSelect`; searches use `Table.transformEntryForSelect`. Only table records and `@relationship` targets project through a table's resolvers: a plain JSON sub-object, or what a `directReturn` (`@computed`) resolver returns, goes through the resolver-free `nestedSelectTransform(selector, undefined)`, because an outer resolver must never run against nested data that shares its name (search/single-record parity is pinned by `../unitTests/resources/searchSelectProjection.test.js`). Table `propertyResolvers` has a null prototype, so no lookup, the plain-column select fast path included, finds an `Object.prototype` member. Both transform caches are keyed by the selector, so one name selected twice with different sub-selects gets two transforms. A lone `*` returns the value unchanged, except a resource-backed `['*']`, which copies; mixed with names `*` copies data keys (a tracked instance's from `toJSON()`, none from a Buffer, Blob or Date). Positional and array projections settle as one promise, `forceNulls` applies after a value settles, function values project as absent, and a selected `__proto__` is read only as an own property. Missing targets, Dates and callable values are pinned by `../unitTests/resources/nestedSelectMissingValues.test.js` and `../integrationTests/resources/relationship-and-status-contract.test.ts`. The `select` branch in `parseBlock` (`search.ts`) unwraps a single-argument `select(x)` only when that argument is not a named sub-select, keeping a single nested selector (`select(rel{a,b})` or `select(rel[select(a,b)])`) wrapped in its outer array and preserving named bracket queries for table-relationship filtering while bare comparisons in selector lists remain syntax errors (pinned by `../unitTests/resources/query-parse.test.js` and `../unitTests/resources/restSelectProjectionFixes.test.js`); [harper#1415](https://github.com/HarperFast/harper/issues/1415) remains open for single-attribute `select(attr)` returning 404 when the selected scalar value is null or missing. Still open, outside these helpers: [a `__proto__` key poisoning a table, and proto-named attributes rejected at insert](https://github.com/HarperFast/harper/issues/1295).
- A record's `toJSON` is a response projection, not durable state. `recordUpdater` (and the cache-fill and audit paths feeding it) projects records to stored fields via `storedFieldsOnly`, so no durable form carries a resolver-owned (`@computed`/`@relationship`) name; materialization skips such names when promoting a decoded record (`assignStoredFields`), which is what keeps rows written by affected releases readable. See harper#2359 and `integrationTests/resources/cachedComputedAttribute.test.ts`.
- **Never** remove `transactional()` from a static method on `Resource` — it owns transaction context lifetime.
- New `Resource` subclasses should override **instance** methods (`get`, `put`, ...) for behavior; static methods are the protocol entry points and stay generic.
- The `transactional()` wrapper resolves pending bodies before `allowCreate`/`allowUpdate` and instance dispatch, passing the same concrete object to both. For POST/PUT/PATCH it collects async name/value pairs with `resolveBody.ts`; Node and Web streams pass through unchanged, and generic iterator parts with additional fields are rejected rather than silently reshaped; QUERY resolves before resource loading so its projection participates in `allowRead`. Other methods resolve promises without collecting iterables: CONNECT carries live messages and PUBLISH can carry stream payloads. Authorization is latched before awaiting ordinary write bodies, and record loading can overlap body arrival. Decoder failures remain 400/413 rather than being remapped to authorization failures. Table's direct promised-hook overloads remain supported; restricted arrays retain their concrete-record refusal and explicitly listed readonly fields retain full-PUT backfill. `../unitTests/resources/requestBody.test.js` pins resolution, object identity, authorization timing and live-message preservation.
- **Overriding a static entry point takes over its whole contract.** Assigning `static post`/`put`/`patch` on a subclass shadows the `transactional()`-wrapped static, so none of that wrapper runs — including body resolution and the `allowCreate`/`allowUpdate` gate. That is by design (it is how `login.ts` implements a deliberately pre-authentication endpoint), and it means an override owns two obligations the wrapper would otherwise have met: (1) **Resolve or consume `data`:** ordinary REST bodies arrive as a pending promise; multipart forms arrive as `AsyncIterable<{ name, value }>`, without an opt-in flag. A static override can consume parts directly or delegate to `super.post(target, data)` (likewise PUT/PATCH). The inherited wrapper collects fields and repeated names, materializing each streaming file into a replayable Blob before advancing. Multipart filenames are own enumerable properties, and Blob decoding restores that shape; Bun’s inherited name setter otherwise hides the filename from a later encoding. Generic iterator bodies use exact name/value pairs; opaque record iterators belong in a static handler or a record property. `resolveBody.ts` owns named-part aggregation; the multipart iterator's internal `RESOLVE_BODY` hook owns file consumption, avoiding an HTTP parser dependency in Resource. Raw streamed Blobs retain `createBlob(Readable)`'s existing storage-backed read contract: save them before reading, or delegate to materialize the form. Collection buffers up to the existing HTTP body limit; applications needing large streaming uploads should consume in a static override. `defineResource.ts` uses the same resolver before body-schema validation, and `login.ts` resolves streamed credentials explicitly. (2) **The override makes the access-control decision:** no `allow*` predicate runs for it; an override that is not meant to be public must check authorization itself.
- **FK-side relationship accessors (`relationship.from`) are a synchronous contract** (v4 parity). The resolvers built in `Table.updatedAttributes` must read through `getSync`/`getEntry` (which block on a RocksDB block-cache miss, like v4's LMDB page faults) — never `get()`, whose `async: true` path returns a Promise on a cache miss and would leak an intermittent value-or-Promise to `record.<relation>` in user code. Pinned by the "relationship property access is synchronous" test in `../unitTests/resources/query.test.js`, which stubs `store.get` to throw. Known gap: the `.to` side (`relatedTable.search(...).asArray`) can still yield Promises when the related table is a caching table whose row needs source revalidation ([harper#3588](https://github.com/HarperFast/harper/issues/3588)). **HTTP caching and relationship resolution** (pinned by `@relationship(from:) ETag / conditional GET invalidation` in `../unitTests/resources/restSelectProjectionFixes.test.js`): resolving a non-empty `relationship.from` foreign key marks the active request context uncacheable (`lastModified = UNCACHEABLE_TIMESTAMP`, skipping caching-source contexts) so single-record GETs with `select(...)` or `.property` projection do not emit a parent-only ETag or return a stale 304 after the target row changes, and `relationship.to` projections are likewise uncacheable through `relatedTable.search(...)` (`Table.ts`); **known gap:** `@enumerable` relationships (both `from` and `to`) that are not explicitly projected resolve inside `toJSON` during response serialization, after REST computes ETag/304, so a target row update can still produce a stale parent-version 304.
- **Queries read related records through the async-capable path; only the accessor is synchronous.** Under asynchronous iteration, a query that selects, filters on, joins through, or sorts by a relationship must not call the resolver's synchronous form, which blocks the worker once per related record that misses the in-memory caches; under synchronous iteration it must, because nothing can wait on a Promise there. Each relationship resolver also carries `resolveKeys` (the FK value, or the `to` index scan's ids) and `loadEntries` (the `returnEntry` result read with `async: true`, settling to a Promise when a read goes to storage; once one read does, the rest go at most `RELATED_READS_IN_FLIGHT` at a time, so one wide row cannot queue thousands of background reads). Consumers that map entries to values decide one-or-many by the resolver's `toMany` flag, not `Array.isArray`, because a single related record may have a composite (array) key; `filterMissing` is applied after loading. Pinned by `../unitTests/resources/relationshipAsyncReads.test.js`, which counts the related table's blocking and Promise-returning reads, including a real cold read (flushed SST, cleared record cache) on RocksDB; its filter and sort cases use a related attribute that is deliberately not indexed, because an indexed one makes the planner lead with an index join instead, which for a many-to-one relationship never reads the related record. **Select:** `Table.transformEntryForSelect` takes the related entries from `loadEntries` and projects them through the target table's select transform as before; the row's projection waits on the Promise. A selection with nested `conditions`, `sort`, `offset` or `limit` (`Table._prepareRelationshipSelection`) instead reads the related keys (`resolveKeys`, or a filter's matched ids) and loads each candidate with `async: true` ahead of its yield point, so cancellation still stops reads at the first yield. Loading them through `loadLocalRecord` instead measured about 0.3 µs per warm related row slower (`../unitTests/resources/relationshipWarmReads.bench.js`) and changed analytics and last-modified accounting. **Filter:** the relationship filter from `filterByType` keeps its synchronous form and adds a `maybeAsync` variant built on `loadEntries`; AND/OR groups and multi-hop paths chain through `maybeAsync`, and `transformToEntries` applies filters through it. The synchronous form stays for callers that need a boolean immediately: a custom index's pushed-down `recordFilter` and the synchronous join bodies used under sync iteration. One synchronous read path remains under a `maybeAsync` filter: the leaf comparator's adaptive switch to an index-derived id set (`attributeComparator`) scans the index and, for a `.to` relationship, reads each match with `getSync`. **Join:** a leading relationship condition's `joinTo`/`joinFrom` iterate the related search asynchronously under async iteration (`scanRelated`), reading related records with the query's read transaction; the scan is the only Promise a join returns. It stops, and yields nothing more, once its iterator is returned, as does the sorted post-ordering iterator. Request teardown (`closeOwnedReadIterators()`, the long-transaction monitor) releases the read snapshot through `onDone()` without returning the iterator, so after each awaited read both check `getReadTransactionGuard(readTxn)`, which throws the same `ReadSnapshotExpiredError` (503) or open-too-long error a RocksDB range read over a released snapshot does; `isDone` alone is no signal, because RocksDB handles never set it. LMDB, deprecated, keeps only the `isDone` check. **Sort:** `getAttributeValue` resolves relationship hops with `loadEntries`; the post-ordering iterator awaits the keys before sorting.
- **A combined `@relationship(from, to)` joins `related[to] == local[from]`, never the local primary key**, and only on an array-typed attribute (a scalar one is logged and gets no resolver). Four paths read `from` independently and must stay in step: the array resolver in `Table.updatedAttributes`, the index-driven join in `searchByIndex` (`joinTo` then `joinFrom`), the join-filtered select in `Table.transformEntryForSelect` (`resolver.from`), and a join filter's switch to an id set in `filterByType`. Pinned by the "@relationship with both from and to" block in `../unitTests/resources/query.test.js`, which uses a related record keyed by the local primary key as a decoy. Two more readers (`drivesRebuildingIndex`, the join estimate's `fromIndex` weighting in `estimateCondition`) affect only condition ordering, not join results, so they are not pinned by that block.
- When adding a new early-return path inside a commit handler in `_writeUpdate`, follow the blob-cleanup protocol in "Blob orphan cleanup" below.
- If you add a new top-level section to `Table.ts`, drop a `// #section: <name>` marker at its start and add a row to the section map above.
- **The table class's published type is the explicit `TableResourceClass` / `TableResourceInstance` pair in `Table.ts`, not the inferred class.** Both are deliberately unexported: the declaration file still carries them, but the user-facing name stays `Table`. TypeScript 6.0+ cannot write a declaration for the class `makeTable()` returns (TS4094 on its `#private` members, so no `Table.d.ts`), and 5.9 leaked those members as `"__#private@…"` keys. A new public member, static or changed signature on the class must be mirrored in the interfaces: the `_TableResourceMatchesItsDeclaredTypes` guard after the class fails `tsc` naming the member, comparing exact types (`resources/typeParity.ts`) because assignability lets `any`, dropped overloads and bivariant parameters through. `#private` state and closure variables need no entry. `unitTests/types/tableClass.type-test.ts` pins the consumer side (subclass overrides, typed statics, no private keys).
- Tests for this layer live in `../unitTests/resources/`.

## RecordObject prototype and entryMap

Records stored in tables are plain objects given a `RecordObject` prototype, which provides `getExpiresAt()` and `getUpdatedTime()`. These methods read from `entryMap` (a `WeakMap` in `RecordEncoder.ts`), which maps each record object to its storage entry.

- `RecordObject` is a shared runtime base class; every encoder creates an isolated `StoreRecordObject` subclass for its `structPrototype`, so table-specific computed getters do not leak across tables. Structon records inherit that prototype during decode. Classic msgpackr records decode as plain objects and are promoted by the store read wrappers before Harper exposes them.
- On LMDB the promotion runs before lmdb-js caches the value (`handleLocalTimeForGets` wraps `store.cache.setValue`): a cache entry is a WeakRef that readers such as the search transform `deref()`, and its target cannot change once created, so it must already be the promoted record (`unitTests/resources/lmdbPrefetchComputed.test.js`).
- Use `record instanceof RecordObject` when behavior must apply to either exposed representation. Do not use `entryMap.has(record)` as a record-type test: `entryMap` exists for storage metadata, and some range-read paths can prototype-promote a record without registering that mapping.
- Point reads and other paths that need storage metadata call `entryMap.set(record, entry)` when exposing a record.
- To give a plain JS object the RecordObject prototype without copying it (preserving mutability), use `Object.setPrototypeOf(obj, primaryStore.encoder.structPrototype)` then `entryMap.set(obj, entry)`.
- Do **not** copy the object (e.g. via `Object.assign` into a new instance) if any code still holds a reference to the original and expects to mutate it — see below.

## Struct mode is gated to primary DBIs (downgrade compatibility)

`RecordEncoder` extends a structon encoder, whose random-access "struct" encoding uses header bytes in `0x20–0x3f`. That range overlaps msgpack positive-fixints, so a reader without struct support (msgpackr v1, i.e. harperdb v4) decodes a struct header as an integer. harperdb v4 only enabled struct mode (its `randomAccessStructure` option) on **primary** DBIs, so non-primary DBIs — notably the `__dbis__` metadata store (table/attribute defs) — were plain records mode. If v5 writes `__dbis__` in struct mode, a v5→v4 downgrade can't decode the metadata, silently treats the instance as a fresh pre-3.0 install, and refuses to boot.

To match v4: `OpenDBIObject` sets `randomAccessStructure = isPrimary`, and `RecordEncoder`, when `randomAccessStructure` is false, makes the struct **write** hook bail (`this._writeStruct = () => 0`) so objects are written in records mode. Two subtleties:

- We **bail** the hook (return 0) rather than clear it (`undefined`). Clearing it shifts msgpackr's positive-fixint boundary from `0x20` to `0x40`, so top-level integers `0x20–0x3f` (e.g. a `NEXT_TABLE_ID` ≥ 32 stored in `__dbis__`) would be written as bare fixints — which the still-installed struct **read** hook misreads as struct headers. Bailing keeps the boundary at `0x20`, so those integers are written as `uint8`.
- The struct **read** hook is left intact, so records a prior v5 already wrote in struct mode still decode (read-compat); only new writes switch to records mode.
- Companion change in `structon`: `prepareStructures` saves the shared structures in the legacy plain-array form when there are no typed structs (instead of the `{named, typed}` Map), so the `Symbol.for('structures')` buffer for a records-mode `__dbis__` is also v4-decodable.

## Non-`initStore` structure saves read inside their own transaction (`PrimaryRocksDatabase`/`RecordEncoder`)

A `PrimaryRocksDatabase` store that never runs `initStore` (notably `__dbis__`) binds `encoder.rocksStore` in `open()` so `RecordEncoder.saveStructures` reads `sharedStructuresKey` inside its compare-and-put transaction, pinning the optimistic snapshot before writing instead of falling back to `rocksdb-js`'s untracked read, and writes pre-encoded bytes (`asBinary`) so `txn.putSync` never re-enters the active `RecordEncoder.encode` mid-pack. `encoder.isRocksDB` must never be set on `__dbis__` because it moves the structure key to `[Symbol.for('structures'), name]` and strips leading byte `0x42` (classic structure `#2`) as a RocksDB version header (`unitTests/resources/recordEncoder.test.js`).

## getFromSource() timing: promise resolves before commit runs

In `getFromSource()` (`Table.ts`), the promise that callers await resolves with the entry **before** the `dbTxn.addWrite` commit callback runs. So `@updatedTime` and `@createdTime` are stamped on `updatedRecord` before it resolves: the caller, a `noCacheStore` read and the model hooks see the stored values (but see the limit below) (`resolvedVersion` is the version a write that is not skipped commits at). The commit never mutates or reassigns `updatedRecord`: it builds its own `recordToStore` (a residency stub, or a copy carrying the created time of a record that landed during the source call), because the caller holds the object and a retried commit must start from the source's answer. It decides residency before `updateIndices`, so the indexes describe exactly the stored value (`unitTests/resources/sourceFillIndexes.test.js`, both engines). Known limit: in that raced first fill the caller's record and the model hooks carry the fill's own created time, not the stored one (a put's hooks never see the commit-time stamps either). The sharing cuts both ways: the caller's mutations are visible to the **commit**, which encodes whatever the object holds at commit time. A downstream consumer that mutates the resolved record before the deferred commit runs corrupts what gets persisted — `finalizeResponse` (`server/REST.ts`) did exactly this, overwriting `.headers` with a web `Headers` (no enumerable own keys → stored as `{}`) and stamping `.status` (#1702; LMDB-only because RocksDB commits encode synchronously). Consumers must copy before mutating; `finalizeResponse` now copies any `entryMap`-tracked record.

## getFromSource() waiters share a fill that stored nothing

A same-thread waiter that finds nothing valid in the store after the leader unlocks serves the leader's entry instead of calling the source again. Only a fill that resolved, committed and kept its write publishes one, and only if the record is copyable plain data (no stream, iterator, Headers or blob; checked once, within a budget) and the source did not set `noCacheStore` (per-request; preset on read-only nodes and dropping tables). A record a request-level `noCacheStore` kept out of the store goes only to waiters that asked for `noCacheStore` too. Failures, stale-on-error answers, a fill from another `source` and other threads' waiters are never shared. Pinned by `unitTests/resources/sourceFillCoalescing.test.js`.

## getFromSource() keeps source versions separate from fill ordering

`getFromSource()` reserves a fallback timestamp before calling the source so competing first fills
whose source does not report a version have a stable ordering token. An inherited request/transaction
timestamp is used when present; otherwise the storage engine supplies a monotonic timestamp. After
the source responds, a valid positive, finite, Date-representable `sourceContext.lastModified` is the
record's candidate version, and the reserved timestamp is only its fallback. A 304 retains the
existing version.

The candidate is capped at local time (`max(reserved token, Date.now())`). A record's version is also
this node's ordering token — `precedesExistingVersion()` compares a write's transaction timestamp
against it — so a source that reports a `lastModified` ahead of local time (a skewed origin clock)
would otherwise make every later local write to that row look out-of-order and be discarded until
wall-clock caught up. Capping costs the shared-version property only for that misbehaving case, and
the cap is logged.

The ordering token is not installed on `sourceContext.timestamp`: the source-resolution transaction
keeps its own default timestamp, so a slow fetch does not backdate its transaction-log entry. LMDB
stores the source candidate directly, preserving its separate source-version/local-time semantics;
only RocksDB clamps a non-advancing candidate because it uses one version for both roles.

Revalidations retain exact-CAS semantics, and a source miss cannot delete a record that raced the
fetch. First fills may replace a raced record only when their candidate version is strictly greater
than the raced record's. The comparison is deliberately not `precedesExistingVersion()`: that breaks
a version tie with the _executing_ node's name, and a fill from a shared source carries no node
identity of its own, so two replicas resolving the same tie could keep different values at the same
version — the one state anti-entropy cannot repair. On a tie the raced record wins on every replica. A
RocksDB replacement whose candidate cannot advance the current version stores at the current version
and carries `VERSION_REUSED` (`resources/RecordEncoder.ts`, aliasing rocksdb-js's own
`VERSION_NOT_UNIQUE_FLAG`); rocksdb-js 2.8.0 ([#766](https://github.com/HarperFast/rocksdb-js/pull/766))
then refuses to publish or confirm that version through the VerificationTable. This avoids inventing
an epsilon timestamp solely to force replacement while keeping stale record-cache values from being
vouched as fresh.

The flag is applied generically to every RocksDB record write whose version does not advance past
the record it replaces (`recordUpdater` in `RecordEncoder.ts`), not just this source-fill path — an
ordinary resequenced (out-of-order CRDT-merged) write gets it too. Those records remain ineligible
for VerificationTable fast-path confirmation until a later write advances their version.

The native layer reads the stored bytes itself: the big-endian version at offset 0, then a big-endian metadata word at offset 8 tagged `0x0E` (`ACTION_32_BIT`), with the flag at literal bit `0x10000`. The bit is persisted, so it cannot follow a renumbered rocksdb-js constant without a migration. `unitTests/resources/caching-rocks-database.test.js` ('marks a record whose version was reused…') pins the layout against raw stored values.

A fill's puts carry no condition of their own: on LMDB the `LMDBTransaction` `ifVersion` block holds
the condition with the primary, index and audit puts in one native write transaction (a per-put
`ifVersion` cannot stop the index writes, and on the unversioned audit store it drops the write); on
RocksDB a conflict retries the commit handler. A write the source makes to the same key through its
context joins the fill's transaction, where neither check sees it. RocksDB reads the fill's
`existingEntry` through that transaction; LMDB's optimistic path reads the committed record, so on
LMDB the fill yields to any earlier same-key write not skipped (`followsAppliedWrite`), and a no-op
`update()` removed at validation leaves the per-key chain (`LMDBTransaction.removeWrite`). On LMDB an
invalidated record keeps its local time only while its audit entry exists to be replaced
(`recordUpdater`), since an appended entry is keyed by the last assigned time.
`unitTests/resources/sourceFillConditionalWrite.test.js` pins both engines.

## getFromSource() record locks outlive neither their handle nor a close (`Table.ts`)

A fill holds a native record lock (`primaryStore.tryLock`) while it awaits the source, and a database close does not wait for it: the close drains only submitted commits. Closing the handle that owns the lock releases it and wakes its waiters: rocksdb-js `DBHandle::close` → `lockReleaseByOwner`, lmdb-js `EnvWrap::closeEnv` (an LMDB close closes the environment, never the dbis). So an unlock that throws on a closed store has nothing to release, and `releaseRecordLock` treats it as a no-op. Two consequences for waiters: the `tryLock` callback only wakes the request (it can fire during the close, where reading the store throws inside a native callback), and the `LOCK_TIMEOUT` timer wakes it too, because closing this thread's handle never notifies a wait on another thread's lock. `unitTests/resources/cacheFillClose.test.js` covers both engines.

## Blob orphan cleanup: pre-saved files outlive cancelled commits

Blobs flagged with `saveBeforeCommit` (or `saveInRecord`) are written to disk in the `beforeIntermediate` phase of a `TransactionWrite`, _before_ the LMDB/RocksDB write commits. The write's commit callback can still skip the actual record write — for older versions, supersedence by future updates, residency mismatches, or full transaction abort. In every such path the file is on disk but no record references it.

The mitigations live in three places:

- `startPreCommitBlobsForRecord` (`blob.ts`) returns the blob list alongside its completion callback so each `TransactionWrite` can attach a `savedBlobs: Blob[]`. `cleanupUnusedBlobs(blobs)` (`blob.ts`) waits for each blob's `saving` promise to settle, then `deleteBlob`s the file — it clears the input list so it's idempotent across repeated calls (e.g. an early-return that also gets caught by the abort path).
- `Table.ts` commit handlers set `write.skipped = true` (and reset to `false` at the top of each invocation) on early-return paths that don't write the record/audit: duplicate-tie, superseded-by-put, no-audit-fullUpdate-loses, a no-audit out-of-order patch that ties the head, meets a head with no record (a delete tombstone or publish entry it must not undo), is already listed in the head's `receivedIdentityRefs`, or is left with nothing after `remainingAgainstRecord` (only commutative ops and keys the record lacks merge; a partial merge sets `write.superseded` so blobs of the dropped keys are reclaimed against the committed record), a losing invalidate, relocate or delete, and cache-resolve version-changed. A skipped write's `replicatedConfirmation` falls back to the stored entry's version (harper#3182), so an unmarked early return would be treated as a write that replicates nothing. The transaction commit success paths (`DatabaseTransaction.commit` and `LMDBTransaction.commit`) walk writes and call `cleanupUnusedBlobs(write.savedBlobs)` for every still-skipped write, except on RocksDB when its appending handle committed or has a durable log and that write staged an audit entry referencing the files. A retained read snapshot can force replay onto a fresh handle: its abandoned, unsubmitted audit batch owns no files, even if `blobsAuditReferenced` remains set. Cleanup is deferred (rather than run inline in the commit handler) because the commit handler runs again on optimistic-lock retries, and a retry can flip a previously-skipped write into a successful one (e.g. the existing record gets deleted between attempts so the older replicated update suddenly wins). Inline cleanup would race the deletion's `setTimeout` against the retry that referenced the blob.
- `LMDBTransaction.abort` and `DatabaseTransaction.abort` walk all writes and run the same cleanup unconditionally (regardless of `skipped`), since nothing was committed — except on `DatabaseTransaction` when the aborted handle already has a durable transaction-log entry (`hasDurableLog(targetTransaction)`), whose logged entry may still be replayed or replicated, or when concurrent immediate commits share one `ImmediateTransaction` and sibling writes belong to another in-flight handle (`targetTransaction`). `DatabaseTransaction.commit` adds an explicit reject handler so a `Promise.all` failure on `completions` (e.g. a blob save errored) aborts the underlying transaction instead of leaking it _and_ the blob files. Both engines funnel synchronous throws and returned rejections from the whole commit chain through that cleanup once (`abortAfterCommitError`); LMDB captures `next` before its success path detaches the link, so a child's rejection still closes every uncommitted link. The cascade skips a link whose native commit is still outstanding — clearing its writes would unlink blobs that commit still references.

**A blob instance outlives its file, so deletion tombstones it.** The `fileId` stays set on a `Blob` whose file has been unlinked, and `saveBlob` short-circuits on a set `fileId` — so a caller still holding the instance (the deploy recorder re-puts the same record object across a deploy) would re-encode a reference to a file that is gone. `cleanupUnusedBlobs` marks the blob's shared file state when transaction cleanup decides the file is no longer usable, before an in-flight save settles; slices share that state with their source. Ordinary supersession keeps its retention and re-reference window; reclamation marks every queued instance only after it claims the unlink. `saveBlob` throws on a discarded instance rather than minting a second reference (issue #2062).

When adding a new commit-handler early-return path, reset `write.skipped = false` per round and set it to `true` only when the round stages neither a record nor an audit entry. If this round stages an audit-only entry via `auditRecordToStore`, leave `skipped` unset. Pass the write to `updateRecord` as its `write` option: `recordUpdater` records the entry it appends on `write.stagedAudit`, from which staging derives `appendedTo` and the confirmation checks read eligibility (below). An earlier attempt's committed or durable audit entry can still own a skipped retry's blobs; RocksDB cleanup checks `blobsAuditReferenced` and the appending handle's durability. Unsubmitted staging owns no files. The manual `cleanup_orphan_blobs` operation is the orphan-recovery safety net; don't rely on it for transactional correctness.

**A removed record's blob files go only once its removal commits.** `removeEntry` (`RecordEncoder.ts`) decides from what `store.remove` returns: a promise gates the unlink on its resolution, anything else is taken as already durable. A RocksDB removal staged in a transaction (`{ transaction }`) returns nothing, so through `removeEntry` its blobs are queued for reclamation at staging time, and an abort leaves the record pointing at files reclaimed `storage.blobRetention` later. `getFromSource()`'s source-miss removal and RocksDB `evict()` therefore stage the removal themselves and delete the removed record's blobs from their own commit completion, keeping any file the record now stored at that key references (queueing a file for reclamation clears its re-reference signal), so an `ERR_BUSY`-abandoned eviction reclaims nothing; `_writeDelete` and `updateRecord`'s superseded-blob deletion still go through the staging-time path ([#2861](https://github.com/HarperFast/harper/issues/2861), [#3367](https://github.com/HarperFast/harper/issues/3367)). `evict()` reads the entry in its own transaction and skips a version other than the one its caller read on every table, not only audited or sourced ones: the read path and the cleanup scan's blob bypass hand it a record read earlier (`evictionBlobs.test.js`). A reused RocksDB version (`VERSION_REUSED`: a resequenced write, a 304 revalidation, a replica store) proves nothing about the value, so eviction also requires the metadata expiry its caller read — the one read-hiding uses — to still be the entry's own: `evict()`'s `observedExpiresAt` (passed by every deferred caller, checked before a TTL demotion; omitted, only the version is checked) and the batch item's scanned `expiresAt`. The `@expiresAt` sweep decides on the field but passes this metadata expiry too; validating the field is left to making that sweep run on RocksDB ([#1481](https://github.com/HarperFast/harper/issues/1481)). The batcher also re-checks the scan's `HAS_BLOBS | REPLICA` routing on the entry it stages: a same-version write can add a blob after the scan sent the record toward `removeEntry`.

**Source-unavailable blobs must not abort the commit.** `startPreCommitBlobsForRecord().complete()` awaits each blob's `saving` promise; a rejection there propagates up and aborts the record's apply (the replication subscription loop catches and logs it as `error in subscription handler`). For a blob the replication source can no longer provide — evicted/expired at the origin, the receiver having flagged the rejection `sourceBlobUnavailable` (harper-pro#403) — that abort permanently wedged a replication copy stream on an expiration cache table whose TTL-evicted blobs are gone everywhere: every orphaned record's apply re-threw, the copy never advanced, and backpressure pinned at ~100%. `complete()` therefore tolerates a `sourceBlobUnavailable` rejection (`isSourceBlobUnavailable`): the record commits with a diverged blob reference, left for proactive backfill (harper-pro#388). Local/transient save faults stay unmarked and still reject, so the write aborts and a reconnect retries it — no silent loss. This is the apply/commit-side complement to the replication receiver's resume-cursor advance (harper-pro#403/#405), which handles the durability-watermark side of the same missing blob.

## Blob compression: policy at `saveBlob`, completeness via the writer lock, codec is per-file truth

Opt-in deflate compression for file-backed blobs (harper#2443) has three load-bearing placements. **Policy resolves in `saveBlob`, not `createBlob`:** every local blob write funnels through `saveBlob` (the msgpackr pack extension, pre-commit saves, native-Blob saves), including the HTTP-upload path, which never sees creation options — an explicit `compress` option or a pre-compressed source (`storedCodec`) still wins. The shipped `false` entries for already-compressed types merge under the operator's `storage.blobs.compression` map with same-key-operator-wins and exact-beats-wildcard precedence; unknown-size streamed writes never compress (a threshold cannot be evaluated without a size). **A compressed body's completeness authority is the writer lock, never its length:** the 8-byte header records the _uncompressed_ size, so the streaming read path (`stream()`'s `readCompressedBlob`) waits for the lock like `bytes()` always has. After the wait it checks **file identity** — `fstat` on its descriptor vs `stat` on the path — because an in-place repair renames a fresh (uncompressed) file over the path while holding that same lock, and can do so either during the wait or in the gap between the first read and the lock probe (so "did we wait" is not a reliable signal). If the inode changed, the descriptor is orphaned: it reopens the path (nulling `fd` before closing the stale descriptor, so a racing `cancel()` cannot double-close a reassigned fd, #1457) and re-reads the header — a repaired (now uncompressed) header is reported retryable 503 so a re-read serves the new file, matching `openStoredBlobBody`. If the inode is unchanged the descriptor is kept and the same-fd re-read still catches an in-place PENDING/ERROR stamp (harper-pro#481). It then inflates with a hard output ceiling at the declared size — a header that lies small is refused before emitting past it, and a clean deflate end short of the declared size is a torn body (500), not a short read. **The header type byte is per-file local truth:** the `storedCodec` hint stamped into stored blob-ref options is only a cheap prefilter for replication senders — every node re-encodes blob refs with local fileIds on apply, and `openStoredBlobBody`/`createBlobFromStoredBody` verify the actual bytes by concurrent inflate (sender: torn body → loud permanent error before the terminal frame; receiver: reject-before-publish), so no relayed metadata can ever mislabel a file. Both concurrent-inflate verifiers settle their pipeline from the inflater's `error`/`close`, not only from the per-chunk `write` callback: a mid-stream `Z_DATA_ERROR` (a corrupt, not merely truncated, body) fires `error`/`close` but never invokes the pending `write` callback, so a verifier waiting only on it would hang the write pipeline forever (receiver) or suspend the send generator with its descriptor and file hold un-released (sender). Do not "simplify" either to await only the write callback. **In-place repair classifies a compressed body once, unlocked and async, and confirms it locked by identity:** a deflate body torn by an unclean shutdown carries a finalized header recording the uncompressed size, so a length-only gate declines exactly the repair compression makes common — `blobFileMissingOrIncompleteAsync` inflates (streamed, output bounded at the declared size) and records the damaged file's `(length, header)` on its storage info; the locked sync recheck `blobFileMissingOrIncomplete` never inflates on the event loop and answers `true` for a deflate body only while length and header still equal that observation (writers only append and repairs replace the file, so unchanged length + header means unchanged bytes), otherwise `undefined`, which declines. Callers (harper-pro's copy-delivery repair) must probe async first. `openStoredBlobBody` sniffs synchronously (lock probe + header) but its `stream()` opens its own descriptor and re-reads the header — a mismatch means the announced form is gone (a repair rename landed) and is reported as a transient 503, not a corrupt body. Read streams own their descriptors in path mode — sharing an fd with an fs stream races its worker-thread `close(2)` (EBADF); the blob hold keeps the path alive instead.

## Over-time transactions are aborted, not force-committed (`DatabaseTransaction`/`LMDBTransaction`)

`startMonitoringTxns()` (a `setInterval` per engine) watches `trackedTxns` and acts when a transaction's `timeout` reaches 0 (after ~2 ticks of `STORAGE_MAXTRANSACTIONOPENTIME`, default 30s). A transaction is tracked once it acquires a read snapshot (`getReadTxn`), and leaves only through its own `commit`/`abort`/`doneReadTxn`/`releaseReadTxn`. Code that commits or aborts a native handle itself opens it raw (`new RocksTransaction(store)`: `Table.evict` on RocksDB, the eviction batcher, `PrimaryRocksDatabase`), never through a wrapper's `getReadTxn`: the wrapper would stay tracked, counted in `getTransactionQueueDepths().readDepth` and reportable as a long-lived holder, until the monitor reaps it, and its coordinated-retry handle resolves a conflict as `RETRY_NOW` and stays open instead of rejecting with `ERR_BUSY`.

- **Write-bearing request transactions are aborted and poisoned** (issue #1407). The monitor calls `abortDueToTimeout()`, which sets `timedOut`, forces `open = CLOSED` (so `doneReadTxn` takes the discard path instead of re-entering `commit()` via the `LINGERING` branch — which would now throw), then `abort()`s. `addWrite`/`commit` both guard on `timedOut` and throw `transactionOpenTooLongError` (503), so the in-flight request rolls back cleanly rather than the monitor silently force-committing a partial write set (atomicity violation + orphaned secondary-index entries that only a full rebuild repairs). The old behavior `commit()`d and reused the still-open transaction. `hasPendingWrites()` walks the `next` chain to decide this: writes to a second database live on `transaction.next` (see `txnForContext`), so a transaction that reads database A (head, tracked via its read snapshot, empty `writes`) and writes database B (`next`) is still write-bearing — without the walk the head looks read-only and the monitor's force-commit path would cascade-commit B, so `abortDueToTimeout()` poisons + aborts the whole chain instead. **Read-only, `sourceApply`, and `isReplay` transactions keep the prior force-commit behavior:** read-only long transactions (large scans/exports) have no atomicity/index risk and must not have their ongoing reads poisoned; canonical-source applies (replication peer / external caching source) and crash-recovery replay have no resubscribe/resume path, since aborting a write would drop it while the resume cursor advances past it — a permanent divergence (harper-pro#348). `sourceApply` is propagated down the `next` chain in `txnForContext`, so gating on the head suffices (replay is additionally synchronous, so the async monitor can't fire mid-replay anyway).
- **The owner's commit waits for the monitor's force-commit, and a transaction parked in its commit phase is spared, not poisoned** (issue #2062). That commit claims every staged write, marks the transaction `CLOSED`, and detaches its handle, so the owner's later `commit()` finds nothing to do. The monitor therefore stores the promise it got back as `monitorCommit`: `commit()` chains on it and the monitor clears it on success. A failure is kept until the owner's final (`doneWriting`) commit rejects with it and releases the context, since the monitor itself only logs it. That release is deliberately not `abort()`: a multi-store commit can fail after its head store landed, and `abort()`'s blob cleanup would unlink files the head's audit entries still reference. A landed store always finishes its own bookkeeping (writes cleared, record locks released) before a chained store's failure surfaces, including a synchronous throw from `next.commit()`. Separately, `commit()` sets `committing` around its pre-commit await (the `before`/`beforeIntermediate` completions — in practice a blob's durable file write) and the monitor logs instead of aborting while it is set. The limit polices an _application_ holding a transaction open with an unfinished write set; once `commit()` is entered the write set is sealed and the caller is awaiting the commit, so the time is core's own I/O, and a multi-tens-of-MB deploy payload legitimately outruns the limit. Poisoning there was actively destructive: `abort()` cleared the write set and unlinked the write's pre-saved blobs, and the resumed commit then found nothing to write and resolved as **success** — the caller was told its write landed, and was left holding a blob whose file was gone but whose `fileId` was still set, so its next `put` silently minted a reference to a destroyed file (the deploy-payload case: `Blob file not found` on the peer, unrecoverably). The grace is bounded — `COMMIT_PHASE_GRACE` over-limit ticks, ~10 min at the 30s default, since sparing re-arms `timeout` — because the transaction still pins a read snapshot; a source that stalls rather than finishing falls through to the normal abort. `sourceApply`/`isReplay` are spared without a bound: they may be neither aborted (harper-pro#348) nor force-committed mid-write (that would durably commit a replica record whose blob file is still being written), and their blob sources are bounded by the receive-side idle watchdog instead.
- **Resuming from that await re-checks that the transaction is still alive, but a submitted native commit is never aborted by the monitor.** `timedOut` (monitor poison, including via the `next` chain) throws `transactionOpenTooLongError`; a write set cleared with the handle released — a plain `abort()` in the same window — throws `Transaction was aborted while its commit was waiting on pre-commit work`. Without both, either path resolves as a phantom commit. `LMDBTransaction.commit` carries the same pair around its own `before` phase. Past the limit a submitted commit is deferred instead: after a short diagnostic grace the monitor poisons fresh ordinary follow-up work on the chain (`poisonAfterStalledSubmittedCommit`), reclaims read snapshots separate from the submitted writes, and logs once that the worker may need a restart. `sourceApply`/`isReplay` are observed, never poisoned. A pre-submit attempt on an already-poisoned link gets no commit-phase grace (`commitAttemptDoomedByPoison()`): its continuation throws on the resume check above, so sparing it would only pin its snapshot.

**Extending the budget for one known-long write:** `DatabaseTransaction.timeoutBudget` is a per-transaction RocksDB floor applied whenever the transaction is re-armed (initial reads, writes, and active multi-store-chain propagation); the effective timeout is `Math.max(txnExpiration, timeoutBudget)`. This makes the budget sticky across a write's pre-commit existing-entry read and later writes, while never shortening a larger global `STORAGE_MAXTRANSACTIONOPENTIME`; RocksDB links added for another store inherit the same floor. Reads after a pending write do not re-arm the transaction: that preserves the idle-limit invariant for orphaned write-holding requests. Also, `resources/transaction.ts`'s `transaction(callback)` (no explicit context) joins whatever transaction is already open on the ambient AsyncLocalStorage context rather than guaranteeing a fresh one. `components/deploymentRecorder.ts`'s `withIsolatedTransaction` builds a new context from only the ambient audit/session fields — not the request `signal`, so a deploy client that stops waiting cannot cancel the tracking writes and strand an `hdb_deployment` row mid-phase (see the disconnect note below) — and every recorder write commits independently without inheriting transaction controls. It uses the sticky budget to give `ingestPayload`'s blob-gated writes a size-appropriate limit instead of the generic default, while coalesced progress flushes are drained and suppressed until ingest settles to avoid same-row transaction conflicts. The ingest helper deliberately floors the shared `deployment_timeout` at ten minutes because `0` means “poll once” for peer waits; consequently an ingest can pin its system-database snapshot for that minimum. Known gap (harper#2057): the extension only reaches RocksDB transactions — on `HARPER_STORAGE_ENGINE=lmdb`, `Table.txnForContext()` chains a separate `LMDBTransaction` (`txn.next`) with its own independently-reset timeout that the LMDB engine's monitor tracks instead. **A commit's conflict retries have their own deadline, separate from the open-transaction limit** (issue #2450). rocksdb-js ≥2.8 wakes a commit parked on another transaction's write intent after `ROCKSDB_JS_PARK_TIMEOUT_MS` (5s) and returns `RETRY_NOW_VALUE` even when the holder never releases, so a wedged intent presents as a stream of transient conflicts rather than one hung commit — and the `MAX_RETRIES` cap alone then keeps the request pending for ~40 park timeouts, minutes past the configured queue limit. `DatabaseTransaction.commitStartedAt` is stamped on the **chain root** (or on the `ImmediateTransaction` instance while a single handle is active, migrating onto the per-write native `RocksTransaction` handle when concurrent commits overlap or a late immediate commit runs on a closed request scope) at its first native submission and read at both retry decisions (the coordinated `RETRY_NOW_VALUE` resolve path and the `ERR_BUSY`/`ERR_TRY_AGAIN` rejection path); past `Math.max(STORAGE_MAXTRANSACTIONQUEUETIME, timeoutBudget)` an unlogged commit takes the existing `abortChainAfterRetries()` cleanup and throws a 503 `TransactionCommitConflictTimeoutError`. One clock per _logical_ commit, deliberately not per attempt: the per-attempt clock is `trackOutstandingCommit()`'s, which measures native liveness and drives `checkOverloaded()`'s thread-wide shedding, so back-dating it would let one uncapped `sourceApply` retry shed every unrelated request on the thread. The clock is released through the promise `commit()` returns (which settles only after the chained stores' commits), so a reused transaction's next batch starts fresh. `retryable` is true only on a chain root that has rotated through no mid-scope commit — anywhere else an earlier store already wrote durable audit entries and ran its hooks that a replayed request would repeat. `sourceApply` is exempt, as it is from the attempt cap, for the harper-pro#348 divergence reason above.

- **Once a transaction has a durable transaction-log entry, it is never aborted on retry** (harper#3236). In rocksdb-js, `Transaction::Commit` flushes staged `TransactionLog` batches (`executeLogWork`, assigning `committedPosition`) _before_ `txn->Commit()` checks optimistic conflicts; on conflict the handle resets onto a fresh snapshot while keeping `committedPosition > 0` so the log is write-once (rocksdb-js#668), and aborting it throws `ERR_TRANSACTION_ABANDONED` and orphans a durable log entry that live reads miss while subscriptions and `replayLogs()` apply.
  - **Per-handle invariant:** once a handle's first native commit returns a conflict (`hasDurableLog(transaction)` = `isRetry && hasStagedLog`, evaluated per native handle so an unlogged link in a multi-store chain still respects `suspendDatabaseCommits` and retry bounds), `DatabaseTransaction` treats it like `sourceApply`: the caller stays awaiting an uncapped retry (so the #2450 deadline and 40-attempt cap apply only before the first log flush or on `audit: false` tables), record-lock lease-expiry aborts are skipped while post-expiry/release native unlock is deferred up to the conflict budget, `deferForCommitInFlight` reclaims separate read snapshots without poisoning or logging the unknown-outcome restart error, and `ImmediateTransaction` stages only writes whose `save()` has been invoked while isolating per-commit state on the native handle when concurrent commits overlap.
  - **Operational cost:** while a logged retry waits on a conflicting write intent (which `abortDueToTimeout` clears after ~2 ticks of `STORAGE_MAXTRANSACTIONOPENTIME` if held by an unsubmitted open transaction), its position in `uncommittedPositions` pins the database's `'local'` transaction-log read watermark for live subscriptions and replication (reported by `noteOverdueLoggedCommit`), the caller awaits convergence without a 503-pending or detached background commit, and `waitForDrain()` holds across retry backoff delays up to its 120s deadline.
  - **Native follow-up (harper#3253):** validating conflicts before `executeLogWork` so a conflicting commit never flushes a log entry or pins the read watermark, exposing `committedPosition`, and reconciling non-conflict or post-drain aborts live in rocksdb-js.

## A client disconnect cancels the request's writes (`resources/transaction.ts`)

`transaction()` treats `context.signal` as the request's lifetime (harper#2001): once it aborts, the request stages no further writes, in this transaction or any later one opened on the same context — a static call joining a poisoned context transaction (`Resource.ts`), a fresh `transaction(context, cb)` on the aborted signal, and a retained instance writing after its scope completed all fail alike. Without this, an orphan keeps its staged writes and native write intents until the monitor sweeps it, and in the incident behind harper#2001 one held past a disconnect wedged a conflicting commit on the same worker. Work that must outlive the client runs on a context built without the signal (`components/deploymentRecorder.ts`); background work must not be armed inside a request's `AsyncLocalStorage` context for the same reason — the analytics flush is armed through `contextStorage.exit()` (`resources/analytics/write.ts`).

- **Poisoning reuses the monitor's path, and cancellation is enforced where a write is admitted — but native submission, not entry into `commit()`, is the point of no destructive return.** `abortDueToDisconnect()` shares `abortAndPoison()` with `abortDueToTimeout()`: poison every link of the `next` chain, then abort each, and `addWrite`/`commit` throw `requestAbortedError` (499); `sourceApply` is never poisoned (no resume path, harper-pro#348). Every transaction created for a request carries its `signal` as `requestSignal` on the chain root — set by `transaction()` and by `txnForContext`'s per-context self-committing transaction. `admitRequestWrite()` runs in both engines' `addWrite` and in each deferred-save admission: an aborted signal poisons the chain and the write is refused; otherwise the first admitted write subscribes the chain root to the signal, and the listener is released once the chain's writes and commit attempts have settled — so a disconnect releases staged writes at once on every path that holds them, including a self-committing write parked in pre-commit work, while a read-only request registers no listener and always completes. A poison landing while a submitted attempt is in flight (`commitsInFlight` plus the chain root's submission marker) flags the chain but aborts nothing, so the attempt reaches its native outcome instead — aborting would race cleanup against an unknown outcome and unlink blobs a successful commit references (#2062), so a submitted write can land after the client is gone. For a disconnect the boundary covers the whole chain: once any store has submitted, the chain's unsubmitted stores ride the cascade already under way instead of being aborted, so the logical commit never splits across stores (#1407); the monitor still aborts an unsubmitted store independently, because it only reaches one whose pre-commit work outlived its grace.
- **Transaction-owned iterators are tracked and closed when unreachable, and an abandoned scope keeps its handle to its own outcome.** `Table.search()` registers each result set with the transaction owning its read reference; `closeOwnedReadIterators()` runs their `onDone` across the chain. `transaction()`'s error path closes them (nothing was returned to consume them) and both monitors' `CLOSED` arm is the backstop, force-releasing a handle that closing does not return. A scope whose unawaited commit is still in flight when its callback throws is abandoned, not aborted (`abandonScope()`): the attempt keeps its handle and reaches its outcome, and the instance is closed and taken off the context so nothing joins it. **Coverage:** `Request`/`UwsRequest` supply the signal for HTTP and Node/Bun WebSockets, and `server/http.ts` drives the uWS WebSocket upgrade's signal from the adapter's `'close'`; MQTT contexts carry no `signal` (`server/DurableSubscriptionsSession.ts`), so MQTT is not covered. Tests use synthetic `AbortController`s (`unitTests/resources/txn-tracking.test.js` `Disconnect abort`, `unitTests/resources/transactionCommitBoundary.test.js`); no end-to-end socket test exists.

## `X-Replicate-To` and the `replicateTo`/`replicatedConfirmation` operation fields are super-user only, gated where they enter (`server/REST.ts`, `verifyPerms`)

`context.replicateTo` sets a legacy table's written-record residency (`Table.getResidency`; `0` pins it to this node); a declarative table uses its installed slot map instead and `context.replicatedConfirmation` makes either engine wait on peer acknowledgement after the write is already durable (`transaction.ts` → `confirmReplication`) — for the first database the request writes only; its LMDB child inherits the requested count, while later database links do not. The consumers trust the context, because application code sets these fields for its own writes on behalf of any user (the documented programmatic replication control). So client input may reach them only for a super user, and the check sits where that input enters: the `X-Replicate-To` header in `server/REST.ts` (403 before the transaction starts, every method — a custom `get` can write), and the `replicateTo`/`replicatedConfirmation` operation-body fields in `verifyPerms` (`utility/operation_authorization.ts`, ahead of the structure-user and allowlist grants). A check inside `Table.allow*` cannot hold this (harper#2898): `loadAsInstance = false` resources never call `allow*`, an application's public resource overrides them, and an application resource writing to a table has no permission target. `X-Replicate-From: none` stays open to every caller by design: it keeps the request from loading records from other nodes and skips `@embed`/`@decide` derivation on its writes (`resources/models/DESIGN.md`). Tests: `unitTests/resources/replicationDirectiveAuthorization.test.js`, `unitTests/utility/operation_authorization.test.js`.

## A read-only server refuses writes at admission (`DatabaseTransaction.admitRequestWrite`, `Resource.ts`)

`isReadOnlyMode()` opens the stores read-only, and a read-only store cannot take a write: LMDB attaches no `ifVersion`/`put` to it (a write used to die with `write.store.ifVersion is not a function`) and RocksDB fails natively with a 500. The invariant is that no write is staged in a read-only process. `admitRequestWrite()` enforces it for every producer, because both engines' `addWrite` and each deferred-save admission pass through it before the write reaches an engine; it throws `ClientError('Server is in read-only mode', 405)`. The static `transactional()` wrapper repeats the check for `put`, `patch`, `delete`, `invalidate` and `update` only, so a REST/ops/direct call fails before authorization and transaction setup (harper#474). `post`, `publish`, `copy` and `move` are deliberately not rejected at the wrapper: a custom `post()` is often a non-storage call that a read-only server must still answer, and the table implementations of those methods stage their writes through `addWrite`. Three producers act before any `addWrite`, so each refuses on its own: `lock()` (it would take a key that only a refused write could use and nothing would release), numeric `getNewId()` (it advances the shared counter and can schedule a range write, all before the create's transaction exists, so it refuses before touching either), and `addAttributes` (the operations API adds attributes to a schemaless table before it stages the record). A read-only node does not subscribe to a table's source, so no source notification reaches admission: its residency-id mint is a direct catalog write ahead of `addWrite`, and a refusal there would orphan the blobs the notification had already saved. The wrapper's early refusal is limited to table-backed classes, since a custom resource's `put` may not touch storage, and it observes a promise-valued request body (`request.data` is already parsing) so a malformed body does not become an unhandled rejection. TTL expiry is the other storage writer that never reaches admission, because `evict` and the cleanup scans write through raw store handles, so each producer refuses on its own: `TableResource.evict`, `scheduleCleanup` and `runRecordExpirationEviction` return before any write or timer, and a read of an expired record on a table with no source resolves to an absent entry without calling `evict` or nulling the shared cached entry (nulling would not hide it on LMDB, whose weak reference still yields the record). Other direct store calls outside a transaction, and other DDL (`dropTable`, `removeAttributes`, `Table.clear`), are outside this guard.

## A record past its expiry on a table with no source is gone before eviction removes it (`Table.ts` `isHiddenExpiry`)

Eviction trails expiry: the sweep runs on the `eviction` interval, a plain read evicts lazily, and a read-only server never evicts. Until then the record is still stored, and these readers treat it as absent: a plain get answers null, the only-if-cached gates in `_loadRecord`, `get` and `ensureLoadedFromSource` answer 504 as for an evicted record, `transformEntryForSelect` skips it (search rows and relationship values), subscribe skips it as a current value, and a local load (`withLocalEntry`) stamps nothing from it on the context, whose `lastModified` becomes the response's `ETag`/`Last-Modified` (a 404 included). Raw write-path loads still see the entry, a retried commit still stamps its base version, the single-record relationship resolver (`getSync`) still returns it, and `includeExpired` searches (SQL UPDATE/DELETE) still match it. `isHiddenExpiry` is false on a table with a source get, which serves a stale record under only-if-cached. It reads the clock last, and `withLocalEntry` calls it only when it would stamp something, because that runs on every local read. Tests: `unitTests/resources/onlyIfCachedExpiry.test.js`, `subscribeExpiredCurrent.test.js`, `readOnlyModeTtl.test.js`.

## RocksDB range activity and snapshot expiration

`PrimaryRocksDatabase.getRange` and `RocksIndexStore.getRange` pass native ranges through `trackReadRange`. The native transaction's owner is captured once when constructing the range; each `next()` records activity before native access, including entries later discarded by filters. The transaction monitor consumes that activity at its existing cadence and applies the same read-only idle policy as point reads. It never renews a pending write holder merely because a scan advances. Iterator references still own the original snapshot; the wrapper does not reopen or rotate it. When a handle with no outstanding reader references is handed to the native commit/retry loop, its read-owner association is removed: retry handlers can construct new synchronous ranges on that still-live write handle without being mistaken for expired readers. Existing wrapped ranges retain their captured owner and cannot resume after their read ownership ends. The association is a module-private symbol property on the handle (`READ_OWNER`), set on attach and kept through detach so a range built later on a stale handle still finds its owner. It is not a `WeakMap`: an entry per read transaction is an ephemeron every scavenge processes. When the `WeakMap` was added, garbage-collection time per REST GET by id (YCSB workload C) rose 45% with no change in bytes allocated.

RocksDB 2.9.0 binds ranges to their supplied transaction and invalidates them when that transaction ends. An abandoned range is still bounded by the idle monitor. Resuming after its snapshot has been released throws an `ReadSnapshotExpiredError` (503) before accessing the native iterator; retry only the read, without replaying previously committed writes. A poisoned write-bearing transaction retains its existing 422 error and rollback behavior. Early iterator return remains a cleanup operation, including after expiration.

## Per-row read work on RocksDB index scans (`RocksIndexStore`, `PrimaryRocksDatabase.getEntry`, `Table.transformEntryForSelect`)

RocksDB index rows store `null`, so `RocksIndexStore.getRange` derives `{ key: indexedValue, value: primaryKey }` from the composite key and always asks rocksdb-js for keys only, whatever the caller's `values` says; `values: true` in `search.ts` is the LMDB contract, where the dupSort value is the primary key. On a caching store, `PrimaryRocksDatabase.getEntry` gives rocksdb-js a fresh literal — `transaction` plus `expectedVersion` (cached) or `populateVersion` (cold) — rather than a copy of the caller's options, which for HNSW is a whole `DatabaseTransaction`; `uncachedRead` and cache-disabled reads still pass the caller's object through unchanged. The literals drop rocksdb-js's other read option, `skipDecode`, which no harper caller passes; a read option harper starts to rely on must be added to both. In the select transform, load options are built once per query, one object for sync loads and one for async, because `loadLocalRecord` sets `options.async` on an async load. A plain column (a string, not `'*'`, with no `propertyResolvers` entry) is assigned directly in the select loop; that is decided per column as each row is projected, because `transformToOrderedSelect` and nested selects rewrite `select` elements after the transform exists. Enforced by `../unitTests/resources/indexRangeSelect.test.js` and the read-options test in `../unitTests/resources/caching-rocks-database.test.js`.

## A read reference belongs to the handle acquisition it was taken on (`DatabaseTransaction.useReadTxn`/`doneReadTxn`, harper#3308)

`readTxnsUsed` and `readTxnRefCount` are never non-zero without a read handle, and neither carries across handle acquisitions. `doneReadTxn(generation)` ignores an iterator return from an earlier acquisition (`readTxnGeneration`, bumped per acquisition, because lmdb-js renews the same `Txn` object for a new snapshot); point-read `disregardReadTxn()` is not generation-stamped, so a cache miss that took no reference or whose acquisition was released can still decrement a later acquisition's count and release its snapshot under another live reader. Enforced by `unitTests/resources/detachedReadRefs.test.js`.

## `getRecordCount`'s estimate is a heuristic guess, not a guaranteed bound on the truth (`Table.ts`)

`[lower, upper]` is a widened heuristic interval, not a guaranteed bound on the live count -- `Table.ts`'s own comment at the computation says so (#2612). The scan only escapes into sampling once it has scanned past `MIN_ESTIMATOR_SAMPLE` entries AND its time budget is exhausted AND it has a usable positive base; then it escapes either because that base puts it short of the table's halfway point, or because `MAX_ESTIMATE_CHECKPOINTS` budget checkpoints have passed regardless of halfway -- so a base that stays past halfway only stays exact if the scan finishes before that checkpoint ceiling. With no usable base at all, below the floor, or still within budget, the scan always finishes exactly. Past the escape, the forward+reverse sample can also turn out to cover the whole table; that case returns an exact sum too, not an estimate. Only the remaining case extrapolates, and `recordCount` there is always clamped into `[lower, upper]`. `lower` is an exact count of the sampled live rows, not itself an estimate -- but `upper` is built from the native estimator's base, which can be wrong, so a confidently underestimated base can produce an `upper` below the true live count (reproduced in `unitTests/resources/getRecordCountCallerImpact.test.js`, pinning that as current behavior). Whenever the caller passes `exactCount: true`, none of this applies: the scan always runs to completion and reports an exact `recordCount` with no `estimatedRange`, regardless of table size. A caller that compares `recordCount` for equality, or does page-count math on it (or on `estimatedRange`) as if either were exact, is relying on something the contract never promised.

## Auto-increment id ranges are claimed by compare-and-replace (`Table.getNewId`)

Worker threads in a process share one id counter (`getUserSharedBuffer('id')`), but each thread decides on its own when the range in the `id_allocation` record is exhausted, so two threads can extend or re-allocate it at the same moment. `replaceIdAllocation` lets exactly one of them install the new range: it writes only while the stored allocation still equals the one the caller read (or none is stored), and a loser bounds its ids by the stored range instead of its own proposal. A losing re-allocation (`alreadyUpdated`) leaves the counter for the winner to move, so between the winner's commit and its `Atomics.store` the loser's limit and the counter can briefly name different ranges. Two properties make this hold on RocksDB:

- **The comparison token is the allocation value, not `entry.version`.** The record is a bare `putSync` with no Harper record metadata, so RocksDB returns no version for it; a version check compares `undefined` with `undefined` and always passes.
- **The read and the write take `{ transaction }` from the `transactionSync` callback, with `retryOnBusy`.** rocksdb-js only joins operations that are given the transaction. When a sibling thread commits between the read and the commit, the commit fails with an optimistic conflict, and the retry reads the sibling's allocation. lmdb-js serializes write transactions and passes no transaction to the callback; its second argument is numeric flags, so the options are passed only on RocksDB. `unitTests/resources/idAllocation.test.js` commits a sibling write between the read and the commit, for both re-allocation and extension.

## Replicated apply failure listeners (`resources/replicatedApplyFailure.ts`)

`registerReplicatedApplyFailureListener(database, listener)` and
`unregisterReplicatedApplyFailureListener(database, listener)` are exported from `harper`.
They register one callback per database on the current worker; registering the same callback
again is idempotent, unregistering removes only that callback, and database removal clears all
of that database's listeners. A replication transport must register on every worker that runs
its source apply loop, before delivering events. Registration does not replay earlier failures.

The listener receives `{ database, table?, nodeId, position, localTime?, error }`. `nodeId` is
the audit header's translated origin id, not the immediate relay; `position` is the failed
event's original `timestamp` (the origin transaction-log key), inherited from the transaction
envelope for sub-writes without their own coordinates, never its record `version` or
peer resume `localTime`. Events without numeric origin and log coordinates cannot be attributed
and are not reported. A transaction commit failure uses its saved begin event, including when
an `end_txn` marker lacks an origin or a new `beginTxn` belongs to a different origin.

**No event is pulled from a replicated source after a terminal apply failure until every
registered listener for the database has been awaited with that failure's origin and position.**
Consecutive `beginTxn` events require pulling the new begin marker to close the preceding
transaction; the preceding failure's notification completes before staging that new marker's
write. The listener set is captured when notification starts, and callbacks run in registration
order outside the source transaction's async context. A listener may therefore persist a hole
in its own transaction. Dropped-entry notifications can run while the source transaction is
still open: persist to dedicated state keys/tables outside the replicated writes, and never
wait for that source transaction to commit. A listener must resolve only after its state is durable and be idempotent for
`(nodeId, position)`: a crash before the later cursor update can replay the same failure.

The hook covers terminal commit/staging failures, malformed transaction envelopes, unknown
operations, valueless puts, and explicitly discarded lock-control entries. These last cases also drain their
notifications before the next source pull, even inside an open transaction. A successful commit
followed by a failing `onCommit` callback or resume-cursor write is logged as before but does not
report a missing write. Conflict retries and successful no-op conflict/dedup resolution are
unchanged. An unsupported operation, including a future operation type, is reported because
core cannot certify that it applied it; transports should consume their own non-write markers
before forwarding events to the table apply loop. The outer subscription-error handler
terminates iteration and is not a skip.

Listener throws and rejections are logged individually and do not stop later listeners or change
continue-on-failure behavior. Core has no timeout or durable fallback for listeners: a hung
listener backpressures the source, and a rejected persistence operation cannot establish durable
hole state. The transport owns recovery and fail-closed behavior for those cases.

## Source transactions are delimited per connection, and a transaction log holds one origin (`Table.sourcedFrom`, `RocksTransactionLogStore`)

A replication receiver feeds one source subscription per database from every connection on a thread, and its receive loop yields partway through a frame. So `beginTxn` / `end_txn` can only delimit a transaction within one connection: each event carries its connection's `txnStream` token, and the apply loop keeps the open transaction per token (untagged events share one default stream, which is the behavior every other source relies on). Without the token, another connection's `beginTxn` commits the open transaction early, its writes join it, and its `end_txn` commits it under its own cursor (harper#1162). `abort_txn` rolls back a token's unfinished transaction; harper-pro sends it after a connection's last queued record when a frame ends without its `end_txn`, so a partial frame never commits.

A transaction-log entry's identity is (`txnLogKey`, `nodeId`): the key alone repeats across origins, and a receiver files a replicated transaction under the origin's key. `RocksTransactionLogStore.put` therefore files an origin's entries in that origin's own log, created on first use, never in the relaying peer's log, so a key stays unique within a log (exact resume, `resumePastExactStart`, depends on it); within `local` it is unique because every key is minted there ("Origin-closed timestamp floor" above). A relayed entry whose origin id has no node name is rejected rather than misfiled; an unnamed id that was not relayed (`viaNodeId` equal to `nodeId` or absent) is not a replication origin and stays in `local`, under a minted key.

A failed transaction on a tagged stream (a non-retryable commit failure, including a segment closed by a later `beginTxn`) is reported at that stream's next `end_txn`: when the `end_txn` carries `onFailure(error, txnLogKey)`, neither its `onCommit` nor its sequence id passes the failure, and `onFailure` returning true _holds_ the stream — every later `end_txn` on it commits its writes without `onCommit` or a cursor, because the source is reconnecting to replay from its durable cursor under a new token (a held token is never reused). A held failure is not reported to the apply-failure listeners, since the replay applies it; a failure the source moves past (`onFailure` false, or no `onFailure`) is. An `end_txn` without `onFailure` keeps the older behavior of recording its cursor, so holding is opt-in per source. When the transaction committed, and any `onCommit` ran, but the sequence-row write itself failed, `onFailure(error, txnLogKey, true)` runs before the error propagates. The third argument tells the source that the commit path completed, so nothing it releases on commit is still held; only what it attached for recording (cursors, floors, route state) was lost. The stream's last sequence id is rolled back, so a repeat of that position writes again. `txnStream` must be an object: streams are held in a `WeakMap`, so a closed connection's state is collected with its token.

An `end_txn` can also carry `originCursors: [nodeId, originLogKey][]`, the highest origin log key the source has durably applied for each origin. The apply loop merges them, keeping the max, into the connection's `[seq, remoteNodeIds[0]]` row as `nodes[].originLogKey`, even when `localTime` did not move (harper-pro#989; the per-origin cursor vector of harper-pro's replication workstream W4, harper-pro#434). A source may attach the array from `onCommit`, and the loop reads it only after awaiting `onCommit`. A held stream records neither the sequence id, origin cursors nor origin floors. A source that sends origin cursors must tag its stream and pass `onFailure`: without them, a failed segment's later `end_txn` still merges its cursor vector, so a cursor would pass the failed transaction; floors from such a source are dropped (below). The same `end_txn` can carry `originFloors: [nodeId, closedFloor, relayable][]` — an origin's closed timestamp floor (harper-pro#922 item 2; the producer is "Origin-closed timestamp floor" above), merged by max into `nodes[].closedFloor` with `nodes[].relayable` (whether the source received that origin directly with full table coverage, so a relay may forward the floor). It is kept apart from `originLogKey`: an applied position can sit above a transaction still open at the origin, a floor cannot, so only the floor is proof that resume may start there. A floor-only `end_txn` writes the row like a cursor-only one. Floors are merged only from a tagged stream that passes `onFailure` — core enforces for floors what it only documents for cursors, since a stored floor is what resume trusts — and an entry whose floor is not a positive finite number is skipped.

## Repeat writes to the same key in one transaction carry their state forward (`DatabaseTransaction`/`Table`)

A transaction can hold more than one write to the same record key — two `patch()` calls inside one `transaction()`, or a replicated transaction carrying two updates to a record. Each write captures `operation.entry` (its idea of the current record) when it is staged, and **neither engine can refresh that from a read**: LMDB queues staged puts and applies them only in the commit batch, so a `getEntry` inside that loop still returns the pre-transaction record (the exclusive `store.transaction()` fallback is no better), and RocksDB read-your-writes only sees writes already staged into the native transaction — which the source-apply path, staging its whole batch before `commit()`, hasn't done yet.

So the writes carry the state forward themselves: `addWrite` chains each write to the preceding write to the same store and key (`linkWrite` → `operation.priorWrite`), a commit handler publishes what it stored on `operation.stagedEntry`, and the next write finds it through `priorStagedWrite()` (the nearest earlier write to the key that published a `stagedEntry`) and uses that entry as `existingRecord`. Consequences worth knowing:

- Only the **record** comes from the earlier write. On LMDB the rest of the entry (version, `localTime`/audit chain, blob metadata) stays the pre-transaction one. RocksDB reloads the entry through the committing transaction (`reloadCommitBase`), so it also carries the earlier write's `additionalAuditRefs` — including that write's own ref, whose identity (shared log key, origin, version) is this write's too. The read-your-writes re-delivery check therefore skips when `priorStaged` is set; a real re-delivery is still caught, because its first write matches there and stages nothing. The keyed audit lookups need no such guard: an earlier write's log entry is unreadable until the native commit, and on a retry round every write that appended carries `stagedOwnAuditEntry` (harper#1824, harper#1970; `unitTests/resources/outOfOrderChainedWrites.test.js`).
- Program order breaks **ties only** (`if (priorStaged && precedesExisting >= 0) precedesExisting = 1`). Every write in a transaction carries the transaction's single timestamp, so a version comparison against what the earlier write landed (e.g. on a retry round after a partial apply) is a tie that the out-of-order machinery would otherwise drop as a re-delivered duplicate. A _strictly newer_ existing version can only be a concurrent transaction's write observed on a retry round; a chained write still goes through the out-of-order merge for it (and a chained delete still yields to it) rather than silently overwriting it. A publish or relocate restamps the head without staging, so on an `audit: false` table on RocksDB a tie is ordered against the committed head (`identityBase`) instead, wherever the publish sits relative to the deferred write; LMDB, whose commits carry no `committedBy`, applies a tie after an unskipped earlier write in program order; the audited walk orders it by log key.
- A superseded write's **blobs are cleaned up post-commit**: when a later write to the key replaces (or deletes) the record an earlier write stored, the earlier write's `savedBlobs` are reachable only through its audit entry — so unless it wrote one (`blobsAuditReferenced`, in which case audit pruning owns them), the commit-cleanup pass deletes them, checked against the final committed record so a blob the later write retained survives. Without this, LMDB (whose replacement path never sees the intermediate entry) leaked the intermediate blob's file permanently.
- The per-key chain map key (`writeKeyId`) is the **store's own canonical key encoding** (ordered-binary, as a latin1 string). JS value identity is wrong in both directions: `1n` and `1` are the same stored key and must chain, while `[0]` vs `[-0]` and `[null]` vs `[NaN]` are different stored keys that JSON/string coercion collapse. Symbol and null keys keep native identity (not key-encodable; never stage records).
- `clearWrites()` discards the chain along with the write set on commit/abort, so a reused transaction never bases a write on a previous batch's staged state.

Before this (harper#1968), every write diffed against the pre-transaction record: the secondary index kept the intermediate value permanently (nothing reconciles an index against the records, so only a rebuild repairs it), and on LMDB the earlier write's changes were dropped outright.

The chain only describes reality if **staging order is also execution order**, and on RocksDB two things used to break that. `addWrite` runs a write's commit handler immediately unless the write sets `deferSave`; `_writeUpdate` does set it and depends on `resource.save()` to run the write, and the source/replication apply path calls `_writeUpdate` directly and never calls `save()` (`replayLogs` does, explicitly). So an apply-path put executes in the commit loop while a delete executes at staging time, whichever was staged first. And the apply loop itself dispatches each record's `writeUpdate()` without awaiting; that function suspends on an async record load (RocksDB `get` is synchronous only on a block-cache hit), so within one transaction a warm key can reach `addWrite` before a cold key that arrived earlier. A leader's `delete K; put K` then staged as `put K; delete K` and executed as `delete K; put K` with neither write chained to the other — both diffed against the pre-transaction record, the delete removed **every** index entry for the record and the put, whose indexed values matched that same record, did no index work at all and re-stored the record. Live record, no index entries, permanent (harper#2211).

Both orders are now pinned. `addWrite` defers a write whose earlier same-key write has not run yet, but **only for writes that both consume `priorStagedWrite()` and publish `stagedEntry`** — marked `chainsStagedState`, today the update, delete, and invalidate writes. `DatabaseTransaction.save()` applies the same rule when an explicit `resource.save()` bypasses `addWrite`: it drains that operation's unsaved predecessor chain oldest-first into the same native transaction before saving the requested write. `_writeRelocate`/`_writePublish` consume and publish neither staged record state, so reordering them past a staged put would hand them a pre-transaction basis they have no way to correct; they keep their eager save. And the apply loop's `stageWrite` chains the writes to any one key through a per-transaction map so staging order is arrival order, dropping settled entries (a bulk transaction retains one entry per in-flight write, not per record) and short-circuiting successors when a predecessor rejects. LMDB was never exposed to the storage-order inversion: `LMDBTransaction.addWrite` defers every write and has always executed them in `this.writes` order.

An ordinary tracked update instance represents one staged write at a time. Once its write is selected for saving — explicitly, as an explicit save's predecessor, or by transaction commit — its direct and lazily tracked nested mutation surfaces throw 409 until `update()` stages a fresh write. Reads remain valid. Record-lock instances retain their separate lifecycle because scoped and held locks deliberately reuse the same instance and lock handle across explicit update/save cycles.

Two consequences of that scoping are worth knowing, both pre-existing and neither closed by the ordering fix. `_writeRelocate` still saves eagerly, so a replicated `put K; relocate K` where the residency list excludes this host strips K to its indexed-attribute stub first and then re-stores the **full record** — content retained on a node the sharding policy excludes. Closing that requires teaching the relocate handler `priorStagedWrite()`/`stagedEntry` before flagging it. Invalidation now consumes and publishes the chain, including its indexed projection; its former lost-invalidation case is closed by the residency index fix. A subsequent patch keeps an incomplete base invalidated, including ordinary cache stubs without a residency list. An invalidation that writes an audit entry leaves blob lifetime to audit retention even when a later write supersedes it. Separately, the apply loop's per-key chain narrows but does not close the cross-key escape: in `{put A, delete B}` where A's resource load rejects and B's is slow, the abort lands at `end_txn` and B's continuation then reaches `addWrite` on a CLOSED transaction, where `save()` commits it alone.

## A tracked instance commits only what it changed, as plain data (`tracked.ts` `collapseChanges`, `Table._writeUpdate`)

Reading a sub-object or array through a tracked instance stores its tracked wrapper in the instance's changes: that wrapper records later nested mutation and is the getters' identity cache (`rec.subObject === rec.subObject`). So the raw changes are not the patch. `_writeUpdate`'s `validate` replaces them, once, with `collapseChanges(this, changes)` whenever the write commits the instance's own changes (`tracksInstance`: an incremental write whose `recordUpdate` is absent or is `this.#changes`, which includes `update(id, obj)`). That result is the one patch every consumer reads — validation and time stamping, `source.patch`, the audit entry, `rebuildUpdateBefore`'s out-of-order basis, and the stored record. `collapseChanges` does not mutate the changes object (it is the live tracked state, or the caller's object); it copies only when something is dropped, collapsed or added, so with nothing to normalize validate stamps times into the changes object itself, as before. A wrapper still backed by the record's same property with `!hasChanges` is dropped. A read must not become a write: in the audit entry it makes an older out-of-order patch to that property lose (`rebuildUpdateBefore` drops fields a newer patch names), and on a conflict retry it restores this instance's stale snapshot over a concurrent writer's value. Patches written before this keep the read-only fields they recorded; a reader cannot tell those from writes. A changed wrapper is collapsed to plain data (`collapseData`; arrays stay arrays); CRDT operations stay operations. Only objects and arrays are wrapped and cached in the changes: a cached value is indistinguishable from an assignment. A Date or Bytes value is read as a copy kept outside them (`readCopy`; an array element is a copy compared by value, so editing one in place writes the array), so an in-place edit never reaches the commit base, which is shared with the cache, and is saved only when reassigned. And `addTo` composes within a transaction (`addToChanges`: a pending addition folds into one addition, so it still commutes with concurrent additions; an assigned value becomes the sum). Own properties that differ from the record are part of the patch and override a change to the same key, except one still holding the value the framework constructed the instance with and not yet committed (a subclass's class fields, `recordOwnBaseline`: a value `structuredClone` reproduces, such as plain data or a Date, compared by content, other objects by identity) (a Table instance has no setter proxy, so an undeclared property on a non-sealed table lands as an own property), and the commit calls `updateAndFreeze(this, patch, false)` so they are not merged a second time over a newer base. A tracked write finds its blobs for pre-commit in this patch, during validate, since blobs can be assigned after staging.

## A delete re-delivered onto its own removal is a no-op (`Table._writeDelete`, harper-pro#826)

When the key already holds no record because this same write — origin node plus log key, `isAuditEntryWrite` — removed it, the delete writes nothing: no index change, no tombstone rewrite, no audit entry. It still stages the removal, so later writes in the transaction see program order unchanged. The removal is either the stored tombstone (a copy in a later frame) or the `stagedEntry` of the nearest earlier write to the key that staged one (an earlier copy in this transaction), which is why a delete's `stagedEntry` carries `localTime` (its log key) and `nodeId` as well as `value`. The walk passes only writes marked `skipped`: a relocate can write a null stub carrying the same identity without publishing it to the chain; invalidation publishes its projection without a removal identity, so any other unstaged write — and any `INVALIDATED` stored entry — means the delete applies. Known gap: a null stored by a publish or a residency-local relocate carries no marker, so if one origin transaction ever arrived split with the delete alone in the later frame, that delete would log nothing (the key is null either way).

Without this, every re-delivery appended another entry under the origin's log key; in a mesh each appended copy is new log tail every peer forwards and re-logs in turn. A delete that follows another write to the key in its transaction still applies — it is not a tie with its own removal. LMDB keys its log by local time, so a stored tombstone there carries no origin log key and only copies within one transaction collapse. Pinned by `../unitTests/resources/replicatedDeleteRedelivery.test.js`.

## A second sequential save() on the same ImmediateTransaction context must chain on `operation.innerCommit`

Two `update()`+`save()` cycles on one resource instance outside `transaction()` reuse one `ImmediateTransaction` after its first cycle has closed it. The second write then commits through a nested `commit()` on a fresh native transaction (the `immediateCommit` branch of `DatabaseTransaction.save()`), whose promise the outer commit's sweep loop discards; that branch stashes it on `operation.innerCommit`, which is `undefined` for a write that commits inline. Both `Table.save()` branches — the ordinary `#savingOperation` path and the lock-writable hold path — wait on it, or `await resource.save()` returns before the write is durable and an immediate read sees the old value. The gap is general to `Table.save()`, not lock-specific. Exercised by `recordLock.test.js` "scoped lock outside transaction() persists across sequential saves until unlock()".

## A commit retry re-saves into the transaction it is retrying; `ImmediateTransaction.save()` must forward it

Every retry and replay round of `commit()` re-stages into the native handle being retried, and
`ImmediateTransaction.save()` forwards whenever `isCommitting` is set or the call carries `transaction`
or `options`: without it, `DatabaseTransaction.save()` opens a fresh handle and nests a `commit()` whose
retry loop re-enters the override without bound (`RangeError`, harper#2825), or a nested retry running
after `isCommitting` reset starts a new top-level commit instead of re-staging onto its own handle. A
retry round's handle is detached, so a re-save that throws releases it before `abort()`, or its write
intents park other writers until GC. Pinned by `immediateTransactionConflictRetry.test.js` ("…not a
nested commit", "releases the replay transaction when a lapsed lease refuses a re-save…") and
`noAbortAfterTxnLog.test.js`.

## A transaction is joinable as a scope only if it stages its writes (`transaction`/`Resource`/`Table`)

`txnForContext` builds an `ImmediateTransaction` for a context slot that is empty or holds
`RELEASED_TRANSACTION`, and installs it there — reached by anything that resolves a transaction without
going through the static-API wrappers, an instance load (`getResource`) being the common one. That
instance reports `open === OPEN`, but its `save()` **is** the commit (`saveCommits`), and nothing owns a
final commit or abort for it.

`TRANSACTION_STATE.OPEN` therefore carries two meanings that are not interchangeable: "will accept a
write" and "stages writes for an owner that will commit or abort them as a unit". Both join sites —
`transaction()` and the `transactional` dispatcher — ask `isJoinableScope()` for the second, not the
first. Joining on OPEN alone meant `transaction(ctx, …)` ran its callback and returned without ever
reaching its own `commit({ doneWriting: true })`: every write self-committed, a throw partway left the
earlier ones durable, and `onError`'s abort never ran — silently, with the handler returning success
(harper#2292, seen live on 5.2.5).

Two things follow from the same invariant:

- A chained link (`transaction.next`, a second database) inherits the head's commit discipline: under a
  self-committing head it is another `ImmediateTransaction`, transitively down the chain. Such a link is
  CLOSED once it has committed, and a further write through it would commit on a native handle nothing
  awaits (harper#2323), so a spent one — closed, no handle, no pending writes — is dropped from the chain
  and rebuilt rather than handed back. A staging link
  there is only swept up if the head's own database is written again (its commit cascades the chain), so
  a handler that writes the second database last silently loses that write.
- A deferred write (`deferSave`, which is every `_writeUpdate`) is only _triggered_ by
  `resource.save()`; it lives in the `writes` of whichever transaction `addWrite` put it in
  (`operation.stagedIn`). So `save()` can run after the context has moved on to a different
  transaction, which a scope opening in between now makes routine. A joinable scope **takes the write
  over**: `detachWrite` from the holder, `addWrite` onto the scope, and `priorWrite` cleared. Every
  commit path decides what to stage, what to replay onto a fresh handle for outstanding iterators, what
  to roll back and whose blobs to reclaim from `writes` alone, so a write in two lists is either
  committed twice or dropped by whichever list is consulted first; and the per-key basis chain belongs
  to the holder, so keeping it would diff the merge and the secondary index against a record that may
  never land. Otherwise the write stays with its holder, the transaction whose commit will see it. Never
  taken over from a `sourceApply` or `isReplay` holder: that never-drop-on-conflict policy lives on the
  transaction and would not travel with the write (harper-pro#348). And only where `addWrite` runs the
  write — `LMDBTransaction`'s never does (its commit applies `writes`), so on LMDB the holder always keeps
  it (`stagesWriteOnSave`). A write whose holder has already **finished** is not revived — it is dropped,
  as it was before any of this — because an aborted holder has already reclaimed that write's blobs, so
  committing it now would store a record pointing at deleted files. `validate` receives the transaction that is
  committing the write (`committedBy`) rather than closing over the one that staged it, so overload
  accounting, the replay marker and a no-op write's removal all follow the takeover.

Ownership is deliberately **not** the test. A context pre-seeded with an externally driven
`DatabaseTransaction` (`replayLogs.ts`, `Table.ts`) is not `scopeOwned`, yet it still owns the writes the
static API gives it and its own `commit()`/`abort()` still governs them; gating on `scopeOwned` would
move those writes onto a transaction the caller does not hold. Writes made with no scope at all keep
committing per write.

## The RocksDB codec is a deployment setting, resolved once per process

`getRocksCompression()` in `resources/databases.ts` resolves one codec for everything this process opens: `storage.rocks.compression` if it names one, otherwise `storage.compression` (default `true`) decides enabled-or-not and the build default supplies the algorithm. It is resolved on first use and frozen.

It has to be one codec, decided before the first open, because RocksDB opens **every** column family of a database in a single `DB::Open` and a family's compression cannot change while it is open. Harper cannot consult per-table metadata first: that catalog (`__dbis__`) is itself one of the families that call opens. So per-table `compression` metadata still records the LMDB-era boolean but no longer selects — a table persisted as disabled inside a deployment that enables compression would need its own codec, and there is nowhere to apply it.

Opens pass `compressionForAllColumnFamilies` (rocksdb-js) alongside the codec. Without it the binding gives every family the caller did not name its _persisted_ algorithm and applies the request only to the target, so families this process never names individually would keep their original codec forever — which is why a database created before the prebuild carried any codecs (every 5.1 instance) stayed uncompressed no matter how new the binary was, and why reconciling a table afterwards failed with `already open with compression ...; cannot reopen it with ...`.

The ordering that still has to hold is a fresh install: `install()` calls `mountHdb()` — which creates the system families — several steps before `createConfigFile()` writes the config file, so `installer.ts` stages the value into the in-memory config (`stageRocksCompression()`, mirroring the `STORAGE_ENGINE` line beside it) before `mountHdb()` runs. Without it the main thread resolves no codec while workers resolve the configured one, and the boot dies with "The system database failed to load". Changing the codec governs newly written files. Existing SST/blob files keep theirs until rewritten; ordinary compaction will not do it (RocksDB skips the bottommost level without a compaction filter), so converting an existing database in place needs `compact({ bottommost: true })`.

Harper's normal RocksDB open path disables RocksDB's native WAL for primary and index column families; durable recovery for runtime transactions comes from rocksdb-js transaction logs. The root handle that owns those logs and the `__dbis__` metadata column family deliberately keep native WAL enabled. `copyDbToRocks` writes directly and does not create rocksdb-js transaction-log entries, so it can use the same no-native-WAL bulk path only when called by `migrateOnStart` for a `<database>.migrating` staging directory. The LMDB source remains authoritative until the copy and verification finish; an interruption deletes that staging directory and restarts the copy. The root and `__dbis__` handles retain native WAL, while every primary and index handle receives `disableWAL: true` (rocksdb-js stores the option per handle). Their metadata-sized WAL traffic is negligible beside the bulk copy. When the last handle closes, rocksdb-js flushes every column family and waits for background work before the verified staging directory is atomically renamed. A direct `copyDbToRocks` call to a non-staging path keeps native WAL enabled because it has neither transaction-log recovery nor the wrapper's discard-and-retry guarantee.

## Schema migration and `runIndexing` internals (`databases.ts`)

When `table()` is called with an attribute newly marked `indexed: true` (or with any change that requires re-building the secondary index), `runIndexing` is launched asynchronously and `Table.indexingOperation` is set to its promise. While running:

**In-flight state tracking (persisted to `attributesDbi`):**

- `attribute.indexingPID = process.pid` — set at migration start; cleared on clean completion. On restart with a different PID, `indexingPID !== process.pid` triggers a re-migration.
- `attribute.lastIndexedKey` — a resumable checkpoint, written at most once per checkpoint period and never before the record floor (`setIndexingCheckpointPeriod`), and only once the index writes it covers have settled and flushed. Cleared on clean completion; preserved on error so a retry starts from this key.
- `attribute.checkpointCertified` / `attribute.checkpointAlgorithm` — the key the checkpoint was stamped with, and the version of the algorithm that stamped it. A checkpoint resumes only when both match; anything else is rebuilt from scratch, because earlier releases could advance `lastIndexedKey` past a record whose index write failed. The algorithm stamp is also kept on a completed index, so a build made under a version that could skip a record stays distinguishable from one that could not.
- `attribute.indexingFailed = true` — set if any record's `index.put` errors during the backfill. `table()` checks this flag: a fresh call in the same or a new process re-triggers the backfill from `lastIndexedKey`.
- `dbi.isIndexing = true` — in-memory flag on the index dbi. Prevents `searchByIndex` from serving partial results (returns 503 "not indexed yet" instead). Cleared only when backfill completes cleanly.

**`isIndexing` propagation across `resetDatabases()` calls:**
When `signalSchemaChange('schema-change')` fires at the start of `runIndexing`, `syncSchemaMetadata` calls `resetDatabases()` which re-opens all tables via `table()`. This creates a _new_ dbi object and assigns it to `Table.indices[attribute.name]`. The condition `if (attributeDescriptor?.indexingPID) dbi.isIndexing = true` (just before `indices[name] = dbi` in the migration-detection block) ensures any dbi created while a migration is in progress also has `isIndexing = true`. Without this, a concurrent `resetDatabases()` would replace the in-progress dbi with a fresh one where `isIndexing` is false, allowing queries to read partial index results.

**Error handling:**

- Per-record sync errors: caught by the inner try-catch. Set `hadIndexingErrors = true`.
- Per-record async rejections (`index.put` returning a rejected Promise): every index mutation the build issues — each value's put, the drops for removed indexes, and the LMDB `clearAsync` — is registered in a per-build set that absorbs its own rejection and sets `hadIndexingErrors = true`. A record fans out into one put per indexed value, so tracking only the last one left the earlier puts' failures visible only if they happened to settle in time.
- A checkpoint drains that set before flushing and refuses to certify if any mutation it covers failed; completion drains it too, so "no errors" means every write settled rather than none had failed yet. The set also bounds how many writes stay in flight (`MAX_OUTSTANDING_INDEXING`).
- On any error: `indexingFailed = true` is persisted; `indexingPID`, `isIndexing`, and `lastIndexedKey` are kept. This leaves the index in 503 "incomplete" state rather than silently serving partial results.

**`Object.defineProperty(attribute, 'dbi', ...)` must use `configurable: true`:**
`attribute.dbi` is defined as a non-enumerable property (to prevent serialization to `attributesDbi`). It is defined with `configurable: true` so it can be re-assigned if the attribute participates in a retry cycle in the same process.

## Cluster-origin table definitions are additive-only (`databases.ts` `table()`)

`table()` distinguishes two kinds of callers by the `origin` field of the definition. Local schema authoring (create_table, `@table`, `defineTable`) is authoritative: its attribute list replaces the live one, and the catalog reconcile removes descriptors (and indexes) for attributes the list no longer declares. A definition with `origin: 'cluster'` — replication's DB_SCHEMA handshake (`ensureTableIfChanged` in harper-pro) or a replicated `define_schema` event (`Table.ts`) — is only ever a _snapshot of a peer's eventually-consistent view_: it can be captured mid-create (only the primary key registered yet) or read from a worker whose thread-local map hasn't absorbed a concurrent local create. Such definitions are applied additively: attributes the local table lacks are added, locally declared attributes are never removed or redefined, catalog descriptors are never reconciled away, and the local `schemaDefined` declaration is never flipped. Before this was enforced, a partial peer snapshot racing a local create_table permanently deleted the just-declared attributes' descriptors — and because the table was `schemaDefined`, the handshake's honor-local guard then refused to ever re-add them from peers, so searches failed with "unknown attribute" forever after (harper-pro nightly `replicationLoad` flake). The deliberate cost of additive-only: attribute _drops_ and _redefinitions_ do not converge through schema gossip — a stale peer can resurrect a locally dropped attribute, and a peer's redefinition of an existing name is discarded. Cluster-wide schema changes converge by applying the schema on every node (component deploy); a versioned schema exchange is the eventual fix. Every discarded peer difference is logged (`Ignoring peer redefinition of ...`), because a silently dropped `indexed` is otherwise indistinguishable from convergence. Where a catalog descriptor already exists, it is the authoritative declaration on this path and the incoming definition is restated from it — in both directions, so a field the descriptor dropped is dropped live too. That is what keeps a caller whose list predates a concurrent `create_attribute` from shadowing it in memory (losing the index registration for the rest of the worker's life) as well as on disk. One exception to "never writes an existing descriptor": an abandoned index build — `indexingFailed`, a foreign `indexingPID`, or a `restartNumber` older than this worker's generation — is still recovered, rebuilding the durable declaration rather than the caller's snapshot. Skipping recovery would leave the index's `isIndexing` flag pinned on with nothing left to clear it, so every query on the attribute would fail with `IndexRebuildingError` for the life of the worker. Regression coverage: `unitTests/resources/clusterSchemaMerge.test.js`.

**Remediating a node damaged before this was enforced.** The fix is forward-only. A node that already lost an attribute's catalog descriptor still has `schemaDefined: true` persisted, so the handshake's honor-local guard refuses to re-add the attribute from any peer and `search_by_value` keeps failing with `unknown attribute`; the recurring `Schema for '<db>.<table>' is defined locally, but attribute '<name>: <type>' from '<node>' does not match local attribute which does not exist` warn is the only detection signal. Local schema authoring is now the only path permitted to write that descriptor back, so remediation is to re-declare the attribute locally on the damaged node — the `create_attribute` operation, or redeploying the component whose `@table` declares it.

## A table is invisible to catalog scans until its create is complete (`databases.ts` `table()` / `initStores`)

The additive-only rule above repairs the _consumer_ of a partial peer snapshot; this rule stops the snapshot from existing. Every worker thread has its own `Table` map, rebuilt by `resetDatabases()` → `initStores` scanning the `__dbis__` catalog whenever any schema-change ITC signal arrives — including one for an unrelated database. On RocksDB catalog rows are individual `putSync` writes and the cross-thread `update-attributes` lock is taken only by writers, so a scan that lands inside a `create_table` used to see the primary row with none or some of the attribute rows, build a `Table` whose `attributes` was that partial list, and emit `updateTable` for it — which harper-pro forwards to peers as a DB_SCHEMA announcement. On a peer whose replication thread had not loaded the table yet, the announcement was applied as an authoritative definition and deleted the locally declared attributes (harper-pro `replicationLoad` "unknown attribute 'name'"; the partial announcement is visible in the node log as `(Re)creating { ... attributes: [ { name: 'id', ... } ] }`).

`table()` therefore writes the primary-key descriptor (`<table>/` — the row `initStores` needs before it will load a table; a row carrying `isPrimaryKey` is accepted too, for pre-5.x catalogs, so the primary-key descriptor must stay the last row written whatever key it lands on) only after every attribute row, still under the exclusive lock, and registers the class in this worker's `databases` map immediately after it. That write is also where the rollback stops: the row is durable the moment the put returns — on LMDB the `finally` that releases the exclusive lock commits the create's write transaction whether or not an error is unwinding — so a create that throws past it (registering the class, persisting relationships) keeps every row it wrote, and undoing them would leave the primary-only catalog this rule exists to prevent. `initStores` skips — with a warn — a table that has attribute rows but no primary row. The catalog is either invisible or complete to every other thread, so no thread can build or announce a partial `Table`. A scan that finds the incomplete catalog also drops a class it still holds from a dropped same-name table, rather than serving that stale generation through the recreate. A create that throws before its primary row is registered nowhere, and `table()` releases what it had opened for the class (primary store, index stores, the audit delete-removal callback, and its storage-reclamation handler — `removeStorageReclamationHandler`, because a RocksDB column family shares its reclamation path with every other family in the database). LMDB already had this property because `exclusiveLock()` there is an environment-wide write transaction. Consequence for an interrupted create: orphan attribute rows, no primary row, and the column families opened before the crash (as before), so the table does not load at all instead of loading with whatever attributes had landed; re-running `create_table` writes the rows, reuses the families, and the new-table reconcile removes any orphan row the new definition does not declare. The guarantee holds only once every schema-creating node runs this code: an older peer still announces primary-first snapshots, so the receiver-side additive rule above stays necessary. Regression coverage: `unitTests/resources/createTableCatalogOrder.test.js` (write order, a create failing on either side of the publish point, and a second worker thread scanning the catalog while the create is paused).

## A keyless table's bare catalog row names its primary store (`databases.ts` `isPrimaryCatalogRow`)

A keyless table's bare `<table>/` row has no `name`, and some in the field have also lost `isPrimaryKey` (the producer is unknown; harper#3225). Its store still holds primary-format records. So the paths that decided primary-ness from the flag alone now use `isPrimaryCatalogRow` (flagged, or a nameless bare row): `initStores` selecting a table's store, `copyDb` copying or verifying a database, and the interrupted-drop and LMDB-drop paths. `primaryCatalogRowFor`, `liveStoreNamesFor` and `dropTableMeta` already decide from the bare key. `initStores` opens whatever it selected as a primary store. Deriving the open flags from `isPrimaryKey` instead opened primary-format records as an index store. On 5.1 the table read as empty and rejected every write; from 5.2 `handleLocalTimeForGets` reached LMDB-only code and the whole database failed to load. Not covered: a keyed table's bare row that loses the flag keeps its `name`, so `initStores` still skips it with the "no primary key row" warning.

A primary key declared on an existing keyless table cannot re-key its records. So `table()` clears `isPrimaryKey`, and the `primaryKey` mark in `properties`, on every declared key attribute, whatever the caller, and they persist as ordinary attributes. A schema-authored declaration logs an error naming the table; a peer definition logs the usual `Ignoring peer redefinition` warning. `updatedAttributes()` resets the class's cached `primaryKeyAttribute`, so nothing (notably `getNewId`) behaves as if the key applied. Regression coverage: `unitTests/resources/keylessTable.test.js`, `unitTests/bin/migrationKeylessTable.test.js`, `integrationTests/database/keyless-table-catalog.test.ts`.

## Per-origin subscription checkpoints (`subscriptionCheckpoint.ts`, `Table.subscribe`, `transactionBroadcast.ts`, harper-pro#922 items 3–4)

A `reportProgress` subscription on RocksDB exposes `checkpoint(holds?)`: the issue's compact form `{ v, scope, time, overlap, exceptions, members }`, where `S = time - overlap` is the inclusive replay boundary of every member not in `exceptions` and `members` is the XOR of `sha256(origin, originGeneration)` over every member, so healthy origins are neither named nor counted while the set is still bound. The per-origin vector stays internal: `B_O = min(F_O, oldest event of O handed to the queue and not yet taken, holds[O])`, encoded with `time = max B`, `S = max(min B, time - MAX_OVERLAP_MS)`; lowering any boundary only adds duplicates. `F_O` is certified by the broadcaster (`startOriginTracking`): every 5 s it captures the qualifying floors (`captureCertifiedFloors`: the own published floor, and every seq-row origin with a level-2 `closedFloor`, `originGeneration`, `fullCoverage`, `certifiedFrom`, no `partialHistory`, `hole` or `floorRevoked`) and schedules a notify pass; the capture a fresh pass began with (`passCapture`) is published as `certifiedFloors` only when that pass drains without a failed read, since every entry below a captured floor was in the log before the capture and the drained pass dispatched it. **Strict availability:** one known origin (own, any seq row, any log) without a qualifying floor means no capture, so `checkpoint()` is undefined. MQTT resumes from a checkpoint only outside the database generation that bound its scalar, and from the scalar within it (`server/DESIGN.md`).

- **Admission** (`admitCheckpoint`, `subscribe({ resume })`, 400/409/410): the scope string must match (database, table, table generation, target, delivery mode, `filterKey`); membership is resolved by subtracting at most four candidates whose route here began at the origin's first retained entry (`certifiedFrom === 0`, log retains sequence 1 — a node that joined after the checkpoint, admitted at boundary 0) from this node's candidates, at most 100 000 combinations; every member boundary must be at or above the resume floor, its origin not revoked, and held here by a full-coverage route with `certifiedFrom ≤ B_O`. Admission facts are rechecked at each replay yield against `auditStore.originStateEpoch`, which the seq-row merge bumps on any qualifier change and a copy-bound writer bumps after its commit. The replay seeks each member's log inclusively (`startByLog`, snapshot false, `includeLogName`), a record target filtered by exact key identity, and the subscription is `ungated`: the broadcaster's `startTime >= key` gate would drop a late lower-key commit, the omission harper#2928 describes. The boundary during the replay is the token's; after it, the certified floors (every entry below one appended before the replay ended was read by it, or dispatched live). **Qualifier lifetimes** (the seq-row merge): a revocation (a downgrade, or an applied-below-floor report) and a hole are sticky within an origin generation; a certificate naming a new origin generation starts that origin over (floor, revocation and `certifiedFrom` cleared, so the route proves its prefix again), and a completed base copy clears `partialHistory` and `hole`. `certifiedFrom` is the start of the route that certified the floor (two whole routes can cover disjoint intervals, so another row's start proves nothing about this floor), and a whole-log replay (a late joiner, a zero boundary) needs that same route to have begun at the origin's first entry, since another whole route can cover a disjoint interval; of two generations of one origin the one whose rows saw the highest floor is current (floors sample the origin's clock; a revoked row keeps the floor it was revoked at; a removed peer's retained row is frozen at its death), and the floor, revocations and holes count only from rows of that generation; a queued event without an origin tag holds every boundary, except a snapshot row, which is state rather than a log position; a repeated copy-completion mark clears a hole whether or not `partialHistory` changed; a certificate without a generation on a row that had one clears its level-2 qualifiers (that route certifies at level 1 now). A certified subscription that resumed from a scalar position delivers twice what its replay read and the live dispatch runs after it went live, and never what committed below its position before then: a scalar resume keeps main's exposure. A route mark or revocation names the generation it was derived under and is ignored once the row's generation moved on. Revocations and holes count only from rows of the current generation, so a dead peer's row for an earlier generation cannot hold the origin back. The epoch lives in a shared buffer (`bumpOriginStateEpoch`, after the row commits), so a recheck on any thread sees it. Every certified subscription is `ungated` once live, not only a checkpoint resume: the scalar-resumed MQTT session a rolling upgrade carries would otherwise drop a late lower-key commit the next floor certifies as delivered.
- **One writer per `[seq, P]` row; copy bounds are applied by the reader.** `updateRecordedSequenceId`, in route P's apply loop, is the only writer of `[seq, P]`: it reads the row and commits it from that snapshot with no cross-thread lock, so any other writer's change can be overwritten (rocksdb-js `occValidation: 'parallel'` does not flag a plain put landing between a commit's conflict check and its write). A source changes its own row only through `end_txn` fields. Route state (`originRouteStates`) is `[id, certifiedFrom, partialHistory, hole, generation?, fullCoverage?]`; `fullCoverage: true` restores a level-2 route's coverage after a copy that ran with partial coverage. A revocation naming no generation against a node with none clears its level-1 floor rather than revoking it, since there is no generation for the revocation to end with. An audit-less base copy (`isCopyApply`) leaves this node's log of each copied origin incomplete below the highest version it wrote, a database-wide fact a route row cannot carry, because the route that certified may be disconnected and has no writer. So the copying source records that version per origin in its own `[copyBound, peerId]` row (`{ [originId]: version }`, committed before the copied row is applied), and `readOriginStates` treats a route's `certifiedFrom` at or below any peer's bound for that origin as absent (`readCopyBounds`; a malformed row throws a 410, so admission refuses and capture issues nothing). A bound for this node's own origin (a copy restoring its own lost rows) raises the own start above it, so an own boundary at or below it, or a whole-log replay, is refused. A bound commit bumps the origin-state epoch, and a capture carries the epoch it read before its scans: `certifiedFloors` drops a capture the epoch has since passed, and an admitted replay rechecks. The two halves ship together: a core without the bound reader admits a route whose start a copy has since voided. Pinned by `subscribeCheckpoint.test.js` and `replicationSeqCursor.test.js`.
- **Not covered:** SSE/WS resume (no transport exposes a token; harper#2448 deferred them too); an origin two hops away (one-hop relay) or reached only over a partial route never qualifies; `eventFilter`/`rowFilter` without `filterKey` issues no token; the own floor qualifies only on an engine with `syncWal`; a late commit below a same-node MQTT scalar (harper#2928), since that resume replays from the scalar. Pinned by `subscribeCheckpoint.test.js` and `durableSessionCheckpoint.test.js`.

## Subscription version selection (`Table.ts`)

`Table.subscribe` resolves audit events through `eventFromAudit` for both replay and live delivery: unless `includeSuperseded` (defaulting to `rawEvents`) is enabled, record mutations must match the current primary version; an absent primary entry cannot establish a current version and is skipped. Publishing advances that primary version too: a put followed by a publish replays the message but not the put under the default rule. Messages and control events are independent. Version filtering precedes historical reconstruction and `previousCount` acceptance, while audit cursors advance over rejected entries. Single-record replay retains its bounded history walk because it also contains independent published messages; only an accepted replay event suppresses the current snapshot, and `eventFilter` also applies to that fallback. Default replay reads the current primary entry for each mutation. Live delivery makes one exception to dropping superseded mutations: when an older write commits after a newer one, out-of-order resequencing merges it into the record under the newer version and marks the entry `VERSION_REUSED`; the newer version's event may already have gone out without the merged change, so a superseded live mutation that the record lists among its folded writes (`additionalAuditRefs`, with that flag set) delivers the record's current state, once per merged write rather than for every older entry (`subscriptionLatePatch.test.js`). A RocksDB transaction's timestamp is assigned when it is created, and commits complete in any order (a transaction whose body awaits, or rocksdb-js's concurrent commit threads), so timestamps are not a delivery boundary: the collection current-state branch does not advance `subscription.startTime` to the newest record time its scan saw, nor filter buffered events by it, because writes to records the scan already passed, messages, and older transactions committing after the scan all fall at or below it (`subscriptionLateCommit.test.js`, harper#2933). Default events already carry only current record versions, so the cost is duplicate current values under the retained-message semantics the scan already has. A delete is materialized from the record's current entry. At the end of a default full-record snapshot, `keepCurrentRecordEvent` refreshes a buffered mutation's value, version and type from that entry when its version has advanced: a publish can advance the version without any replacement row-state event, so dropping the buffered mutation would lose the update or deletion (`subscriptionBufferedState.test.js`). A recreated row turns a buffered delete into its current put; messages keep their independent payloads. The original localTime and audit-size attribution stay with the buffered event, and row/event filters run on the refreshed value at delivery. Duplicate current-state deliveries remain intentional, including equal-version folded writes; no per-key dedupe is introduced. Raw current-only events retain the stale-drop rule. This repairs already-buffered events only: the pre-existing live version guard can still reject a mutation before it is buffered when a later publish is already visible. Publishing's existing metadata mask can also clear INVALIDATED; refresh follows the resulting primary state rather than changing publish semantics. `includeSuperseded` subscribers without certified progress keep the time gate, since their events are historical records, and so does the `previousCount` branch; both still drop an older transaction that commits after the scan. Progress-reporting snapshots keep every buffered event and leave the live time gate untouched, including durable MQTT QoS>0 on RocksDB. Every subscriber of a key on a thread receives the same audit-record object in one notify pass, so `currentEntryForAudit` reads that entry once per audit record instead of once per subscriber (`subscriptionEntryRead.test.js`). It memoizes on the record object's identity (plus store and record id), which holds only because `readAuditEntry` decodes a fresh object per log entry and a key's subscribers are walked synchronously; the memo is cleared by a microtask after each pass, so it never outlives the delivery it serves or pins a dropped table's store. Opting into superseded full records retains audit-history reconstruction costs and retention limits, including patch reconstruction on durable MQTT live delivery. Collection `startTime` replay leaves `subscription.startTime` — the exclusive replay cursor, separate from the per-topic positions `DurableSubscriptionsSession.saveSubscriptions` persists — never past a key with an unhandled in-table record: RocksDB gives every record of a transaction one `txnLogKey`, so the cursor moves to a key only on reaching the next key or finishing, and an early return (failed send, close at a yield or drain) leaves it up to one transaction back, which the resume re-sends (`subscriptionReplay.test.js`, "cursor after replay stops early"). The cursor counts events handed to the subscription queue, not consumed ones; `close()` discards the queue. Initial current-state delivery (`!request.omitCurrent`, both collection scan and single-record) and the reload re-snapshot (`currentScopeRecords`) skip entries with `expiresAt < Date.now()` on tables without a source `get` (`!hasSourceGet`, after updating `cursorMaxTime` in the collection scan) without evicting, so SSE, WebSocket, and MQTT retained (`rh: 0`) subscribers connecting during `[expiresAt, expiresAt + eviction]` do not receive expired records; tables with a source `get` are unchanged (subscribe does not call the source), and `startTime`/`previousCount` replay (which walks audit history via `eventFromAudit` and under default settings still carries the current entry's value) and live/buffered write delivery (`eventFromAudit` / `keepCurrentRecordEvent`) remain unaffected (`subscribeExpiredCurrent.test.js`, harper#3209). A `reload` marker (one table-wide audit entry, `recordId: null`) means rows were back-filled with no history, and every path that reaches one handles it alike. A consumer that keeps positions is closed with `RELOAD_REFUSAL` (410 `RESUME_HISTORY_UNAVAILABLE`, which resets a durable MQTT session): live when `reportingProgress`, in a collection replay when the resume is checked or the request sets `reportProgress`, since LMDB keeps positions it gets no certificate for. Any other user-table subscriber gets its current scope again, never ahead of the history, initial snapshot or buffered events in progress, whose older values would overwrite it. A `startTime` replay re-snapshots inline and moves `subscription.startTime` past a marker only once that scope is handed off, so an early stop resumes before the marker; consecutive markers share one scan, and live commits during a scan after the cursor has finished are buffered behind it. A `previousCount` backfill and a live marker that lands while history or the initial snapshot is pending re-snapshot after the buffered events drain; a marker spends no `previousCount` slot. System-database and `rawEvents` subscribers get the raw marker, in every collection scope. A failed re-snapshot closes the subscription. Both current-scope scans read a non-root scope as `[thisId, …]` array children, so neither delivers rows for a string-path prefix such as MQTT `T/team/#` (harper#3481) (`reloadMarker.test.js`, `durableSessionResume.test.js`).

## Audit-store `'committed'` notification batching (`transactionBroadcast.ts`)

The cross-thread subscription path (default `crossThreads`) drives every `Table.subscribe()` consumer. When the database's audit store emits `'committed'`, we walk the audit log via the reusable `auditStore.subscriptionLogRange` and dispatch matching records to subscribers. The commit listener, yielded continuations, idle registration restart, and certified-progress failure checks all use that same range. These properties of this path are easy to break and worth knowing about before changing it:

- **`databaseSubscriptions.activeCount`** is the count of live `Subscription` instances on a database. It is incremented at the end of `addSubscription` (after the Subscription is created, so the `scope: 'full-database'` early-return path correctly skips counting) and decremented in `Subscription.end()`. `notifyFromTransactionData` short-circuits when this is zero — the reusable rocksdb iterator, or LMDB's `lastTxnTime` cursor, stays put. **Registration is the delivery boundary.** A subscriber receives only entries that the broadcaster reads after it registers: when `activeCount` is zero, the RocksDB iterator restarts at the end of the log (the committed watermark, so a transaction still uncommitted then is still delivered, and a pending yielded pass continues on the new iterator), and LMDB's cursor moves to the newest committed log key (`newestCommittedKey`; a `Date.now()` seed trails the native-clock keys by up to a millisecond and redelivered a write committed just before); otherwise, unless a notify pass has yielded part-way through a backlog, `addSubscription` first dispatches what is already committed to the existing subscribers, synchronously and at most one notify batch (`NOTIFY_BATCH_SIZE` entries), leaving any rest to a scheduled pass. So a new subscriber does not receive a message, or a notification for a write, committed before it registered; history comes only from an explicit `startTime` or `previousCount` request. Same-thread (`crossThreads: false`) delivery happens at commit, so it has no backlog to bound. The boundary is not exact in three cases, each of which can deliver pre-registration entries to the new subscriber: a backlog longer than one batch at registration, or a pass that has yielded part-way through one (replication catch-up), since draining it synchronously would stall the worker; the subscribe happens inside a dispatch, which is already walking the iterator; and an entry committed before registration sits behind a transaction still in flight then (the watermark hides it from the dispatch). Without this short-circuit, an idle database with no subscribers still pays the audit-log iteration cost on every commit during replication backlog catch-up.
- **`notifyScheduled` + `setImmediate`** in the `'committed'` listener defers the iteration off the commit microtask. Multiple `'committed'` events that land in the same event-loop turn collapse into one notify pass. `notifyScheduled` stays set for the entire drain — including across yield-and-resume turns — so a re-entry from a new `'committed'` event cannot spawn a second concurrent notify on the same iterator.
- **Batched yielding** in `notifyFromTransactionData` (`NOTIFY_BATCH_SIZE`) is gated by `allowYield`. The `'committed'` path passes `allowYield = true`; the `listenToCommits` (same-thread `aftercommit`) path does not, because that path holds an inter-thread `'thread-local-writes'` lock that must not span event-loop turns. `subscribersWithTxns` is carried across yields via `subscriptions.pendingTxnSubscribers` so the `end_txn` signal fires exactly once when the iterator truly drains. When `activeCount` drops to zero mid-yield, the next continuation drops the carry-over to avoid invoking ended subscribers' listeners.
- **A notify pass never reads a closing or closed audit store.** LMDB delivers `'committed'` from native code, including for the writes `close()` flushes after its status is already `closing`, so a pass can run after its store began closing. The subscriptions are ended only at reopen (`endSubscriptionsFromEarlierHandles` needs the new store's generation to pick the error), so until then `activeCount` is still positive. The pass checks `rootStore.status` before `resetReadTxn`/`getRange`: a read there throws out of `setImmediate`, and on a `closing` LMDB store it also arms lmdb-js's read-txn reset timer, which throws its own uncaught exception. It still rotates `nextTransaction`, as the no-subscriber path does (`databaseGeneration.test.js`, "Commit notification racing a database close").
- **The ancestor key walk must strictly shrink.** `notifyFromTransactionData` notifies a changed key and then each `/`-delimited ancestor (`a/b/c` → `a/b/` → `a/` → the `null` root). It stops when the computed parent equals the current key, because a key rooted at `/` otherwise yields `/` as its own parent forever, and this loop is synchronous inside the notify pass with the batch yield outside it, so a single non-terminating walk seizes every worker holding a subscription on the table (harper#2687). Any change to the parent computation must keep a `/`, `/foo`, or `//x` key terminating in `unitTests/resources/transactionBroadcastKeyWalk.test.js`.
- **Ending a subscription never reshapes a subscriber array a delivery loop is walking.** Listeners run synchronously inside the fan-out and can end their own or any other subscription there: a throwing `rowFilter`/`eventFilter` closes one through `failSubscription`, and a `'data'` listener can call `end()`. Splicing in place shifted the next subscriber past the loop, which then silently missed that record (harper#2771). `Subscription.end()` therefore marks the subscription ended at once — it nulls `subscriptions`, the liveness signal `Table.subscribe` also reads, and decrements `activeCount` — but when its key's array is being walked it only sets the array's `hasEnded`. Each array counts the loops walking it in `traversals`, and the loop that brings the count back to zero compacts the ended entries out, detaching an emptied key and table as `end()` would. Outside a walk, `end()` removes the subscription immediately. Each loop walks only the array's length at its start, so a subscription added to a key during that key's delivery starts with the next record. The `reload` walk visits at most as many keys as the table had when it started (a key added during the walk can take the place of one that left). Without both bounds, a listener that ends and re-subscribes extends the loop forever. The per-key, `reload` and `end_txn` loops all skip a subscription whose `subscriptions` is null. A new loop over these arrays needs the same count, bound and check (`unitTests/resources/transactionBroadcastEndDuringDelivery.test.js`).
- **Closing with a final message always finishes, then rethrows.** `IterableEventQueue.close(finalMessage)` delivers the message while `closed` is still false. Then, in a `finally`, it sets `closed`, settles a waiting iteration and emits `'close'`, so `Subscription.end()` deregisters the subscription even when a `'data'` listener throws on the message. A waiting iterator gets the final message before it completes, and `'close'` fires once even if a listener closes the queue while handling the message. The listener's exception is rethrown. If a `'close'` listener also throws, its error replaces the first. A caller that must not throw catches it: `failSubscription` in `Table.subscribe` logs it, so nothing escapes into the replay's `.catch` or the fan-out, and `endSubscriptionsFromEarlierHandles` warns and goes on to the next subscription (`IterableEventQueue.test.js`; `subscriptionReplay.test.js`, "a replay that fails"; `transactionBroadcastEndDuringDelivery.test.js`).

## `createBlob(readable)` and `table.put()` don't synchronously drain the source

When a blob attribute is created from a Node `Readable` (e.g. `createBlob(stream)` then `row.payload_blob = blob; await table.put(row)`), the put does **not** wait for the underlying stream to fully drain into the file before resolving. Internally `saveBlob` kicks off a `writeBlobWithStream` pipeline whose `storageInfo.saving` promise is tracked separately. The put resolves once encoding has captured the blob reference; the bytes finish writing concurrently.

Consequence for callers that wrap the source in a hashing `Transform`: calling `hash.digest('hex')` after `await table.put()` is unsafe — more `chunk.update()` calls can still fire as the stream drains, producing `Error [ERR_CRYPTO_HASH_FINALIZED]: Digest already called`. Finalize the hash only after the source has ended and the blob's `storageInfo.saving` has settled, as `components/deploymentRecorder.ts`'s streaming ingest does (`await Promise.all([putDone, tapDone, saving])` before `digest`). Its in-memory sources, and its capped fallback for a missing deployment table, buffer and hash before the put instead.

## Table drops, the `dropping` tombstone, ghost tables, and lifecycle stamps

A table is a set of RocksDB column families (`T/` plus `T/<attr>`) and a set of catalog rows in the
`__dbis__` store, with no transaction spanning the two. `Table.dropTable()` therefore persists a
`dropping: true` flag on the primary catalog entry (`T/`) before any destructive work, then drops the
column families (awaited - a failed drop must surface as the operation's error), then removes the
catalog rows. If the process dies or a drop fails partway, the tombstone survives; the boot-time schema
load (`completeInterruptedDrop`) and a same-name `table()` create both complete the interrupted drop
instead of re-opening the surviving rows with create-if-missing, which resurrected "deleted" tables.

**Lifecycle stamps (harper#1212).** The tombstone is node-local, so a peer offline for a replicated
`drop_table` would bring the table back through the schema handshake. Two durable facts give every node
one rule: the primary row carries `createdTime` from create (`declareTable`, kept from a peer's propagated
definition), and the tombstone carries `droppedTime` (`dropTable({ peer: true, droppedTime })` applies a peer's), which
every completion path promotes to a `/dropped/<table>` row (`promoteTombstoneToDropMarker`) before removing
the tombstone — no second-write crash cut. Both come from `tableLifecycleTime()`, the record-version clock;
`isDeadGeneration(createdTime, droppedTime)` is strict (equal survives, a missing stamp is 0). The marker
outlives a same-name recreate, only a newer drop overwrites it, the load parser skips `/dropped/` rows, and
`getTableDrops` / `recordTableDrop` / `onTableDropRecorded` serve replication; a recorded marker is announced on every
thread (each owns its own replication connections) and advances that thread's `tableDropEpoch`.

A drop with no `droppedTime` (a node-local table's, a `localOnly` one, or a tombstone written before the stamps
existed) is never given one at completion: a time invented then could postdate a peer's live recreate. On RocksDB
its completion leaves an untimed `/dropped/<table>` row instead, name history for the store naming below. Every
reader of a drop time skips that row (`getTableDrops`, `pendingOrRecordedDropTime`, `isDroppedPeerGeneration`
and the create checks), so peers never learn of the drop, and a timed drop overwrites it.

The rule is enforced where a generation becomes or stops being live, under the lock that publishes the primary
row or writes the tombstone, so no peer path can check it and then act on a catalog another thread changed (`unitTests/resources/dropTableLifecycle.test.js`):

- A create carrying a peer's generation (`origin: 'cluster'`, or a supplied `createdTime`) throws
  `TableGenerationDroppedError` (409) when a marker here retires it, and so does a stamped one for a name live here,
  before its attributes merge into the newer generation. The check precedes the create journal and every store
  open, so a refused create leaves nothing to reclaim. A peer that kept no stamp is stored at `0`: any drop retires
  it and nothing backfills it. `undefined` is left to tables created on a pre-stamp build.
- A peer's drop (`dropTable({ peer: true, droppedTime })`) never retires a `replicate: false` table, and with a
  time only a generation created before it; `writeTombstone` re-checks the row it locked. A kept generation
  resolves `false` and writes no tombstone or retirement journal, and the peer's time is recorded as a marker
  either way. A tombstone is written only after the rule passed, so the recovery that completes one judges
  nothing again. The operation bridge treats a drop as a peer's only through `REPLICATED_FROM`, which
  `server.operation` sets from its context: a JSON body cannot claim it, and `schema.dropTable` discards a
  client's `droppedTime`.
- A node-local table's own drop leaves no `droppedTime` and is not forwarded. A marker from an earlier,
  replicated generation of the name is kept and still sent.
- `dropTableMeta` removes a name's rows only when no primary row, live or still dropping, exists.
- A table with no stamp was created by a build that stored none, so before the first load on a build that stamps;
  that load writes the bound as `createdBefore` on its primary row (`catalogCreatedBefore`). A drop recorded after
  the bound retires the table outright, and only an older drop leaves the replication layer's upgrade heuristic
  anything to decide. A table created during a rollback to such a build gets its own bound at the next load.
- The legacy per-table layout (`databasePath` is not the database name) has no database catalog for a marker,
  so its drops leave none.

**Store names and 5.2 rollback (harper#3102).** A RocksDB table's store names are distinct from its `createdTime`
stamp: a generation suffix (`T/@<generation>`) on the primary row, which `writeTombstone` also checks as identity.
First-time creates use bare primary/index names only when this node has no `/dropped/` row of the name (timed or
untimed, including one recorded for a peer's drop this node kept or never held), no journal row for the table,
and no `T/` column family. Any name history requires a suffix, including after local-only reclamation. Incoming
primary-attribute suffixes are replaced by this node's physical naming choice, while a peer's `createdTime` is
kept. Create journals have their own identity; when a creating and retired journal name the same primary, the
creating row leaves that primary to the retired row's blob sweep. Recovery reads their current phases under the
catalog lock. Their `creatingStores` field must stay separate from `stores`, which shipped 5.3 readers
destructively reclaim without recognizing a published bare primary. Reclamation always preserves stores owned by
the live, non-dropping catalog and never sweeps that primary's blobs: a 5.2 writer can reuse bare names while
ignoring the retired journal. A drop whose tombstone another thread completed first retires only its own stores
that the live catalog does not own, and still resolves `true`. Tables with suffixed names keep them and remain
outside 5.2 rollback support, as do suffixed recreates. During interrupted-drop recovery, a bare predecessor can
remain until its asynchronous reclamation finishes; 5.2 ignores that recovery state and can expose predecessor
rows through a recreate. `unitTests/resources/dropTableGeneration.test.js` enforces naming, crash recovery, and
live-store ownership; `integrationTests/upgrade/first-create-downgrade.test.ts` exercises the real 5.2 round trip.

## The exclusive `update-attributes` lock is a bounded synchronous wait, and drop-then-recreate needs the column-family eviction fix (`Table.ts`)

The create/schema-update path's exclusive `update-attributes` lock is a synchronous bounded wait
(`acquireUpdateAttributesLock` in `Table.ts`: brief hot spin, then `Atomics.wait` backoff, retryable
`ServerError` after the 10s `UPDATE_ATTRIBUTES_LOCK_TIMEOUT`, harper#2251). Release is structural —
`table()` releases in a single `finally` and `dropTable` uses `withUpdateAttributesLock` — so a throw
inside the locked window cannot leak the lock (`unitTests/resources/updateAttributesLock.test.js`).
Because the acquire can throw, `table()` takes the RocksDB lock _before_ it mutates the live `Table`
(attributes, class metadata, index handles): losing the race then leaves this worker's in-memory
schema exactly as it found it, and moving any mutation above that acquire reintroduces schema drift
the catalog never saw. LMDB keeps the lazy acquire — its `exclusiveLock()` is an environment-wide
write transaction that cannot time out, so taking it eagerly would stall every write to the database
on an unchanged reload. A successful acquire that waited past `UPDATE_ATTRIBUTES_LOCK_SLOW_WAIT` (1s)
warns once, since contention is otherwise invisible until it becomes a timeout. The locked sections
MUST stay synchronous: the wait blocks the event loop, so an awaited operation inside one would stall
a concurrent acquirer to its deadline. Dropping then recreating a same-named table within one process
depends on rocksdb-js's column-family eviction fix (≥ 2.1.0, rocksdb-js#647; `package.json` pins a
later release): without it the recreate reuses a dangling handle and every write fails with "Invalid
column family specified in write batch". Regression suite: `unitTests/resources/dropTableGhost.test.js`,
which fails by design on pre-fix bindings.

## RocksDB transaction log purges are database-wide only (`ResourceBridge.deleteTransactionLogsBefore`)

On RocksDB, every table in a database writes to one shared set of transaction logs (partitioned per
origin node, not per table), and `purgeLogs()` deletes whole log files — rocksdb-js has no table
filter, and adding one would mean rewriting files instead of deleting them. So a table-scoped
`delete_transaction_logs_before` is unimplementable at the storage layer; the bridge rejects
`table` on RocksDB with a 400 rather than silently purging every sibling table's history
(harper#2049 — the original code did exactly that, and a _typo'd_ table name did too, because a
missing table fell through to the no-table branch; that now 404s). Two consequences to preserve:
the deprecated `delete_audit_logs_before` op _requires_ `table`, so it always errors on RocksDB
(the message steers callers to the new op without `table`); and the table/no-table checks in the
bridge use `!= null` presence, not truthiness, so a table named `"0"` addressed numerically stays
table-scoped instead of widening to a database purge.

## Boot replay reads bypass the primary-record cache

`DatabaseTransaction.save` reads replay commit bases with `uncachedRead`: WeakRef targets survive a synchronous replay job even after cache eviction, so caching already-durable records behind a stale watermark retained the whole scanned backlog (harper#2950); enforced by `replayCommitBoundaries.test.js`'s cache-identity and crash-reopen heap-growth tests.

## Replay limits do not establish data loss

`replayLogs`' time and progress guards cannot prove tail durability or peer completeness from a potentially stale `txn.state`; their diagnostics require preserving a separate database/log copy before further writes can advance the replay position, checking that position before recovery, and verifying peer completeness before re-cloning. `replayCommitBoundaries.test.js` enforces the advice on durable-backlog and unflushed-tail crash/reopen cases, including recovery from a copy taken after the aborted boot closed without further writes; elected replay still rejects without peer recovery advice (harper#2951).

## Query-plan range estimation blends statistical estimates by confidence (`search.ts`)

`estimateCondition` estimates range comparators (`starts_with`/`prefix`, the `between` family, `lt`/`le`/`gt`/`ge`) via
the store's `estimateCount({start, end, …}) → { count, confidence }` (rocksdb-js ≥ 2.8.0) instead of flat table
fractions, blended as `round(confidence × count + (1 − confidence) × fraction-heuristic)` so a low-confidence estimate
degrades to the historical behavior rather than replacing it. Invariants that are easy to break:

- **Capability is feature-detected per store** (`typeof store.estimateCount === 'function'`) because LMDB-backed and
  custom index stores do not implement it. The result shape is validated (`Number.isFinite(count)`,
  `0 ≤ confidence ≤ 1`) and the native call is try/caught, so a store that answers differently — or one closing
  concurrently — degrades the plan to the fraction heuristic instead of NaN-poisoning condition ordering.
- **The estimated range must be the executed range.** Construction mirrors `searchByIndex`'s comparator switch;
  bounds longer than `MAX_SEARCH_KEY_LENGTH` fall back entirely because execution truncates + filters (wider range
  than the estimable one). Two ways this has already been got wrong: `lt`/`le` need `searchByIndex`'s null-exclusive
  lower bound, or the estimate counts the `[null, primaryKey]` entries an `indexNulls` index holds and execution
  skips, which on a mostly-null index is worse than the flat heuristic it replaces; and `RocksIndexStore` must widen
  value-space bounds to `[value, MAXIMUM_KEY]` composite bounds, because the base implementation's byte-successor
  semantics exclude the wrong entries on composite `[value, primaryKey]` keys. `getRange` and `estimateCount`
  therefore share one `translateIndexBounds` helper rather than two copies.
- **Open lower bounds are per store** (`openStart` in `searchByIndex`, mirrored in `estimateRangeCondition`). A
  secondary-index scan opens at `null` exclusive: `true` sorts above `false`, so opening there drops boolean `false`
  rows. A primary store keeps symbol-keyed metadata (`Symbol.for('id_allocation')`, and `Symbol.for('structures')`
  under LMDB) between `null` and `false`, so its scans still open at `true` or they return that metadata as rows.
  Both are pinned by `searchBooleanFalseIndex.test.js`.
- **Negated conditions estimate `Infinity` at the root** (`estimateConditionForTable`), following the filter-only
  convention (`contains`/`ends_with`): the negated flag always forces `needFullScan`, so `estimated_count` here is
  execution-cost ordering, not result cardinality — a narrow negated range must never become the driving condition.
- **Non-driving filters drop null and omitted values the way index ranges do** (`filterByType`, harper#3212). No index
  holds an omitted value and `lt`/`le` ranges start above `null`, so range filters and `ne null` reject omitted values
  and `lt`/`le` reject null. SQL `IS NULL` counts omitted as NULL, so it is pushed as filter-only `ne null, negated`.
- `estimatedEntryCount` reads `estimate-num-keys` (O(1)) rather than iterating; it skews high on
  overwrite/delete-heavy data until compaction, which is acceptable for the relative-ordering and
  explicitly-estimated consumers it feeds (and it is a divisor — keep the ≥1 floor).

## A table declaration lands where its application's `databases` binding resolves the name (`resources/databases.ts`)

`table()` is the global instance of an internal target-bound factory, `declareTable(target, definition)`.
A `TableTarget` is the small binding the declaration body needs and nothing more: the root store, the
`tables` graph the class is published into, what to do after a lost create race (another thread created
the table first), and who owns the column-family wrappers the declaration opens. The global target is
`database()` / `databases[name]` / `resetDatabases()`, and it adopts every RocksDB wrapper into the
root's owned list (see [the teardown note](#a-rocksdb-databases-teardown-closes-every-wrapper-its-loads-and-declarations-opened-databasests-harper3120)); a branch target (harper#2264) is that branch's
`rootStore` / `tables` / `reloadBranch`, and it adopts every wrapper into `branch.openedStores` so
`close()` releases them.

An application that declared `branchedDatabases` declares through `scopedTableFactory(branches)`, which
routes each declaration by database name — to the branch of that name, or to `table()` itself. GraphQL
`@table` (`graphql.ts`), `scope.ensureTable` (`components/Scope.ts`, `componentLoader.ts`) and
`defineTable` (`defineTableUsing`, through `security/jsLoader.ts`) all go through it. **An unbranched,
shared application gets `table` and `defineTable` by identity** — `scopedTableFactory(undefined) ===
table`. An isolated application gets a declaration-only wrapper even without branches, so its own
schema can claim maintenance that no pool worker configured; hydrated tables remain pool-owned.

Consequences to preserve:

- A branch root store's `databaseName` is its STORE identity (`initStores` stamps `storeName`), and the
  branch's blob roots resolve from it. The create path may only fill the name in when it is unset
  (`??=`), never overwrite it with the logical name.
- A branch Table class carries the base's logical name, so the Table statics that resolve the global
  schema by name (`dropTable`, `addAttributes`, `removeAttributes`, audit-enabling `subscribe`) stay
  refused through `assertSchemaMutable`. Schema evolution of a branch table is the factory's
  existing-Table path — the re-declaration `@table`/`defineTable`/`ensureTable` perform on every reload —
  which runs entirely against the branch's own store and catalog.
- A branch is scope-private: no `updateTable` event names a branch class (declaration, reload and
  relationship hydration all pass the announcement policy through), so replication and analytics never
  observe one. Cross-thread propagation still happens: the ITC schema-change signal carries
  `branchPath`, and `syncSchemaMetadata` (`server/itc/serverHandlers.js`) hands such a message to
  `reloadBranchAt`, which re-reads the catalog into the branch's `tables` on every thread that holds
  that branch open — the same pre-backfill signal the base path relies on so a worker keeps a new index
  maintained while another worker's backfill runs — instead of running the global rescan.
- The lost create race is handled per target: the global path rescans everything (`resetDatabases`);
  a branch reloads only itself, and the relationships that reload queues are hydrated through the
  application's own branch set (`branch.relatedBranches`, stamped by `prepareBranches`), never the
  global map.

## Ordering an in-memory result set reads each record at most twice (`Table.ts` `transformToOrderedSelect`)

Ordering an in-memory result set reads each record from the store at most twice: once to load it,
and at most once more to materialize it after the sort if the cache let it go in between. The
comparator never reads the store: sort keys are resolved once per row before the sort, so a GC
between load and compare cannot turn every comparison into a store read (harper#2675). The ordering
owns its working set; the cache cannot know about it.

`transformToOrderedSelect` consumes SKIP before pagination or counts. Top-level `Table.search` enables its local-only invalidation filter before grouping or sort-key resolution, so computed resolvers never receive these incomplete entries and an interleaved stub cannot split an indexed group. Nested callers leave that filter disabled. The materializer still checks flags after lazy primary loading. `getAttributeValue` treats missing record fields as absent keys while preserving entry-metadata resolvers for ordinary reads. Closing the iterator stops further materialization and delivery, including a pending source load resolving to either SKIP or a record; source rejections retain their existing behavior.

## Each hop of a multi-store commit cascade starts with a full idle window (`DatabaseTransaction`)

Once a chain enters `commit()` its write set is sealed and the caller is awaiting the commit; the
idle limit polices an application holding a transaction open, not the commit itself. Every link
therefore starts each hop of the cascade with a full idle window of its own engine, never with the
remainder the pre-commit phase or an earlier hop happened to leave (harper#2675). The bound is per
hop: a native commit that stalls for a whole window still lets the monitor reap the waiting links,
and the cascade gains no crash or cross-store atomicity from this.

## A related-table read uses the related table's own database link (`Table.ts` relationship resolvers, `search.ts` join)

A native read transaction belongs to one database (RocksDB rejects a foreign one; LMDB reads the wrong data), so every read of a related table takes its transaction from that table (`_readTxnForContext` / `_txnForContext`), never from the declaring table's `txnForContext`. A join into another database scans after REST commits the request, so it leases that link's handle when it runs (`search.ts` `leaseRelatedReadTxn`, `DatabaseTransaction.leaseReadTxn`); the leases live on the search's `filtered` object and `Table.search` releases them with its own handle. Either side of a search can scan for ticks with the other idle (a drained join map, a filtered or sorted source, a related scan yielding per rejected entry, the middle hop of a multi-hop join), so the RocksDB monitor renews a search's holder and leased links together while any of them showed its own range activity this tick or the last, consuming the flag of a link it never walks (a `save()`-adopted handle). Renewals never count, so abandoned opposite-direction leases are reaped. LMDB snapshots are reference-counted and need none of this. A related read after commit takes a handle-free transaction and sees the latest state (harper#3603); each database is read at its own snapshot.

## `enc:v1:` env values decrypt through a registered decryptor, and skip non-fatally without one (`resources/loadEnv.ts`, `resources/secretDecryptor.ts`, `utility/envFile.ts`)

Core recognises the `enc:v1:` value prefix (`isEncryptedEnvValue`), exposes a decryptor registration
hook, and decrypts through the registered decryptor when loading `.env` files; the cryptography and
the cluster-shared private key live in the Pro env-secrets component. Without a registered decryptor
an encrypted value is skipped with an error logged, never fatally: the node still boots, the value
can be replaced through `set_env_value`, and a replicated encrypted value cannot crash a non-Pro
node. The application sees a missing variable rather than ciphertext. Plaintext and encrypted values
coexist per value; `get_env_keys` and `get_component_file` still expose key names only. The
envelope format, key model and client flow are user-facing and belong in HarperFast/documentation.

## Closing an LMDB database closes its environment, never its dbis (`databases.ts` `closeDatabase`)

Aliases that resolve to one path share one LMDB root store but open their own dbis. `mdb_env_close` releases
every dbi, while lmdb-js's `DbiWrap.close()` calls `mdb_dbi_close` on the `MDB_env*` captured at open, so closing a
dbi after another alias closed the environment is a use-after-free (an intermittent segfault in the lmdb unit run).
`closeDatabase` closes an LMDB root once, skips its dbis, and closes every alias sharing it; RocksDB column families
are refcounted and still close one by one (shared-store cases in `databaseAliasIdentity.test.js`). Only `closed`
counts as closed: lmdb (through 3.5.8) resolves `close()` early while a read is in flight on an environment that
never wrote, so a drop unlinked an open `.mdb`. `openLmdb` gives each root one close completion, resolved by lmdb's
close callback (dropped on rejection); a close finding `closing` awaits it, and a drop removes the file after it even
when an earlier close finished. Remove the wrapper once lmdb returns its deferred close (`lmdbCloseCompletion.test.js`).

## A RocksDB database's teardown closes every wrapper its loads and declarations opened (`databases.ts`, harper#3120)

A redeclare (an insert that adds an attribute, `addAttributes`, a cluster definition) used to reopen
`__dbis__` and every indexed column family, overwriting the references the table graph holds. rocksdb-js
releases a native handle only on close or garbage collection, so the replaced wrappers held the
process-global refCount up and online `restore_backup` (which waits 3 s for closure) refused the database
as held open. `declareTable` now reuses the root's one `__dbis__` wrapper (`internalDbisFor`) and, on a
redeclare, a plain index's open wrapper on an unchanged store (`indexFor`); a custom index (HNSW) is
always reopened, since `openIndex` builds its state from the current options, and is never reused for a
plain declaration. Every wrapper `initStores` or `declareTable` opens for a global RocksDB root is
recorded in `ownedRocksStores` under the root path, as a `WeakRef` so collection still releases an
unreachable one. `closeDatabaseStores` closes the live entries before the root, and drains the record
again afterward for a declaration that resolved the root mid-close. A wrapper whose close failed
(including a custom index's cleanup close after its setup threw) is held strongly, since collection may
not release it; the record is keyed by path because a lenient close discards the root object even after
a failure. A wrapper is never closed when the graph stops pointing at it: a query that took it before
the redeclare still opens ranges through it, and a closed wrapper would refuse them (a range already open
keeps reading either way). Short-lived wrappers (column-family drops, the blob sweep) close themselves
and are not recorded; `destroy()` closes every wrapper on the root, so a drop only forgets the record.
Enforced by the redeclare and close-failure cases in `unitTests/resources/closeLoadedDatabases.test.js`
and, end to end, `integrationTests/database/restore-backup-online.test.ts`.

## Every `.mdb` under a storage path must open as LMDB (`databases.ts` `getDatabases`)

A rescan (`resetDatabases()`, which any schema change triggers) opens each `.mdb` at the top level of the storage
path and of every configured database path, and one directory below the storage path as a legacy
`<schema>/<table>.mdb` table. lmdb-js (3.5.6, and still 3.5.7) frees its `ExtendedEnv` twice when `mdb_env_open`
fails (`EnvWrap::openEnv`, then `closeEnv`), so a non-LMDB file there takes the process down with SIGSEGV and no
stack at the next rescan. Until lmdb-js returns the open error, tests keep non-database fixtures outside those
paths; `unitTests/bin/copyDbIntegrity.test.js` rescans while its fixture exists (harper#2669).

## A local-only write marks both the record and its audit entry, and replay preserves it (`Table.ts` internal writes, `replayLogs.ts`)

`LOCAL_ONLY` rides both persisted forms — the audit entry's `extendedType` and the stored record's `metadataFlags` — so a replication sender skips it by a bitmask test without decoding the value. Record mutations set both from `options.localOnly`. A publish applies the option only to its message audit entry and preserves the existing row bit, because a message does not change the row's replication eligibility. The static protocol verbs never carry the option; of the instance verbs only `publish(target, message, options)` forwards one. Crash replay re-derives it from the entry, because replay re-encodes the record but never re-appends its audit entry (replay transactions are `isRetry`). The row bit reflects its latest mutation, so a caller needing a row to stay local re-asserts it on every mutation. Reload and derived-index `evict` markers are always local-only; lock control entries never are. Enforced by `unitTests/resources/localOnly.test.js` (both engines; crash + boot replay on RocksDB). Ordinary LOCAL_ONLY creates and same-slot updates retain existing placement, including a non-owner projection or omission; their complete audit body is not delivered to owners. Only an application attribute-slot transition that excludes its writer is newly refused. Other LOCAL_ONLY writes succeed without confirmation; this adds no cross-database rollback guarantee.

## Legacy record-based residency is the listed nodes plus the writer, and a patch over a stub stays a stub (`Table.ts` `_writeUpdate`, harper#2257)

A node outside a record's residency keeps an `INVALIDATED` stub (primary key, non-computed indexed fields and created time — never `null`) whose `residencyId` names the nodes holding the complete record; a read fetches from one of them. Two rules keep a listed node complete. A write made here (not `isNotification`, `sourceApply` or replay) whose record-based residency excludes this node adds this node to the list and stores the full record, warning once per table per thread: before this, an ordinary write destroyed the writer's copy while the log recorded a plain upsert. And a patch whose base (stored, or staged earlier in the transaction) is a record-based stub is stored as a stub again on every path. Without an explicit received residency it keeps the base's `residencyId` and does not consult the residency function: the merged row lacks the fields a placement decision needs, and the base's list is the one naming a complete holder. An explicit received residency stays authoritative, but does not make the receiver complete. A replicated or source write with no residency list, and `setResidencyById`, still omit or stub as before; an id-based omission writes no row and leaves any stored row and its index entries as they were (harper#3566). Enforced by `unitTests/resources/writerResidency.test.js` (both engines).

Transport invariant: a stub is never sent, served, or stored as a complete record through harper-pro GET_RECORD and its copy sender, except the legacy base-copy fallback for a peer without `residencyStubCopy` or whose capabilities are not yet learned. For a peer listed in the stub’s residency (or with no residency list), that fallback sends the stored projection as an ordinary `put`, which an equal-version holder skips; a receiver without the row stores it as complete. A capable peer receives `invalidate`. Excluded peers still receive an invalidation or are skipped under id-based residency. See harper-pro's `replication/DESIGN.md`, Send-side residency. `loadLocalRecord`, `ensureLoaded`, and full-record query materialization propagate residency loader errors. A holder’s versioned answer settles the read immediately, whether it contains a live record or a deletion at version V: both are positive evidence from a holder. A tombstone retains its versioned GET_RECORD frame, including for older requesters. An unversioned empty reply is weak evidence: it can mean no row, or a stub on the legacy GET_RECORD path. If no versioned answer arrives, absence requires every listed non-self holder to answer and at least one unversioned empty reply; an unreachable holder keeps the result at 502, and all not-resident answers produce a descriptive 502. Reads do not compare versions across holders or perform quorum/read-repair reads, for live records or deletions. A successful instance load advances the request’s last-modified version to the resident’s version. The local-only collection policy is below; single-record local-only reads are outside this transport/collection guarantee.

`Table.transformEntryForSelect` skips invalidated entries for top-level local-only collection reads (`replicateFrom: false`), after lazy primary-entry loading reveals their flags. This includes residency stubs and invalidated cache entries without residency metadata, even for indexed-only projections. Sorted reads follow the ordering invariant above. Skipped local-only entries do not consume the ordered scan limit or load from a source; approximate-index candidate lists can yield short pages. Complete local rows remain eligible; ordinary reads still revalidate through their source. Collection deletes reuse this search filter, so a local-only delete leaves invalidated candidates untouched. This filter does not change single-record reads or nested projections. The motivating failure was a Pro static-sharding local-only query returning `{id, tag}` stubs as complete rows (harper-pro#436); enforced by `unitTests/resources/residencyReads.test.js` on both engines. Query projections stay local only for stored indexed fields and the primary key, which every residency stub carries (`residencyStub`, and `_writeInvalidate` with a residency list); selecting a computed index loads its resolver inputs from the resident. `_writeInvalidate` keeps the primary key and updates stored-field indexes with the incoming projection (including removed fields). Ordinary cache invalidation carries forward the commit base's indexed values and created time (a refill reads its created time from the stub); on a table with no secondary index it still stores `null`, so that refill restamps the created time. Invalidation joins the same-key write chain and publishes its staged projection, so subsequent writes diff the correct indexes on both engines. Stored vector fields are retained and indexed; computed indexes retain their committed entries because a stub lacks resolver inputs. A write, refill or eviction over a stub treats a computed index's old value resolved over the stub as a guess (`updateIndices`' `existingIsStub`, from the flags of the entry or staged write it replaces): the guess is removed when it differs, the new value is always written (HNSW derives the old node itself), and when the resolver throws (it needs a field the stub lacks) the committed entry stays (harper#2370). Invalidation reads incoming indexed fields through their accessors, and keeps an equal-origin/equal-version full row when the incoming residency still includes this node. Ordinary cache invalidation and non-resident demotion still apply. Enforced by `unitTests/resources/residencyReads.test.js` on both engines.

## A read keeps a fetched record as a local replica and never relocates it (`Table.ts` `_storeReplica`, harper-pro#436)

Reads are placement-neutral (harper-pro#436 step 1). **Local replicas are RocksDB-only.** LMDB is deprecated: its effective replica lifetime is always zero, so `_storeReplica` declines before transferring blobs or modifying rows/indexes, and every remote read remains a proxy read. Replica options still validate, but cannot enable LMDB admission or maintenance. LMDB tables never register a replica armer or open the deadline store at load; catalog wake messages and maintenance restart cannot arm a sweep. LMDB replica rows from unreleased draft builds are unsupported; no migration is provided. Live LMDB drop removes auxiliary catalog metadata without opening a replica store; an old draft-only named DBI may remain allocated, while generic interrupted-drop recovery still removes catalogued auxiliary DBIs. Schema rescans reapply persisted replica options to an already-loaded class through the same validated setter used by declarations, preserving record TTL settings and cleanup ownership. Unchanged effective lifetimes do not reset or rearm the replica sweep. New lifetimes apply to subsequent admissions and renewals; existing deadlines are not rewritten. A read of a stub fetches from a resident and `_storeReplica` keeps the body as a `REPLICA` row: the stub's `residencyId`, `version`, origin `nodeId` and `additionalAuditRefs` are preserved, so the row's canonical identity, its audit head and conflict ordering are those of the stub, and only the body comes from the resident. The write is audit-free, in its own transaction (`writeReplica`), so nothing replicates and `getHistoryOfRecord` is unchanged. **Admission keeps only a body that is the stub's own head write and that no later fold can change** (harper#3640, harper#3642). The resident's answer carries `fullWriteHead`, the log key of its head when that head is flagged `FULL_WRITE_HEAD` (harper-pro reads it with `fullWriteHeadKey`), and `storeReplicaRow` keeps the body only when the key still holds a stub, and the answer matches that stub (`answersStub`): its version; its writer (by name, since a retrieval socket has no node map); its head log key, which must be the stub's version; and every stored index field. The stub must carry no audit ref: a ref is either an out-of-order fold or the head of another write by the same writer at the same version, which would hide the write logged at that version. Created time is not compared (a live residency stub does not carry it) and comes from the body. `_storeReplica` checks the requested stub before any blob transfer, and `storeReplicaRow` checks the current row. A full-write head is what keeps the body current: an older write that reaches the resident later is superseded instead of folded in, and every newer write reaches this node as a stub write, which demotes the replica. Anything else is served and not kept. So a table written only by patches (counters via `add()`) never caches replicas, and an answer from a responder without the field is never kept: core alone caches nothing until harper-pro sends it. The row is `REPLICA | FULL_WRITE_HEAD` and keeps the stub's version, writer, `additionalAuditRefs` and `receivedIdentityRefs`, so admitting it never changes the stub tier; demotion keeps all of them. On RocksDB, `replicaExpiration: 0` stops new admissions and the replica sweep; existing replicas remain until overwritten or evicted. A replica is a complete local row to every reader and every incoming write (`_writeInvalidate`, `_writeUpdate`, `_writeDelete`, `_writeRelocate` overwrite it as they overwrite a stub, and a patch over it stays a stub with its residency, as over a stub); it is never counted by `confirmingResidents` because it is not in the list.

**The row keeps the record's own expiry; the replica deadline lives beside it.** A replica row's `expiresAt` is exactly the resident's reported one (else the `@expiresAt` field or the table's `expiration`), so record-expiry semantics are unchanged on every path: an expired replica reads, reloads, evicts and sweeps as an expired resident row does, and a demoted stub keeps that expiry. The replica's own deadline, `min(now + replicaExpiration, row.expiresAt)`, is an entry in a per-table local store (`<table>/@replicas`, `openReplicaDeadlineStore`, key = record id, value = ms), catalogued beside the indexes so `storeNamesFor` and interrupted-drop recovery remove it with the table; the row is `{ auxiliary }`, which `initStores`, `declareTable`'s stale-row pass and `catalogAttributes` skip (`isAuxiliaryCatalogRow`). The store is created before the first replica row, outside the replica write transaction, and is never audited or replicated. The entry is written in the row write's transaction (`putSync` with the raw RocksDB transaction), deleted at the same hook where every overwrite updates indexes (`dropReplicaDeadline`, gated on the replaced row being a `REPLICA`, so ordinary writes pay nothing), and deleted by demotion in its transaction. Reads never consult it: a replica past its deadline is served until the sweep demotes it, and a stub whose record expiry has passed reads as absent rather than fetching an expired record from a resident. The arm message opens the store on each RocksDB thread; an entry an overwrite could not clear is garbage the sweep removes. **Renewal:** a read hit of a replica carrying `FULL_WRITE_HEAD` (one kept by an earlier build runs out its lifetime) renews its deadline once `replicaRefreshFraction` of the lifetime has passed (default 0.5, range (0, 1], 1 = fixed), on RocksDB: `refreshReplica` is a point get and a one-entry write, never a row write, capped at the row's `expiresAt`. Each thread checks a key at most once per `min(fraction, 1 − fraction) × lifetime` (`replicaRefreshCheckedAt`, bounded by evicting stale checks) with at most 50 in flight, so a hot replica costs one small write per fraction of its lifetime per thread.

**Sweep.** A per-table timer separate from the record TTL scan (`scheduleReplicaSweep`, owner-only, every `max(replicaExpiration / 4, 1 s)`, paused by `stopMaintenance`, re-armed by `resumeMaintenance`, drained by `closeMaintenance`, never two passes at once) walks the deadline store, not the primary store (harper#3373): a passed deadline demotes its row through `evict()` → `demoteReplica` (stub = indexed fields, residency, identity and the record's expiry; no audit entry; computed index entries kept; blobs released after the commit), passing the deadline it acted on, which demotion re-reads where no renewal or new admission can interleave (from the committed state after staging the entry's removal, so a renewal committed before that is seen and one committed after it conflicts the optimistic commit, which resolves `RETRY_NOW` and counts as no demotion) so a replica renewed meanwhile is kept; an entry whose key holds no replica is garbage, deleted once its deadline has passed through the same exclusion (`dropOrphanDeadline`), so a replica admitted meanwhile never loses its entry; a sweep-driven `evict()` of a row that is no longer a replica is a no-op, never a removal. Once per load the first pass also walks the primary store's metadata and gives a fresh lifetime to any `REPLICA` row without an entry (`repairReplicaDeadlines`): RocksDB flushes column families independently and database copies carry only primary and index stores, so a row and its entry can part after a crash or a restore, and no replica may be permanent. The sweep is armed on every thread's class by a thread message when a replica is stored while the owner's shared armed flag (a per-table `getUserSharedBuffer`: admission counter and flag) is clear, and at load from the catalog row; the owner stands down after a complete empty pass with no admission since it began, so a table that stopped serving remote reads pays nothing.

Known limits: equal-version storage sets `VERSION_REUSED` on RocksDB, which keeps the row out of the decoded-object cache; a renewal that races a demotion can leave an entry for a stub row until its deadline passes (bounded garbage); an older binary ignores the deadline store, reads a replica as a plain full row and may remove the auxiliary catalog row on redeclaration, so verify that every replica has been demoted before downgrading; lowering `replicaExpiration` does not rewrite existing deadlines or establish that the table is drained; invalidation stubs still carry no expiry (harper#3365); a commutative op that reaches the resident below its audit floor still folds onto a flagged head and clears the bit there, but a replica admitted before that fold is not told (this node skipped the same write as older), so it stays stale while its key stays hot. Replica admission, demotion and orphan cleanup use raw transaction handles; `commitRawTransaction` aborts on rejected commits as well as coordinated conflicts. A native `ERR_TRY_AGAIN` regression in `unitTests/resources/replicaMaintenanceTransactions.test.js` verifies orphan cleanup releases its handle. RocksDB 2.12.0 does not support snapshot-free range iteration; that iterator-lifetime limitation remains. Enforced by `unitTests/resources/residencyReplicas.test.js` on RocksDB and `unitTests/resources/replicaEngine.test.js` on both engines; the wire half by harper-pro `residencyReplicaWire.test.mjs` and the four-node `residencyReplicas.test.mjs`.

## `replicatedConfirmation` counts only the residents of each written record (`DatabaseTransaction` `confirmationTarget`, harper-pro#1031)

Peers acknowledge a database-wide position even after receiving only a stub, so `confirmationTarget` freezes other-owner groups for confirmable writes. `recordUpdater` records each fresh staging as none, local, or replicable; `confirmsNothing` excludes unaudited, LOCAL_ONLY and copy-apply writes from counts, feasibility, owner lists and positions. Native retries retain the submitted staging's eligibility and captured update owners when the slot is unchanged; they do not rerun live admission for that already-submitted placement. Early count refusal applies only to audited, noncopy, nonlocal writes. Declarative writes use `confirmingOwnerNames`; legacy IDs use `confirmingResidents`' bounded immutable-list cache, with both ID mappings claimed transactionally by `getResidencyId`. Retries retain per-round residency IDs and exclude the writer from carried-over `replicateTo` counts. Owner resolution and count feasibility precede native submission under the engine's abort path; a refused write becomes inert even if application code catches the error. Source `before` hooks may already have run. Both engines share the confirmation registry. An LMDB write-bearing child supplies its write set and committed position while its logical committer owns the count; only the first database link inherits the root count. RocksDB uses the committed handle’s reserved log key, not the record version, falling back to the stored version only when every write lost ordering. LMDB uses the actual committed audit position for omitted non-owner rows and otherwise the newest eligible stored `localTime`, including a superseding entry when every write lost. `residencyConfirmation.test.js` and `replicationConfirmationOutcome.test.js` pin these outcomes.

## Replication confirmation failure means the linked writes committed locally

`ReplicationConfirmationError.replicationUnconfirmed` attests only to writes committed locally whose confirmation hook failed; it promises neither peer receipt nor fsync. `confirmReplicationAfterCommit` observes the hook immediately, and `settleCommitCompletions` waits for local work first, including a child's deferred confirmation failure when that link has an explicit count. Local write/flush failures reject promptly without the flag. The wrapper preserves the original public code, message and status through `cause`, does not mutate a shared rejection, and sets `retryable: false` because replay could duplicate committed writes. REST problem details, operations responses and terminal streams expose the flag; string-valued errors render the wrapper's class name, while object responses preserve the original public code. Programmatic callers inspect `cause` for the original class and identity. An independent nested commit's flag cannot attest to an enclosing scope's pending or previously discarded writes: abort/callback funnels strip it, preserving the cause and nonretryable outcome. Discarded-write evidence latches on the logical root across timeouts, disconnects and repeated aborts; committed/submitted writes and self-committing instances do not set it. With no pending or discarded enclosing writes, the nested flag may remain, but never attests to later application steps. A failed scope cannot resume writes. Wrapping copies diagnostics best-effort when getters fail; unreadable structured details use the ordinary response. HTTP guards cover the confirmation extensions, not arbitrary getters for base `statusCode`, `code`, `message` or `detail`. Pinned by `replicationConfirmationOutcome.test.js` and `serverErrorHandler.test.js`.

## This node's short id is 0, confirmed per audit store (`nodeIdMapping.ts` `getThisNodeId`)

Every audited write stamps the writing node's short id, so `getThisNodeId` sits on the write path. `getIdMappingRecord` leaves the current node name (`getThisNodeName()`, which `server.hostname` returns) at id `0` whenever it runs, remapping a previous local name to a fresh id on a rename, and no other mapping writer assigns `0`. `getThisNodeId` therefore reads and unpacks the mapping record only to confirm that, and caches the confirmation per audit store and node name; a different name (after `clearThisNodeName()`) takes the read path again, which performs the remap. The confirmation is per worker while the record is shared, and a worker that resolved a different name remaps the record under the others, so it expires after `THIS_NODE_ID_CONFIRM_MS` (monotonic time) and `invalidateNodeNames` drops it wherever the record is written. Pinned by `unitTests/resources/thisNodeId.test.js`.

## Query primary-key identity is the stored encoding (`search.ts` `CandidateKeySet`)

A query compares primary keys by the store's own key encoding (`writeKeyId`), never by a joined string or object identity: a composite key decodes to a fresh array per read, and `['t', 7]`, `['t', '7']` and `'t\0007'` join to the same string. The adaptive id filter and the OR union use `CandidateKeySet`; a hit in the id filter replaces the record predicate (`Table.ts` `idFiltersApplied`), so a lossy identity returns a non-matching record. The OR dedupe set is per iteration, and `searchByIndex` resolves a comparator alias once before reading the range flags. `joinFrom` and `joinTo` still key by object identity (#3394). Pinned by `unitTests/resources/searchKeyIdentity.test.js`.

## Validation keeps a patch operation and coerces only its operand (`Table.ts` `validate`)

A top-level `{ __op__, value }` patch on a numeric (`Int`/`Long`/`Float`/`Number`/`BigInt`/`Any`) or untyped attribute whose `__op__` is in `crdt.operations` keeps its envelope (replacing it with a scalar turns an increment into an assignment, and `updateAndFreeze` applies no nested envelope) with its finite-number/bigint operand coerced in place or into a new envelope when frozen (`0n` included; stored-value checks are harper#3568), enforced by `unitTests/resources/validation.test.js` (harper#3577).
