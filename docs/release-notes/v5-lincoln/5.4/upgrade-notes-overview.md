Full-text indexes using fulltext 0.5.0 with current field-based declarations, or prerelease 0.6, rebuild locally after this upgrade. Plan for search unavailability and review the [Tantivy upgrade requirements](#tantivy-027-and-existing-index-rebuilds) before deploying; direct downgrade to fulltext 0.5.x is unsupported.

An OIDC exchange now refuses a token that two enabled trust policies give a different user or different operations, where before the first policy by `id` answered (see [Conflicting Trust Policies Are Refused](#conflicting-trust-policies-are-refused)). Before upgrading, run `list_oidc_trust` and look for two enabled policies, with the same issuer and audience, whose claims can match the same runs but which name different users or `operations`, such as the policies of two `harper deploy setup=true provider=github-actions` runs that share a workflow, branch and environment. Drop, disable or narrow one of each pair, or the runs both match stop authenticating. A 5.4 node's `list_oidc_trust` names each pair in `invalid_reason`. Upgrade every node: a node still running 5.3 keeps answering with the first policy by `id`.

The `harper` CLI now stops with an error when a `.env` file in the current directory sets its target, credentials or connection settings and the environment does not (see [A Project `.env` No Longer Configures the CLI](#a-project-env-no-longer-configures-the-cli)). Before upgrading the CLI, move those names out of project `.env` files, including the `HARPER_CLI_TARGET` line that `npm create harper@latest` and earlier `harper login` versions wrote there.

Harper 5.4 marks failed transactions as aborted in the RocksDB transaction log by default ([`storage.rocks.transactionLogAbortMarkers`](/reference/v5/database/storage-tuning#storagerockstransactionlogabortmarkers); see [Failed Transactions Are Marked Aborted](#failed-transactions-are-marked-aborted-in-the-transaction-log)). Harper 5.3.4 and earlier cannot read those markers and would treat the failed transactions as committed. Do not downgrade a node to them, or open its database files or backups with them, after it has run 5.4 with the setting on. Harper 5.3.5 and later read the markers. Setting it to `false` later stops new markers but does not remove ones already written.

- **Upgraded instances keep their `applications.lockdown` mode.** Only new installs get the new `seal-after-load` default; an instance installed earlier keeps the mode it was installed with (`freeze-after-load` since 5.0.2, `freeze` in 5.0.0 and 5.0.1) until you change it. A configuration carried over from v4 without a `lockdown` value still has no lockdown. To switch, set `applications.lockdown: seal-after-load` (in a cluster, only after every node runs v5.4.0 or later). See [Intrinsics Are Sealed Instead of Frozen by Default](#intrinsics-are-sealed-instead-of-frozen-by-default).
- **Before downgrading an instance that uses a seal mode to 5.0.1 through 5.3, set `applications.lockdown: freeze-after-load`.** Those releases treat the seal modes as `freeze` and lock the intrinsics before any application code loads, so a dependency that extends one while it loads, such as `reflect-metadata`, fails. Code that assigns to an existing intrinsic property after load, which sealing allows, also throws on the older release. 5.0.0 has no after-load mode.
