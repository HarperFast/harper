### Restoring a `get_backup` Archive

`restore_backup` now restores a `get_backup` archive: `harper restore_backup database=data file=./data.tar.gz`, against a running server (remote ones included), at the next startup with `on_restart=true`, or with Harper stopped. The archive is extracted as it is uploaded, beside the database directory and each blob root, proven while the database keeps serving, and then installed by renaming, so its bytes are written once and the database is closed only for the swap. An archive made with `exclude_blobs` is restored with `allow_engine_only=true`, over the blob files already on the instance, which can be all that is left after a loss; archives with more blob roots than the instance are refused. After such a restore, or a managed restore with `allow_engine_only`, a new blob never reuses a file a restored record references, even where the restored records' blob files are missing. An interrupted archive restore is finished with `resume=true`. A new operation, [`server_info`](/reference/v5/operations-api/operations#server_info), returns the server's version and `capabilities`, and the CLI uploads only to a server that lists `restore_backup_archive`: an older server would restore its latest managed backup instead. See [restoring a `get_backup` archive](/reference/v5/backups/operations#restoring-a-get_backup-archive) ([harper#2639](https://github.com/HarperFast/harper/issues/2639), [harper#4431](https://github.com/HarperFast/harper/issues/4431)).
