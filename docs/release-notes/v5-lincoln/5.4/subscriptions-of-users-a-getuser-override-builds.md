### Subscriptions of Users a `server.getUser` Override Builds Stay Open

A component can override `server.getUser` to build users from a password or token, such as a JWT sent as the MQTT password, with no `hdb_user` record behind them. Their MQTT, WebSocket and SSE subscriptions stopped delivering at the first periodic re-authorization, about 30 seconds after subscribing, with the connection left open, and their MCP sessions lost their tools at the next user change. Harper now keeps such a user as it was admitted when it logs in through MQTT, HTTP Basic or a Bearer validator: re-authorization runs `allowRead` against it, and its subscriptions end when the connection closes, or at its `authExpiresAt` if the override sets one. Users that log in with an `hdb_user` record behind them are still revoked when they are dropped, deactivated or moved to another role, and so is a user whose name lost its `hdb_user` record within `logging.auditRetention` (3 days by default). An HTTP Basic login through `server.getUser` that returns a memoized user whose `hdb_user` record was dropped since its first lookup is also refused with `401`, matching Bearer validators. If the `hdb_user` table isn't audited (see `logging.auditLog`), a delete leaves no trace, so a user returned under a name other than the one it logged in with is checked by name at each re-authorization, and revoked unless an `hdb_user` record has its name. See [Row-Level Access Control with Explicit Filters](/reference/v5/database/schema#row-level-access-control-with-explicit-filters).
