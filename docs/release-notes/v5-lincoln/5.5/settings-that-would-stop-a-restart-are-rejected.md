### Settings That Would Stop a Restart Are Rejected When Set

`set_configuration` now answers 400, and writes nothing, for values Harper used to accept and then failed on: a [`storage.rocks.compression`](/reference/v5/database/storage-tuning) codec the build does not provide, which kept the next start from loading the system database; HTTP and operations API timeouts or `http.maxHeaderSize` that Node.js refuses, which stopped the server; and negative, mistyped or over-long durations for `storage.transactionLog.coolingInterval`, [`storage.reclamation.interval`](/reference/v5/database/storage-tuning#storagereclamationinterval) and [`storage.maxTransactionQueueTime`](/reference/v5/database/storage-tuning#storagemaxtransactionqueuetime), whose timers Node.js runs after 1 ms instead once a delay passes about 24.8 days. `storage.longTransactionReportThreshold` takes the same range. `http.headersTimeout` may no longer exceed `http.timeout`, the operations API is checked with the values it inherits from `http`, and `storage.maxTransactionOpenTime`, `storage.reclamation.threshold`, `storage.rocks.blockCacheSize`, `storage.rocks.writeBufferManagerSize` and `threads.heapSnapshotNearLimit` are held to their documented types and ranges. `config-root.schema.json` states the same bounds.

Before upgrading, check the configuration file and any environment override for these settings. Harper now stops at startup, naming the setting, instead of starting with such a value, and `harper stop`, `restart` and `status` refuse in the same way until the value is fixed. A duration written in milliseconds (`500ms`) needs rewriting as a fraction of a second (`0.5s`). Also rejected: `M` (months) and `y` (years) units, a duration past about 24.8 days, a reclamation interval of `0`, `storage.rocks.compression` given as a list such as `[lz4]`, and a quoted number for an HTTP timeout or RocksDB size.
