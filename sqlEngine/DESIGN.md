# SQL engine v2

## LIKE: one tokenizer, linear matcher

`tokenizeLike` (`expressions/like.ts`) is the only definition of a v2 LIKE pattern: literal characters, `_` (one character), `%` (any run); the `ESCAPE` character, checked before the wildcards, makes the next character literal. Every consumer calls it: `normalizeLike` (`parser/normalizer.ts`) to validate, `compileExpr` to build the row matcher, and `leafToCondition` (`optimizer/whereToConditions.ts`) to build index conditions. A pushed index condition replaces the row filter with no re-check, so a second reading of the pattern selects or deletes the wrong rows: before [#3878](https://github.com/HarperFast/harper/issues/3878), the index rewrite read `'t0!%' ESCAPE '!'` as `starts_with 't0!'`.

- The index rewrite works on tokens: a pattern maps to `equals`/`starts_with`/`ends_with`/`contains` only when every token other than one leading and one trailing `%` is a literal, and the condition value is the unescaped literal.
- Malformed patterns (a trailing escape, an `ESCAPE` that is not one character, a segment between `%` wider than `MAX_LIKE_SEGMENT_WIDTH`) fail in the normalizer with `EngineRuntimeError`. Later, `validateScannable` would turn the query into an `EngineUnsupportedError`, and `auto` would run it on legacy instead.
- `compileLikeTokens` never backtracks: `%` splits the pattern into fixed-width segments, the first and last are anchored, and each middle segment takes its leftmost fit after the previous one. A segment is matched by `indexOf`/`startsWith`, or by one RegExp with no quantifier or alternation, which cannot backtrack; cost is O(value × pattern). Both tokenizers (`tokenizeLike`, legacy `tokenizeAlasqlLike`) reject a segment over 10,000 units: V8 fails to compile a RegExp of about 50k atoms, and matching a longer segment as several RegExps cost O(value × width) per row. A whole-pattern RegExp is not an option: separated `%` runs backtrack polynomially (`'%_%_…%_Z'` blocked a worker, [#1930](https://github.com/HarperFast/harper/issues/1930)), and V8's linear engine is an experimental flag that Bun lacks. No middle-segment RegExp search wider than `DIRECT_SEARCH_WIDTH` (64) may meet a line terminator under a `_` (`findSegment`): it fails there after scanning up to the width and retries one position later, so `'%' + '_'×10000 + '%'` over values with a line feed every 10,000 characters cost O(value × width) per row ([#3936](https://github.com/HarperFast/harper/pull/3936)). Up to that width, retrying costs less than stopping at each terminator. A segment with no unit matching a line terminator is searched only between them. Otherwise `_` becomes `[^X]` for a noncharacter X that every other unit treats like a second one, Y; the search runs on the value with X replaced by Y, and each candidate moves each run of `_` past the last terminator it covers. `[^]` cannot stand for `_`: under `i`, V8 compiles each one about 100× slower. A relaxed match that a `_` rejects can cost the width; past `RELAXED_BUDGET` × the window of those, the plain search takes over, since such dense rejections are where it fails fast. That bounds the worst case by the plain search's, not below: no RegExp strategy here is linear for every segment holding a unit that matches a line terminator. If its literals and classes leave no such pair among the 34 noncharacters, it also falls back to the plain search, as legacy classes do anyway: a run of `[a-z]` over text with a space every 10,000 characters costs O(value × width) with no line terminator involved. `unitTests/sqlEngine/like.test.js` bounds the cost in a child process.
- Matching is case-sensitive and per UTF-16 code unit. `%` matches line terminators and `_` does not, as in legacy, so `auto` returns the same rows whichever engine serves it (legacy differs only in case).
