# SQL engine v2

## LIKE

`tokenizeLike` (`expressions/like.ts`) is the only definition of a v2 LIKE pattern: literal characters, `_` (one character), `%` (any run); the `ESCAPE` character, checked before the wildcards, makes the next character literal. Every consumer calls it: `normalizeLike` (`parser/normalizer.ts`) to validate, `compileExpr` to build the row matcher, and `leafToCondition` (`optimizer/whereToConditions.ts`) to build index conditions. A pushed index condition replaces the row filter with no re-check, so a second reading of the pattern selects or deletes the wrong rows: before [#3878](https://github.com/HarperFast/harper/issues/3878), the index rewrite read `'t0!%' ESCAPE '!'` as `starts_with 't0!'`.

- The index rewrite works on tokens: a pattern maps to `equals`/`starts_with`/`ends_with`/`contains` only when every token other than one leading and one trailing `%` is a literal, and the condition value is the unescaped literal.
- Malformed patterns (a trailing escape, an `ESCAPE` that is not one character, a segment between `%` wider than `MAX_LIKE_SEGMENT_WIDTH`) fail in the normalizer with `EngineRuntimeError`, so `auto` returns a 400 rather than falling back. Raised any later, `validateScannable` would make it an `EngineUnsupportedError`, which `auto` runs on legacy.
- `compileLikeTokens` never backtracks: `%` splits the pattern into fixed-width segments, the first and last are anchored, and each middle segment takes its leftmost fit after the previous one. A segment of only `_` needs no search (a middle one advances by its width). Any other segment is matched by `indexOf`/`startsWith`, or by one RegExp with no quantifier or alternation, which cannot backtrack. A fixed count is no exception: `[^]{9998}` searches about 3,000× slower than the atoms written out. Cost is O(value × pattern). Both tokenizers (`tokenizeLike`, legacy `tokenizeAlasqlLike`) reject a segment over 10,000 units: V8 fails to compile a RegExp of about 50k atoms, and matching a longer segment as several RegExps cost O(value × width) per row. A whole-pattern RegExp is not an option: separated `%` runs backtrack polynomially (`'%_%_…%_Z'` blocked a worker, [#1930](https://github.com/HarperFast/harper/issues/1930)), and V8's linear engine is an experimental flag that Bun lacks.
  - A segment wider than `DIRECT_SEARCH_WIDTH` (64) in which no unit matches a line terminator is searched only between them (`findBetweenLineTerminators`, in windows of doubling size): a search failing at each one would retry every start, O(value × width).
  - The RegExp search stays O(value × width) on values built to defeat V8's skip tables, at any breaking character: legacy `[^b]`×10000 over `b` every 5,000 characters, or a 10,000-character literal over near-copies of it, take 150–190 ms per 100 KB row. Bun's RegExp engine lacks V8's skip tables, so there a run of `_` before a literal the value lacks costs value × run: `_`×5000 then a literal, about 60 ms per 100 KB row.
- `unitTests/sqlEngine/like.test.js` bounds the cost in a child process.
- Matching is case-sensitive and per UTF-16 code unit. `%` and `_` match line terminators, in both engines, so `auto` returns the same rows whichever engine serves it (legacy differs only in folding case and in reading `[…]` as a character class). `_` is `[^]`; under legacy's `i` flag, where V8 compiles each `[^]` in about 0.05 ms, a pattern with more than 64 `_` writes it as `[^X]` over the value with X replaced by Y, for consecutive units X and Y among the noncharacters or the Private Use Area that the pattern names nowhere; no case mapping reaches them, so a class tells them apart only by naming one. A pattern naming a unit of every such pair is a 400, since `[^]` would compile for seconds (SF-86). No other unit tells X from Y, so only a segment holding `_` sees the rewrite: an anchored one over the units it covers, a middle one in search windows of doubling size. A row the anchors reject costs no pass over the value, and a match near the search start costs about the width.

## UPDATE SET

The value `runUpdate` (`executor/runMutation.ts`) writes to a column is that column's `SET` assignments evaluated with `compileExpr` against the pre-update row, a repeated column reading its own previous assignment's result. The atomic `Addition` that keeps concurrent `col = col + N` statements from losing increments is used only where `addValues` on the value read gives that same result (`additionFor`); CRDT addition treats a null or non-numeric prior as absent, so an unconditional `Addition` wrote `N` where the expression meant `NULL` or `NaN`. `evaluateAssignments` folds a repeated column in place on the selector's row, which `physicalProject` creates fresh for every match. `unitTests/resources/sqlUpdateSetFolding.test.js` holds each rule.
