# Continuation measurements, 19 October 2026

The contained cleanup removes eager admission startup, reuses the first highlighted page’s retained reader under the lease drain guard, and resolves configuration once per command. It adds no cache and changes no defaults. The measurements below describe the resulting implementation; they do not isolate a latency improvement from those cleanups.

Apple M4 Pro, Node 24.16.0, published fulltext 0.6.0 / Tantivy 0.26.2, RocksDB. The [fixture and commands](README.md) reproduce the workload. [Archived structured results](https://github.com/HarperFast/harper/blob/f4a8fbe0da2ff237ffce343312c2febce9512c5f/benchmarks/fulltext-continuation/results-2026-10-19.json) contain all 48 first-page cases, 12 resumed-page cases, separate profiles, native limits and the compiled admission module’s fingerprint. The environment’s commit field is the base HEAD during measurement; its uncommitted policy hoist is included in the commit carrying this report.

These are historical measurements, before the review repair that restores a separate 10,000-hit ordinary-search ceiling. Qualification and archived evidence are tracked in [Qualify native full-text filtering and catalog-scale operation for v5.4](https://github.com/HarperFast/harper/issues/2512).

## First pages

Each corpus has short records containing “widget”; one in 500 passes the sparse filter. The query asks for 25 rows. Exact and prefix queries, indexed and unindexed filter fields, ordinary search and continuation are checked against independently ordered eligible IDs. One warmup precedes 20 sequential samples. Every case returned the expected rows or the explicit raw-hit error. At 100k records, all four ordinary no-match cases returned 400 for `maxRawHitsPerRequest`; continuation exhausted the snapshot successfully. The ordinary path counts its initial replay against the same budget. An empty completed snapshot is valid; the fixture never treats a budget error as an empty success.

Continuation’s fixed native batches and lack of the ordinary path’s companion-index gate are visible here: no-match queries at 100k take about 0.6 seconds at p95, and event-loop delay reaches about 30 ms at p95. This remains within the default request budget on this machine, but is material work. The native collector rescans matches for successive batches. Neither a faster limits resolver nor a small page limit removes that native cost.

## Configuration work

Separate V8 precise-coverage runs count resolver calls across requester, snapshot owner and admission authority. These are function-call counts, not CPU percentages or wire-message counts. Small inlined helpers are excluded. Original baseline runs interleaved profiling and timing, so their latencies are deliberately omitted from the result artifact and are not used for before/after latency claims.

| Request                                     | Before | After |
| ------------------------------------------- | -----: | ----: |
| 100k resumed, local                         |     25 |    13 |
| 100k resumed, remote                        |     49 |    25 |
| 100k initial continuation, sparse-unindexed |    111 |    54 |
| 100k initial continuation, none-unindexed   |    800 |   399 |

The unchanged resolver with populated settings measured 515–526 ns per call across five uncontended 100k-call runs. The absent-settings fast path measured 4–9 ns; it is a best case, not the normal populated YAML configuration. Removing duplicate validation saves allocations and modest CPU work, not the hundreds of milliseconds spent traversing a large sparse snapshot. Every later command resolves current settings; the regression test mutates the same settings object to verify shrink and recovery.

## Limits of these observations

- These are warm, short-record synthetic workloads with 20 timed samples per case. They do not establish p99, a production SLO, cold-storage behavior or capacity beyond RAM. The first 10k ordinary exact/sparse case had a p95 of 52.39 ms; it is retained in the table rather than discarded as warmup noise.
- macOS HTTP reaches one Harper worker. Cross-worker continuation is measured by the separate two-worker harness, not inferred from HTTP routing. The loaded phase has three search samples and sequential control probes, not a sustained concurrent throughput test.
- Event-loop delay is a 1 ms histogram, not an isolated measurement of native blocking. Process RSS includes all workers, native memory, previous corpora and retained runtime state; the raw RSS observations do not qualify memory bounds.
- The fixture verifies result IDs, counts native read calls and resolver calls, and records errors. It does not count RocksDB reads, page faults or operating-system I/O. Those and exact wire-message counts remain part of catalog qualification.

## Review repair, 20 October

The repair keeps `search()` iterable and makes paging explicit through `searchPage()`. Ordinary searches now also apply a configurable 10,000-hit ceiling and the shared five-second execution budget. Their limit failures are errors, not successful partial pages. Native fulltext remains 0.6.0.

The [new measurements and complete records](https://github.com/HarperFast/harper/issues/2512#issuecomment-6303389103) use the same machine, 100,000 records and 20 sequential samples. They identify the measured compiled build; the commit field names the base of the then-uncommitted repair.

| Workload                                                        |                           p95 after repair |
| --------------------------------------------------------------- | -----------------------------------------: |
| Ordinary sparse/no-match, indexed or unindexed, exact or prefix | 21.26–33.49 ms (explicit work-limit error) |
| Initial continuation, sparse                                    |                             60.02–69.23 ms |
| Initial continuation, no matches pass the filter                |                           649.52–747.47 ms |
| Resumed five-row page, owner worker                             |                             13.11–13.50 ms |
| Resumed five-row page, another worker                           |                             14.15–15.18 ms |

The ordinary path does less work under its restored ceiling; this is not an algorithmic speedup. Continued no-match searches still traverse the snapshot and remain costly. Historical continuation p95 was 617.67–664.26 ms, so this run does not establish an improvement there. Resumed-page p95 was 13.66–17.96 ms in the immediate before run, depending on mode and worker. These warm local observations do not establish production latency or isolate a single optimization's effect.
