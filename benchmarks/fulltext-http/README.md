# Full-text HTTP qualification

Run from a built feature worktree inside a Git checkout; copying the script outside a checkout is unsupported. This creates an isolated Harper install with the standard integration-testing lifecycle; no product API or native query limits change.

```sh
npm run build
node benchmarks/fulltext-http/run.mts
node benchmarks/fulltext-http/run.mts --scale=nightly --output=/absolute/new/report-directory
```

Quick is the default: 1,000 rows per table, one client, no writes and one second per case. It is a harness smoke, not performance qualification. Nightly selects 100,000 then 1,000,000 rows, 8/32 clients, 0/10 writes per second and 60-second cells. Both scales exercise relevance, stored rank sorting, sorted highlights, exact counts and a structured rank-sort control. Flags override presets; the old `FULLTEXT_HTTP_*` environment interface is replaced by CLI flags.

| Flag                 | Values                                                            | Quick / nightly           |
| -------------------- | ----------------------------------------------------------------- | ------------------------- |
| `--rows`             | comma-separated multiples of 1,000, up to 1M (20M with `--large`) | 1000 / 100000,1000000     |
| `--clients`          | comma-separated integers, 1–32                                    | 1 / 8,32                  |
| `--writes`           | comma-separated 0,10 per second                                   | 0 / 0,10                  |
| `--cases`            | comma-separated relevance,sort,highlights,exact,structured        | all five                  |
| `--duration`         | integer seconds, 1–300                                            | 1 / 60                    |
| `--expected-workers` | 1 or 2                                                            | 1 on macOS; 2 elsewhere   |
| `--large`            | explicitly permit catalogs up to 20M                              | off                       |
| `--output`           | new directory with an existing parent                             | fresh temporary directory |
| `--help`             | show options without starting Harper                              |                           |

Each run exclusively creates a new output directory, so provenance and errors cannot mix with an earlier run. Keep reports outside the checkout. Reports and `FULLTEXT_HTTP_RESULT` lines record resolved scale; each summary includes actual rows, clients, configured write rate, duration, successful sample count, failures and verdict. An empty successful population prints `p95_ms=na`. No result is automatically published to the trend dashboard.

Each deterministic bucket contains 1,000 matches. Both `Product` (audited, native full-text) and `PlainProduct` (same schema without full-text) are seeded. Timed requests rotate deterministically across all buckets. An untimed strict-freshness barrier validates all IDs in the first and last bucket before restart. Timed requests retain default lag settings. Exact counts use REST GET/Prefer; other cases use HTTP QUERY. Responses are fully consumed and validated. Failed requests are retained and never silently retried. Any read/write rejection marks the cell unqualified; a completed unqualified matrix exits nonzero. Overload cells continue collecting outcomes unless a correctness/resource guard fails.

Output includes per-cell p50/p95/p99/max latency, completed requests, throughput, rejection/timeout/unknown-count counts, separate failure-latency tails, client CPU, admission/drain timing, bounded diagnostic samples and an append-only error NDJSON stream. `QualificationState` is an authenticated benchmark-only diagnostic resource. It reports worker thread IDs, shared process RSS/CPU and each worker's bounded event-loop-delay histogram. Observing both workers proves diagnostic requests reached both; it does not establish how timed query traffic balanced. Fresh diagnostic connections avoid keepalive affinity. CPU/RSS are process-wide: never sum samples from the two workers. `diagnosticRange` identifies each cell's samples. `bucketStart` and `bucketsAttempted` expose actual query coverage: a slow cell can visit fewer than all catalog buckets. A provenance file records exact Harper HEAD, native runtime/addon hash and harness file digests and compiled Table/query implementation digests. Histogram intervals reset per diagnostic call; concurrent samples can contain very short intervals.

After fixture creation and readiness, Harper restarts once. A bounded 30-second diagnostic-only wait must observe the required worker count in that same fresh process before timed work. `--expected-workers` defaults to one on macOS and two elsewhere; every run records and verifies that scope. Explicit `--expected-workers=1` permits a single-HTTP-worker measurement while retaining configured thread count 2; reports label that scope and do not imply active two-worker HTTP serving. On macOS, exclusive HTTP port binding prevents the Linux reuse-port arrangement, so use explicit `--expected-workers=1`; true multiworker HTTP qualification still needs a supported host. The first case's first native query follows that recorded wait. Subsequent cases share that process, and all warm cells follow three untimed requests per case. These are **not OS-cold measurements**: filesystem/page cache is untouched. The recorded first-query order makes this distinction explicit.

Safety guards: 45-second request timeout, 15-minute fixture setup deadline, 6-GiB shared server RSS, 12-GiB install disk use and at least 2 GiB free disk. Guard violations fail and trigger lifecycle cleanup. Disk use is checked every 10,000 inserted rows and every ten sampler ticks; RSS is sampled each second during workloads. In-flight work drains under request timeouts before teardown. SIGINT/SIGTERM set a persistent stop request checked before catalog setup, readiness retries, restart and warmup; cleanup runs without clearing that request. The harness gives integration-testing a dedicated monitor registry and waits for its monitor to exit during final cleanup, without affecting concurrent suites.

The writer table matches each case: `Product` for native search cases and `PlainProduct` for the structured control. It targets ten requests per second without catch-up bursts; actual achieved write counts/latencies are reported. Known exact totals must be 1,000; unknown totals are recorded as degraded outcomes below. Stored sorts must return rank 0–19; relevance pages must contain 20 distinct deterministic in-bucket records. No expected relevance tie prefix is asserted across native versions.

Latency includes receiving/parsing the full response and the client correctness oracle. The fixed-size native histogram records successful latency separately from rejected/timeout latency, including their counts. Throughput uses the admission window plus in-flight drain; final diagnostic sampling is outside that denominator. Client CPU includes request generation and validation; it is not server CPU. Server CPU deltas are process-wide and sampled across cell boundary diagnostics; they include diagnostic overhead. Eight short diagnostic requests per sampler tick and periodic disk checks add measurement overhead. No cell is claimed contention-free, and no OS-cache eviction is attempted.

An exact-count page with valid rows and `Content-Range: items 0-19/*` is the documented bounded-count degradation. It records `QUALIFICATION_UNKNOWN_COUNT`, a separate `unknownCounts` counter and failure latency; the cell remains unqualified while collection continues. A wrong known total, wrong record or missing/duplicate row remains a fatal oracle mismatch.

`--large` explicitly permits up to 20 million rows per table. It changes only the row ceiling; the 15-minute setup deadline, 12-GiB disk ceiling, free-space reserve, query work budgets, 1,000 matches per bucket and round-robin access remain unchanged. Start with a 10-million-row pilot, for example `--large --rows=10000000`, and retain failures if the existing limits stop it. The fixed 50,000 diagnostic-sample cap also remains: a long full matrix can stop at that harness bound, independently of Harper capacity. Seeding 10 million rows consumes 8,000 samples; 20 cells of 300 seconds add about 48,000 more, exceeding the cap before boundary diagnostics. The 20M ceiling is input validation, not a supported-capacity or setup-time promise. Both tables are seeded even when a case subset omits the structured query, preserving the matched fixture and shared-log load; the unchanged deadline can reject a larger catalog. Provenance records the opt-in. Size subsequent experiments from measured setup time and footprint, rather than automatically increasing safety limits.

A large durable catalog does not prove an active working set larger than memory. The two tables share a RocksDB database and transaction log; combined install bytes cannot establish per-table query footprint. For Linux pressure experiments, record the enforced cgroup limits, memory events/refaults/pressure and current server PID's read I/O/fault counters. Existing `system_information` metrics can distinguish block-cache misses and compaction; primary-column-family `liveSstFilesSize` excludes secondary indexes. Missing counters are unavailable. Seeding/compaction I/O is not query I/O, process restart is not an OS-cold run, and a sampler's worker coverage does not prove balanced query traffic. Keep smaller-envelope controls separate so their results cannot be attributed solely to catalog growth.

A cell marked `qualified` means it completed at least one validated response without an observed read/write failure. It does not certify statistical confidence, full catalog coverage or release readiness. Inspect `reads.completed`, `bucketsAttempted` and the admission window; short or slow cells can cover only part of the catalog.

Disk walks run with the C locale. A single valid `du` total is accepted after exit 1 only when every diagnostic reports a path disappearing during the walk; `diskSamplesWithVanishedFiles` records these observations. Missing totals, permission errors, I/O errors and other exits remain fatal. The disk and free-space limits still apply. This tolerates normal concurrent index-file retirement; neither a successful walk nor a partial walk is an atomic filesystem snapshot.
