`alasqlFunctionImporter.ts` imports the CommonJS date-helper object by default; native namespace imports did not expose its object-literal properties in [#562](https://github.com/HarperFast/harper/pull/562). `unitTests/sqlTranslator/alasqlFunctionImporter.test.js` verifies the registered date functions in both test runtimes.

## SQL column attribution

`verifyPermsAST` checks attribute permissions only for the attributes `sqlStatementBucket` records per table, and it runs once, before the router picks legacy or v2, so the bucket alone decides what every engine may read. A column the bucket misses, or records against the wrong table, is read unchecked.

So the bucket attributes columns with the binder's own rules, which live in `columnScope.ts` and are called by `bind.ts`, `logical/build.ts` and the bucket alike:

- A qualified column is attributed only when exactly one table in the statement (not only the tables an ON has joined so far) has the qualifier as its alias or base name. v2 prefers an alias over a base name, while legacy SQL matches either, so only then do both engines read the same table. Any other qualifier is reported by `getUnresolvedColumnRefs()`, and non-super statements are refused.
- An unqualified column in a join goes to every in-scope table that declares it. Each JOIN ON first looks only at the tables joined so far, then, when none of them declares the column, at every table in the statement (legacy SQL can bind it to a later join). If no table declares the column, it stays on the FROM table, where a role with attribute permissions is refused because the attribute is not found.
- `USING (c)` records `c` on the joined table and on `usingLeftOwner` (the nearest preceding declarer, else FROM): the same two operands v2 compares.
- When the registry cannot describe a table, unqualified and USING columns go to every candidate table, so the check fails closed.
- UPDATE and DELETE also need `read` on every column their WHERE or SET expressions read (`getWriteStatementReads()`), separately from the write permission; only SET targets need `update`. A column qualified by a name other than the target table is refused. The primary key is exempt: the statement reports the keys it touched, as NoSQL update and delete do. Only attribute-level denials apply; table-level `read` is not required.
- An unqualified `*` in a join expands to the FROM table's readable attributes qualified by its alias, so each expanded name binds to the table whose permissions chose it rather than to whichever table declares it.
- A relationship column also reads its related table, which the statement never names. `addRelatedTableDenials` refuses a statement that reads one whose related table the role cannot read, judged by that table's own permission so a write-only root still answers for it; the denial is reported only once the statement passes its own table and attribute checks, so it never names the target of an attribute the role cannot see. A non-super `*` leaves such a relationship out. Every other related record is narrowed at the Table read that produces it, because legacy `->`, WHERE and v2's UPDATE SET use the value before any serialization. So every engine read carries the caller (`sqlSelect` for legacy SELECT, UPDATE and DELETE; `ctx.user` in v2 scans) to `_authorizeSelectedRelationships`.
- Every walk uses `astNodes()`: iterative, with no depth limit, and visiting shared nodes once. `recursive-iterator` silently stopped at depth 100, so a column nested in 80 function calls went unchecked, and it threw on the subquery node AlaSQL shares between `where` and `exists`.

Row accessors that name no column, AlaSQL's `_`, JavaScript expressions, `?`/`$n` parameters (the `sql` operation binds none, and legacy SQL fills them with its own rows) and a JSON literal that sets `__proto__` (every walk here reads own properties, but AlaSQL evaluates the prototype), are refused for non-super users by `getRowAccessors()`. Legacy SQL's row container always carries the primary key (`dataLayer/SQLSearch.ts` keys rows by it), so a whole-row read would expose it whatever the role allows. The JavaScript refusal stays unconditional for non-super users, even if the `_` refusal is ever relaxed for roles without attribute permissions.

Enforced by `unitTests/sqlTranslator/column-attribution.test.js`, `unitTests/sqlEngine/columnScope.test.js`, `unitTests/resources/sqlRelationshipReadPermissions.test.js`, `integrationTests/security/sql-attribute-perms.test.ts` and `integrationTests/security/relationship-related-table-permissions.test.ts`.

## Legacy SQL text round trip

Legacy SQL writes the authorized AST back out with `toString()` and AlaSQL parses that text again (`dataLayer/SQLSearch.ts` `_buildSQL()`, `dataLayer/update.ts`, `deleteTranslator.ts`, and the compiled SET and INSERT expressions), so the permission check holds only if the text parses back to the same statement. AlaSQL writes string and JSON literals unescaped, so `'x'', ssn, ''y'` came back as three columns, and numbers as `1e+25` or `Infinity`, which read back as columns. `installLegacySqlText()`, run by `alasqlFunctionImporter`, replaces the `StringValue`, `Json` and `NumValue` writers with ones that read back as the same value. `assertLegacySqlText()` refuses, with a 400 on the legacy path only, what the writers cannot spell: a name containing `` ` ``, `[`, `]` or `'` (brackets cannot hold `]`, and Harper leaves an alias starting with `[` unbackticked), an `@variable`, `$param` or `->`/`!` member name other than letters, digits and `_`, which AlaSQL writes unquoted, a string ending in an odd run of backslashes, which has no single-quoted spelling, a number that overflows, and, in a SELECT that reads a table, an unaliased function column whose text holds `]`, since `SQLSearch` aliases it as `[<its text>]`. It then re-parses the backticked statement text and refuses it unless it is one statement that reads each table-qualified column, function and variable no more often than the authorized statement does, so an AlaSQL writer not replaced here fails closed. INSERT takes literal values as data and writes only its other values as text, so only those are checked. v2 binds the AST directly.

Text `SQLSearch` builds after the check names columns only as `[<name>]`. `_processJoins` writes each table's primary-key result through `generatedName()`: bracketed, double-quoted only when the key holds `]`, refused when it holds both, so an alias holding `"` cannot end the name.

Enforced by `unitTests/sqlTranslator/legacySqlText.test.js` and the quoted-string case in `integrationTests/security/sql-attribute-perms.test.ts`.

## Legacy LIKE

`installAlasqlLike` (`alasqlLike.ts`, applied by `alasqlFunctionImporter.ts`) replaces `alasql.utils.like`, whose per-pattern RegExp backtracks polynomially ([#1930](https://github.com/HarperFast/harper/issues/1930)), with the v2 engine's segment matcher in alasql's semantics: case-insensitive, `[set]` classes. RegExp syntax alasql leaked into its pattern (`\`, `^`, `$`, escape + letter) is literal. Under `sql.engine: auto` a LIKE with no index driver runs here, so this path must stay linear too. The same function wraps `alasql.yy.Op#toString` to keep `ESCAPE`: legacy SQL re-parses `where.toString()` (`SQLSearch._buildSQL`, `update.ts`, `deleteTranslator.ts`), and alasql's serialization drops it.
